## 3. 进度维护规则

任务表是实现状态的唯一记录入口，里程碑状态由所属任务及验收结果汇总。

| 状态 | 含义 |
| --- | --- |
| TODO | 尚未开始 |
| IN_PROGRESS | 已有 Agent 负责并正在执行 |
| BLOCKED | 存在明确外部或前置依赖阻塞，必须记录原因与解除条件 |
| IN_REVIEW | 实现与自测或设计草案与文档检查完成，等待独立审查或本次任务的验收确认 |
| DONE | 交付物、相关测试和验收证据齐全，审查问题已处理 |
| BACKLOG | 已记录但不在当前执行范围 |

开始任务时更新状态和负责人；完成时填写证据，至少包括实现文件或提交引用、测试命令及结果、对应设计决策。未运行的测试明确标注原因，不将“代码已写完”直接当作完成。证据较长时链接到独立的验收记录。

里程碑完成条件：所属任务全部为 `DONE`，阶段验收通过，无影响本阶段契约的未解决阻塞。发现设计或实现缺陷时，可将任务重新打开并保留原验收记录。

## 6. 开发 Agent 的执行协议

设计文档保持简洁：每项用 2～3 句话说明规则，配一个简单例子；沿用已有架构与用例，不重复展开。具体字段、SQL 和锁可在对应开发任务中明确并同步必要结论，不作为继续推进的文档前置条件。

由用户逐项将任务交给专门的开发 Agent 实现，再交回当前对话独立验收。当前对话只维护文档、审查和运行必要检查，不添加或修改实现代码；开发 Agent 按以下顺序执行：

1. 阅读 `AGENTS.md`、本计划、相关设计决策与当前代码，确认前置任务实际可用。
2. 将任务更新为 `IN_PROGRESS`，记录负责人。存在其他工作区改动时，保留并避免覆盖。
3. 完成任务范围内的实现与有针对性的测试；需要改变已确定契约时同步设计和受影响任务。每份被修改文档均在前部列出本次主要修改及涉及章节。
4. 执行验收命令，记录实际结果。基础设施不可用或验证未完成时，准确记录限制。
5. 完成自测后更新为 `IN_REVIEW`，提交变更清单和验收证据，等待用户交回当前对话验收；不自行标记 DONE 或继续下一任务。
6. 验收问题交回开发 Agent 修复；独立验收通过后由验收方记录 `DONE`。

任务指令模板：

```text
请按 AGENTS.md 和 docs/开发计划与进度.md 执行任务 Txx：<任务名称>。
先核实前置任务及相关设计决策，再完成本任务的实现、测试和文档。
不要自动扩大到后续里程碑。遇到契约缺口时在对应设计文档记录决策；
重大歧义说明影响和建议，同时继续不受影响的工作。
完成自测后更新为 IN_REVIEW，填写负责人和验收证据，报告命令、结果和剩余问题。
等待用户安排独立验收，不自行标记 DONE 或继续下一任务。
```

设计任务可以直接交给 Agent 开始。后续实现任务应以已验收的契约作为输入；不能把本文的决策问题或建议当成已经完成的设计。
