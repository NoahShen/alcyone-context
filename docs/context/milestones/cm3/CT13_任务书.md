## 1. 目标与边界

```text
Pending Raw
  → 单次 database.read 读取全部 Organized 快照（id ASC）
  → 释放 ReadContext
  → 固定开销 + 逐条预算分批（串行）
  → 每批 LlmTask.CANDIDATE_SCANNER（只返回 candidate_ids）
  → 批内 ID 校验 + 跨批稳定去重
  → 全部批次成功才返回候选
```

- 只做候选召回；不执行 NEW/MERGE/UPDATE，不写数据库。
- 不按 Runtime/Agent/Domain 硬过滤；Raw 本身不含 Agent/Domain 过滤条件。
- 任一必需批次失败、非法 ID、截断/JSON 错误 → 整条 Raw 失败；不得以局部结果当空候选。
- 空 Organized 快照 → 返回空候选，不调用 LLM。
- 单条 Organized 连同固定 Prompt/Raw 无法容纳 → 显式预算失败；不跳过、不截断。

## 3. 预算算法（CT13 冻结建议）

对每条 Raw：

1. 读取全部 `OrganizedMemory`，按 `id ASC` 稳定排序；空集合直接返回 `emptyList()`。
2. 构造固定部分：System Prompt + Raw（id/content/createdAt/generatedBy）+ 输出契约 + Schema。
3. 用 `LlmBudget.estimate`（`ConservativeTokenEstimator`，Task/Profile/安全余量）估算空候选请求：
   - 若 `estimatedInputTokens > task.maxInputTokens` 或 `requiredTotalTokens > profile.contextWindowTokens` → **固定开销预算失败**，整条失败。
4. 按 ID 顺序逐条加入候选并重新估算：
   - 加入后仍满足两条上限 → 继续加入；
   - 加入后超限且当前批非空 → 当前批封批，下一条开新批；
   - 当前批为空且单条仍超限 → **单条预算失败**，整条失败。
5. 每批请求：
   - `LlmRequest.task = CANDIDATE_SCANNER`；
   - `responseFormat = profile.jsonMode`（仅 `JSON_SCHEMA`/`JSON_OBJECT` 合法）；
   - `maxOutputTokens = task.maxOutputTokens`；
   - `schema` 仅 `JSON_SCHEMA` 使用候选 Schema；
   - 预算已包含输出保留与安全余量。
6. 所有批次顺序调用；任一批 `LlmException`/解析失败/ID 非法/`finish_reason == "length"` → 整条失败；不返回部分候选。

**预算失败类型建议**：复用 `LlmException(LlmErrorCode.LOCAL_BUDGET_EXCEEDED)`，消息只含固定原因/受控数值，不含 Raw 正文/Key/URL；CT16 将该条保留 Pending。

## 4. 候选 ID 与稳定去重

- 每批响应必须是 JSON object，仅允许 `candidate_ids`；值为字符串数组，可为空。
- 每个 ID 必须属于该批实际发送的 ID 集合；未知/跨批/空白/非字符串 → 整批失败。
- 重复 ID：稳定去重（保留首次出现），不视为失败。
- 所有批次成功后合并；建议按快照 `id ASC` 输出，保证确定性；不重排为模型返回顺序。
- 不预设候选数量上限，不静默截断；输出上限由 Task 预算与 `finish_reason` 显式失败保护。

## 5. 快照与取消/关闭

- 单次 `database.read { ... }` 内分页读取全部 Organized（如 `scanPage(offset, 256)`），在内存按 `id` 排序；**ReadContext 不得逃逸**，读取结束后才调用 LLM。
- 不在读事务内做 HTTP/LLM；不在 LLM 期间持有数据库连接。
- `CancellationException` 原样传播；不捕获后转普通失败；不写任何状态。
- 关闭/超时由 CT16 Scheduler 取消并 join；CT13 只保证不吞取消、不产生部分结果。
