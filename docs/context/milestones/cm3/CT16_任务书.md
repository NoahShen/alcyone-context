## 1. 目标

```text
Extraction/Dreaming Raw+Pending COMMIT
  → Immediate Trigger ─┐
Periodic Cron → has pending? ─┤
                              ▼
               单 Worker / 饱和 Trigger Counter
                              ▼
            每轮固定 Pending ID 列表（raw.created_at,id ASC）
                              ▼
                  逐条：Source 幂等 → Scanner → Governance
                              ▼
                    CT15 原子提交 + Pending 出队
                              ▼
                  Committed 后 Map 通知接缝（默认 no-op）
```

- Immediate Trigger 由 Extraction/Dreaming 成功后通知；一次事务多 Raw 只请求一次。
- Periodic Cron 只检查 `organization_pending` 是否非空，不为空才请求 Worker。
- 一次 Trigger 代表一次**全量扫描机会**；Worker 每轮先固定本轮 Pending ID 列表，本轮新入队留后续 Trigger/轮次。
- 单条普通失败保持 Pending 并跳过，本轮继续；不得在轮内反复取失败项形成无限重试。
- CT16 才接 Factory/Impl、Config/Loader 与生产生命周期；CT16 DONE 前不得宣称 CM3 完成。

## 2. 配置草案

### 2.1 冻结结构

```yaml
context:
  organization:
    triggers:
      immediate:
        enabled: true
      periodic:
        enabled: true
        cron: "*/10 * * * *"
```

推荐 Core/Runtime 配置模型：

```kotlin
data class OrganizationConfig(
    val immediateEnabled: Boolean = true,
    val periodicEnabled: Boolean = true,
    val cron: String = "*/10 * * * *",
)
```

- `ContextConfig.organization: OrganizationConfig? = null`：`null` 表示未配置 Organization，保持兼容且不建 pipeline。
- 出现 `context.organization` 即视为“显式启用”；空映射使用默认 Trigger，但必须存在合法 Candidate/Governance LLM 绑定。
- 普通 YAML 可省略；未知键、类型错误、非法 cron、无任何 Trigger 等按 `INVALID_CONFIG`/`UNKNOWN_FIELD` 拒绝。
- D4 固定上海时区，`timezone` 键拒绝；D2 要求两个 Trigger 都 disabled 时 `INVALID_CONFIG`。

### 2.2 LLM 绑定门

`context.organization` 存在时必须同时具备：

- `context.llm` 非 null；
- `CANDIDATE_SCANNER` Task 与其 Profile；
- `GOVERNANCE` Task 与其 Profile；
- 两个 Profile 的 `jsonMode` 为 `JSON_SCHEMA` 或 `JSON_OBJECT`。

缺少任一绑定不得静默 no-op；推荐在 `Factory.create` 前完成纯配置校验并抛 `ContextConfigException(INVALID_CONFIG)`，不打开数据库/网络/协程。具体裁定见 D2/D3。

## 3. 组件与职责（建议）

| 层 | 组件 | 职责 |
| --- | --- | --- |
| Core/Port | `OrganizationPendingReadOps/Repository.listAllByRawCreatedAt()` | 单次读快照获取本轮固定 Pending ID；不新增表/索引 |
| Runtime | `OrganizationConfig` + `ContextConfig/Loader` | 解析 Trigger 配置并校验；不启动 Cron |
| Runtime | `OrganizationScheduler` | 饱和 Trigger Counter、单 Worker、轮次消费、关闭与状态 |
| Runtime | `OrganizationPeriodicCron` | 固定时区五字段 cron；到点仅查 Pending 并 request；不补跑 |
| Runtime | `DefaultOrganizationWorker` | 固定列表逐条 Source 幂等、Scanner、Governance、CT15 Commit、Map 唤醒 |
| Runtime | `OrganizationPipeline` | 装配 Scheduler/Cron/Worker，提供 `OrganizationWakeup`、激活门和统一关闭 |
| Runtime | `OrganizationMapWakeup` | internal `suspend fun onOrganizedCommitted()`；默认 no-op，不实现 Map |
| Runtime 接线 | `AlcyoneContextFactory/Impl` | 显式配置门、构造/启动/关闭、Immediate 唤醒闭包、Worker 状态 |

不复用 `ExtractionScheduler` 的业务队列语义：其键是 SessionKey，CT16 是一次 Trigger 对应一次全量 Pending 轮次；只复用生命周期/关闭原则，不强行改 CT09 组件。

## 4. 冻结契约

### 4.1 Pending 固定列表

- 新增 `listAllByRawCreatedAt(): List<String>`：`JOIN raw_memory`，按 `raw.created_at ASC, raw.id ASC`，无 limit。
- 在单次 `database.read` 内取得完整 ID 列表；读取结束后才逐条调用 LLM。
- 本轮处理列表固定；本轮中新入队 Raw 不混入当前列表，后续 Trigger 的新轮可看到。

### 4.2 Scheduler / Counter

- 状态建议 `NEW / RUNNING / CLOSING / CLOSED`；单 Worker Job。
- `triggerCount: Int` 饱和到 `Int.MAX_VALUE`；`request()` 仅在 RUNNING 接受。
- Worker 未运行时启动唯一 Worker；运行中只增计数。
- Worker 每轮开始前在锁内消费一个 Trigger；执行截止式固定 Pending 列表；整轮结束后若计数 >0 再开下一轮，否则退出 Worker。
- `request()` 与 Worker 退出判断共用同一同步边界；不得丢失“退出瞬间新 Trigger”。
- 普通单条失败不终止 Worker；Worker 级不可恢复异常进入可观察失败状态，不自动重建第二 Worker。

### 4.3 逐条治理

单条建议流程：

1. 读取 Raw 与 Source 是否存在；Raw 缺失/数据库错误作为该条失败。
2. Source 已关联：短写事务再次核验 Source；若 Pending 残留则精确删除 1 行；不调用 Scanner/Governance。
3. Source 未关联：CandidateRetriever → GovernanceService → CT15 Committer。
4. `Committed`：调用 Map 通知接缝；`AlreadyAssociated`：不触发 Map。
5. `CancellationException` 原样传播；其他单条异常安全记录后跳过，继续本轮下一条。

### 4.4 Periodic Cron

- UNIX 五字段；启动不立即扫描、严格未来、无补跑、无持久化调度状态。
- 每次 tick 只做 `pending.hasAnyPending()`；false 不 request。
- 查询/调度普通失败 WARN，内部固定可取消退避，不紧凑循环；`CancellationException` 传播。
- `cron` 建议默认 `*/10 * * * *`；时区默认/是否可配置见 D4。

### 4.5 生命周期

- Organization pipeline 只在 `context.organization` 显式配置且 LLM 绑定合法时创建。
- 生产 start 顺序建议：DB/VFS/LLM → Organization pipeline → Extraction runner/pipeline（Immediate wakeup 指向 Organization）→ 启动两条 pipeline → 发布 RUNNING → 激活业务执行。
- Organization worker 在 RUNNING 前由 activation gate 阻塞；启动阶段 Cron tick/Trigger 可计数但不得执行业务。
- Context 进入 STOPPING 时在同一生命周期锁内对 Extraction/Organization 同步 `beginClosing()`；之后先停 Organization Cron，再取消并 join Organization Worker（同时先关闭 Extraction 以停止新 Raw 生产），最后释放 LLM/DB。精确顺序待 D10。
