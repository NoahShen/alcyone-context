## 1. 目标

CT15 接收一条已治理 Raw 的 ID、本次实际提供给 Governance 的候选快照，以及 CT14 校验后的 `GovernanceDecision`，在**单个短 `database.write` 事务**内完成以下闭环：

```text
Raw ID + Candidate Snapshot + Validated Decision
  → 事务内重查 Source/Pending
  → 已关联：仅清理残留 Pending，不再修改 Organized
  → 未关联且 Pending：校验目标版本
  → NEW / MERGE / UPDATE 原子写 Organized + Source + 水位 + Pending 出队
  → COMMIT
```

- LLM 与候选检索在事务外完成，CT14 决策也先由 Runtime Service 产出；D3 要求在提交写事务内再做一次纯确定性 Validator 复验，不调用 LLM/HTTP/VFS。
- Source 关联是来源幂等权威事实，不能把字段更新或 Pending 状态当作已治理依据。
- 任一写入、版本校验或影响行数不符都整笔回滚；源未关联时 Pending 保留。
- 仅清理已经关联 Raw 的残留 Pending 属于幂等收尾，不改 Organized，不推进水位。

## 2. 冻结输入与 API

以下为 D2 冻结接口：

```kotlin
class OrganizationCommitter(
    private val database: ContextDatabase,
    private val idGenerator: MemoryIdGenerator,
    private val clock: Clock,
    private val maxIdAttempts: Int = 3,
) {
    suspend fun commit(
        rawId: String,
        candidates: List<OrganizedMemory>,
        decision: GovernanceDecision,
    ): OrganizationCommitResult
}
```

- `candidates` 必须是本次 Scanner 返回且实际提供给 Governance 的原快照；`MERGE/UPDATE` 用其中的 `targetMemoryId + updatedAt` 验证决策是否过期。
- 不传完整 `RawMemory`、不新增 request DTO；CT15 不直接依赖 CT14 Runtime Service。
- 同一写事务先重查 Source/Pending。Source 已关联时优先幂等收尾，不执行决策校验；仅 Source 未关联且 Pending 存在时，调用 CT14 `GovernanceDecisionValidator` 复验字段与候选权限，再继续版本检查和写入。

D4 冻结结果只表达安全业务结局，不携带正文：

sealed interface OrganizationCommitResult {

## 3. 冻结事务语义

### 3.1 来源幂等与 Pending

每次 `commit` 都在新的 `database.write` 事务开头重新读取：

- `organizedMemories.findOrganizedByRaw(rawId)`；
- `pending.exists(rawId)`。

| Source | Pending | 动作 |
| --- | --- | --- |
| 已关联 | 有 | 只删除残留 Pending，必须命中 1 行；不修改 Organized、不推进水位，返回 `AlreadyAssociated(pendingRemoved=true)` |
| 已关联 | 无 | 无写入，返回 `AlreadyAssociated(pendingRemoved=false)` |
| 未关联 | 无 | `STALE_DECISION` 拒绝旧/失效决策，不创建、不静默成功 |
| 未关联 | 有 | 继续执行本次 NEW/MERGE/UPDATE |

- 数据库查询错误不能被解释为“未关联”；`CancellationException` 与 `ContextPersistenceException` 原样传播。
- 不新增独立任务状态、Journal、Deferred 或幂等键。

### 3.2 目标版本

- `NEW`：不使用 target，不检查 Organized 版本。
- `MERGE/UPDATE`：target 对应候选必须存在于本次候选快照；事务内重读目标行，目标必须存在，且 `stored.updatedAt == candidate.updatedAt`。
- 目标缺失或 `updatedAt` 不一致即过期决策：整笔不写，未关联 Raw 的 Pending 保留，等待下一轮重新检索/治理。
- 不允许用正文比较、`createdAt` 比较或“最后写入获胜”代替版本检查。

### 3.3 动作写入

| 动作 | Organized 写入 | Source | Pending |
| --- | --- | --- | --- |
| `NEW` | 生成新 ID；`createdAt` 为本次新增时刻；`updatedAt` 为已分配水位；写入 content/domains | 新 Organized + 当前 Raw | 删除 1 行 |
| `MERGE` | 保持 ID/createdAt/domains；content 缺席时保留当前 content，仅在提供时更新；无论 content 是否变化都推进 updatedAt | target + 当前 Raw | 删除 1 行 |
| `UPDATE` | 保持 ID/createdAt；替换 content；domains 提供时替换，缺席时保留；推进 updatedAt | target + 当前 Raw | 删除 1 行 |

- 旧 Source 关系全部保留；当前 Raw 只新增一条关联。
- `MERGE` 不修改 domains；`UPDATE` 的 domains 语义以 CT14 校验后的规范化决策为准。

### 3.4 全局毫秒水位

在同一写事务中读取 `maxUpdatedAt()`，按下式分配：

```text
nowMs = clock.instant().truncatedTo(MILLIS)
previousFloor = previousGlobalMax == MAX ? 显式失败 : previousGlobalMax.plusMillis(1)
next = previousGlobalMax == null ? nowMs : max(nowMs, previousFloor)
```

- NEW、MERGE、UPDATE 均占用一个严格大于当前全局 MAX 的毫秒水位。
- 仅清理 Source 已关联 Raw 的残留 Pending 不推进水位。
- D9 冻结：`nowMs = clock.instant().truncatedTo(MILLIS)`；NEW `createdAt=nowMs`，`updatedAt=max(nowMs, previousGlobalMax+1ms)`；MERGE/UPDATE 保留原 `createdAt` 并推进 `updatedAt`。`previousGlobalMax == Instant.MAX` → `WATERMARK_EXHAUSTED`，不 clamp、不倒退。

### 3.5 影响行数与 ID 冲突

- NEW：Organized insert、Source insert、Pending delete 均必须恰好 1 行。
- MERGE/UPDATE：Organized update 或 `advanceUpdatedAt`、Source insert、Pending delete 均必须恰好 1 行。
- 已关联且 Pending：Pending delete 必须恰好 1 行。
- Organized ID 只对**显式主键预检命中**做有限整笔重试，默认最多 3 次；每次重试重新进入 `database.write` 并重跑 Source/Pending/版本检查。不得捕获所有持久化异常并笼统重试，不得 `INSERT OR REPLACE`。
- 任一行数、约束或写入异常都让当前事务回滚；非 ID 冲突不得伪装成可重试碰撞。
