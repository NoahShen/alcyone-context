## 1. 目标与冻结结论

把 CT07 Count 通知 Port 与 CT05 Idle 查询接成**进程内 Trigger + 单 Worker Scheduler**：

```text
Ingestion COMMIT → Count Trigger（countPending ≥ threshold）┐
Cron Idle（findIdleSessions）───────────────────────────────┴→ ExtractionScheduler.request(SessionKey)
                                                              → 单 Worker（全局串行）
                                                              → ExtractionRunner.execute(SessionKey)（CT11 提供实现）
```

| # | 裁定结论 |
| --- | --- |
| D1 | 配置 `context.extraction.triggers.count.threshold=5`、`triggers.idle.enabled=true`、`idleTimeout=10m`、`cron="*/5 * * * *"`；全部可省略，逐层拒绝未知键；不增加 `count.enabled`。threshold 为 Int 且 ≥1；idleTimeout 为有限正 Duration，计算防溢出；直接构造与 YAML 共用同一校验；`idle.enabled=false` 不豁免校验，仅关 Idle（有 Runner 时 Count 仍启用）。 |
| D2 | UNIX 五字段 Cron，固定 `Asia/Shanghai`，不提供 timezone 键；非法值 `ContextConfigException(INVALID_CONFIG)`，含字段路径、不附带可泄漏原值的解析 cause；每次从当前时刻取严格未来 tick，不启动即扫、不补跑；测试用注入 Clock/tick，不真实等 5 分钟。 |
| D3 | 方案 A：Core 新增 **public** `core.extraction.ExtractionRunner`（`suspend fun execute(SessionKey)`，跨模块使用，不是 `context/api` SDK）；Runtime pipeline/Scheduler/诊断/接缝全部 `internal`。公共 Factory 不提供 Runner、不创建生产 pipeline；仅内部组装入口接受 Runner，用真实 SQLite 通知链验证 start/close。CT11 接入真实服务后才宣称生产提取启用。不新增 Core Scheduler Port。Count 复用既有 `IngestionNotifier`，签名不改。 |
| D4 | CT09 **立即取消并真实等待**，不先等 Runner 自然完成、不新增 grace 配置；`shutdownTimeout` 只观察。顺序：锁内进入 CLOSING 并封闭全部 Trigger/Scheduler 准入 → 停 Cron 新扫描 → 取消并 join 扫描、Worker 及结构化子任务 → 清理队列/计数并发布关闭结果。不 drain 队列；`close(Channel)` 不等于任务终止；关闭/dequeue 竞争必须有一致执行准入。owner `NonCancellable`；并发 close 共享成功/失败结果；等待者取消只退出自身等待；失败也必须发布终态。清空集合/计数为 0 不能证明结束，必须 join 真实 Job（含 finally/结构化子协程）。Runtime 顺序：封闭准入、收尾通知与 pipeline，再 `llm → vfs → executor`；封闭动作锁内不挂起。create 零后台副作用；重复 start 只有一个消费者/时钟；启动/关闭竞争与部分失败由唯一所有者逆序清理；未成功发布运行状态不执行 Runner。Runner/扫描回调内关闭自身须在改状态前具名拒绝（复用既有生命周期错误口径）。 |
| D5 | `Int` 饱和到 `MAX_VALUE`，不新增 Long；计数包含执行中的一次机会；每 Session 至多一个排队项或一个执行位置；正常返回/普通异常消费一次，剩余排到队尾，全局单 Worker 且不饿死其他 Session。状态/计数/入队/完成/关闭封闭同一一致性边界（普通短锁可），锁内无 I/O/用户回调/挂起。`trySend` 失败不得留下无人消费的正计数；运行态异常发送失败可观察、不得冒充接受成功。关闭后 request 返回 false/no-op，不打 WARN。`CancellationException` 不当作普通失败消费；正常关闭取消按 D4；Runner 在非关闭状态自行抛 CE 导致唯一 Worker 结束 → 必须封闭准入并使终止可观察，不得保留 RUNNING 外观接单，也不自行重启/重放；确定性测试覆盖。 |
| D6 | Idle single-flight：重叠 tick 跳过、不排队；`extraction.idle.skipped` DEBUG + internal 跳过计数；查询失败 `extraction.idle.failed` WARN，下次自然 tick 再查；CE 原样传播、不记普通扫描失败。Worker 普通失败 `extraction.run.failed` WARN，隔离后继续；非预期消费者终止 `extraction.worker.stopped` WARN。日志只含固定事件名、计数、耗时、受控分类；不输出 SessionKey/消息/SQL/原始异常文本，不直接传 Throwable。Idle 条件保持 CT05 已验收语义（至少一个 pending，且所有状态最新 `created_at` ≤ now-idleTimeout）；验证等号边界、较新 complete/failed 阻止旧 pending、timestamp 无关、多 Runtime/Agent/Session 隔离；不新增索引/改 SQL。 |
| D7 | Count 每次 CREATED+COMMIT 后查 `countPending >= threshold`；不新增独立 Turn Counter；查询失败交既有通知 reporter，不发 Trigger、不影响已提交 Ingestion；取消沿既有链传播；DUPLICATE 不通知。允许订正 `IngestionNotifier` 历史 KDoc，不改签名。 |
| D8 | 允许 `internal` 只读计数/队列/执行状态、`scanOnce`、Clock/tick 与受控屏障；不新增公开 `ContextStatus` 字段、不持久化诊断。测试验证真实执行/退出，不只验证计数；溢出用受控接缝，不循环 MAX_VALUE 次；并发断言用屏障与有界等待。 |
