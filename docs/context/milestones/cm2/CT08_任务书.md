## 1. 目标与范围

把 `context.llm.*` 从「接受但不校验」改为**首次消费并严格校验**，并在 `context/runtime` 提供真实 LLM 调用实现（Ktor Client + CIO）；Core 侧复用**已存在**的 Port，不新增业务抽象。

| 项 | 归属 | 说明 |
| --- | --- | --- |
| `context.llm` 解析与校验 | `context/runtime`（`ContextConfigLoader`） | ENV 展开、未知字段、类型/范围、Profile 引用存在性、预算静态自洽 |
| Task → Profile 路由 | `context/runtime` | 按 `LlmTask` 选 Profile；缺映射/缺 Profile → 具名配置错误 |
| 真实调用实现 | `context/runtime` | 实现既有 `core.llm.LlmClient`（Ktor Client + CIO）；**Core 不得依赖 Ktor** |
| 三类 JSON mode | `context/runtime` | 按 Profile `jsonMode` 发送；与 `LlmRequest.responseFormat` 不一致 → 发送前 `INVALID_REQUEST` |
| 有限重试与总期限 | `context/runtime` | 冻结默认值 + 有限覆盖，见 §3 |
| Token 预算与估算 | `context/core`（纯逻辑） | `ConservativeTokenEstimator`；发送前双条件校验；余量只计一次 |
| Usage 与诊断 | `context/runtime` | 真实 Usage 与估算分开；缺失 Usage = 未知（不是 0）；诊断字段白名单；最小内部调用统计归 B5 |

**复用既有 Core Port（禁止新建平行抽象）**：`LlmClient`、`LlmRequest`、`LlmResponse`、`LlmMessage`、`LlmTask`、`LlmResponseFormat`、`TokenUsage`、`TokenEstimator`（`context/core/src/main/kotlin/.../core/llm/`）。**不得新增 `ExtractionLlm` 或等价重复接口**；仅允许：`LlmRequest` 末尾追加 `schema: String? = null`（**B2 添加**；Kotlin 源码兼容，不宣称 JVM ABI 不变），以及在 `core.llm` 新增 `LlmException`/`LlmErrorCode`（继承 `api.ContextException`）与 `ConservativeTokenEstimator` 实现。

## 2. 配置契约（Q1，冻结 §3.2）

```yaml
context:
  llm:
    safetyMarginPercent: 20            # 可省略，默认 20
    profiles:
      extraction:
        baseUrl: ${LLM_BASE_URL}       # 支持既有 ${ENV} 展开
        apiKey: ${LLM_API_KEY}         # 支持既有 ${ENV} 展开；不要求必须是 ENV
        model: some-model
        contextWindowTokens: 64000
        jsonMode: json_schema          # json_schema | json_object | prompt_only
        connectTimeoutSeconds: 10      # 可省略（默认 10）
        requestTimeoutSeconds: 180     # 可省略（默认 180）
        socketTimeoutSeconds: 120      # 可省略（默认 120）
        maxAttempts: 2                 # 可省略（默认 2，含首次，1..5）
    tasks:
      EXTRACTION:
        profile: extraction
        maxInputTokens: 12000
        maxOutputTokens: 3000
        totalTimeoutSeconds: 360       # 可省略（默认 360）
```

- **未配置 `context.llm`**：`ContextConfig.llm == null`，保持 CM1 行为（ingestion-only），不构造 HttpClient、不发起请求、不因缺失而启动失败。
- **已配置**：严格校验——未知字段 `UNKNOWN_FIELD`（含路径）；`baseUrl` 为绝对 http(s) 且无 userinfo/query/fragment；`apiKey` 展开后非空白（ENV 缺失 → `MISSING_ENV`，只报 ENV 名）；`model` 非空；`jsonMode` 属于三类；数值在范围内；`tasks` 键属于 `LlmTask`（大小写不敏感）且目标 Profile 存在；`maxInputTokens + maxOutputTokens ≤ contextWindowTokens`。
- 错误消息**只含字段路径与 ENV 名**，绝不含 Key 值、URL 凭据、正文；`toString` 全脱敏（Key 恒为 `<redacted>`）。
- 同一进程多 Profile 各自持有独立凭据，**不得串用**；Key 只出现在当次请求 Header 与配置对象内部字段中，配置不热更新。
- **直接 Kotlin 配置与 YAML 同样校验**（同一 `validateLlm`），先取自有集合快照再校验并使用同一快照。

## 3. 调用、超时、重试与取消（Q3/Q4，冻结 §3.5）

- **默认值**：connect 10s / 单次 request 180s / socket 120s（Profile 可覆盖）；Task `totalTimeout` 360s（可覆盖）；`maxAttempts` 2（含首次，可配 1..5）；退避 1s→10s + 轻量 jitter（常量，不配置）。**总期限覆盖全部尝试与退避，使用单调时钟。**
- **只重试可判定的暂时错误**：连接失败/传输 IO、单次请求超时、408、临时 429（有效 `Retry-After` 或限流类 code）、500/502/503/504。其他 5xx、额度耗尽 429、无法安全判定的 429、401/403、400/404/409/422 及 JSON/业务校验失败**不重试**。
- **Retry-After**：整数秒与 HTTP-date 均支持；有效值优先且不截短——若所需等待超过剩余总期限则**直接失败**而非提前重试；无效值回退到退避。
- **取消**：调用方取消与 Runtime 关闭导致的在途取消**都原样传播 `CancellationException`**，不重试、不包装、不转换为普通失败；只有关闭**之后**（含 `CLOSING` 期间）的新调用返回既有 `ContextLifecycleException(CLOSED)` 且不发起 HTTP。
- **响应处理**：HTTP 非 2xx → 按冻结 §3.5 分类的具名失败（含状态码，不含正文/Key）；2xx 但 body 非法 JSON、缺 `choices[0].message.content`、空输出、`finish_reason=length`、明确拒答 → 具名失败，**不修复、不猜测、不做 Markdown 围栏提取**。
- **Usage**：Provider 未返回 usage → `LlmResponse.usage == null`（未知，**不得填 0**）；估算值与真实 Usage 在类型/日志中可区分。
- **Token 预算**：Estimator 是保守估算（不是已证明上界）；发送前校验「估算输入 ≤ Task `maxInputTokens`」与「估算输入 + 输出保留 + 安全余量 ≤ Profile `contextWindowTokens`」，余量只计一次；本地超限与 Provider context-limit 错误分类不同。
- **关闭**：单个 `HttpClient`；`close()` 封闭准入并等待**本地在途真实收尾**（受控 finally / Job 完成屏障）后才关引擎；不要求远端服务器放行响应；关闭等待不被单个等待者取消；不复用通知协程 scope。
- **重定向**：`followRedirects = false`，禁止凭据跨重定向泄露。

## 5. 验收标准（A01～A08）

| # | 标准 |
| --- | --- |
| A01 | 未配置 `context.llm` 时行为与 CM1 完全一致：`ContextConfig.llm == null`（断言配置对象，不是 `AlcyoneContext` 上不存在的字段）、启动不失败、stub 收到 0 次请求、既有 ingestion 仍可入库 |
| A02 | 已配置时严格校验生效：未知字段、缺 `profiles`、空白/缺失字段、非 http(s)/含 userinfo 的 `baseUrl`、非法 `jsonMode`、越界数值、未知 task、task → 未知 Profile、预算静态不自洽、`apiKey` 的 ENV 未设置 → 具名配置错误（`UNKNOWN_FIELD`/`MISSING_ENV`/`INVALID_CONFIG`），消息含路径/ENV 名、**不含 Key 值与正文**；Kotlin 直接配置走同一校验 |
| A03 | Task→Profile 路由正确：多 Profile 场景下每个 Task 使用其声明 Profile 的 baseUrl 路径/key/model；**真实受控 HTTP 交叉断言不串密钥**（stub 记录 path、`Authorization`、`body.model`） |
| A04 | 三类 `jsonMode` 按 Profile 发送（`json_schema` 含 schema、`json_object` 仅 type、`prompt_only` 无 `response_format`）；`LlmRequest.responseFormat` 与 Profile 不一致、`json_schema` 缺/非法 schema → **发送前** `INVALID_REQUEST` 且 0 请求 |
| A05 | 重试语义：可重试失败在 `maxAttempts` 与总期限内有限重试（500,500,200 → 3 次成功；`maxAttempts=2` 持续 500 → 2 次失败）；400 只 1 次；429 带有效 `Retry-After` 按真实到达间隔等待，若超出剩余总期限则直接失败；**额度耗尽 429 判定优先于 `Retry-After`**（不重试）；总期限自 `complete()` 入口起算、每次尝试/退避前重算剩余；持续失败在总期限附近返回（耗时上限断言，不用 sleep 猜）；408 可重试 |
| A06 | 取消与关闭：①调用方取消 → `CancellationException` 原样传播（不包装、非 `CLOSED`），取消后不再重试；②关闭后（含关闭期间）新调用 → `ContextLifecycleException(CLOSED)` 且 0 新请求；③`closeAsync()` 等待**本地**在途真实收尾（跟踪只在 `invokeOnCompletion` 移除 + 受控 finally 屏障），不依赖 stub 放行响应；④清理失败仍发布终态 `CLOSED`，重复关闭重抛同一失败（不直接 return）；⑤清理 owner 不可取消、等待者可取消 |
| A07 | 响应与预算：非 2xx 具名失败且不泄密；2xx 非法 JSON/空输出不修复直接失败；`finish_reason=length`/拒答具名失败；缺失 Usage = 未知（null，非 0），估算与真实 Usage 可区分；超 Task 输入预算或超 Profile 容量（含余量，只计一次）→ 本地预算错误且 0 请求；Provider context-limit 分类不同；`ConservativeTokenEstimator` 有纯逻辑单测（Core 不依赖 Ktor） |
| A08 | 依赖与零侵入：`context/core` 无 Ktor（build 文件 + 编译类路径双证据）；`vfs/*` tracked diff 为空（81 基线 mismatch=0）；无新增表/索引/`user_version`；日志/异常/`toString` 无 Key 与正文（独特标记断言）；`followRedirects=false` 有重定向证据；B5 的最小内部统计可读且无 Key/正文 |
