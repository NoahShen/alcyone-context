## 2. 关键结论

### 2.1 无 Schema/Repository 缺口

CT15 所需操作均可在单个 `database.write` 内完成：

1. `tx.organizedMemories.findOrganizedByRaw(rawId)`；
2. `tx.pending.exists(rawId)`；
3. `tx.organizedMemories.findById(target)` + `updatedAt` 比对；
4. `tx.organizedMemories.insertNew/update/advanceUpdatedAt`；
5. `tx.organizedMemories.insertSourceLink`；
6. `tx.pending.dequeue`。

D12 冻结 **不改 SQL/Schema/Port**；不需要新增 Source 布尔查询或其他 Repository 方法。

### 2.2 事务内重查优先于来源幂等

Source 是治理成功的权威事实。必须先查 Source，再决定是否使用本次决策：

- Source 已关联时，即使本次传入决策已过期/非法，也应优先完成残留 Pending 清理；否则会把已完成 Raw 错误留在队列。
- Source 未关联且 Pending 缺失时，本次决策已失去可执行对象，应拒绝而非静默创建。
- 数据库读失败必须中止，不能 fallback 到 Scanner/治理或 NEW。

### 2.3 目标版本校验只能依赖 updatedAt

- CT13 候选保留原始快照对象；CT14 只能操作这些候选。
- CT15 在拿到写锁后，读取当前目标；仅 `updatedAt` 相等才允许 MERGE/UPDATE。
- 任何成功 Organized 变更都必须推进 `updatedAt`，包括无 content 的 MERGE；因此内容/分类/来源变化都能被版本检查覆盖。
- 不比对正文/domains 作为版本，不把“当前内容相同”当作可写入。

### 2.4 水位分配

D9 冻结每个实际修改 Organized 的事务只修改一行，按以下安全算法：

```text
previous = tx.organizedMemories.maxUpdatedAt()
nowMs = clock.instant().truncatedTo(MILLIS)

if (previous == null):
    next = nowMs
else if (previous == Instant.MAX):
    fail WATERMARK_EXHAUSTED
else:
    next = max(nowMs, previous.plusMillis(1))
```

- NEW：`createdAt` 与 `updatedAt` 使用同一毫秒基准；`updatedAt >= createdAt`。
- MERGE/UPDATE：保留原 `createdAt`；`updatedAt = next`。
- 已关联 Raw 的 Pending 清理不改 Organized，因此不分配新水位。
- 不使用 `Clock` 决定事实时间；`createdAt/updatedAt` 只代表系统生成/更新时刻。

### 2.5 动作写入顺序

D8/D10 冻结顺序如下（同一事务内，行数断言不可放松）：

#### NEW

1. 生成 Organized ID；
2. 读取全局 MAX 并分配水位；
3. `insertNew`，必须 1 行；
4. `insertSourceLink(newId, rawId)`，必须 1 行；
5. `pending.dequeue(rawId)`，必须 1 行；
6. 返回 `Committed(NEW, newId)`。

ID 预检命中时整笔回滚并重新生成，最多 3 次；每次重试都重新获取写事务并重跑 Source/Pending/版本检查。

#### MERGE

1. 读取/比对目标 `updatedAt`；
2. 分配水位；
3. content 未提供：`advanceUpdatedAt(target, next)` 必须 1 行；
4. content 提供：`update(current.copy(content=..., domains=current.domains, updatedAt=next))` 必须 1 行；
5. Source insert 1 行、Pending delete 1 行；
6. 返回 `Committed(MERGE, target)`。

#### UPDATE

1. 读取/比对目标 `updatedAt`；
2. 分配水位；
3. `update(current.copy(content=decision.content, domains=decision.domains ?: current.domains, updatedAt=next))`；
4. Source insert 1 行、Pending delete 1 行；
5. 返回 `Committed(UPDATE, target)`。

不得在 `update` 后再次 `advanceUpdatedAt`：两者都会更新同一行，额外行数没有业务收益。

## 3. 冻结错误与结果模型

D4/D5 冻结新增 Core 内部 `OrganizationCommitException`，消息只含安全原因，不包含 content、完整 Raw ID、Key、URL。分类如下：

| 情况 | 建议分类 |
| --- | --- |
| target 不存在或 `updatedAt` 不符 | `STALE_TARGET` |
| Source/Pending 均不存在 | `STALE_DECISION` |
| Organized/Source/Pending 影响行数不符 | `ROW_COUNT_MISMATCH` |
| Organized ID 预检冲突重试耗尽 | `ID_COLLISION_EXHAUSTED` |
| `previousGlobalMax == Instant.MAX` | `WATERMARK_EXHAUSTED` |
| CT14 Validator 拒绝字段/候选权限 | 安全非法决策 reason（例如 `INVALID_DECISION`） |

- `CancellationException` 原样传播。
- `ContextPersistenceException` 原样传播，不包装、不伪装成 ID 冲突。
- 过期目标属于单条普通失败，由 CT16 记录后跳过并保留 Pending；CT15 不自动重试 LLM。
- 已关联幂等分支返回结果，不以异常表示成功。

## 4. 并发与“未确认 COMMIT 结果”

- 写事务内先重查 Source/Pending，再写目标；唯一 WriteSlot 保证检查与写入之间没有本进程其他写事务插入。
- 若前一次 COMMIT 已成功但调用方未收到结果，再次处理同一 Raw 时必须看到 Source：
  - Pending 残留：只出队；
  - Pending 已删：no-op 成功；
  - 不重复创建/更新 Organized。
- 不依赖“上一次调用返回值”判断是否已治理，只依赖 SQLite Source 权威事实。
- 可在测试中使用 wrapper 委托真实 `database.write`，在成功返回后抛出一次受控“结果未知”异常；随后重新调用必须幂等收敛且数据库无半成品。该 wrapper 只存在于测试源集。

| 类别 | 真实 SQLite 验证 |
