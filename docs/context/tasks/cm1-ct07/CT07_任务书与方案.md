## 1. 范围（严格）

### 1.1 包含
1. **Core 共用 Ingestion Service**：规范化、校验、限额、单写短事务幂等（CREATED/DUPLICATE/TURN_CONFLICT）、`created_at` 服务端 Clock、COMMIT 成功边界。
2. **Runtime SDK 接线**：在冻结接口 `AlcyoneContext` 增加/实现 `suspend fun ingestConversation(turn: ConversationTurn): IngestResult`；不新增其他公开契约。
3. **Server 最小 HTTP**：`POST /v1/conversations/turns`；Bearer 静态 Key 注册与 `runtime_id` 绑定；错误映射 401/403/400/409/413/503/500（及 201/200）。
4. **提交后异步通知 Port + 受控替身**：仅首次 CREATED 且 COMMIT 成功后通知；通知失败不回滚、不改变接收结果；DUPLICATE 不通知。

- CM2+ 任何能力；不改 VFS、不改 CT04/CT05/CT06 已验收语义。

## 2. 契约与数据流

### 2.1 冻结接口（CT01）
```kotlin
interface AlcyoneContext : AutoCloseable {
    suspend fun ingestConversation(turn: ConversationTurn): IngestResult
    suspend fun start(); override fun close(); suspend fun closeAsync(); suspend fun getStatus(): ContextStatus
}
```
- `IngestResult(id: Long, status: IngestStatus{CREATED,DUPLICATE})`；`ContextIngestionException(errorCode: INVALID_TURN|PAYLOAD_TOO_LARGE|TURN_CONFLICT|UNAUTHORIZED|FORBIDDEN)`（仅 Server 使用后两者）。
- SDK 调用前必须已 `start()`；未启动 → `ContextLifecycleException(NOT_STARTED)`，已关闭 → `CLOSED`。不新增公共方法。

### 2.2 Core Service（`context/core`）
`IngestionService`（名称待实现定，仅 Core 内可见）职责：
1. **规范化**：`timestamp` 必须为带明确 offset 的 ISO-8601，解析为 `Instant` 后用 `TimeCodec.format` 统一为 `+08:00` 毫秒文本；messages 顺序与 `content` **原样保留**（不 trim、不截断、不去重）；`ChatMessage` 已是强类型。
2. **校验**：四个 ID 非空白且长度 ≤ `maxIdLength`（默认 256）；`messages` 非空且 ≤ `maxMessages`（256）；单 Turn 规范化 UTF-8 字节 ≤ `maxTurnBytes`（2 MiB）；role 由枚举保证。超 ID/messages 数量/字节 → `PAYLOAD_TOO_LARGE`（ID 空白/时间非法/消息空 → `INVALID_TURN`）。
3. **幂等与单写事务**：一次 `database.write { }` 内按四元键查找 → 不存在则 INSERT（`pending`，`created_at = clock.instant()` 经 TimeCodec）→ `CREATED`；存在且规范化 timestamp + 有序 `(role,content)` 相同 → `DUPLICATE`（原 id，不刷新任何字段）；存在但内容不同 → `TURN_CONFLICT`。比较不含 id/created_at/extraction_status。
4. **COMMIT 边界**：仅 `write` 成功返回后才返回结果并触发通知；失败向上抛具名异常，不伪报 CREATED。
5. **限额来源**：`context.ingestion.{maxTurnBytes,maxMessages,maxIdLength}`（CT06 暂未消费，本任务开始读取并校验；缺省 2 MiB/256/256）。非法配置在 CT06 配置层报错（本任务补校验与测试）。
6. **通知**：`CountTriggerPort`（Core Port，`fun onCreated(sessionKey: SessionKey)` 或 suspend 等价）在与事务分离的异步路径调用；仅 CREATED；异常捕获并脱敏记录；不回滚、不改变结果；DUPLICATE 不调用。CT07 只提供 Port + 受控替身，不实现 Count/Extraction。

### 2.3 Runtime（`context/runtime`）
- `AlcyoneContextImpl.ingestConversation` 委托 Core Service；生命周期门（start 前 NOT_STARTED、closed 后 CLOSED），复用已打开的 `ContextDatabaseImpl` 与 Clock。
- 默认通知替身：no-op（或可注入的受控记录替身，仅测试/宿主接线用），不启动后台 Worker/Cron。

### 2.4 Server（`context/server`）
- `POST /v1/conversations/turns`，`Authorization: Bearer <key>` + JSON 六字段。
- **静态注册**：`server.ingestion.clients.<runtimeId>.{runtimeType,apiKey}` 由 Server 解析（环境变量展开、缺失/空白报配置错误、Key 不打印）；同一 Runtime 内新增 Agent/Profile 不需注册。
- **认证**：Key→runtimeId；未认证 401；请求体 `runtime_id` 与 Key 绑定不一致 403。
- **限额先于完整解析**：读取请求体前按 Content-Length/流式读取上限拦截，超 2 MiB → 413；反序列化后再按消息条数/ID 长度校验。
- **响应**：CREATED→201；DUPLICATE→200（同一 id）；INVALID_TURN→400；TURN_CONFLICT→409；PAYLOAD_TOO_LARGE→413；PERSISTENCE_UNAVAILABLE→503；其余→500。响应不含 Key/正文/连接信息。
- Server 复用同一 Core Service（与 SDK 同一校验/幂等逻辑），不建第二套。

## 8. Architect 批准记录（2026-10-29）

**结论：方案批准，Q1～Q5 裁定如下；可按 B1→B2 开始实现。**

- **Q1**：超长 ID 使用 `PAYLOAD_TOO_LARGE`/HTTP 413。CT01 将四个业务 ID 的最大长度列为输入上限，且技术设计 §4.3 明确默认 256；因此与 maxMessages/maxTurnBytes 一样按超限处理。
- **Q2**：JSON 顶层与消息对象未知字段拒绝为 `INVALID_TURN`/400。使用 kotlinx.serialization strict JSON；忽略未知字段会静默放过拼写错误，且CT01明确负责配置/输入契约应防止静默忽略。JSON 反序列化错误映射400，错误文本只给字段类别，不回显请求正文。
- **Q3**：批准 Core Port `suspend fun onCreated(sessionKey)`；Runtime 在返回成功前启动异步通知，不等待结果；替身异常脱敏捕获，失败不回滚、DUPLICATE 不通知。禁止创建 Worker/Cron/持久队列。
- **Q4**：批准 Server 解析 `server.ingestion.clients`；Context Runtime 继续只负责 context/vfs。Server 对该子树严格未知字段、类型、ENV缺失/空白和Key冲突校验；Key不得进入异常、日志、toString。
- **Q5**：批准路由插件 `Application.ingestion(...)` 与最小 CIO 启动封装；不发布/不部署/不新增完整管理权限系统。

### 定点补充要求（实现必须落实）

1. **配置快照与范围**：`context.ingestion` 限额在 Runtime Loader 解析后必须归实例所有（复制值），非法值在加载时拒绝。Server 注册集合在解析后同样归 Server 所有；调用者修改原集合不能绕过认证。不得修改 CT06已验证的 VFS/Context配置所有权。
2. **HTTP限额边界**：`maxTurnBytes`必须先于完整 JSON 反序列化执行（Content-Length与流式读取双重防护）；计数、ID长度与规范化载荷在SDK/HTTP同一Service校验。413响应不产生数据库行。响应和日志不得包含 Key、请求正文、内部连接信息。
3. **时间与幂等**：必须显式拒绝无明确offset的时间字符串并按给定offset解析；存储统一`TimeCodec.format`。等价offset、JSON对象字段顺序/文本空白不影响比较；消息顺序变化必须冲突。DUPLICATE不更新createdAt/status，不再次通知。
4. **事务与并发**：单写短事务内查找/比较/INSERT，通知必须在事务外。Repository唯一约束竞争必须重读权威记录并返回DUPLICATE/CONFLICT；不能把唯一冲突笼统映射500。COMMIT失败不得返回CREATED。
5. **生命周期**：SDK在CREATED/STARTING调用NOT_STARTED，STOPPING/CLOSED调用CLOSED（CT06状态语义不变）。B2 HTTP与Context生命周期需明确：Context未启动返回503；关闭过程不再接入新请求，已接纳请求的完成与关闭协议不得互相死锁。
6. **接口范围**：仅实现CT01冻结`ingestConversation`；API不新增其他公共方法/模型/错误码。Core不依赖Ktor Server/YAML/JDBC实现；Server不直接访问Persistence内部。通知Port属Core内部，不得挂到API公共契约。
7. **测试**：B1/B2分别真实文件SQLite；B2用Ktor test host并覆盖401/403/400/409/413/503/500、同Runtime新agent允许、跨Runtime拒绝、DUPLICATE不通知、通知失败不回滚、并发同键、重开一致。补配置快照修改、无offset时间、流式超限、strict JSON未知字段等反例。

## 9. B1 复核阻断修复设计（Lead，2026-10-29）

### 9.1 R1 时间 offset 契约

- **保持 API `ConversationTurn.timestamp: Instant` 不变**（CT03 冻结），不改公共契约。
- 新增 Core 内部工具 `IngestionTimestampText`（`context/core/.../ingestion`，不依赖 HTTP/YAML/JDBC）：
  - `parseRequiringOffset(text: String): Instant`：仅接受带**明确 offset** 的 ISO-8601（`OffsetDateTime.parse`/等价），`+08:00` 与 `Z` 均合法并得到同一 `Instant`；无 offset（如 `2026-10-23T20:15:00`）、非法格式、纯日期等一律抛 `ContextIngestionException(INVALID_TURN)`，消息只给字段类别、不回显原文。
  - 该工具供 B2 Server DTO 使用；B1 直接在真实测试中覆盖：无 offset/非法 → `INVALID_TURN`；`+08:00` 与等价 `Z` → 同一 Instant；存储一律 `TimeCodec.format`（`+08:00` 毫秒）。
- **SDK 可信路径限制如实记录**：SDK 入参已是 `Instant`，无法保留/校验原始文本 offset；SDK 只保证按 Instant 幂等与 `TimeCodec` 规范存储，不声称在 SDK 层拒绝无 offset 文本。该限制写入 `IngestionService` KDoc 与 CT07 交付文档，不引入原始文本载体、不改 API、不让 Core 依赖 HTTP。
- B2 必须用该工具解析 HTTP `timestamp` 字符串并映射 400 `INVALID_TURN`；`+08:00` 与 `Z` 等价请求必须得到 DUPLICATE。

### 9.2 R2 通知失败可见性与关闭语义

- Core 新增内部诊断 Port `IngestionNotificationReporter`（不与 API 公共契约）：`fun reportFailure(cause: Throwable)`；**只传异常对象，不传 SessionKey/正文**。
- `IngestionService.notifyCreated`：捕获非取消异常 → 调用 reporter（默认 no-op）；`CancellationException` 不吞：记录后原样抛出（供关闭路径可见）。
- Runtime：
  - 通知使用**懒创建**的受限协程作用域（首次通知才创建，`Dispatchers.IO.limitedParallelism(1)` 串行），create/构造不启动线程；跟踪在途通知 Job。
  - 默认 reporter 用 SLF4J 记录**仅异常类名 + 固定上下文**（不含 SessionKey 值/正文）。
  - `close`：先取消剩余通知 Job 并逐个 reporter 记录取消（类名），不阻塞既有清理协议；通知失败不影响已提交 Turn。
- 测试（真实可见性，不得“不抛即通过”）：
  - 注入记录型 reporter：notifier 抛错时 reporter 收到同一异常且 CREATED 仍成功、Turn 未回滚；DUPLICATE 不通知、reporter 不收到。
  - 关闭期间挂起通知被取消：注入阻塞型 notifier，close 后 reporter 记录取消、Scope 内无残留 Job；断言不泄露 SessionKey/正文。
  - 懒创建：create 后无通知任务/无线程创建（仅在首次 CREATED 通知后出现）。

### 9.3 边界
- 不改 API 公共模型/方法；Core 不引入 HTTP/YAML/JDBC；Server 不直接访问 Persistence；不建 Worker/Cron/持久队列；B1 通过后再做 B2。
