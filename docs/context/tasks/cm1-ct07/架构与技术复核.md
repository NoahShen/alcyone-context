### R1：冻结输入契约要求时间字符串必须明确携带offset，B1无法执行

技术设计§4.3和批准记录§8均要求“timestamp必须是有效且明确携带时区偏移的ISO-8601时间”。CT03冻结公共模型`ConversationTurn.timestamp`为`java.time.Instant`，`Instant.parse`确实无法区分输入文本是`Z`、`+08:00`还是服务端转换结果；B1注释写着“API层已归一”，但没有任何API层/HTTP层解析器，Core只能看到Instant。现有测试仅提交`Instant.parse("...Z")`，并不能证明等价offset输入被接受、无offset输入被拒绝。

这不是B2专属问题：B1声称交付“SDK Ingestion规范化、校验与限额”，Service无法校验该冻结条件，且方案§2.2把它列为Core Service职责。SDK路径若无法保留原始文本offset，就需要明确职责边界并把原始文本带进B1校验，不能留到B2后凭空恢复。

**修复要求（由Lead给具体设计后交Worker）**：保留`ConversationTurn.timestamp: Instant`冻结公开类型；B1增加内部规范化/解析边界（例如HTTP Request DTO解析后构造Turn前校验原始timestamp文本，SDK侧新增内部输入载体或服务参数携带原始文本），确保：无offset/非法时间→INVALID_TURN；`+08:00`与`Z`等价offset→DUPLICATE；存储仍统一`TimeCodec.format`。不得把HTTP依赖引入Core，不得改变API冻结签名；若SDK可信路径不能提供原始文本，需如实记录并仅由HTTP DTO执行该检查，但不能声称SDK已执行offset校验。

### R2：通知失败“记录脱敏异常”未落实，close直接取消fire-and-forget

批准记录与任务书均要求通知异常“脱敏记录”，失败不回滚但可见。当前实现：

- `IngestionService.notifyCreated`捕获Exception后空处理，注释称“记录异常类名”，实际没有日志或任何诊断记录；
- `AlcyoneContextImpl`为通知创建`SupervisorJob()+Dispatchers.Default`常驻scope，`shutdown()`第一行`notificationScope.cancel()`。正在挂起的通知会在close时被取消；`notifyCreated`对`CancellationException`原样抛出且不记录。失败/取消均不可见，也没有测试断言close时未完成通知的语义。

这不是Worker/Cron/队列要求：只需有限、无后台常驻任务的异步通知。可接受方案包括：为每次CREATED启动有界独立Job并在完成后记录结果；或使用限定用途scope，close仅停止新通知并尽力等待/取消既有通知，同时记录取消/失败；或同步边界内调用快速替身但明确失败可见。不得让scope在create阶段启动任何线程；`create()`仍零副作用。

**修复要求**：通知失败和关闭时取消必须以安全、脱敏方式记录（项目已有SLF4J API，Runtime可用；消息只含异常类名和固定上下文，不含SessionKey三值或正文）。补真实测试：通知异常记录可见；close期间挂起通知的取消/完成行为明确；DUPLICATE仍不通知；不启动Worker/Cron/持久队列。若记录需要Logger，测试用捕获Provider或最小internal可注入记录器，不能靠吞异常后“不抛即通过”。

### R1：时间offset契约（关闭）

- `IngestionTimestampText.parseRequiringOffset`使用`OffsetDateTime.parse`，仅接受带明确offset的ISO-8601；`+08:00`与`Z`得到同一`Instant`。

- `IngestionService` KDoc如实记录SDK `Instant`路径无法校验原始文本offset；B2 HTTP DTO必须使用该解析器。

### R2：通知失败可见性与关闭语义（主路径关闭，保留一个竞态阻断）

- `IngestionNotificationReporter`只接收异常对象；`notifyCreated`非取消失败上报且不回滚，`CancellationException`上报后原样抛出。
- Runtime通知scope懒创建，使用`Dispatchers.IO.limitedParallelism(1)`；跟踪Job；默认SLF4J reporter只输出固定上下文和异常类名。
- 现有测试真实断言同一异常实例、DUPLICATE不通知、create/start不创建scope、close取消挂起通知且无残留Job。

### R3：close与已接纳ingest的竞态可能重新创建通知scope（阻断）

当前时序：
1. `ingestConversation`观察到`RUNNING`；
2. `service.ingest`完成COMMIT并返回`CREATED`；
3. `shutdown()`先行调用`cancelNotifications()`，快照并取消旧Job、把`notificationScope`置空；
4. `launchNotification()`随后执行，`notificationScope()`会重新创建一个全新scope并launch通知。

结果：该通知发生在close取消之后，不会被本轮`cancelNotifications()`取消；若notifier挂起，close后的“无残留Job”承诺失效。现有close测试只覆盖通知已先挂起再close的顺序，没有覆盖“COMMIT完成后、launch前close获胜”的竞态。

**修复要求**：
- 在`notificationLock`内增加通知准入关闭标志。`cancelNotifications()`先置关闭，再快照/取消旧scope；`launchNotification()`在同一锁内检查该标志，close后不得创建新scope或新Job。
- 若COMMIT成功但通知因close未能准入，必须以固定脱敏`CancellationException`上报reporter，不得静默丢失；不得包含SessionKey/正文。
- 加锁顺序不得引入suspend或反锁；`launchNotification`必须先把Job加入跟踪集合再放行执行，保证close快照可见。
- 增加确定性竞态测试（可用最小internal post-ingest/pre-notification gate或等价真实数据库包装）：先证明COMMIT已成功且调用停在通知launch前，调用`close`，再放行；断言不重新创建scope、无通知Job残留、reporter收到取消且不泄露业务值。
- 保持create/start零通知副作用、既有通知失败/取消测试全部通过；更新实际测试计数与交付SHA。
