## 2. R1 根因与修复目标

- 现状：Worker 的 `catch (CancellationException)` 在非关闭态直接 `state=CLOSED`、清计数、创建并 `complete(null)` 的 `closeOutcome`；随后 `closeAsync()` 走共享结果路径立即返回。
- 后果：Worker Job 的真实子任务（`CoroutineScope(currentCoroutineContext()).launch`，finally 里 `NonCancellable` 等待）尚未结束，close 已成功；`closeActionForTesting` 注入的清理失败被跳过。
- 目标：**封闭准入与“清理完成”分离**；由**不会 self-join 的唯一清理 owner** 完成真实 Worker/子任务 join、释放自身 scope parent Job 与队列资源后，才发布共享结果。正常 close、非关闭 CE、并发 close 共用同一清理与成功/失败结果。

## 3. 锁定的修复协议

1. **非关闭 CE**：Worker 只做两件事——在状态锁内将 `RUNNING → CLOSING`（封闭准入）并记录 `worker.stopped` WARN；**不得**自行置 `CLOSED`、清计数或发布 `closeOutcome`。随后触发唯一清理。
2. **唯一清理 owner**：必须由**不是失败 Worker 自身**的协程执行（例如 Scheduler 自有的 cleanup scope / sibling Job），避免 self-join；owner 全程 `NonCancellable`。只有第一个进入 CLOSING 的路径创建 `closeOutcome` 并启动清理；其余（外部 close、并发 close、Worker CE 与 close 竞争）只 await 同一结果。
3. **owner 清理顺序**：
   - 取消 Worker Job（含其结构化子任务）；
   - 丢弃队列：`close`/`cancel` Channel，**不 drain**；释放排队引用；
   - `join` 真实 Worker Job（等待其 finally 与全部结构化子 Job；不得以计数/集合为空代替）；
   - 执行 `closeActionForTesting`（如有）；
   - 清空 `pending`/`queuedItems`；
   - 取消并释放 Scheduler 自有的 scope parent Job；置 `scope/worker/cleanup` 引用为空；
   - 状态置 `CLOSED`，**最后**发布 `closeOutcome`（成功 `null` / 失败同一异常）。
4. **共享结果**：清理失败也发布 `CLOSED` + 同一失败实例；`CLOSED` 后重复 close 重抛同一实例；等待者取消只退出自身等待，不影响 owner；owner 不得被等待者取消。
5. **自关闭拒绝**：Runner 回调内调用 `closeAsync()` 仍须在改状态前具名拒绝；cleanup 不得继承 Runner 执行标记（不得形成自等待）。
6. **不得回退**：普通失败消费一次并继续、队尾重入、计数饱和、trySend 回滚、关闭后 request no-op、start 幂等/CLOSED 拒绝、正常 close 语义、日志脱敏（无 SessionKey/异常文本/Throwable）。
7. **不宣称** OS 线程泄漏修复；只要求释放自身 scope parent Job、Channel 缓冲与排队引用。
