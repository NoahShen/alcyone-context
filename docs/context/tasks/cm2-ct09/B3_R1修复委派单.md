## 2. 锁定的修复协议

1. Pipeline 增加**状态感知关闭门**（普通短同步，非挂起）：
   - `beginClosing()`：幂等，仅设置内部 `closing/admission=false`；锁内不挂起、不调用 Context、不等待。
   - `requestFromIdle` / `requestFromCount`：门关闭后返回 false/no-op，不再向 Scheduler 提交新请求。
   - 包装 Runner：`activation.await()` 之后、调用真实 Runner 之前检查关闭门；门关闭则**直接返回，不执行 Runner**（不能仅检查 Context 对象状态）。
   - `closeAsync()` 开头也调用 `beginClosing()`（覆盖启动失败/直接关闭路径）。
2. `AlcyoneContextImpl.shutdown()` 在**首次状态锁内**（RUNNING→STOPPING 同一 `synchronized(lock)` 块）调用 `pipelineToClose?.beginClosing()`；必须在释放锁前完成，不能等 `cancelNotifications` 或 `releaseResources`。
   - 该调用只做普通短同步；不得在锁内挂起、不得 self-wait。
   - STARTING/STOPPING 路径按现有语义；未发布 pipeline 由 start 清理路径关闭。
3. 不改变 `activate` 语义（不能用 `activate=false` 代替 closing，避免悬挂）；不改变 Scheduler/IdleCron 已验收协议；不得回退 B1/B2。
4. 关闭顺序、通知收尾、真实 join 与资源释放顺序保持 B3 已验收实现。
5. 已准入并在 STOPPING 前已启动的 Runner 属在途，由 pipeline close 取消/等待；判据是 STOPPING 后不得**新启动** Runner。

## 3. 必须新增的正式回归（`ExtractionPipelineLifecycleTest`）

使用既有 `beforeNotificationSnapshotForTesting` 在 Context 已 STOPPING、通知收尾未完成时设置屏障：

1. **新 Idle tick 不得在 STOPPING 窗口启动 Runner**：真实 SQLite 插入空闲 pending；close 进入 STOPPING 屏障；发送新 tick；有界等待 500ms 内 Runner **0 新进入**；放行后 close 完成、CLOSED、无遗留任务。
2. **已排队项不得在 STOPPING 窗口启动 Runner**：先让第一项 Runner 进入并阻塞，使第二项留在 Scheduler 队列；进入 STOPPING 屏障；放行第一项；有界等待内第二项 **不进入 Runner**；放行 close 后完成、CLOSED。
3. 断言 STOPPING 后 `requestFromIdle`/Count 路径不再新增执行（可用 Scheduler 队列/执行计数与 0 Runner 证据）；不破坏既有 13 例。
