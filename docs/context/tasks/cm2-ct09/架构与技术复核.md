### 5.2 B3-R1：Context 进入 STOPPING 后 pipeline 仍可启动新 Runner

`shutdown()` 在状态锁内把 RUNNING→STOPPING，但从该点释放锁后，先执行 `cancelNotifications()`、`waitForStart`，再进入第二次状态锁并调用 `releaseResources()`。在这段窗口内：

- `IdleCron` 与 `ExtractionScheduler` 仍是 RUNNING 组件；
- 新 Idle tick 可启动扫描，并把结果提交给 Scheduler；
- Scheduler 的新入队或既有队列项也可到达执行准入并调用 Runner；
- Context 层没有统一的 extraction admission 封闭；Pipeline 自身也没有对外关闭/禁止准入接口。

两个受控探针均在真实关闭窗口复现。探针用 `beforeNotificationSnapshotForTesting` 在 Context 已为 `STOPPING`、尚未完成通知收尾时屏障外部 close；此时：

1. 发送一个 Idle tick，IdleTrigger/IdleCron 继续运行，随后 Runner 进入，观察到生命周期为 `STOPPING`；
2. 先安排一个排队项并让第一段扫描完成（该项已入队但未执行），再进入同一 STOPPING 屏障，放行后 Runner 从队列启动，生命周期为 `STOPPING`。

### 3.2 B2-R1：持续调度错误形成不可取消的紧凑循环

定位 `IdleCron.kt:177-191`：runTicks 捕获普通失败后只 WARN 再 continue，没有可取消等待或显式取消检查。当默认 awaitNextCronTick 在到达 delay 前持续抛异常，整个循环不再有挂起点。closeAsync 在 156 行取消 loop 后，157 行的 NonCancellable join 因而无法完成。
