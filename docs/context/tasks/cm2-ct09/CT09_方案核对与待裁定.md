## 2. 与冻结设计的冲突/差异（需裁定）

### C1 配置分区位置冲突

- 技术实现设计 §1.6：Runtime 负责 `context`/`vfs` 分区，其他顶层分区忽略；**核心数据流 §7.3** 的配置示例却写顶层 `extraction:`（技术实现设计 §7.3 是 Memory Map 最终一致性，不是 extraction 示例）。
- 现状 Loader 的 `CONTEXT_KEYS` 不含 `extraction`。
- **需裁定**：CT09 配置放 `context.extraction.*` 还是顶层 `extraction.*`。

### C2 时区可配置 vs 固定

- 技术实现设计 §1.7「各任务可配置自己的时区」；**核心数据流 §7.3** 示例含 `timezone: Asia/Shanghai`（可配置）。
- CM2 Q6 已裁定：runtime 内固定 `Asia/Shanghai`。
- **需裁定**：CT09 是否**不提供** timezone 配置键（固定上海），并在文档中记录与 §1.7 的差异。

### C3 CT09 无 Extraction 实现时的 Runner 归属

- 设计 §5.3 的 Worker 调用 `MemoryExtractionService.execute(sessionKey)`；该服务属 CT11。
- CT09 若直接接线生产流水线，只能用 no-op/占位 Runner，违反「阶段未实现的流水线不得冒充正常运行」。
- **需裁定**：采用哪种接线策略（见 D3）。

### C4 “Session Counter”表述

- 开发计划 CT09 行写「Session Counter」；设计 §5.2/§7.2 的 Count Trigger 是**每次通知后查 `countPending`**，不维护持久化/独立计数器。
- **建议**：不新增独立计数器，按设计查询 pending；「Counter」理解为触发计数 `pendingTriggers`（Scheduler 内）。

### C5 `IngestionNotifier` 注释中的历史命名

- Port KDoc 仍写「B2 实际接线」（CM1 时期编号），不影响契约；CT09 可顺手订正为「CT09 实际接线」，但不改签名。

## 3. 待裁定项与建议（D1～D8）

### D1 配置分区与键（关联 C1）

**建议**：`context.extraction`，与 §1.6 的 Runtime 负责分区一致；在**核心数据流 §7.3** 示例旁加注「实现落 `context.extraction`」，不改冻结语义。

候选键（全部可选、有默认值、未知键拒绝）：

```yaml
context:
  extraction:
    triggers:
      count:
        threshold: 5          # 默认 5，>=1
      idle:
        enabled: true         # 默认 true
        idleTimeout: 10m      # 默认 10m，>0
        cron: "*/5 * * * *"   # 默认，UNIX 5 字段
```

**需确认**：键名/层级是否按上表；是否增加 `count.enabled`（设计未要求，建议不加）。

### D2 Cron 方言、时区与非法值（关联 C2）

**建议**：`cron-utils` UNIX 5 字段（分/时/日/月/周），固定 `Asia/Shanghai`，**不提供** timezone 键；`cron` 非法 → `INVALID_CONFIG`（消息含字段路径，不回显原值）；启动时计算下一次触发，不补跑停机期间错过的次数。

**需确认**：固定时区是否最终口径；是否允许 `enabled=false` 完全关闭 Idle（Count 仍生效）。

### D3 Runner Port 与生产接线（关联 C3）

**建议（方案 A，推荐）**：
- Core 定义 `ExtractionRunner`（`suspend fun execute(sessionKey: SessionKey)`，`core.extraction` 包，非 `api` 公开 SDK）；
- Runtime 实现 `ExtractionPipeline`（Scheduler + Count/Idle Trigger + Worker），构造时必须注入 Runner；
- `AlcyoneContextImpl` 仅在**内部工厂重载/测试入口**接受 Runner 并启动 pipeline；**公共 `AlcyoneContextFactory.create` 在 CT09 不启用生产 Trigger**（Runner 为 null → pipeline 不创建，行为与 CT08 后一致），CT11 提供真实 Runner 后一行接通；
- CT09 验收用 Fake Runner 证明 Count/Idle/Scheduler/生命周期闭环，不以 no-op 冒充生产运行。

**备选 B**：CT09 就接线一个 no-op Runner（`execute` 立即返回）让流水线“运行”，仅日志声明未实现 —— 不推荐，违反“不得冒充正常运行”。
**备选 C**：CT09 完全不做 Runtime 接线，只交付独立组件与单测，CT11 再接 —— 与 Q4「start/close 集成点」不符。

**需裁定**：A/B/C；若选 A，是否接受「生产默认不启动，CT11 接通」这一阶段性行为。

### D4 Scheduler 关闭语义

**建议**：`closeAsync()` 顺序——停止 Cron → 停止接受新 Trigger → 关闭 Channel → 取消 Worker 并 `join`（`NonCancellable` 等待退出）→ 清空计数；在途 Runner 收到 `CancellationException`；不持久化、不补跑剩余计数。Context `shutdownTimeout` 仍只作观察，不引入新的强杀上限。

**需确认**：是否要求“先等待当前 Runner 完成再取消”（设计 §1.8 第 4～5 步的“可配置超时后取消”），还是 CT09 直接取消（CT11 的原子提交保证不产生半提交）。

### D5 Scheduler 计数溢出与关闭后请求

**建议**：`pendingTriggers` 用 `Int` 饱和到 `Int.MAX_VALUE`（不 wrap，保持单个排队项）；`request` 在 CLOSING/CLOSED 时返回 `false`/no-op，不抛给 Count 通知；Channel `trySend` 失败（已关闭）同样安全处理；锁内不做挂起。

**需确认**：饱和 vs `Long`；关闭后请求是否记录 WARN（建议 DEBUG/无日志，避免关闭噪声）。

### D6 Idle 扫描重叠与失败

**建议**：单飞（single-flight）——上一轮扫描未结束时本轮跳过，不排队；扫描/查询失败记录脱敏日志并等待下一次 Cron，不使 Worker 退出；无 catch-up。失败日志是否需要事件名/字段由 Architect 定（可复用 CT08 风格但无 LLM 字段）。

**需确认**：跳过时是否需要可观测计数/日志级别。

### D7 Count Trigger 阈值与查询失败

**建议**：`countPending >= threshold` 才 `request`；查询失败通过既有 `IngestionNotificationReporter` 脱敏上报，不影响 Ingestion、不触发；DUPLICATE 不通知（CT07 已保证）。阈值只决定“是否触发”，不限制本轮处理条数。

**需确认**：阈值是否允许 0（建议禁止，>=1）；查询失败是否需要在下一轮 Idle 自然补偿（设计已如此，建议是）。

### D8 可观测性与测试接缝

**建议**：全部 `internal`，不新增公开 API/`ContextStatus` 字段：
- `ExtractionScheduler` 暴露 `internal` 测试访问器（pending 计数、队列深度、执行次数）；
- Idle 扫描暴露 `internal suspend fun scanOnce()` + 可注入 `now`/`awaitNextTick`（默认 Cron），测试不等待 5 分钟；
- Runner 由测试注入 Fake；关闭/启动竞态用 latch/屏障（沿用 CT08 B4 模式）。

**需确认**：是否允许新增 `internal` 接缝（与既有 `*ForTesting` 同模式）；是否要求日志事件名。
