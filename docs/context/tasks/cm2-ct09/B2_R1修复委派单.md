## 2. 锁定的修复协议

1. **每轮等待 tick 前**检查当前协程取消状态（`ensureActive`）；不得只加 yield/ensureActive 而保留运行态紧凑错误循环。
2. **普通调度失败**（默认 tick 源抛异常）：记录既有 `extraction.idle.failed` WARN（白名单、不附 Throwable/SessionKey/文本），随后执行**内部固定 1 秒的可取消退避**（不新增配置、不暴露公开参数），再回到循环，从当前 Clock 重新计算严格未来 tick。
3. 退避**不是 tick**：退避结束不得直接扫描、不得补跑错过的 tick；仍须等待下一次自然未来 tick 才触发。
4. `CancellationException` 原样传播；关闭取消 loop 时，在 `delay`/`awaitTick` 中立即响应，**不等待满 1 秒退避**；owner 仍按现有 NonCancellable + join 完成清理。
5. 普通故障恢复后按自然 tick 继续；持续失败时每轮之间有受控间隔，CPU/日志不形成紧凑循环。
6. 不改变 Cron 严格未来、固定上海、启动不扫描、不补跑、tick 异步扫描/真实 skip、close 语义；不改变 Idle/Count/B1。

## 3. 必须新增/调整的正式测试（`IdleCronTest.kt`）

1. **默认 tick 源 + 极端 Clock 持续失败可及时关闭且零扫描**：不注入 tick source，注入可恢复 Clock 返回 `Instant.MAX`；启动后等待至少一次 WARN；`withTimeout(≤3s)` `closeAsync()` 必须完成、state CLOSED、零扫描、无遗留任务；Clock 读取次数不得出现紧凑循环级增长（有界断言）。
2. **连续失败尝试之间有受控间隔**：用记录时间戳的测试 Logger 捕获 WARN；等待至少 2～3 次失败，断言相邻 WARN 间隔 ≥ 约 900ms（固定 1s 退避），不是单次失败后直接读阻塞 Channel。
3. **退避中关闭可取消**：持续失败进入 1s 退避后立即 `closeAsync()`；关闭应快速完成（不等待满 1s），loop 被取消、零扫描。
4. **故障恢复后仅自然未来 tick 扫描、不补跑**：先持续失败，再恢复 Clock 到下一未来 tick 前（如 `*/5` 的 00:04:59Z）；断言恢复后不立即扫描，等到 00:05:00Z 才恰好一次扫描，不补跑此前错过的 tick。
5. 保留既有 8 个 Cron 用例语义（严格未来、不补跑、启动不扫描、每 tick 一次、真实重叠 skip、close join、调度失败后继续、tick 源关闭）；必要时适配因 1s 退避增加的等待（用有界等待，不 sleep 猜）。
