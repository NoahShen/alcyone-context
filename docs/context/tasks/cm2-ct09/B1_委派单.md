## 3. 锁定的实现契约

### 3.1 配置（D1/D2）

- 层级：`context.extraction.triggers.count.threshold`、`context.extraction.triggers.idle.enabled`、`.idleTimeout`、`.cron`；全部可省略；**逐层拒绝未知键**；不增加 `count.enabled`。
- 默认：`threshold=5`、`enabled=true`、`idleTimeout=10m`、`cron="*/5 * * * *"`。
- `threshold` 为 `Int` 且 `>=1`；`idleTimeout` 为**有限正** `Duration`（拒绝 0/负/无限；后续截止时间计算防溢出）；`cron` 为 **UNIX 五字段**（分/时/日/月/周），用 `cron-utils` 校验；固定 `Asia/Shanghai`，**不提供 timezone 键**（出现即未知键）。
- 非法值 → `ContextConfigException(ContextConfigErrorCode.INVALID_CONFIG)`，消息含字段路径、不回显原值、不附带可泄漏原值的解析 cause（cron 解析异常不得挂 cause）。
- **直接 Kotlin 构造与 YAML 加载共用同一校验**：`ExtractionConfig` 构造即校验（`init`），Loader 构造同一类型；`idle.enabled=false` 不豁免其余字段校验。
- `ContextConfig` 末尾新增 `val extraction: ExtractionConfig = ExtractionConfig()`；现有字段与默认行为不变；YAML 未配置 → 默认值。

### 3.2 Core Runner Port（D3）

```kotlin
package com.github.noahshen.alcyone.context.memory.core.extraction

interface ExtractionRunner {
    suspend fun execute(sessionKey: SessionKey)
}
```

- Kotlin public（跨模块），不放入 `context/api`，不新增其他 Core Scheduler Port；仅此一次执行职责，不实现 Snapshot/LLM/Turn 状态。

### 3.3 Scheduler（D4/D5/D6 的 B1 部分）

`internal class ExtractionScheduler(runner: ExtractionRunner)`，独立于 Context 生命周期（B3 才接线）：

- 状态 `NEW / RUNNING / CLOSING / CLOSED`；`start()` 幂等（重复 start 不产生第二个消费者/scope；CLOSING/CLOSED 后 start 抛既有 `ContextLifecycleException(CLOSED, ...)`）。
- `request(sessionKey): Boolean`：仅 RUNNING 接受；否则 false/no-op（关闭后不打 WARN）。锁内 `pendingTriggers[session]` 饱和 `Int.MAX_VALUE`（不 wrap）；仅 `0→1` 入队一次；`trySend` 失败必须回滚该次计数（不得留下无人消费的正计数）、返回 false，并以固定事件 `extraction.scheduler.enqueue.failed` WARN 可观察（不传 Throwable、不含 SessionKey）。
- 单 Worker 全局串行：从 Channel 取 Session，调用 `runner.execute`；正常返回/普通异常均消费一次计数；剩余 >0 在锁内排到队尾（不饿死其他 Session），归零移除；执行期间同 Session 不重复入队。
- 普通异常隔离：记录 `extraction.run.failed` WARN（仅固定事件名、`elapsedMillis`、`pendingSessions` 等受控数值；**不含 SessionKey/消息/SQL/异常文本，不传 Throwable**），继续下一 Session。
- 取消：`CancellationException` 不作为普通失败消费；正常关闭取消按关闭协议收尾；**非关闭状态**下 Runner 自行抛 CE 导致唯一 Worker 结束 → 必须封闭准入、进入 CLOSED、使终止可观察（`extraction.worker.stopped` WARN）、不得保留 RUNNING 外观继续接单、不得自行重启/重放；后续 `closeAsync()` 不得悬挂（发布同一终态结果）。
- 关闭 `closeAsync()`（唯一清理入口）：
  1. 若在 Runner 回调内调用 → 在改状态前具名拒绝：`ContextLifecycleException(CLOSED, "closeAsync() cannot be called from inside its own extraction runner; let the runner finish first")`，不得自等待；
  2. 锁内：CLOSING/CLOSED → 等待者；NEW/RUNNING → 置 CLOSING、创建共享 `closeOutcome`、owner=true；
  3. owner 全程 `NonCancellable`：先封闭准入 → 取消 Worker Job → `close(Channel)`（**不 drain** 队列）→ join Worker 及其结构化子任务（真实 `join`，不得以计数/集合为空代替）→ 清理计数；
  4. 任何清理失败必须发布终态（`CLOSED` + 同一失败），不得滞留 CLOSING；owner 抛该失败；重复 close 重抛**同一实例**；
  5. 等待者 `await` 共享结果；自身取消只放弃本次等待，不影响 owner；成功/失败都必须发布。
- 关闭/dequeue 竞争：入队、执行准入、完成消费与关闭封闭使用同一把普通短锁（锁内无 I/O/用户回调/挂起），保证关闭后不会再启动新的 `runner.execute`。
- `NEW` 未启动直接 close → CLOSED，无 Worker。

### 3.4 测试接缝（全部 internal，生产无行为）

- 只读：`stateForTesting()`、`pendingForTesting(session)`、`pendingSessionsForTesting()`、`queueDepthForTesting()`、`executionCountForTesting()`。
- 溢出：受控设置计数的接缝（如 `setPendingForTesting(session, count)`，clamp 0..MAX），**不得循环 MAX_VALUE 次**。
- `trySend` 失败：受控关闭 Channel 的接缝（如 `closeChannelForTesting()`），验证 request 返回 false 且计数回滚。
- 关闭失败/阻塞：owner 清理钩子（如 `closeActionForTesting: (() -> Unit)?`）用于注入失败或阻塞，验证共享失败与等待者取消；生产为 null。
- 运行标记：Runner 执行期间安装协程/线程标记，用于 `closeAsync()` 自身回调拒绝（同步/挂起均生效，复用 `NotificationExecutionMarker` 模式）。

## 4. 测试要求

### 4.1 `ExtractionConfigValidationTest`

1. 默认值（threshold 5 / enabled true / 10m / `*/5 * * * *`）。
2. YAML 省略/部分覆盖/全量覆盖；直接 `ContextConfig(extraction=...)` 构造同等校验。
3. threshold=0/-1/非整数 → `INVALID_CONFIG` 含路径；`idleTimeout=0`/负/无限 → 拒绝；`cron` 空/4 字段/6 字段/非法 → 拒绝；`timezone` 键 → `UNKNOWN_FIELD`。
4. 未知键：`context.extraction`、`triggers`、`count`、`idle` 四层各一例。
5. `idle.enabled=false` 时非法 idleTimeout/cron 仍拒绝（不豁免校验）。
6. 既有 `ContextConfigLoaderTest` 若追加断言，仅新增，不改旧断言。

### 4.2 `ExtractionSchedulerTest`

1. 单次 request → 1 次真实 `execute`；同 Session 连续 3 次 → 3 次执行（执行中触发计数+1、完成后队尾重入）。
2. 同 Session 不并发（Fake Runner 屏障 + 有界等待，最大并发 1）；不同 Session 全局串行。
3. 普通异常：消费一次、记录 `extraction.run.failed`（SLF4J 捕获、无 Throwable、无 SessionKey/正文），继续处理下一 Session。
4. 溢出：接缝置 MAX，再 request 仍为 MAX、队列仍单项；不 wrap。
5. `trySend` 失败：接缝关闭 Channel 后 request 返回 false、计数回滚、`extraction.scheduler.enqueue.failed` 可观察。
6. 关闭后 request false/no-op 且不 WARN；start 幂等（不产生第二个消费者）。
7. 非关闭 CE：Runner 抛 CE → CLOSED、request false、`extraction.worker.stopped` WARN、closeAsync 不悬挂且可观察失败；不重启/重放。

### 4.3 `ExtractionSchedulerCloseTest`（独立关闭）

1. 先封闭准入：CLOSING 期间 request false，不再启动新 `execute`。
2. 在途 Runner 阻塞：`closeAsync()` 取消并真实 join；Runner 收 CE、finally 屏障已执行、close 返回后无新执行；**不 drain** 排队项。
3. 共享结果：注入清理失败 → 终态 CLOSED、`closeAsync` 抛同一实例、重复 close 重抛同一实例（`assertSame`）。
4. 等待者取消：owner 清理阻塞时，第二个 `closeAsync` 被取消只退出自身等待；放行后 owner 完成，后续 close 正常/同失败。
5. Runner 内调用 `closeAsync()` → 具名 `CLOSED` 拒绝、无自等待；外部 close 仍可完成。
6. `NEW` 未启动 close → CLOSED；重复 close 安全。
