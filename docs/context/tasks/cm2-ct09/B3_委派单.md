## 3. 锁定的 Pipeline 契约

`internal class ExtractionPipeline`（runtime/extraction）：

- 构造：`config: ExtractionConfig`、`database: ContextDatabase`（已取得的真实 DB）、`runner: ExtractionRunner`、`clock: Clock`、`idleTickSource: IdleTickSource?`、`callbackOwner: Any`（Context 实例，用于回调标记）。
- 组件：`CountTrigger`（作为 `IngestionNotifier`）、`ExtractionScheduler`、`IdleTrigger`、`IdleCron`（仅 `idle.enabled=true`）。
- **激活门**：包装 Runner 先等待 `CompletableDeferred<Unit>` 激活；`start()` 只启动 Scheduler/Cron（门关闭），**Runner 不得在 Context 发布 RUNNING 前执行**；Context 发布 RUNNING 后调用 `activate()` 完成门。
- `start()`：启动 Scheduler；`idle.enabled=true` 时启动 IdleCron；`idle.enabled=false` 不创建/启动 Cron，但 Count/Scheduler 可用；失败向上抛（供 Context 逆序清理）。
- `closeAsync()`：**先关 IdleCron（停 tick/扫描并 join），再关 Scheduler（Worker/Runner 真实 join）**；两者都尽力执行，失败 `chain`；最后抛主失败。关闭后不再触发。
- `ingestionNotifier` 暴露 `CountTrigger`；Count 查询 pending、阈值、失败 reporter、DUPLICATE 语义不变。
- 回调标记：Runner 执行与 Idle 请求回调安装 `ExtractionCallbackMarker(callbackOwner)`；`AlcyoneContextImpl.close()/closeAsync()` 在改状态前检测 `currentOwner() === this` 并抛出**具名** `ContextLifecycleException(CLOSED, "close()/closeAsync() cannot be called from inside an extraction runner/scan callback; let the callback finish first")`，不得自等待。
- 测试接缝（`internal`）：`startFailureForTesting`、`closeFailureForTesting`、`idleRequestHookForTesting`、只读状态/组件访问器（关闭窗口/门可用测试可观测状态）。

## 4. Runtime 接线契约

### 4.1 Factory

- 公共 `create(contextConfig, vfsConfig)` **签名与行为不变**：不接收 Runner、不创建 pipeline；配置照常解析（`context.extraction` 已由 B1 校验）。
- 内部测试重载新增（均可选）：`extractionRunner: ExtractionRunner? = null`、`idleTickSource: IdleTickSource? = null`、`pipelineConfigurator: ((ExtractionPipeline) -> Unit)? = null`（构造后、start 前设置测试接缝）；传给 Impl。
- `create` 仍零后台副作用：不建 pipeline、不启线程/协程。

### 4.2 `AlcyoneContextImpl`

- 构造新增 internal 参数：Runner、Idle tick、pipeline configurator（默认 null）；新增 `private var extractionPipeline: ExtractionPipeline?` 与 `internal fun pipelineForTesting(): ExtractionPipeline?`。
- `performStart` 顺序：`executor → vfs → llm → pipeline`：
  - 仅 `extractionRunner != null` 时构造 pipeline（用已取得的 `ContextDatabase`、`config.extraction`、clock、tick source、callback owner=this）；
  - 构造后执行 configurator（测试接缝）；
  - `pipeline.start()`（门关闭）；`startProbe`；锁内发布字段与 `RUNNING`；**发布成功后** `pipeline.activate()`；
  - `ingestion = createIngestionService(database, pipeline?.ingestionNotifier ?: ingestionNotifier)`；无 Runner 时行为同 CT08（沿用注入 notifier）。
  - `close` 获胜（`!published`）：不得误报 start 失败；逆序清理 `pipeline → llm → vfs → executor` 后 CLOSED。
  - 非竞争 pipeline 启动失败：逆序清理已取得资源（pipeline 若已部分启动也须关闭）并 CLOSED，抛出原始主失败。
- `shutdown`：状态锁内封闭准入（STOPPING）→ `cancelNotifications()` 等待既有通知 → 取得并置空 pipeline/llm/vfs/executor → `releaseResources(pipeline, llm, vfs, executor)`，顺序 **pipeline → llm → vfs → executor**，每项独立 try/catch + `chain`；pipeline 清理失败也发布终态并继续释放其余资源。
- 不得在通知/扫描/Runner 未结束时释放 DB/LLM/VFS；不得以计数/字段为空代替真实 join。
- 回调内 close 检查顺序：在 `close()`/`closeAsync()` 入口、`beginClose` 改状态之前；与既有 notification 拒绝并存。

## 5. 测试要求（真实 SQLite + Fake Runner）

`ExtractionPipelineLifecycleTest`（runtime 测试，可用 `ContextFixture`/真实 `ContextDatabaseImpl`）：

1. **公共零 pipeline**：公共 `create` → start RUNNING、`pipelineForTesting()==null`、无 IdleCron/Worker；close 成功；行为同 CT08。
2. **无 Runner**：内部 create（runner=null）→ 不建 pipeline/Cron/Worker。
3. **Count 触发**：内部 create + FakeRunner（记录执行）→ 真实 SQLite 写入 4/5 pending；第 5 条 CREATED 通知后 Runner 执行；DUPLICATE 不重复执行。
4. **Idle 触发**：`idle.enabled=true` + 可控 tick；真实 SQLite 插入空闲 pending；tick → Runner 执行；无 pending 不执行。
5. **idle.enabled=false**：不启动 IdleCron（tick 无扫描），Count/Scheduler 仍可用（阈值触发）。
6. **关闭取消在途 Runner 并等 finally**：FakeRunner 阻塞 + finally 屏障；close 返回时 finally 已执行、无新执行、CLOSED。
7. **释放顺序**：pipeline close hook → llm close hook → releaseProbe VFS/EXECUTOR，按 `[pipeline, llm, VFS, EXECUTOR]` 记录；pipeline 清理失败仍继续释放其余。
8. **start/close 竞争**：startGate 阻塞 start，close 获胜；start 不误报失败、pipeline 不激活/不执行 Runner、CLOSED。
9. **pipeline 启动失败**：configurator 注入 startFailure；start 抛原始失败、逆序清理（VFS/EXECUTOR 记录）、CLOSED、不发布 RUNNING。
10. **Runner 回调内关闭**：FakeRunner 调 `impl.close()` / `closeAsync()` → 具名 CLOSED 拒绝、无自等待；外部 close 仍完成。
11. **Idle 扫描回调内关闭**：configurator 设置 `idleRequestHookForTesting` 在 Idle 请求回调内调 close → 具名拒绝；外部 close 完成。
12. **关闭后 0 触发**：close 后手动 tick / 尝试 Count 触发 → 无 Runner 执行；不得访问已释放 DB（以无触发/无异常证据）。
13. **并发 close 共享失败**：pipeline closeFailure 注入；两个并发 close 得到同一共享失败、终态 CLOSED；等待者取消不影响 owner。
