## a. 模块与包结构

### 模块划分

沿用技术实现设计 §1.3，五模块 + 跨模块测试：

```text
context/
├── api/                     # 对外 Kotlin 契约；不暴露 SQLite / Ktor Server / YAML
├── core/                    # 业务规则 + 内部 Port；不直接依赖基础设施
├── persistence-sqldelight/  # Context SQLite Schema、Repository、事务、Slot 连接适配
├── runtime/                 # 手动依赖组装 + LLM Adapter + Worker/Cron + 生命周期
└── server/                  # Ktor+CIO HTTP；只依赖 Runtime 公开能力

integration-tests/context/   # 跨模块端到端测试
```

### 包名自主选择与不冲突论证

实现方自主选择包根为 `com.github.noahshen.alcyone.context.memory.*`：

| 模块 | 包根 |
| --- | --- |
| `context/api` | `com.github.noahshen.alcyone.context.memory.api` |
| `context/core` | `com.github.noahshen.alcyone.context.memory.core` |
| `context/persistence-sqldelight` | `com.github.noahshen.alcyone.context.memory.persistence.sqldelight` |
| `context/runtime` | `com.github.noahshen.alcyone.context.memory.runtime` |
| `context/server` | `com.github.noahshen.alcyone.context.memory.server` |
| `integration-tests/context` | `com.github.noahshen.alcyone.context.memory.integration` |

**架构理由**：
1. **与既有包绝对隔离**：既有 VFS 模块统一使用 `com.github.noahshen.alcyone.context.vfs.*`，既有 `common` 模块使用 `com.github.noahshen.alcyone.context.common.*`。Context 业务模块采用 `com.github.noahshen.alcyone.context.memory.*`，在第三段以 `memory` 表征长期记忆沉淀与治理核心语义，避免了在 `com.github.noahshen.alcyone.context` 根下与 VFS 平铺造成的概念混淆；
2. **发布坐标独立**：Maven Group 统一为 `com.github.noahshen.alcyone`，Context 模块 artifactId 前缀统一为 `alcyone-context-*`（如 `alcyone-context-api`、`alcyone-context-runtime`），与既有 `alcyone-vfs-*` 完全不同，不存在发布与依赖解析冲突；
3. **备选方案评估**：若未来业务扩展至记忆之外的通用上下文总线，包根可重构为更中性的 `com.github.noahshen.alcyone.context.context.*`；当前阶段以 `memory` 为包根最贴合系统核心领域。

### 依赖方向与模型归属澄清

```text
api          → 语言与基础库（kotlinx-coroutines-core；无基础设施依赖）
core         → api + common（通用时间/ID，implementation）
persistence  → core + api
runtime      → core + persistence + vfs/runtime + Ktor Client (仅 LLM Adapter)
               + kotlinx.serialization + JDK Clock
server       → runtime + Ktor Server (CIO)
```

**依赖与模型归属规则**：
1. **`api` 模块依赖边界**：`api` 不依赖任何具体基础设施（不依赖 SQLite、SQLDelight、Ktor、YAML 或通用 DI 框架），仅依赖语言与必要基础库——主要是 `org.jetbrains.kotlinx:kotlinx-coroutines-core`（用于提供 `Flow<ByteArray>`、`suspend` 契约及 `CancellationException` 语义）以及 Kotlin 标准库；
2. **公开模型归属于 `api` 模块**：所有作为 SDK 公开契约的数据类型——包括 CM1 实际落地的 `ConversationTurn`、`ChatMessage`、`IngestResult`、`IngestStatus`、`ContextStatus`，以及 CT03 定义、后续公开的 `RawMemory`、`OrganizedMemory`、`MemorySourceRef`、`ResourceMetadata`、`BootstrapContext`、`MemoryMapView`、`MapStatus`、`DreamingResult`——**其类型定义均直接归属于 `context/api` 模块**；
3. **单向依赖保证纯净性**：`context/core` 实现业务规则与内部实体，对外返回 `api` 模块中定义的公开模型；**绝对不允许未来让 `api` 去引用 `core` 内部类型**，确保 `core -> api` 的严格单向依赖；
4. **内部 Port 留在 `core`**：五大 Repository 接口（`ConversationRepository` 等）、`ContextDatabase`、`LlmClient`、`TokenEstimator`、`MemoryIdGenerator` 属于内部扩展点，定义在 `context/core`，不进 `context/api`；
5. **Slot 连接适配方案留在 `persistence`**：基于探针 P1 证伪 stock `JdbcSqliteDriver` 单连接假设的事实，CT04 将在 `context/persistence-sqldelight` 中落地自持物理连接的 `SqlDriver` 适配器（见 §h7）。

#### 公开数据契约模型（定义在 `context/api`，由 CT03 落地）

以下模型类型直接由 **CT03** 在 `context/api` 中定义，严格区分外部输入契约与内部持久化实体，避免混淆：

1. **`ConversationTurn`（公开 SDK 输入契约模型）**：
   - **严格直接依据技术实现设计 §4.1 与核心数据流设计 §3.2**：仅含必填六字段——`runtimeId: String`, `agentId: String`, `sessionId: String`, `sessionTurnId: String`, `timestamp: Instant`, `messages: List<ChatMessage>`；
   - **外部输入契约绝对不含 `id`、`createdAt`、`extractionStatus`**：内部自增 `id` 绝不允许外部调用方提供，`createdAt` 由服务端在首次 INSERT 时由系统 Clock 统一分配（ISO-8601 上海时区 `+08:00` 文本），`extractionStatus` 是服务端的内部流水线处理状态（初始为 `pending`）。
2. **`ChatMessage` 与 `ChatRole`**：
   - `ChatMessage(role: ChatRole, content: String)`；`ChatRole` 为枚举 `USER`, `ASSISTANT`, `TOOL`。
3. **`IngestResult` 与 `IngestStatus`**：
   - `IngestResult(id: Long, status: IngestStatus)`；`IngestStatus` 为枚举 `CREATED`（首次入库成功）、`DUPLICATE`（规范化内容完全一致的幂等重放）。
4. **`RawMemory` 与 `MemorySourceRef`（公开证据模型）**：
   - **严格直接依据核心数据流设计 §9.3**：定义 5 字段不可变逻辑模型（`id: String`, `content: String`, `generatedBy: MemoryOrigin`, `sources: List<MemorySourceRef>`, `createdAt: Instant`）；`MemorySourceRef` 为 sealed 接口（`ConversationTurnRef` / `RawMemoryRef`）；类型定义归属 `context/api`，CM2 实现业务生成并由后续公开方法返回。
5. **`OrganizedMemory`（公开当前认知模型）**：
   - **严格直接依据核心数据流设计 §13.7**：定义 6 字段逻辑模型（`id: String`, `content: String`, `domains: List<String>`, `createdAt: Instant`, `updatedAt: Instant`, `rawMemoryIds: List<String>`）；底层证据关联通过 `organized_memory_source` 关联表持久化；类型定义归属 `context/api`，CM3 实现业务治理并由后续公开方法返回。
6. **`ContextStatus` 与 `ContextLifecycleState`**：
   - `ContextStatus(lifecycle: ContextLifecycleState, workers: Map<String, WorkerStatus>, storage: StorageStatus)`；`ContextLifecycleState` 为枚举 `CREATED`, `STARTING`, `RUNNING`, `STOPPING`, `CLOSED`。

#### 内部持久化实体（定义在 `context/core` / `context/persistence-sqldelight`，不进 api）

- **`StoredConversationTurn`（内部持久化会话记录）**：由 Core/Persistence 内部持有，包含 SQLite 自增主键 `id: Long`、四元业务键、服务端入库时间 `createdAt: Instant`、有序会话正文 `messages` 以及提取状态 `extractionStatus: ExtractionStatus`（`PENDING`, `COMPLETE`, `FAILED`）；
- **`organized_memory_source` 关联表**：`(organized_memory_id, raw_memory_id)` 联合主键，双向外键 `ON DELETE RESTRICT`；
- **`organization_pending` 表**：`raw_memory_id TEXT PRIMARY KEY REFERENCES raw_memory(id) ON DELETE RESTRICT`；
- **`dreaming_checkpoint` 表**：单行 `id = 1`，`last_processed_turn_id: Long`（CHECK >= 0，初始 0）。

#### 内部 Port（CT03/CT05 定义在 core，不进 api）

| 类型 / Port | 模块 | 权威职责 |
| --- | --- | --- |
| `ConversationRepository` | `context/core` | Turn 幂等插入、按四元键查找、Session 窗口读取、最新 Pending、Count、Idle、ID 范围扫描（`ReadOps` + `TxOps`） |
| `RawMemoryRepository` | `context/core` | Raw ID/批量精确查询、分页扫描、批量插入（不可更新、不可物理删除） |
| `OrganizedMemoryRepository` | `context/core` | Organized ID/批量查询、来源正反查、MAX 更新时间、NEW/UPDATE、插入来源关联、推进单调水位 |
| `OrganizationPendingRepository` | `context/core` | exists 检查、按 Raw 创建时间排序取下一条、入队、出队 |
| `DreamingCheckpointRepository` | `context/core` | 读取单行水位、CAS 条件更新水位 |

## c. YAML 配置方案与 CM1 基础错误契约（冻结）

### 1. 三条核心配置处理规则（恢复正式段落）

1. **相对路径基准**：
   - 配置文件中出现的所有相对路径（如 `context.database.path`、`vfs.database.path`、LocalFs 挂载的 `backend.root`），**一律以该 YAML 配置文件所在目录为基准**解析为绝对路径。严禁以当前进程工作目录（CWD）解析，确保在任何启动目录下路径解析结果绝对确定。

2. **环境变量展开规则**：
   - 支持字符串字段中的 `${ENV_NAME}` 语法占位符；在字段值反序列化与解析前完成展开；
   - **缺失与空值处理**：引用的环境变量未定义、或其值为空字符串（trim 后长度为 0）时，系统立即终止启动并抛出 `ContextConfigException(MISSING_ENV)`；
   - **脱敏禁令**：异常消息仅包含具体的 YAML 字段路径（如 `context.llm.profiles.fast.apiKey`）与环境变量名（如 `FAST_LLM_API_KEY`），**严禁在异常文本、Cause 链或应用日志中回显任何敏感配置值**。

3. **未知字段处理规则**：
   - **负责分区严格校验**：Context Runtime 负责解析 `context` 与 `vfs` 分区。在负责分区内发现任何未识别的未知字段时，立即终止启动并抛出 `ContextConfigException(UNKNOWN_FIELD)`，消息中指明未知的具体字段路径（如 `context.database.unknown_prop`），防止拼写错误被静默忽略；
   - **非负责顶层分区完全忽略**：Context Runtime 不负责 `server` 分区。解析时对顶层出现的 `server` 分区直接跳过（不校验内部结构、不报错），由独立的 Server 组件自行加载。纯 SDK 模式下可直接省略 `server` 分区。

### 2. 配置样例：CM1 最小可运行 vs 完整全集蓝图

#### (a) CM1 最小可运行配置样例（测试与 Ingestion 最小接入）

> **规则说明（R1 落实）**：CM1 阶段不强制要求配置 LLM API 密钥（无需设置 `FAST_LLM_API_KEY` 等），不校验未实现的 Task/Profile，**无需配置 `namespaces` 与 `mounts`**（VFS 源码 `MountRouter.of` 接受空集合）。普通单元测试、集成测试以及日常 Ingestion 运行只需此最小配置即可起跑：

```yaml
# config/alcyone-cm1-minimal.yaml
context:
  database:
    path: ./data/context.db            # 缺省 ./data/context.db，相对本配置文件所在目录

vfs:
  database:
    path: ./data/vfs.db                # 相对本配置文件所在目录（Context 侧决策默认值）
```

| | | `FORBIDDEN` | Bearer Key 有效但与请求体内的 `runtime_id` 绑定不一致 | 403 FORBIDDEN |

#### 幂等成功响应（非异常）
- `IngestStatus.CREATED` → HTTP `201 CREATED`，返回 `{ "id": <turnId>, "status": "CREATED" }`；
- `IngestStatus.DUPLICATE` → HTTP `200 OK`，返回 `{ "id": <turnId>, "status": "DUPLICATE" }`（内容与库内完全一致的重放，非错误）。

#### 取消语义（CancellationException）
- `kotlinx.coroutines.CancellationException` 属于协程正常协作取消信号，**严禁捕获后包装为普通业务异常或超时异常**；
- 遇到 `CancellationException` 必须在清理资源（短事务回滚、Slot 归还）后**原样向外传播**。

#### 敏感信息防泄露禁令
以下敏感内容**绝对禁止**出现在任何异常信息（`message`）、Cause 链、以及日志（SLF4J / Logback）中：
1. **API Key / Token**：包括 `FAST_LLM_API_KEY`、`HERMES_INGEST_KEY`、WebDAV 密码等；错误日志仅可记录 key 的哈希前缀或 `***` 占位；
2. **会话正文与 Memory 内容**：用户消息文本、模型原始 Prompt、Conversation 原始消息严禁打印在普通应用日志中；
3. **敏感连接信息**：包含密码的 URL（如 `http://user:pass@host`）必须在进入配置与异常前脱敏为 `http://***@host`。

#### Core 不依赖 VfsException 理由
Context Core 与 VFS 严格解耦：`VfsException` 仅用于 VFS 文件操作层；Context Core 拥有自己独立的业务领域异常体系（`ContextException` 及其子类），编译期完全不依赖 VFS 异常类型。VFS 异常在 `context/runtime` 边界被捕获并转换为 Context 领域异常。

## f. Map/备份/权限后续方案记录（G3/G4/G6/G7，仅记录不实施）

### G3：Map 安全替换现状核对（记录仅，未经批准不实施）

**VFS 当前能力核对（依据源码）**：
1. `Vfs.move(source, target)`：目标已存在时**明确抛出 `VfsErrorCode.ALREADY_EXISTS`**（依据 `vfs/core/.../DefaultVfs.kt:1198`），绝不执行静默覆盖；
2. `Vfs.write(uri, content, options)`：写入模式 `REPLACE_EXISTING` 在底层物理 I/O 成功而状态库登记失败时可能返回 `UNKNOWN` 或 `PARTIAL`，并不承诺物理旧文件不被破坏；
3. VFS 目前无公开的 `moveOrReplace` 或 `safeReplace` 原子替换 API；
4. **跨 Mount 无法安全降级**：跨 Mount 移动走「读源→写目标→删源」，中途失败会残留半写文件；
5. **后端能力差异**：Local FS 在同一文件系统下可通过底层 `Files.move(ATOMIC_MOVE)` 实现 POSIX 原子 rename；但 WebDAV 远端协议标准 `MOVE` 方法对已有目标的覆盖语义依服务端实现而异，缺乏跨环境一致的原子替换保证。

**方案评估**：
- **选项 A（VFS 新增公开安全发布 API）**：在 `vfs/api` 新增 `suspend fun safeReplace(uri: VfsUri, content: ByteArray)`，Local FS 下利用同盘原子 rename 保证替换要么完全成功要么保留旧文件；
- **选项 B（Context 侧分步 write + move 适配）**：**不可行**。因 VFS `move` 遇到目标存在报 `ALREADY_EXISTS`，且分步覆盖无法规避中途失败损坏旧文件；
- **结论**：G3 是明确的功能缺口。CT17 实施前必须形成经批准的 VFS 扩展方案；**缺口未关闭前 CM4 不得验收**。

---

### G4：备份大小与写入接口（记录仅，未经批准不实施）

**VFS 当前能力核对（依据源码）**：
1. `Vfs.write(uri, content: ByteArray)` 接受全量内存字节数组，受 `VfsLimits.defaultWriteMaxBytes` 约束（**默认限额 16 MiB，可配置调整，非绝对硬上限**）；
2. `Vfs.openStream(uri, options)` 支持流式读取，但 VFS **没有公开流式写入 API（无 `writeStream`）**；
3. 不得假设「分批写入 + move」可以组合出安全发布：分批写入会暴露半写文件，违反备份一致性要求。

**方案评估**：
- 小于限额的快照可直接通过 `Vfs.write` 配合唯一文件名（如 `context-20261025-030000.db`）写入，避免覆盖；
- 超出限额的大快照需要评估：(a) 调大 `vfs.limits.defaultWriteMaxBytes`，或 (b) 由 VFS 在后续扩展提供 `writeStream` 流式写能力；
- **结论**：大备份发布方式属于 CT27 前置评估事项，本任务仅记录现状，不提前实现。

---

### G6：调用者权限边界澄清（属 CT06/CT28 落地项）

**核对依据**：
- `vfs/api` 的 `Vfs` 接口与 `VfsRuntimeConfig` 实际代码：VFS 仅接受文件路径操作，**完全不提供调用者身份上下文、不提供逐 Agent / 逐 Domain ACL**；
- 旧架构设计多处提及「VFS ACL」，属概念混淆。

**权责边界（已冻结）**：
1. **身份认证归 Context/Server**：Context Server 负责通过 HTTP Bearer Key 校验调用者身份；Ingestion Key 与特定 `runtime_id` 强绑定；Context Read Key 控制长期记忆读取；
2. **Resource URI 范围检查归 Context**：Context 校验请求访问的 `alcyone://resources/...` 处于允许的逻辑命名空间；
3. **VFS 保留原有底层约束**：VFS 仅继续执行既有的挂载路径合法性、只读挂载保护及后端文件系统拒绝规则；
4. **MVP 不新增复杂权限系统**：MVP 不设计逐 Agent/Domain 的细粒度动态 ACL，不凭空宣称具备未实现的能力。

### G7：Online Backup API 能力结论（引探针证据，记录仅）

**探针实测证据（`tools/validation/cm1-compat-probe`，P3）**：
1. Xerial SQLite JDBC 3.49.1.0 包含 `org.sqlite.core.NativeDB.backup(dbName, destFileName, observer)`；
2. **API 调用规则（重要排雷）**：`dbName` 必须为源连接上的逻辑库名（如 `"main"`），**绝不能传入源文件路径**；传入文件路径会返回 `rc=1` 且目标文件保持 0 字节；

## h. Architect 补充生命周期硬性要求（逐条可测试判据）

### h1. `create()` 仅配置接收与依赖组装，无资源启动副作用

- **业务规则**：`AlcyoneContextFactory.create(...)` 仅接收配置对象、组装依赖图；**严禁在此阶段打开数据库、创建文件、连接网络或启动协程**。`AlcyoneVfs.create(...)` 必须推迟到 Context `start()` 时执行。
- **可测试判据**：
  1. 调用 `create(...)` 后，断言 `context.database.path` 与 `vfs.database.path` 对应文件**在磁盘上不存在**（若原先不存在）；
  2. 进程文件描述符列表中无新增打开的 SQLite 文件句柄；
  3. `create` 过程因配置非法抛出异常时，无任何残留后台线程或未关闭资源。
- **测试入口（CT06 实现）**：`context/runtime` 单元测试 `CreateNoSideEffectTest`。

### h2. 普通启动缺库/错版本拒启，显式初始化接口先行

- **业务规则**：普通日常 `start()` 遇到数据库文件不存在或 `PRAGMA user_version` 不匹配时，**必须直接抛出异常拒绝启动**。严禁在检查前使用读写模式打开数据库导致 SQLite 自动创建 0 字节空库。显式初始化 API 在 CM1 内必须提供并可被测试调用；**Schema 迁移与升级工具属于 CM6 范围，CM1 仅提供首次创建空库并写入最新 Schema 的显式初始化入口**。
- **可测试判据**：
  1. 删除 `context.db`，调用普通 `start()`，断言抛出 `ContextPersistenceException(DATABASE_NOT_INITIALIZED)`，且磁盘上**不产生新的 `context.db` 文件**；
  2. 修改 `context.db` 的 `user_version` 为非目标值，调用普通 `start()`，断言抛出 `ContextPersistenceException(SCHEMA_VERSION_MISMATCH)`，且文件内容未被修改；
  3. 调用显式 `AlcyoneContextFactory.initializeDatabase(config)`，断言文件被创建、6 表 5 索引齐备、Checkpoint 行初始化为 0、`user_version` 写入最新版本。
- **测试入口（CT04/CT06 实现）**：`context/persistence-sqldelight` 集成测试 `MissingDbRejectsStartTest`、`SchemaVersionProtectionTest`、`ExplicitInitializeTest`。

### h3. `context.db` 与 VFS 状态库物理路径隔离

- **业务规则**：仅保留两条有充分设计依据的隔离规则，Context 侧必须独立校验（不依赖 VFS 侧已有检查）：
  1. `context.database.path` 规范化绝对路径与 `vfs.database.path` 规范化绝对路径**不得为同一文件**；
  2. `context.database.path` **不得位于任何已配置的 VFS Local FS 挂载根目录内**（对等落实 VFS `requireOutsideMounts` 约束，因为挂载目录内文件可被公开的 VFS `delete` 接口删除，会导致 Context 数据库被意外破坏）。
- **可测试判据**：
  1. 配置两者路径相同，调用 `create` 或校验，抛出 `ContextConfigException(INVALID_CONFIG)`；
  2. 配置 `context.db` 位于挂载根 `./storage/memory/context.db` 内，抛出 `ContextConfigException(INVALID_CONFIG)`。
- **测试入口（CT06 实现）**：`context/runtime` 配置校验单元测试 `PathIsolationValidationTest`。

### h4. 生命周期并发规则与状态机 CAS（R3 修正）

- **状态机**：`CREATED → STARTING → RUNNING → STOPPING → CLOSED`。使用 `AtomicReference` 进行 CAS 状态迁移。
- **并发与幂等规则**：
  1. **并发 `start()` 幂等等待**：若实例正处于 `STARTING` 状态，后续并发调用的 `start()` 必须**等待同一启动任务完成信号**（通过 `CompletableDeferred` 或互斥锁，行为与 VFS `close()` 并发闸门完全一致），启动成功后直接返回成功；若当前已处于 `RUNNING` 状态，再次调用 `start()` 同样直接幂等返回成功；**彻底删除有歧义的 `ALREADY_STARTED` 异常**；
  2. **重复 `close()` 幂等安全**：多次并发或串行调用 `close()`，共享同一次关闭 Deferred，不重复释放资源；
  3. **CLOSED 后调用拒绝对策**：实例进入 `STOPPING` 或 `CLOSED` 态后，调用任何业务方法（如 `ingestConversation`）立即抛出 `ContextLifecycleException(CLOSED)`；
  4. **并发 `start()` 与 `close()` 竞争规则**：以状态机 CAS 为准。若 `close()` 先胜出进入 `STOPPING`，则 `start()` 的 CAS 迁移失败，检测到关闭态后回滚已初始化的部分资源并抛出 `ContextLifecycleException(CLOSED)`。
- **可测试判据**：
  1. 100 个并发协程同时调用 `start()`，断言所有调用均成功返回，底层初始化仅执行一次；
  2. 50 个并发 `start()` 与 50 个并发 `close()` 竞争，最终状态必为 `CLOSED`，无资源泄露，无死锁；
  3. 关闭后调用 `ingestConversation` 或 `start()`，必抛 `ContextLifecycleException(CLOSED)`。
- **测试入口（CT06 实现）**：`context/runtime` 集成测试 `LifecycleConcurrencyTest`。

### h5. 等待阻塞任务退出，确认无在途操作后释放连接

- **业务规则**：`close()` 进入 `STOPPING` 后的释放顺序：
  1. 状态机 CAS 置为 `STOPPING`，拒绝新业务请求与触发器；
  2. 停止 Cron 定时器；
  3. 向在途的协程发出取消请求，并等待其退出至配置的优雅期限（默认 30s）；
  4. **显式等待在途 JDBC / LLM 操作计数器归零**，确认底层无并发 SQL 执行中；
  5. 关闭并释放 Context SQLite 物理连接（每个 Slot 的固定 Connection）；
  6. 关闭 LLM Client（HttpClient）；
  7. 调用 `AlcyoneVfs.close()` 释放 VFS 实例；
  8. 状态机置为 `CLOSED`。
- **可测试判据**：
  1. 注入一个耗时 2 秒的写事务，中途触发 `close()`，断言 `close()` 等待该事务完成后才关闭数据库连接，不产生 `SQLException: connection closed`；
  2. 超时未退出的任务被协作取消，`CancellationException` 正常传播；
  3. 释放顺序日志断言：VFS 与 SQLite 连接释放必定在 Worker 停止之后。
- **测试入口（CT06 实现）**：`context/runtime` 集成测试 `GracefulShutdownInFlightTest`。

### h6. 不复制 VFS 自动建库/自动迁移机制

- **业务规则**：Context 数据库为独立权威存储，**严禁将 VFS 状态库的自动创建/自动迁移行为复制到 Context**。
  - VFS 内部的自动迁移仅作用于其自身状态库（`vfs.database.path`）；
  - `context.db` 在非显式初始化模式下，缺失必须报错；版本不符必须报错；
  - 禁止在普通启动路径调用 SQLDelight 的 `Schema.create(driver)` 或 `Schema.migrate(...)`。
- **可测试判据**：
  1. 提供一个空文件或低版本 `context.db`，调用常规 `start()`，断言抛出异常拒绝启动，未执行自动 DDL 迁移；
  2. VFS 自身状态库升级不触发 Context 数据库操作，两者连接与事务完全隔离。
- **测试入口（CT04 实现）**：`context/persistence-sqldelight` 集成测试 `NoAutoMigrationTest`。

### h7. CT04 显式固定 Connection SqlDriver 适配方案（优先复用 SQLDelight JdbcDriver）

基于探针 P1 证伪 stock `JdbcSqliteDriver` + `ThreadedConnectionManager` 单物理连接假设的实测结果，CT04 在 `context/persistence-sqldelight` 中必须采用以下**优先复用 SQLDelight 既有 JdbcDriver 的适配落地方案**：

1. **优先继承/包装 SQLDelight 既有 `JdbcDriver`，严禁从零重写**：
   - CT04 适配实现**严禁从零重写整个 `SqlDriver`**：应优先继承或包装 SQLDelight 既有的 `app.cash.sqldelight.driver.jdbc.JdbcDriver`（或提供自定义的 `ConnectionManager`，直接参考 VFS 已验证成熟的 `SingleConnectionJdbcDriver` 实践）；
   - 直接复用 SQLDelight 成熟高效的 `PreparedStatement` 参数绑定、`QueryResult` 游标映射及执行机制；
   - 核心机制是让该驱动绑定的 `ConnectionManager` 直接向调用方提供该 Slot 独占的物理 `java.sql.Connection`，`closeConnection(conn)` 设为空操作（或保留连接），逐语句执行绝对不释放、禁止 auto-close；

2. **Slot 自持物理连接与生命周期**：
   - 数据库执行器维护固定数量的 Slot（1 个 WriteSlot + N 个 ReadSlots，默认建议 N=2）；
   - **每个 Slot 内部显式持有唯一一条专用的底层物理 `java.sql.Connection`**，由 Xerial `DriverManager.getConnection` 打开，并通过上述适配驱动包装；
   - 逐语句执行（`execute` / `executeQuery`）绝对不关闭底层物理连接；物理连接在 Slot 整个生命周期内常驻保持；
   - 只有在 Context Runtime 进入 `STOPPING`、等待在途操作计数归零后，才由 Slot 显式调用 `connection.close()` 关闭物理连接，彻底规避 stock `driver.close()` 为空操作导致的物理连接泄漏；

3. **连接级 PRAGMA 持续生效保证**：
   - 在 Slot 创建并打开该物理连接时，立即在该连接上执行初始化 PRAGMA：
     * WriteSlot 连接：`PRAGMA journal_mode=WAL`、`PRAGMA synchronous=FULL`、`PRAGMA foreign_keys=ON`、`PRAGMA busy_timeout=5000`；
     * ReadSlot 连接：`PRAGMA foreign_keys=ON`、`PRAGMA busy_timeout=5000`、`PRAGMA query_only=ON`；
   - 物理连接固定常驻，上述连接级 PRAGMA 在整个 Slot 生命周期持续生效，彻底消除 stock 驱动因不断新建连接导致的 PRAGMA 失效隐患；

4. **单物理连接事务与固定线程执行模型**：
   - 严格遵守技术实现设计 §2.5 / §2.6 的固定线程执行模型与短 `ReadContext` / `TransactionContext` 原设计；
   - 写事务在 WriteSlot 唯一自持的物理连接上直接执行（`autoCommit = false` -> SQL -> `commit()` / `rollback()` -> `autoCommit = true`），事务完全绑定在该物理连接自身，不依赖 `ThreadLocal` 状态，避免协程跨线程恢复引起的静默事务切换。

> **边界声明**：该方案的完整 Kotlin 实现类（如 `SlotConnectionDriver`）与多连接隔离集成测试在 **CT04** 落地完成；本任务（CT01）负责完成事实证伪、技术选型与架构契约锁定。
