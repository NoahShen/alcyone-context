## 3. R2 必须修复的问题

### R2-1：Dreaming 异常路径写了 raw 文件，却把调用记录全部丢弃

`ProductionDreamingEvalRunner.kt:52-63` 在 stage 抛普通异常时调用 `writeLogicalEvidenceSafely` 后重新抛出；`RealModelEvalCli.kt:207-220` 随即只构造 `SampleResult(sample, error=...)`，没有读取或返回 recorder 的 logical calls。

因此 malformed JSON、Provider 失败等情况下，`raw/production-call-*.json` 可能存在，但 `result.json` 的 calls 为空，报告 `productionLogicalCalls/succeeded/failed/missingRawEvidence` 全部少计。这正是 R2 要消除的证据断裂。

**退回要求**：让 Dreaming 成功、普通失败、取消共享同一终态调用快照和 raw 引用；至少补真实 stage malformed-response 与 transport-failure 测试，断言 result 调用数、状态、raw path/SHA 与汇总一致，而不是只断言文件存在。

### R2-2：CLI 取消产物把当前样本写成空调用，丢弃已经捕获的取消记录

`RealModelEvalCli.kt:104-124` 捕获 CE 时，若当前 production call 已取消，`reviewed` 仍是循环开头创建的 `SampleResult(sample)`；`writeCancelledArtifacts`（230-279）使用这个空结果生成当前样本与 partial report。

与此同时，非 Dreaming `ProductionEvalRunner.kt:83-85` 已在抛出 CE 前写取消 raw evidence，Dreaming 路径也尝试写。这会产生“raw 中是 CANCELLED、result/report 中零调用”的同一目录矛盾；Dreaming 还同时有 R2-1。

**退回要求**：取消终态必须携带当前已捕获 logical calls 和引用，report/run manifest 反映部分执行；补真实 CLI 或等价端到端取消测试，不能只用人工构造空 `SampleResult` 的 writer 单测冒充取消链路通过。

### R2-3：一个 Ktor client 上的 raw exchange 没有逻辑调用关联，存在确定性串扰

`EvaluationRawExchangeCapture.kt:20-57` 使用整个 client 共享的一个 `buffered`；`ProductionEvaluationAdapters.kt:44-94` 每次调用覆盖同一个 `ktor.rawExchangeObserver`，返回后 drain 整个共享 buffer，finally 又可能清除另一个仍在运行调用的 observer。

`RawExchangeObservation` 没有 callId/coroutine 关联。两个并发 `complete` 会发生：

- B 覆盖 A 的 observer，A 的 attempt 可能完全丢失；
- A 先 drain 会把 B 的 attempt 归到 A；
- A 的 stop 会清掉 B 的 observer。

这是结构可推导的确定性错误，不是低概率性能问题。当前串行单测未覆盖。Search 当前生产路径可串行完成，但不能据此把一个 client 级 recorder/capture 宣称为支持并发的正确接缝；同模型 Judge 与生产并发、其他组装或未来 parallel execution 都会破坏证据归属。

**退回要求**：在调用前建立稳定 callId，并把 callId/每次 attempt 关联贯穿 observer；或明确以每逻辑调用独立 client/capture 隔离且测试证明。必须加两个交错调用的确定性测试，验证 attempts、状态和 observer 恢复均不串扰。不得用事后按时间或 task 猜归属。

### R2-4：报告的 complete/selected/sampleCount 和 artifact 集合没有统一不变量

`RealModelEvalCli.kt:389-496` 的 `writeReport` 接受任意 `results/selected/finished`，直接写 `complete=finished`；没有断言 `complete => sampleCount == selected`、结果 ID 与 selection 一致、无重复、每样本 result/raw 文件存在。`writeRunManifest` 同样只接收调用方参数。

现有 partial 测试甚至用 `selected=3`、一个结果和 `finished=false` 证明 writer 接受不一致选择，但没有测试“缺样本却 complete=true”必须拒绝。正常 main 的 finally 用 `completed.size == samples.size`，只能保护当前串行正常路径，不能让报告生成器、取消路径和未来复用具备可信边界。

此外 `humanReviewStillRequired` 只是 `results.any { status == REVIEW_REQUIRED }`，全 PASS/FAIL 时可写 false，与报告文本仍要求 PASS calibration audit 相矛盾；它不是 H1/H2/H3 已复核证据。

**退回要求**：建立单一 run snapshot/validator，统一 selection、结果、调用和 raw/result SHA；不完整时强制 `complete=false` 或安全失败，禁止生成自相矛盾的 complete 报告。人工复核状态应独立显式记录，未执行 H1/H2/H3 时不能由状态分布推导为完成。
