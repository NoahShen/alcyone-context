## 失败及精确恢复

固定集 `reflection-failure` 用 **schema 拒绝** 验证失败语义：非重试，无部分提交、checkpoint 不前进，Reflection 不得被误记为成功。它不代表网络限流。

`DreamingPublicEntryEndToEndTest.public run retries reflection 503 then a 429 failure resumes from the same checkpoint` 使用真实 Ktor HTTP：
- Reflection 首次 **503** 后按生产退避策略重试，第二次成功，checkpoint=1、Raw=1。
- 下一 turn 的 Reflection 连续两次 **429 + Retry-After: 0 + rate_limit_exceeded**，耗尽两次尝试后失败；checkpoint 保持 1、Raw 保持 1。
- 同一 Context 再次公开 `runDreaming()`，从 checkpoint=1 恢复，只扫描同一来源 turn=2，生成 1 条 Raw，最终 checkpoint=2、Raw=2。

相关 Ktor 精确等待/限流边界仍由 `KtorLlmClientRetryTest` 验证；这里验证 Dreaming 公共入口与提交水位。测试结果以最终 integration XML 与退出码为准。

## 独立 JVM SIGKILL 恢复

`DreamingCommitCrashRecoveryTest` 启动独立子进程 `DreamingCommitCrashRecoveryProbe`，第一进程在真实生产 DreamingCommitter 事务返回后、通知测试进程前被 SIGKILL；该点已写入 Raw、pending 和 checkpoint=1，但外部调度者尚未收到完成通知。第二个 JVM 使用相同 SQLite 数据库恢复，从旧 checkpoint 继续下一批，不重复已提交 Raw。

结果：通过。崩溃后 checkpoint=1、Raw=`ct26-crash-1`、pending=`ct26-crash-1`；恢复进程输出 `RECOVERY_RESULT=1:2:1:1`，随后 checkpoint=2、Raw 为 `ct26-crash-1,ct26-crash-2`，无重复 Raw，pending 归属无重复。stdout 路径由 JUnit `CT26 controlled probe pid=... crash=... output=...` 记录；结果 XML：`context/runtime/build/test-results/test/TEST-com.github.noahshen.alcyone.context.memory.runtime.dreaming.DreamingCommitCrashRecoveryTest.xml`。

本场景证明**已提交但通知前崩溃**的幂等恢复；不声称 Reflection 成功后未提交或任意事务中崩溃都已实测。
