## 2. 与设计/现状的差异与冲突

### C1 Candidate Retriever 尚不存在

设计 §6.4 只有逻辑接口；当前无 `core/organization`、无 Runtime 实现。**需新增 Core Port + Runtime 实现**，但不新增公开 SDK。

### C2 快照排序与分页

设计要求「至少 id/content，按 ID 稳定排序」；现有 `scanPage` 按 `created_at ASC,id ASC`。若直接使用，排序不是纯 ID，且分页依赖 offset。**建议**：单次 `read` 内分页读取全部后，内存按 `id ASC` 排序；不新增 Repository 方法，避免改 CT05 契约。

### C3 预算归属

设计只说「Token Budget」；未指定固定开销/单条/输出保留的精确公式。现有 `LlmBudget` 已提供输入/输出/余量三部分，但没有「单条候选放不下」的专用分类。**建议**：CT13 用现有 `LlmBudget.estimate` 做三段判定（固定/单条/批次），失败用 `LlmException(LOCAL_BUDGET_EXCEEDED)`；不新增公共错误码。

### C4 候选 ID 校验位置

设计要求 Core 校验每个 ID 属于该批模型实际可见集合。**建议**：Runtime 严格 JSON 解析 + Core `CandidateIdValidator` 纯校验；Core 不引入 serialization。

### C5 Prompt 归属

Extraction Prompt 在 Core 资源；Organization 无资源。**建议**：候选/治理 Prompt 与 Schema 均放 Core `prompts/`，版本化 v1；Runtime 只构造请求/解析。

### C6 LLM 模式

设计未明确 `PROMPT_ONLY` 是否允许。Extraction 只允许 `JSON_SCHEMA`/`JSON_OBJECT`。**建议**：Organization 同样只允许两种结构化模式；`PROMPT_ONLY` 不建生产 Organization pipeline（CT16 gate），CT13 直接构造时拒绝。

### C7 无硬过滤

Raw 无 Agent/Domain 字段；候选必须覆盖全部当前 Organized。**建议**：不增加任何 `WHERE agent/domain` 条件；测试用不同 domains/来源证明均进入扫描。

### C8 生产接线时机

CT13 若接 Factory/Impl，会形成「只有 Scanner、没有 Governance/Commit」的半成品。**建议**：CT13～CT15 只交付组件与测试；CT16 B2 才接生产 pipeline，与 CT09/CT11 的分批模式一致。

## 4. 预算/快照算法（CT13 详细）

### 4.1 快照

```kotlin
val snapshot = database.read { read ->
    val all = mutableListOf<OrganizedMemory>()
    var offset = 0
    while (true) {
        val page = read.organizedMemories.scanPage(offset, PAGE_SIZE)
        if (page.isEmpty()) break
        all += page
        if (page.size < PAGE_SIZE) break
        offset += page.size
    }
    all.sortedBy { it.id }
}
// ReadContext 已释放；以下只使用 snapshot
```

- `PAGE_SIZE` 建议 256（不新增配置）。
- 空 snapshot → 返回空列表，不构造请求。
- 若分页期间数据变化：单次 `read` 事务保证同一快照；不跨 read。

### 4.2 固定开销

- 构造 `fixedMessages = prompt.system + prompt.raw(raw) + prompt.outputContract`。
- `fixedDecision = LlmBudget.estimate(request(fixedMessages, emptyBatch), schema, task, profile, margin, estimator)`。
- 若 `fixedDecision.estimatedInputTokens > task.maxInputTokens` 或 `requiredTotalTokens > profile.contextWindowTokens` → 抛预算失败（固定开销）。

### 4.3 分批

- 按 snapshot 顺序逐条加入 `batch`；每次用 `batch + item` 构造 messages 并 `estimate`。
- 若通过 → 保留；若超限：
  - `batch` 非空 → 封批；新批从当前 item 开始；
  - `batch` 为空 → 单条预算失败。
- 所有 items 都被分配；不设固定每批条数，不跳过。
- 每批请求 `maxOutputTokens = task.maxOutputTokens`；`schema` 按 Profile 模式。
- 每批 `LlmClient.complete` 顺序执行；任一批失败立即抛，不继续后续批。

### 4.4 响应校验

- 解析：顶层 object 仅 `candidate_ids`；数组元素必须 string；空数组合法。
- 批内：ID 必须在 `batch.map { it.id }.toSet()`；未知/跨批/空白 → `LlmException(INVALID_RESPONSE)`。
- 重复：稳定去重（首次）。
- `finish_reason == "length"` → 失败（截断）。
- 最终候选按 snapshot `id ASC` 排序；不按模型返回顺序，保证确定性。

## 8. Architect 裁定同步（2026-11-01）

CT13 局部 Q1～Q8 全部按推荐批准，并追加以下 B1 验收约束：

- 预算失败复用 `LOCAL_BUDGET_EXCEEDED`；非法估算值保留 `INVALID_REQUEST`；估算/发送共用请求构造，Schema 仅 `JSON_SCHEMA` 计入；等于边界允许。
- 换批后必须重新检查当前单条能否独立放入新批；固定开销、首条、后续超大项均覆盖；不得吞掉后续预算失败并返回之前候选。
- 分页用同一 ReadContext，页大小 256，偏移受检；覆盖 >1 页、整页倍数、分页间并发写入不混入快照、下一次 search 可见变化。
- LLM 回调内可完成独立 DB 写，证明 ReadContext 已释放；候选映射回原快照对象，不重查成不同版本。
- 严格 JSON；未知/跨批/空白 ID 拒绝；重复稳定去重；中间批失败/截断/取消不产生部分返回，后续批不再调用。
- 空集合零 LLM；构造期配置校验不访问 DB/LLM；批间/长预算循环可响应取消。
- Prompt 明确高召回、兼容补充/矛盾/纠错均可关联、输入内容是待比较数据而非指令、不执行治理；正文含分隔符仍保留程序级批内 ID 权限边界；增加 Prompt/Schema 正式测试。
- 允许新增通用预算分批小组件及测试；具体文件见 CT13 任务书 §6；不提前实现 Retrieval/Governance。
