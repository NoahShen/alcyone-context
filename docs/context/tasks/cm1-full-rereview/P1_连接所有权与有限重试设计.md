# P1 修复设计：Slot 连接所有权与有限内部重试

**日期**：2026-10-29
**状态**：Architect 有条件批准实施（2026-10-29）；落实下列 §9 修订后，由原 Worker 在 F1 独立复核通过后实施。设计批准不代表代码验收。
**对应裁定**：`docs/context/milestones/cm1/CM1_全面复查.md`「修复裁定与 CM2 方案约束」第 2 条

## 1. 缺陷回顾（只读审计 P1）

- `ContextSlot.kt:396-401`：`close()` 先 `disposed.compareAndSet(false,true)`（397），再 `physicalConnection = null`（401），**之后**才 `physical.close()`（414）。若 close 抛异常，连接引用已丢失且 `disposed=true` 使重试直接 return（397）→ 物理连接永久不可释放。
- `ContextDatabaseExecutor.releaseAll()`（`441-459`）：对每个 Slot `runCatching{close()}` **只尝试一次**，且入口即 `released = true`（442-445）→ 无二次机会；失败仅聚合抛出。
- 与 F2 rev5 的 `releasePoisonedConnection`（`ContextSlot.kt:219-233`）不对称：后者已做到「close 成功才清所有权」，但全局路径没有。

## 2. 目标语义（三条必须分开表达）

| 语义 | 含义 | 载体 |
| --- | --- | --- |
| **逻辑停止接单** | 不再准入新请求；幂等 | `disposed`（仅表示「不再接新工作」，不再兼作「已释放」） |
| **线程退出** | Slot 单线程已终止 | `executor` 的 `shutdown`/`awaitTermination` 结果（独立记录） |
| **物理资源释放成功** | `physical.close()` 真正成功 | `physicalConnection == null`（**仅在成功后**置空） |

关键：`disposed=true` 不得阻止**清理路径**再次尝试物理 close。

## 3. 设计：`ContextSlot` 停止接单 / 线程退出 / 物理释放 三态独立（按 §9 修订）

**顺序固定**：停止接单 → 排空/确认在途 JDBC 已退出（由 Executor 完成）→ 等待 Slot 线程退出 → 物理 `close()`。禁止在 JDBC 仍在执行时抢关。

```kotlin
// 唯一清理入口：幂等，可重复调用（重试也走这里，不绕过 disposed）
override fun close() {
    disposed.compareAndSet(false, true)   // 仅「停止接单」；不再兼作「已释放」
    releaseAttempt()                      // 每次清理尝试的唯一入口
}

/** 一次清理尝试：线程退出与物理释放分别跟踪，任一失败都不得被另一成功掩盖。 */
private fun releaseAttempt() {
    // 1) 线程退出判定（即使没有物理连接也必须执行）
    var interrupted = false
    var threadFailure: Throwable? = null
    try {
        executor.shutdown()
        interrupted = awaitTerminationInterruptibly()
    } catch (failure: Throwable) {
        threadFailure = failure
    } finally {
        // 无论是否有物理连接、是否失败，中断事实都在 finally 恢复
        if (interrupted) Thread.currentThread().interrupt()
    }

    // 2) 物理连接释放：成功才清所有权
    val physical = physicalConnection          // 可为 null：不得因此提前 return 吞掉上面结果
    var connectionFailure: Throwable? = null
    if (physical != null) {
        connectionFailure = runCatching {
            ContextSqliteErrors.map("closing ${kind.label} slot $index connection") { physical.close() }
        }.exceptionOrNull()
        if (connectionFailure == null) {
            physicalConnection = null
            physicalDriver?.dispose()
        }
    }

    // 3) 失败聚合：保留首次原因，不覆盖、不自我 suppressed
    recordAttemptFailure(threadFailure, connectionFailure)   // 见 §5
    val primary = threadFailure ?: connectionFailure
    if (primary != null) throw primary
}

/** 保留每个资源各自的首次失败；后续尝试失败作为 suppressed 追加，且跳过自身。 */
private fun recordAttemptFailure(threadFailure: Throwable?, connectionFailure: Throwable?) {
    threadFailure?.let { firstThreadFailure.compareAndSet(null, it) }
    connectionFailure?.let { firstConnectionFailure.compareAndSet(null, it) }
}
```

要点（对应 §9）：
- `physicalConnection ?: return` 已删除：**无物理连接时仍执行线程退出判定、失败聚合与中断恢复**。
- `awaitTerminationInterruptibly` 返回的中断事实在 `finally` 恢复，不因失败路径丢失。
- 线程退出失败与物理释放失败**分别跟踪**（`threadFailure` / `connectionFailure`），不以一个成功代替整体成功。
- `close()` 每次都经停止接单入口（`disposed.compareAndSet` 后仍执行 `releaseAttempt`），重试不绕过 `disposed`。

## 4. 设计：`releaseAll()` 有限内部重试（保留首次失败、不自我 suppressed）

```kotlin
private fun releaseAll() {
    synchronized(protocolLock) { if (released) return }   // 已全部成功过才跳过

    val slots = readSlots.asReversed() + writeSlot
    val pending = slots.toMutableList()                  // 仍需成功的 Slot
    val firstFailures = IdentityHashMap<ContextSlot, Throwable>()  // 保留首次原因

    for (attempt in 1..MAX_RELEASE_ATTEMPTS) {           // 2 次：次数上限，非耗时上限
        val stillFailing = mutableListOf<ContextSlot>()
        pending.forEach { slot ->
            val failure = runCatching { slot.close() }.exceptionOrNull()   // 经停止接单入口
            if (failure == null) {
                firstFailures.remove(slot)
            } else {
                val first = firstFailures[slot]
                if (first == null) firstFailures[slot] = failure
                else if (first !== failure) first.addSuppressed(failure)   // 避免自我 suppressed
                stillFailing += slot
            }
        }
        pending.clear()
        pending += stillFailing
        if (pending.isEmpty()) break
    }

    synchronized(protocolLock) { if (pending.isEmpty()) released = true }

    if (pending.isNotEmpty()) {
        val primary = firstFailures.values.first()
        firstFailures.values.drop(1).forEach { other ->
            if (other !== primary && primary.suppressed.none { it === other }) primary.addSuppressed(other)
        }
        throw ContextPersistenceException(
            ContextPersistenceErrorCode.PERSISTENCE_UNAVAILABLE,
            "releasing context database resources failed for ${pending.size} slot(s)",
            primary,
        )
    }
}
```

要点：
- 重试**经 `slot.close()`（停止接单入口）**，不直接调用 private helper、不绕过 `disposed`。
- 首次失败保留在 `firstFailures`；后续失败 `addSuppressed` 且**跳过同一实例**，避免自我 suppressed。
- `released` 仅在**全部成功**后置位。
- 重试成功时返回共享成功；**历史失败**保留在内部诊断（`firstFailures`/`getReleaseFailure()`），与「最终仍有未释放资源」明确区分。

## 5. 与「唯一共享关闭终态」的兼容性（§9 裁定）

- `beginClose()` 以 `closeProtocol != null` 判定「已发起」；后到者只 `await`/`awaitBlocking` 同一协议，不改写结果。
- 因此**同一实例只进行一次清理轮次**（轮次内最多 `MAX_RELEASE_ATTEMPTS = 2` 次尝试）。
- 轮次结束仍有未释放资源时：发布**共享失败**；后续 `close()`/`closeAsync()` 返回**同一失败实例**，**不重开新轮次、不修改终态**。
- 该失败仅表示「关闭协议已终结、仍有资源未释放」，**不得宣称物理资源全部释放**；连接引用保留在 Slot 内供诊断（`getReleaseFailure()`）。
- 不做后台/定时/跨实例重试。

## 6. 测试设计（直接断言物理资源，不只断言异常）

| 用例 | 注入 | 断言 |
| --- | --- | --- |
| T1 首次 close 失败、重试成功 | Driver 代理：对该 Slot 的 `Connection.close()` **首次**抛 SQLException，第二次放行 | 清理**成功**；`physicalConnection` 已清空；真实 Connection `isClosed=true`；共享结果为成功 |
| T2 持续失败 | 每次 `Connection.close()` 都抛 | 清理失败；真实 Connection 仍 `isClosed=false`（**保留所有权**，可诊断）；共享结果为同一失败实例；后续 `close()`/`closeAsync()` 返回**同一失败**（不改写） |
| T3 其他 Slot 仍尽力 | 仅写 Slot 持续失败，读 Slot 正常 | 读 Slot 全部真实关闭；写 Slot 保留引用；失败信息含 suppressed 聚合 |
| T4 中断不丢清理 | 清理期间 `Thread.interrupt` | 清理继续完成、中断标志恢复、结果与真实终态一致 |
| T5 失败后不重开新轮次 | T2 之后再调用 `close()` | 只等待同一协议，**不再**尝试 close（用计数型代理断言 close 调用次数不增加） |
| T6 `releasePoisonedConnection` 失败后全局重试 | 中毒连接首次 close 失败（已有 rev5 路径）→ 全局 close 再试 | 全局重试成功时真实关闭；仍失败时保留引用并共享失败 |
| T7 无物理连接但线程清理失败 | Slot 连接已被成功释放（`physicalConnection==null`），注入 `awaitTermination` 失败（最小 internal 钩子或已 shutdown 的 executor 代理） | **不得因无连接而吞掉线程失败**：清理尝试仍返回失败、中断标志恢复、共享结果失败；断言在测试兜底之前 |
| T8 首次失败原因保留 | 同一 Slot 两次尝试都失败且异常不同 | 最终异常的 cause 为**首次**失败，第二次作为 suppressed 追加；无同一 Throwable 自我 suppressed |

- 复用 `TestDatabases` / `ContextDatabaseFactory`，真实文件 SQLite + Driver 代理（只包 `close`），`finally` 恢复 Driver 与清理临时目录。
- 断言必须**在执行器/兜底清理之前**（避免「已由测试兜底关掉」的伪通过）。

## 7. 不改变的行为

- `beginClose` 的「回调内 close 具名拒绝」保持。
- 取消/失败传播契约保持：等待者取消只取消自身 await，共享清理在 `NonCancellable`。
- 不新增公共 API；`getReleaseFailure()` 保持 internal。
- `releasePoisonedConnection` 的 rev5 语义保持（close 成功才清所有权），P1 与其对齐而非替换。

## 8. 待确认

1. `MAX_RELEASE_ATTEMPTS = 2` 是否合适（Lead 建议 2：一次重试，足够覆盖瞬时失败且不拖长 close）。
2. T2/T5 的「失败后不重开新轮次」是否与架构期望一致（Lead 理解：是，符合「不得令后续 public close 改写既有共享终态」）。
3. 是否需要暴露「未成功释放的 Slot 数」到诊断（Lead 建议通过 `getReleaseFailure()` + 异常消息计数，不新增 API）。

## 9. Architect 实施裁定（2026-10-29）

- 同意同一清理轮次最多两次尝试、仅重试失败 Slot；这是重试次数上限，不保证 JDBC close 的耗时上限。
- 同意唯一共享终态不变：后续 public close/closeAsync 不开启新轮次，不修改已发布结果。持续失败仅代表关闭协议已终结，不能宣称物理资源全部释放；保留连接引用及内部诊断。不新增公共诊断 API。
- §3 伪代码不得直接照抄：`physicalConnection ?: return` 会吞掉先前线程退出失败，也会跳过中断恢复。无物理连接时仍须完成线程退出判定、聚合失败和中断恢复；保存 awaitTerminationInterruptibly 返回的中断事实，并在 finally 恢复。
- 顺序保持停止接单、排空/确认在途退出、等待 Slot 线程退出、物理关闭。不得因本轮重试与尚在执行的 JDBC 抢关。线程退出与物理连接释放分别跟踪，不以其中一个成功代替整体成功。
- 所有清理尝试均须经过 Slot 的停止接单入口；§4 示例直接调用 private releasePhysicalResources 不可作为最终实现，也不能绕过 disposed 设置。保持最小内部接口。
- 持续失败须保留首次失败及后续尝试失败，不能用 failures[slot] 覆写而丢掉首次原因；聚合时避免同一 Throwable 自我 suppressed。重试成功可返回共享成功，历史失败须与最终未释放诊断明确区分。
- T1～T6 批准，并补无连接但线程清理失败的控制路径验证（可复用最小内部钩子）；全部物理释放断言在测试兜底之前执行。F1 和 P1 分别提交 Lead 初验与 Architect 独立复核，不合并隐藏边界。
