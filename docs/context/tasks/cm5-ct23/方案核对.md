## 2. 建议实现结构

### 2.1 Core

```text
core/dreaming/
  DiscoveredTopic.kt
  DiscoveredTopicValidator.kt
  DreamingTopicDiscoveryPrompt.kt
  DreamingTopicConsolidationPrompt.kt

core/resources/prompts/
  dreaming-topic-discovery-v1.md
  dreaming-topic-discovery-schema-v1.json
  dreaming-topic-consolidation-v1.md
  dreaming-topic-consolidation-schema-v1.json
```

`DiscoveredTopic` 是 Core public 非 SDK 工作 DTO；Runtime 跨模块消费。Validator 是纯逻辑，接受本次 Batch 的 Turn ID 集合或 Consolidation 输入 Topic 列表。

### 2.2 Runtime

```text
runtime/dreaming/
  DreamingTopicDiscoveryStage.kt
  LlmDreamingTopicDiscoveryStage.kt
  JsonDreamingTopicDiscoveryParser.kt
  JsonDreamingTopicConsolidationParser.kt
  LlmDreamingTopicBatchBudget.kt
  DreamingTopicBatchProcessor.kt
```

- Stage 返回 `List<DiscoveredTopic>` 供 CT24 继续取证。
- Budget adapter 实现 CT22 `DreamingBatchBudget`，与 Stage 共用 Discovery 请求构造。
- Processor adapter 实现 CT22 `DreamingBatchProcessor`，只把最终 Topic 数写入 outcome；不改变 CT22 类型。

## 4. 需 Architect 明确的细项

1. `keywords` 空数组是否合法；若合法，是否所有非空元素必须非 blank。
2. Consolidation 是否严格限制输出 `1..N`，并要求来源并集不增不减（推荐是）。
3. Discovery 输入渲染是否携带 runtime/agent/session/sessionTurnId；Lead 推荐携带，以支持跨会话规律判断，但不携带 extractionStatus。
4. 是否接受 `DreamingTopicDiscoveryStage` + CT22 processor 薄 adapter 的双 seam，而不是现在直接改 `DreamingBatchOutcome` 携带 Topic。
5. 是否确认 Discovery 与 Consolidation 共用 `DREAMING_TOPIC`，不新增 Task enum。
6. JSON 字段使用 `sourceTurnIds` camelCase（与设计一致），而不是 Extraction 的 `source_turn_ids`。

## 5. 测试矩阵候选

### 5.1 Core

- DTO 防御性复制、不可修改列表、toString 不泄露正文。
- `topics: []` 合法。
- title/description 空/空白拒绝；原文保留。
- keywords 类型/空元素/去重策略按裁定。
- sourceTurnIds 空、未知、跨批、负数、重复、边界 Long。
- Discovery/Consolidation Prompt 六原则、跨会话、矛盾保留、数据非指令、无凭据。
- Schema strict、四字段 required、additionalProperties=false。
- Consolidation 数量与来源并集校验。

### 5.2 Runtime Parser

- 合法 Discovery/Consolidation；空 topics。
- 顶层/元素 unknown/missing/type 错误。
- string/bool/float/超大整数 ID；重复/乱序保留规范。
- 围栏、前后文本、空串、重复 key/截断 JSON。
- 错误不带原始正文/cause。

### 5.3 Runtime Stage / Budget / Adapter

- Discovery 0 topics：1 次请求、0 Consolidation。
- 1 topic：1 次请求、0 Consolidation。
- 2+ topics：2 次请求，顺序 Discovery→Consolidation，均 `DREAMING_TOPIC`。
- invalid Discovery → 0 Consolidation；invalid Consolidation → 整批失败、无返回部分。
- Discovery budget exact boundary/overrun 0 LLM；Consolidation overrun 仅已发送 Discovery、0 Consolidation。
- JSON_SCHEMA 发送 Schema；JSON_OBJECT 不发送且不计 Schema。
- missing Task/Profile/PROMPT_ONLY → INVALID_CONFIG；CE 原样。
- 真实 SQLite + Fake LLM + CT22 Coordinator：processor 尾 ID/计数正确、失败保水位、CE。

## 6. 风险与边界

- 程序不能验证 Topic 的语义忠实性、Topic 相关性和矛盾是否被“正确”保留；只能通过 Prompt、确定性字段/来源/数量校验与后续评测约束。
- Fake LLM 仅证明协议、预算、来源权限和失败原子性，不代表真实模型质量。
- Consolidation 的“相关/重复”判断由模型完成；至少 2 Topic 时固定调用一次，避免引入未裁定的启发式语义分类器。
- CT23 不持久化 Topic，不写 Raw/Pending/Checkpoint；后续 CT24/CT25 才能形成权威记忆。
