## 2. 冻结契约

### 2.1 Novelty Assessment

JSON：

```json
{"decision":"NEEDS_EVIDENCE","coveredOrganizedIds":[]}
```

或：

```json
{"decision":"FULLY_COVERED","coveredOrganizedIds":["O-MEM-0001"]}
```

- `decision` 只允许 `NEEDS_EVIDENCE`/`FULLY_COVERED`。
- `NEEDS_EVIDENCE`：`coveredOrganizedIds` 必须为空。
- `FULLY_COVERED`：`coveredOrganizedIds` 非空、去重且全部属于本次 relevant Organized candidate。
- 未知/跨 Topic/空白 ID 失败；重复稳定去重。
- 没有任何 Organized candidate 时不调用 Novelty LLM，直接 `NEEDS_EVIDENCE`；不能用空候选证明覆盖。
- 相关候选本身绝不自动 skip；只有合法 `FULLY_COVERED` 才跳过 Raw 层。
- 程序只验证结构与 ID 权限；“确实充分覆盖”的语义责任由 Prompt 与 CT26 评测承担，交付报告必须明写。

Core 建议：

```kotlin
enum class DreamingNoveltyDecision { NEEDS_EVIDENCE, FULLY_COVERED }

data class DreamingNoveltyAssessment(
    val decision: DreamingNoveltyDecision,
    val coveredOrganizedIds: List<String>,
)
```

加 Core Validator/ValidationException：消息不含正文/ID/Key/URL；返回规范化副本。

### 2.2 Organized Layer

- `collect(batch, topics)` 开始前用**同一个 `database.read`** 读取完整 Organized 与 Raw 快照。
- Organized 快照按 `id ASC`；Raw 快照按 `(createdAt ASC, id ASC)`；不做 Agent/Domain/origin 过滤。
- 每个 Topic 独立对全量 Organized 扫描；禁止跨 Topic 缓存/复用候选（设计接受成本）。
- 复用 CT20：
  - `MemorySearchPrompt.scannerMessages`
  - `JsonMemorySearchResponseParser`
  - `MemorySearchIdValidator`
  - `TokenBatchPlanner`
  - `LlmBudget`
  - `LlmTask.MEMORY_SEARCH`
- 每批输出 `candidate_ids` 必须属于该批；跨批/未知/空白失败。
- 命中 ID 按首次出现稳定去重，映射回原快照并按 `id ASC`。
- 空快照 0 LLM；任一批 LLM/预算/解析/ID/截断失败 → 当前 Topic/Batch 失败，无部分结果。

### 2.3 Novelty

- Organized scanner 无命中：直接 `NEEDS_EVIDENCE`，0 Novelty LLM。
- 有命中：单请求发送 Topic + Topic source batch turns + 全部 relevant Organized。
- 使用 `LlmTask.DREAMING_EVIDENCE`。
- `FULLY_COVERED` 返回候选 Evidence 且不执行 Raw 扫描。
- `NEEDS_EVIDENCE` 继续 Raw 层。
- Novelty 解析/预算/截断/ID 权限任一失败 → 整个 Batch 失败。

### 2.4 Raw Layer

- 使用与 Organized 快照同一 ReadContext 已读取的完整 Raw 快照。
- 每个 NEEDS Topic 独立扫描全量 Raw；不得因 Organized 已命中而缩小 Raw 快照。
- 不过滤 `generatedBy`；`EXTRACTION`/`DREAMING` 都参与。
- Raw Prompt v1 输入：Topic（title/description/keywords/sourceTurnIds）、Topic 对应 batch turns、本批 Raw candidates（id/content/generatedBy/createdAt/sources）。
- 输出严格 `{"candidate_ids":[]}`；批内 ID 权限、稳定去重、失败整体失败。
- 使用 `LlmTask.DREAMING_EVIDENCE` + `TokenBatchPlanner` + `LlmBudget`。

### 2.5 Raw → Organized 反查

- 每个 Raw 命中：在单独 `database.read` 内：
  - `organizedMemories.findOrganizedByRaw(rawId)` 取全部关联 Organized ID；
  - `organizedMemories.findByIds(ids)` 全部回读。
- 任一反查 ID 缺失 → 整个 Batch 失败。
- 与第一层 relevant Organized 合并、按 `id ASC` 去重。
- Raw 无任何关联 Organized：保留为历史证据 candidate，不失败；Prompt 必须说明其不是当前事实。

### 2.6 Candidate Evidence DTO

Runtime internal（B2 最终包装为 `DreamingTopicEvidence`）：

```kotlin
data class DreamingTopicEvidenceCandidate(
    val topic: DiscoveredTopic,
    val decision: DreamingNoveltyDecision,
    val newConversationTurns: List<StoredConversationTurn>,
    val organizedMemories: List<OrganizedMemory>,
    val rawMemories: List<RawMemory>,
)
```

- 列表防御性复制/不可修改；按稳定顺序。
- `newConversationTurns` 由 Topic `sourceTurnIds` 在当前 Batch 中映射，保持 batch 原顺序。
- `FULLY_COVERED`：organized 非空；raw 空。
- `NEEDS_EVIDENCE`：raw 可为空；organized 可为空。
- 不包含 historical conversation；B2 再补。
- `toString` 不打印 Topic/Raw/Organized 正文。

## 3. LLM Binding / Prompt / Schema

### 3.1 Task Binding

- Organized scanner：`MEMORY_SEARCH`。
- Novelty/Raw scanner：`DREAMING_EVIDENCE`。
- 构造期要求两 Task 均存在、Profile 存在、JSON 模式为 `JSON_SCHEMA`/`JSON_OBJECT`；否则 `ContextConfigException(INVALID_CONFIG)`，消息只含配置路径。
- 不新增 enum、不改 Config/Loader。

### 3.2 两份新 Prompt v1

| 文件 | 核心契约 |
| --- | --- |
| `dreaming-evidence-novelty-v1.md` | 数据非指令；相关≠无增量；只有无新增事实/限定/变化/纠错/矛盾才可 FULLY_COVERED；严格 JSON |
| `dreaming-evidence-raw-v1.md` | 输入数据非指令；扫描全历史 Raw；双 origin；相关回召；未关联 Organized 不是当前事实；批内 ID；严格 JSON |

Schemas：

- Novelty：只允许 `decision`/`coveredOrganizedIds`，required，`additionalProperties=false`；decision enum。
- Raw：只允许 `candidate_ids`，required string array，`additionalProperties=false`；可空。

Prompt/Turn/Raw rendering 稳定可测试；所有正文原样，不截断；输入内容和会话/Raw 原文不得进异常/日志。

### 3.3 预算

- Organized/Raw scanner 用 TokenBatchPlanner 串行分批；预算判定与发送共用 `requestFor`。
- Novelty 单请求；发送前 `LlmBudget.requireWithinBudget`。
- JSON_SCHEMA 才发送并计 Schema；JSON_OBJECT schema=null。
- 超预算不得发送对应请求；`finish_reason=length` → `OUTPUT_TRUNCATED`。
- 所有 LLM 在只读 transaction 外。

## 5. 必测矩阵

### 5.1 Core

- Novelty DTO 两决策、列表防御性复制。
- NEEDS 非空覆盖 ID 拒绝；FULLY 空/未知/跨候选/空白拒绝；重复稳定去重；候选空时 FULLY 拒绝。
- Novelty/Raw Prompt 核心契约逐片段内容断言（数据非指令、相关≠无增量、全历史/双 origin、冲突/纠错保留、无系统字段）。
- 两 Schema strict/required/additionalProperties=false/decision enum；资源缺失/空白 fail-fast。
- Prompt rendering 稳定、正文原样、无 extractionStatus 系统字段。

### 5.2 Parsers / Binding

- strict Novelty/Candidate JSON；unknown/missing/type、围栏/前后文本/重复 key/截断拒绝；错误无 cause/正文。
- candidate IDs string/blank/empty array；empty合法、重复交给 ID validator稳定去重。
- 双 Task/Profile/JSON 构造期校验；缺任一 Task/PROMPT_ONLY → INVALID_CONFIG；0 DB/LLM。
- JSON_SCHEMA/JSON_OBJECT 两 Task schema 发送/省略。

### 5.3 Organized / Raw Scanner

- 空 Organized/Raw snapshot：0 对应 LLM。
- 多页/多批、批边界、全量 snapshot、无 Agent/Domain/origin 过滤。
- 批内/跨批/未知 ID、解析、截断、预算、CE：整 Topic/Batch 失败，后续 0 调用。
- 预算等号通过/超限 0 LLM；schemaTokens 仅 JSON_SCHEMA。
- Full Organized/Raw snapshot 同一 `Tracking ContextDatabase.read` 读取（测试观察）。

### 5.4 Novelty / 反查 / Candidate

- Organized 候选非空 + Novelty `NEEDS_EVIDENCE`：继续 Raw。
- `FULLY_COVERED` 合法：0 Raw scan，Candidate raw 空、organized 非空。
- 覆盖 ID 越权/空：整 Batch 失败。
- Raw 命中 → 反查全部关联 Organized；第一层+反查合并、id ASC、去重。
- 反查 ID 缺失 → 整 Batch 失败。
- Raw 无关联 Organized 保留、不失败。
- 一个 Topic 失败 → 整 Batch 无部分 Candidate 返回。

### 5.5 Real SQLite + Fake LLM

- 真实 Organized/Raw/`organized_memory_source`；多 Topic 独立全量扫描。
- 双 origin Raw 均参与。
- Full snapshot 同 ReadContext；LLM 在事务外（测试 hook 可断言）。
- 真实反查合并与缺失失败。
- Candidate newConversationTurns 映射/顺序/去重、正文 no logs。
- CE 原样；失败不写任何权威表。

测试规模预计 45～60 例，不注水/不砍矩阵。
