## 2. 待裁定项

### D1 Validator/Service 模块与 JSON 解析（阻断边界）

设计 §5.7 要求 Core 严格校验，但 Core 当前依赖仅 api/common/coroutines，无 `kotlinx-serialization-json`（CT08 §c 曾明确 Core 不引入 Ktor/kotlinx.serialization）。CT11 需要解析 `LlmResponse.content` JSON。

**建议 A（推荐）**：Core 新增 `kotlinx-serialization-json` 依赖（纯本地 JSON，无 Ktor/网络），Validator + `MemoryExtractionService` 放 Core，严格校验与事务语义集中在 Core。
**建议 B**：Core 只定义 `ExtractionResultValidator` 接口/DTO，Runtime 用 serialization 实现；Service 放 Core，避免 Core 新依赖，但校验规则实现位于 Runtime。
**建议 C**：Service/Validator 全放 Runtime，Core 仅 Port/模型；与 §5.7「Core 严格校验」偏离最大。
请裁定 A/B/C（Core 依赖边界是否允许新增 serialization-json）。

### D2 Organization 通知 Port

CT13 尚未实现 Organization Immediate Trigger；设计 §5.8 要求 COMMIT 后新增 Raw > 0 通知。**建议** Core 定义 `OrganizationNotifier`（`suspend fun onRawMemoriesCommitted()` 或等价），Runtime 默认 no-op（CT13 接入真实实现），CT11 测试用 Fake 验证：成功调用一次；失败只记录/吞掉，不回滚、不重提取。请确认 Port 名称/签名/可见性（Core 内部或 public 非 api）。

### D3 生产接线与公共 Factory（范围）

CT09 D3 规定公共 create 到 CT11 才启用真实提取。**建议** CT11 修改 `AlcyoneContextFactory`/`AlcyoneContextImpl`：当 `context.llm` 配置存在时，用同一 `KtorLlmClient` + CT10 Builder 构造真实 `ExtractionRunner`，再组装 CT09 Pipeline/Count/Idle；无 LLM 时仍不建 pipeline（保持 CT08/CT09 行为）。公共 `create` 签名不变。请确认 CT11 是否包含此生产接线（而非留 CT12）。

### D4 ExtractionRunner 请求构造与 Builder 协作

Builder 返回 Context 但不暴露本次实际 `LlmRequest`（task/profile/schema 私有）。Service 需构造完全相同的请求调用 LLM。**建议**：

- 在 Runtime `DefaultPreExtractionContextBuilder` 增加 `internal fun requestFor(context: ExtractionContext): LlmRequest`（复用同一 task/profile/schema/Prompt 渲染）；Service 调用；
- 或 Builder 返回 `Built(context, request)`（修改 CT10 结果契约，不推荐）。
请确认新增 internal `requestFor` 是否属于 CT10 组件回改；若不允许，Service 用同一 LlmConfig/Prompt 重建请求并加一致性测试。

### D5 单 Turn 超预算循环

**建议** Service `execute(sessionKey)` 循环：`builder.build` → `SingleTurnOverBudget`：在短写事务内 `markFailed(anchorId)` 并验证影响行数=1，然后继续 `build` 下一条 Pending；`NoPending` 结束；`FixedOverheadOverBudget` 抛配置/技术错误（不写 failed）；`Built` 进入 LLM。请确认：

- markFailed 失败（行数 0）时是重新 build 还是抛状态错误；
- 是否设置单次 execute 的最大迭代数（防御无限循环；设计未要求）。

### D6 Validator 严格规则

**建议**：只接受 JSON object；`memories` 必填数组（可空）；元素只允许 `content`/`source_turn_ids`（拒绝未知字段）；`content` 非空白 string；`source_turn_ids` 非空整数数组；每个 ID 必须在 `ExtractionContext.turns` 中，且至少一个为 Snapshot PENDING；重复 ID 按首次出现去重；框外/其他 Session/不存在 ID 拒绝；整批任一非法 → 全拒绝、0 写。请确认是否拒绝未知字段（schema `additionalProperties:false` 已暗示）及是否允许重复 ID 去重。

### D7 原子事务与 Target 条件更新

**建议** 一个 `database.write` 内：

1. 预检 Raw ID 是否已存在（碰撞）；
2. `insertBatch(raws)`，影响行数 == raws.size；
3. 每个 Raw `enqueue`，影响行数 ==1；
4. 每个 Target `markComplete`，总影响行数 == Target 数（任一 0 → 抛错回滚）；
5. 空 memories 时只执行 Target complete；
6. 事务外通知（raw>0）。
请确认按 Target ID 逐个 `markComplete` 并汇总行数，还是需要新增批量条件更新 SQL（不建议改 SQL）。

### D8 Raw ID 碰撞识别与有限重试

持久化层不暴露主键冲突码；**建议**在事务内先 `findById` 预检新 ID，若存在则视为已知碰撞，事务外重新生成全部 Raw ID 并重试整笔（最多 3 次）；其他持久化失败不重试、不覆盖。请确认预检+有限重试是否满足“只对确定的 ID 碰撞重试”。

### D9 通知失败语义

**建议** COMMIT 成功后调用 `OrganizationNotifier`；通知异常只记录（不重抛/不回滚/不重新提取），Raw/Pending 已权威入库，CT13 Periodic Cron 可恢复。若 raw=0 不通知。请确认。

### D10 错误分类与日志

**建议**：

- 非法响应/校验失败 → `LlmException(INVALID_RESPONSE)`（或 `LlmErrorCode.INVALID_RESPONSE`）；Target 保持 pending，由 Scheduler 记录失败并继续；
- LLM 超时/拒答/截断/网络 → 原 `LlmException` 传播，0 写；
- 固定开销超预算 → `LlmException(CONFIGURATION)` / 专用技术异常，不标 failed；
- 单 Turn → 标记 failed 后继续，不作为失败抛出；
- DB/事务错误 → 原异常传播，0 部分写；
- 日志不含 Raw content/source/Key/URL/Prompt；不把异常正文打入日志。
请确认错误类型/日志归属（Service vs Scheduler）。

### D11 RawMemory 系统字段与来源

**建议**：`id = MemoryIdGenerator.nextRawMemoryId()`；`content` 原样（trim 后非空）；`generatedBy=EXTRACTION`；`sources` 由 Snapshot Turn 映射为 `ConversationTurnRef(runtimeId,agentId,sessionId,sessionTurnId)`（重复按首次）；`createdAt=clock.instant()`。不新增字段。请确认。

### D12 空 memories 与通知

**建议**：校验通过且 `memories=[]` → 不写 Raw/Pending；同一事务把所有 Target 标 complete；不通知 Organization；成功返回。请确认。

### D13 取消/关闭

**建议** LLM 调用、事务、通知均传播 `CancellationException`；事务由 `database.write` 自身处理；关闭时 Scheduler 取消 Runner，未提交事务回滚；不做自动重试/补偿。请确认。

### D14 分批与测试归属

**建议**：

- **B1** Validator/来源映射 + 原子提交（真实 SQLite + Fake LLM；Core 或 Runtime 按 D1）；
- **B2** Runtime ExtractionRunner（单 Turn 循环/LLM 错误/ID 碰撞/通知失败）+ 真实 SQLite；
- **B3** 公共 Factory 生产接线（LLM 配置 → 真实 pipeline/Runner）+ 全量 `./scripts/check`、81 基线、文档/证据。

请确认批次/是否将生产接线放 B3，以及是否允许修改 CT10 Builder（D4）与 CT09 Factory/Impl。
