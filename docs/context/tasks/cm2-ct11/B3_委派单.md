## 2. 锁定的生产接线

### 2.1 Factory/Impl

- 公共 `create(contextConfig, vfsConfig)` 签名不变；新增 internal 可选 `organizationWakeup: OrganizationWakeup = OrganizationWakeup { }`（B2 的 internal 类型），传给 Impl。
- `performStart`：`executor → vfs → llm → pipeline` 不变；**合法性判定**（新增，由 Lead 依据 Architect“有 context.llm 合法配置”口径裁定）：仅当 `context.llm` 同时满足 ①存在 `LlmTask.EXTRACTION` Task、②其 Profile 存在、③Profile `jsonMode` 为 `JSON_SCHEMA`/`JSON_OBJECT` 时，才视为“合法 extraction 绑定”并构造真实 Runner；不满足（无 EXTRACTION Task / Profile 缺失 / PROMPT_ONLY）**不建 extraction pipeline**，但保留既有 LLM client 生命周期（CT08 `LlmRuntimeLifecycleTest` 的 PROMPT_ONLY 通用配置必须继续 start 成功）。
- 当 `extractionRunner` 未注入且绑定合法时，构造真实 Runner：
  - `DefaultPreExtractionContextBuilder(assembledDatabase, llmConfig, extractionConfig, ConservativeTokenEstimator())`
  - `JsonExtractionResultValidator()`
  - `ExtractionCommitter(assembledDatabase, MemoryIdGeneratorImpl(clock), clock)`
  - `DefaultExtractionRunner(builder, builder::requestFor, acquiredLlm!!, validator, committer, assembledDatabase, maxWindowIterations = extractionConfig.initialWindowTurns, wakeup = organizationWakeup)`
  - 用该 Runner 构造 `ExtractionPipeline`（callbackOwner=this、tick source 按现有内部入口）。
- 无 `context.llm`：不构造 Runner/pipeline（保持 CT09 后行为）。
- 注入 `extractionRunner`（测试）优先于默认 Runner；不改变 CT09/CT10 内部测试语义。
- `maxWindowIterations` 使用 `extractionConfig.initialWindowTurns`（1..1024，已校验）。
- 公共 create 不暴露 Runner/LLM；无新公开 API。
- 绑定合法但 Builder 构造期仍抛 `ContextConfigException(INVALID_CONFIG)`（例如未来新增约束）：按既有 start 失败逆序清理/CLOSED，不吞掉。
- 不合法 extraction 绑定不会构造 Builder，因此不会触发 Builder 的 PROMPT_ONLY fail-fast；这是为兼容 CT08 通用 LLM 生命周期测试的**显式边界**，B3 提交 Architect 复核确认。
- 生产 `OrganizationWakeup` 默认 no-op（CT13 接入）；B3 测试通过 internal create 注入 Fake 验证 raw>0 唤醒、raw=0 不唤醒。
- 日志/错误消费：非法响应/LLM 错误由 Scheduler 记录 `extraction.run.failed`；日志不含 Raw/来源/Key/URL/Prompt；B3 测试至少确认失败不会使 Context 崩溃、Target 仍 pending。
