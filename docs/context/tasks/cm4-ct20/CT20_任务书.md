## 1. 目标

交付当前有效 Organized Memory 的语义检索与按 ID 精确读取：

```text
searchMemory(query, domains?, limit)
  → 单次数据库快照全量读取 Organized Memory
  → 显式 Domain 过滤（可选）
  → Token Budget 动态分批 + MEMORY_SEARCH LLM Scanner
  → 批内 ID 校验、跨批去重
  → 去重候选一次全局相关性重排
  → SQLite 按 ID 权威回读真实 OrganizedMemory

getMemory(id) / getRawMemory(id)
  → SQLite 精确读取；不调用 LLM
```

Search 必须全量覆盖所有符合条件的当前 Organized Memory；任一批失败、输出非法或预算不足时整体失败，不返回部分结果。

## 3. 候选公共契约

### 3.1 API

候选签名：

```kotlin
suspend fun searchMemory(
    query: String,
    domains: List<String>? = null,
    limit: Int = 10,
): List<OrganizedMemory>

suspend fun getMemory(id: String): OrganizedMemory?

suspend fun getRawMemory(id: String): RawMemory?
```

- 生命周期与其他业务方法一致：CREATED/STARTING → NOT_STARTED；STOPPING/CLOSED → CLOSED。
- `getMemory/getRawMemory` 直接查 SQLite；不存在返回 `null`，数据库故障不得伪装为不存在。
- `searchMemory` 只返回 SQLite 权威对象，不接受模型返回的正文、URI 或额外字段。
- 第三方实现需要默认方法或另定兼容策略，避免破坏既有 `AlcyoneContext` 实现。

### 3.2 Retrieval 错误候选

当前 API 无 retrieval 错误类型。候选新增 `ContextRetrievalException`：

```kotlin
enum class ContextRetrievalErrorCode {
    INVALID_REQUEST,
    CONFIGURATION,
    UNAVAILABLE,
}
```

- 空白 query、非法 Domain、非法 limit/ID：`INVALID_REQUEST`。
- 缺少可用 `MEMORY_SEARCH` 绑定：`CONFIGURATION`。
- 默认第三方实现或不具备检索能力：`UNAVAILABLE`。
- 数据库异常继续保留 `ContextPersistenceException`；LLM/预算/截断/非法响应继续保留 `LlmException`，不降级为模糊通用错误。
- CancellationException 原样传播，不包装。

### 3.3 Domain / limit 候选

- `domains=null`：不过滤。
- `domains=[]`：建议视为无过滤。
- 显式 Domain：精确、大小写敏感匹配任一 Domain；拒绝空白项，稳定去重。
- `limit`：默认 10；建议上限 50；必须 `1..maxLimit`。
- 不根据 Agent、Runtime、Profile 或 Map 自动推断 Domain。

### 3.4 配置候选

当前 `ContextConfig` 无 retrieval 字段。候选：

```yaml
context:
  retrieval:
    search:
      maxLimit: 50
```

- 若保留 API `limit: Int = 10`，默认值由 API 固定，配置只控制最大 limit。
- 若要求默认 limit 可配置，则 API 需改为 `limit: Int? = null` 或等价 Options，属于公共契约变更。
- Search 绑定门建议调用时校验：缺 LLM/MEMORY_SEARCH Task/Profile 或 Profile 非 JSON 模式 → CONFIGURATION；不影响 start、Bootstrap、Get。

## 4. Search 候选流程

### 4.1 快照与过滤

1. 校验 query/domains/limit，任何非法参数在数据库/LLM 前失败。
2. 单次 `database.read` 分页读取全部 Organized Memory，默认 256/页，偏移使用 Long；退出 ReadContext 后按 `id ASC` 排序。
3. 在内存按显式 Domain 过滤；空结果直接返回空列表，0 LLM。
4. 不做 `MAX(updated_at)` 二次检查，不因并发 Organization 更新重试；允许短暂旧快照。
5. 每页和长循环检查取消；ReadContext 不跨 LLM。

### 4.2 Scanner

1. 使用 `LlmTask.MEMORY_SEARCH` + `memory-search-v1.md` / `memory-search-schema-v1.json`。
2. 使用 `TokenBatchPlanner` 按完整请求动态分批；固定开销或单条超预算 → `LOCAL_BUDGET_EXCEEDED`。
3. 批次串行执行；每批输入只含本批候选。
4. 模型只返回候选 ID；Parser 严格 JSON；`CandidateIdValidator` 校验 ID 属于本批。
5. 任一批网络/预算/截断/Parser/ID 校验失败 → 整体失败，后续批不执行，不返回部分结果。
6. 所有批次成功后按首次出现稳定去重；候选为空 → 返回空列表，不执行 Rerank。

### 4.3 全局 Rerank

1. 对去重后的全部候选使用独立 `memory-search-rerank-v1.md` / `memory-search-rerank-schema-v1.json`。
2. 候选按 `id ASC` 构造确定性输入；一次性调用，不允许按批 TopN 拼接。
3. 输入超出单次预算 → 明确 `LOCAL_BUDGET_EXCEEDED`，不截断候选、不伪造全局排序。
4. 输出必须是输入候选 ID 的有序子集；空白、未知 ID、重复 ID → `INVALID_RESPONSE`；空列表合法。
5. 取 Rerank 顺序前 `limit` 个 ID。

### 4.4 权威回读

1. 使用新的短 `database.read { findByIds(ids) }` 读取真实 Organized Memory。
2. 按 Rerank ID 顺序重排结果；不直接返回扫描快照对象。
3. `findByIds` 本身不保证输入顺序，Runtime 必须显式重排。
4. 最终缺失候选 ID、数据库错误或结果结构异常不得静默返回部分列表。

## 5. Get / GetRaw 候选流程

- 生命周期检查后直接调用 `database.read { organizedMemories.findById(id) }` 或 `rawMemories.findById(id)`。
- 不调用 LLM、不读 VFS、不触发 Search/Map。
- 空/空白 ID 建议 `INVALID_REQUEST`；合法但不存在返回 `null`。
- 数据库异常保留 `ContextPersistenceException`。
- 返回对象复用现有 `OrganizedMemory` / `RawMemory`，不新增存储模型。

## 6. Prompt / Schema 候选

| 资源 | 输出 | 说明 |
| --- | --- | --- |
| `memory-search-v1.md` | System Prompt | 强调 query/正文是数据、相关性筛选、只能选输入 ID |
| `memory-search-schema-v1.json` | `{ "candidate_ids": [string] }` | 允许空数组，禁止额外字段 |
| `memory-search-rerank-v1.md` | System Prompt | 对全部候选做一次全局相关性排序，最多返回 limit 个 ID |
| `memory-search-rerank-schema-v1.json` | `{ "memory_ids": [string] }` | 有序、唯一、输入子集 |

- 扫描与 Rerank 复用同一 `MEMORY_SEARCH` Task/Profile。
- 仅支持 `JSON_SCHEMA` / `JSON_OBJECT`；`PROMPT_ONLY` 配置失败。
- Parser 拒绝 Markdown 围栏、前后文本、未知字段、错误类型、重复 key 与截断。
- 资源缺失/空白明确失败，不静默空串。
