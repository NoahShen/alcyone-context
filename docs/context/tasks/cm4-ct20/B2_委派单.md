## 2. 冻结行为

### 2.1 公共 API

```kotlin
suspend fun searchMemory(
    query: String,
    domains: List<String>? = null,
    limit: Int = 10,
): List<OrganizedMemory> = throw ContextRetrievalException(UNAVAILABLE, ...)

suspend fun getMemory(id: String): OrganizedMemory? =
    throw ContextRetrievalException(UNAVAILABLE, ...)

suspend fun getRawMemory(id: String): RawMemory? =
    throw ContextRetrievalException(UNAVAILABLE, ...)
```

- 第三方默认方法抛 `ContextRetrievalException(UNAVAILABLE)`；不返回假空列表/假 null。
- Real Impl 覆盖三方法。
- CREATED/STARTING → `ContextLifecycleException(NOT_STARTED)`。
- STOPPING/CLOSED → `ContextLifecycleException(CLOSED)`。

### 2.2 Get / GetRaw

- RUNNING 下空白 ID → `ContextRetrievalException(INVALID_REQUEST)`。
- 合法但不存在 → `null`。
- 直接 `database.read { organizedMemories.findById(id) }` / `rawMemories.findById(id)`。
- 不调用 LLM、不读 VFS、不触发 Search/Map。
- DB 异常保留 `ContextPersistenceException`，不得伪装 null。

### 2.3 Search

- RUNNING 下调用 B1 `MemorySearchService`；参数、Domain、limit、Scanner/Rerank/回读语义全部复用 B1，不在 B2 重实现。
- 每次调用使用当前实例 DB、LLM client、LLM config 与 `retrieval.search.maxLimit`。
- 缺 `MEMORY_SEARCH` Task/Profile 或 PROMPT_ONLY → B1 CONFIGURATION；start、Bootstrap、Get/GetRaw 不受影响。
- Search 不在 start 时构造/校验 LLM binding，不做后台 worker。
- DB/LLM/CE 继续保留 B1 语义。

### 2.4 Retrieval 配置

新增 `RetrievalConfig.kt`：

```kotlin
data class RetrievalConfig(
    val search: SearchConfig = SearchConfig(),
)

data class SearchConfig(
    val maxLimit: Int = 50,
)
```

- `ContextConfig.retrieval: RetrievalConfig = RetrievalConfig()`，现有 Kotlin 构造默认兼容。
- `maxLimit` 默认 50，范围 1..1000；直接构造非法 → `ContextConfigException(INVALID_CONFIG)`。
- Loader 新增 `context.retrieval.search.maxLimit`：
  - 缺省/空 mapping → 默认 50；
  - 严格拒绝 retrieval/search 未知键、错误类型、越界；
  - 只控制上限，不改 API 默认 limit=10。
- Loader 不解析 LLM binding，不创建服务。

### 2.5 Factory / Impl

- 公共 `create()` 签名不变；继续零副作用。
- Factory 将 `ContextConfig.retrieval` 传入 Impl。
- Impl 在 RUNNING 状态锁内取得当前 database/LLM 引用；锁外执行 DB/LLM。
- Search 使用 `MemorySearchService(database, llm, llmConfig, retrieval.search.maxLimit)`。
- Get/GetRaw 使用 `database.read`。
- 不新增公共 Factory 参数或 ContextStatus 字段。

## 4. 测试矩阵

### 4.1 API 默认契约

- 三方法均抛 UNAVAILABLE；不是空列表/null。
- 消息含 errorCode，无 cause，不回显 query/ID/正文。

### 4.2 Config / Loader

- RetrievalConfig/SearchConfig 默认 50；1/1000 通过；0/负/1001 拒绝。
- ContextConfig 旧构造默认 retrieval。
- Loader retrieval/search 缺省、空 mapping、覆盖 1/1000。
- unknown、错误类型、越界 → ContextConfigException INVALID_CONFIG；错误信息不回显原值。
- Loader 不因缺 LLM/MEMORY_SEARCH 失败。

### 4.3 Runtime Wiring / Lifecycle

- CREATED/STARTING 三方法 NOT_STARTED；STOPPING/CLOSED CLOSED。
- RUNNING 未配置 LLM：Get/GetRaw 可用，Search CONFIGURATION。
- RUNNING 有 LLM 但缺 MEMORY_SEARCH/PROMPT_ONLY：Search CONFIGURATION，Get 不受影响。
- Get/GetRaw 存在完整对象、缺失 null、空白 ID INVALID_REQUEST、0 LLM。
- 损坏 DB row → 原 ContextPersistenceException，不伪装 null。
- Search 使用配置 maxLimit；limit > maxLimit → INVALID_REQUEST。
- Search 通过真实 Ktor client + HTTP stub 调用 Scanner + Rerank，返回 SQLite 权威对象。
- Search 缺绑定不阻塞 start/Bootstrap/Get。

### 4.4 Integration E2E

真实 Factory + 初始化 SQLite + 真实 Runtime/Ktor client + JDK HTTP stub：

- 预置 Organized/Raw。
- `searchMemory` 完成 Scanner + Rerank，返回真实 SQLite 顺序/内容。
- `getMemory/getRawMemory` 精确读取，0 额外 LLM。
- 重复 Get/GetRaw 不新增请求。
- close 后三方法均 CLOSED。
- 真实模型 not-run。
