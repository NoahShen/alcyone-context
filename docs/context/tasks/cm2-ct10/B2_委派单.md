## 2. 锁定的 Builder 契约

```kotlin
internal class DefaultPreExtractionContextBuilder(
    private val database: ContextDatabase,
    llmConfig: LlmConfig,
    private val extractionConfig: ExtractionConfig,
    private val estimator: TokenEstimator = ConservativeTokenEstimator(),
) : PreExtractionContextBuilder
```

### 2.1 构造期 fail-fast（D10/D11）

- `llmConfig.tasks[LlmTask.EXTRACTION]` 缺失 → `ContextConfigException(INVALID_CONFIG)`，消息含 `context.llm.tasks.EXTRACTION`。
- Task 引用 Profile 不存在 → `INVALID_CONFIG`，消息含 `context.llm.tasks.EXTRACTION.profile`（或 `context.llm.profiles.<name>`），不回显 Key/URL/正文。
- Profile `jsonMode == PROMPT_ONLY` → `INVALID_CONFIG`，消息含 `context.llm.profiles.<name>.jsonMode`，说明只允许 `JSON_SCHEMA`/`JSON_OBJECT`。
- 构造期只读配置，不访问 DB/LLM。

### 2.2 build 算法（D5～D7）

整个 `build` 在**一个** `database.read { read -> ... }` 回调内完成；回调内无挂起、无 LLM、无 I/O（除测试钩子）。

1. `anchor = read.conversations.latestPending(sessionKey)`；`null` → `NoPending`（不渲染/不估算）。
2. 构造基础请求：`ExtractionPrompt.messages(emptyList())`；`schema = if (profile.jsonMode == JSON_SCHEMA) ExtractionPrompt.schema() else null`；`LlmRequest(task=EXTRACTION, messages, responseFormat=profile.jsonMode, maxOutputTokens=null, schema=schema)`；`LlmBudget.estimate(request, schema, task, profile, llmConfig.safetyMarginPercent, estimator)`；`ExtractionBudgetPolicy.classify` 非 Fits → `FixedOverheadOverBudget(decision.requiredTotalTokens)`。
3. `limit = extractionConfig.initialWindowTurns`；循环：
   - 调用 `betweenReadsForTesting?.invoke()`（internal 钩子，非挂起；仅测试用，生产 null）；
   - `turns = read.conversations.sessionWindow(anchor.timestamp, anchor.id, limit)`；空 → `NoPending`（防御）；
   - 构造完整请求（`ExtractionPrompt.messages(turns)`、同一 schema/格式）；`LlmBudget.estimate`；`classify`：
     * Fits → `Built(ExtractionContext(sessionKey, turns))`；
     * 非 Fits 且 `turns.size == 1` → `SingleTurnOverBudget(anchor.id, decision.requiredTotalTokens)`；
     * 否则 `limit = ExtractionBudgetPolicy.nextWindowSize(turns.size)` 继续。
4. 不写库、不改 `extractionStatus`、不调用 LLM；`SingleTurnOverBudget`/`FixedOverheadOverBudget` 只是结果。

### 2.3 快照与窗口

- `latestPending` 与所有 `sessionWindow` 在同一个 `read` 回调内，保持同一 SQLite 快照；折半期间其他连接补录不得混入。
- `sessionWindow(anchor.timestamp, anchor.id, limit)` 包含锚点、按真实会话顺序返回；不得跳过中间 Complete/Failed。
- 折半按实际读取条数 K（D6）：`K=max(1,floor(K/2))`；配置 N 只是初始 LIMIT。
- 窗口只含一个 Session；Target 由返回 Turn 的 `extractionStatus == PENDING` 判定。

## 3. 测试要求（真实 SQLite）

使用既有 `withTriggerDatabase`/`insertTurn` 测试夹具（CT09 B2 fixture）或等价真实 `ContextDatabaseImpl`；Fake/受控 `TokenEstimator` 控制窗口大小。至少覆盖：

1. **无 Pending**：空库/仅 complete+failed → `NoPending`；不触发 Prompt 估算（可记录 estimator 调用为 0）。
2. **锚点**：多 Session 隔离；最新 pending 按 `timestamp DESC,id DESC`；同 timestamp 用较大 id；较新 complete 不抢锚点。
3. **连续窗口/History**：P/C/P/P 序列按真实顺序返回；包含中间 complete/failed；不跳过中间 Turn；窗口外旧 Pending 不在结果。
4. **折半**：受控 estimator + 低预算，验证实际窗口序列（如 8→4→2 或 32→16→8→4）首次满足即停止；不在满足后继续缩小；窗口外 Pending 未处理。
5. **N=1 单 Turn**：只剩 1 条仍超 → `SingleTurnOverBudget(anchor.id, requiredTotalTokens)`；DB 状态未改（仍 pending）；不写 failed。
6. **固定开销**：基础请求超 task.maxInput/contextWindow → `FixedOverheadOverBudget(requiredTotalTokens)`；不进入窗口/不写状态。
7. **快照**：`betweenReadsForTesting` 在 read 回调内阻塞；另一连接写入更新 pending；放行后结果不包含新 Turn（同一快照），且后续折半也不混入。
8. **预算边界**：等于 `maxInputTokens`/`contextWindowTokens` 视为 Fits（通过受控 estimator 构造精确值）。
9. **无 LLM**：不注入 LlmClient；Builder 无网络调用（编译期/构造即可证明）。
10. **Fail-fast**：缺 EXTRACTION Task、Task 引用缺失 Profile、`PROMPT_ONLY` 各一例；`INVALID_CONFIG`、消息含路径、无 Key/URL。
