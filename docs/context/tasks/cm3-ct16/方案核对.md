## 2. 现存缺口与冲突

### C1 配置启用门未实现

当前 `organization` 存在与否都等价于“被忽略”。直接接入会把“未配置”和“配置但缺 Task/Profile/非法模式”混为一谈，违反 Q13。必须把 `organization` 改为 nullable 配置快照，并在显式配置时做 LLM 绑定门。

### C2 Pending 固定列表缺失

`nextByRawCreatedAt()` 不能用于整轮：每处理一条后重新查询会把轮中新入队项混入旧轮，且无法保证“每轮固定集合”。需新增一次性 list。

### C3 已有 CT15 API 不足以单独表达“已关联清理”

Extraction 的 OrganizationWakeup 可以正常触发，但 Worker 在调用 LLM 前需要处理 Source 已关联。CT15 `commit` 的 Source 分支会在 Validator 之前返回，但仍要求构造一个 decision 参数；生产路径不应传伪 decision。建议保留 CT15 DONE 的 5 文件不变，在 CT16 Runtime 内做独立的 Source 预检/清理短事务（D7），而不重开 CT15。

### C4 生命周期有两条 pipeline

Organization 需要与 Extraction 共享同一个 LLM client，且在 Extraction 提交后唤醒。生产必须让 Extraction `OrganizationWakeup` 指向已构造的 Organization Pipeline；组织 pipeline 又依赖 LLM。构建顺序和关闭顺序必须明确，不能形成循环资源。

### C5 状态未记录 Worker

`ContextStatus.workers` 当前为空。CT16 应至少报告 Organization Worker 的 IDLE/RUNNING/STOPPED/FAILED；单条业务失败不应把 Worker 标为 FAILED。是否在 B2 实现，待 D12。

## 3. Q10 时区核对

### 3.1 现状

- 技术实现设计 §6.2 示例含 `timezone: Asia/Shanghai`，同时写“默认 `Asia/Shanghai`”；核心数据流 §13.9 写“Cron、时区可配置”。
- Extraction 已冻结为固定 `Asia/Shanghai`，Loader 遇到 `timezone` 作为未知键拒绝。
- 数据库时间全部固定上海 `+08:00`，业务系统默认上海时区。

### 3.2 推荐

**固定 `Asia/Shanghai`，`context.organization.triggers.periodic.timezone` 不加入配置，出现即 `UNKNOWN_FIELD`。** 理由：

- 与已有 Extraction Cron、默认运行维护和 SQLite 上海时间保持一致；
- 避免同一 Runtime 内两个 Cron 使用不同日历时区造成运维歧义；
- 技术设计的“可配置”尚未形成已验收契约，当前没有真实需求证明必须增加。

若 Architect 选择可配置，则必须校验 IANA ZoneId、明确默认上海、补时区边界测试；不能只透传任意字符串。

## 4. Q13 配置启用与非法绑定门

推荐门如下：

| 配置状态 | 行为 |
| --- | --- |
| `context.organization` 不存在 | 不创建 Organization pipeline；保持 extraction-only/ingestion-only 兼容 |
| 存在且结构合法、LLM/Task/Profile/JSON 模式完整 | 创建 pipeline；trigger 按配置 |
| 存在但任一必填绑定缺失/非法 | `ContextConfigException(INVALID_CONFIG)`；不静默降级为 disabled |
| 存在但 immediate/periodic 均 disabled | 推荐 `INVALID_CONFIG`；完全禁用应删除 organization 子树，避免“配置了但永不运行” |
| 未知键/类型/非法 cron | Loader 拒绝；不启动任何资源 |

绑定门推荐在 `AlcyoneContextFactory.create` 的纯配置校验阶段完成；`ContextConfigLoader` 只负责 `organization` 结构与字段合法性，跨 `context.llm` 的任务/Profile/模式校验放 Factory，避免 Loader 承担业务依赖判断。这样 `create` 失败前不会打开数据库或启动协程。

## 5. 固定 Pending 列表方案

新增到 `OrganizationPendingReadOps`、`OrganizationPendingRepository` 与其 SQLDelight 实现：

```kotlin
fun listAllByRawCreatedAt(): List<String> // TxOps 继承 ReadOps 自动获得
suspend fun listAllByRawCreatedAt(): List<String> // 普通 Repository
```

SQL：

```sql
SELECT p.raw_memory_id
FROM organization_pending p
JOIN raw_memory r ON r.id = p.raw_memory_id
ORDER BY r.created_at ASC, r.id ASC
```

- 单次 `database.read` 完成后才调 LLM；列表即本轮固定 ID 集合。
- 不新增 limit、表、索引或持久队列。
- 新 Pending 在本轮开始后不进入该列表；下一 Trigger 的新轮可见。

## 6. Scheduler / Counter 设计建议

### 6.1 API

```kotlin
internal fun interface OrganizationRoundRunner {
    suspend fun runRound()
}

internal class OrganizationScheduler(
    private val runner: OrganizationRoundRunner,
) {
    fun start()
    fun request(): Boolean
    suspend fun closeAsync()
    internal fun statusForTesting(): OrganizationWorkerStatus
}
```

`OrganizationPipeline` 包装 Scheduler/Cron/Worker，并暴露 `requestImmediate()`/`OrganizationWakeup`。

### 6.2 计数与退出

- `triggerCount` 为 `Int` 饱和计数；请求超过 `MAX_VALUE` 不溢出，保留“仍有意愿”的可观察状态。
- 单 Worker 示例：

```text
request():
  lock:
    if state != RUNNING: reject
    triggerCount = saturate(triggerCount + 1)
    if worker == null: start lazy worker

worker loop:
  lock:
    if triggerCount == 0: worker = null; exit
    triggerCount--
  run fixed pending round
  repeat
```

- `worker` 的置空与 `request` 的启动判断必须同锁；退出瞬间到达的 Trigger 要么阻止退出、要么在置空后启动新 Worker，不能丢失。
- 单条失败不减少/增加 Trigger；一次完整轮结束才消费一个 Trigger。
- 同一个 Trigger 不得自动重试失败 Raw；后续 Trigger 才允许重试。

### 6.3 Worker 级错误

建议将“轮次查询失败”和“单条失败”分开：

- 单条普通失败：记录安全错误、继续同轮下一条。
- `listAllByRawCreatedAt`/整轮级失败：记录 `organization.round.failed`，消费当前 Trigger；若还有 Trigger，短暂固定可取消退避（例如 1s，不新增配置）后下一轮，避免数据库持续故障紧凑循环。
- Worker 不再因为普通失败退出；只有未处理的结构化取消/不可恢复异常进入 FAILED/CLOSED 可观察状态，不自动重建第二 Worker。

该退避/失败状态细节待 D9。

## 7. 逐条 Worker/Pipeline 设计

### 7.1 Source 预检

建议 CT16 在 Runtime 内使用 `OrganizationSourceGuard`（或 Worker 私有方法）：

1. `database.read` 查 Source 是否已关联；查询错误作为该条失败。
2. 已关联时 `database.write` 再核验；若 Pending 仍存在，精确 `dequeue` 1 行；若已无 Pending，no-op 成功。
3. 未关联则返回 false，进入 Scanner。

这样不修改 CT15 已完成 API，不传伪 GovernanceDecision；CT15 仍在最终提交时再次做 Source/版本/幂等检查。

### 7.2 未关联单条

1. 读取 `RawMemory`；不存在/错误则该条失败。
2. `OrganizationCandidateRetriever.search(raw)`。
3. `LlmGovernanceService.decide(raw,candidates)`。
4. `OrganizationCommitter.commit(raw.id,candidates,decision)`。
5. `Committed` 后调用 `OrganizationMapWakeup`；`AlreadyAssociated` 不调用；所有 LLM/DB 调用均在短事务外/短事务内边界正确。

### 7.3 单条异常隔离

- `CancellationException` 原样传播，停止 Worker/轮次。
- `ContextPersistenceException`、`LlmException`、Governance/Committer 安全异常：记录固定事件名和分类，不记录正文/ID/Key/URL；继续下一条。
- 单条失败不改 Pending；下一 Trigger 可重试。

## 8. Cron、Map 与状态

### 8.1 Periodic Cron

- 建议独立 `OrganizationPeriodicCron`，不修改 CT09 `IdleCron`。
- UNIX 五字段、上海时区（待 D4）、严格未来、不启动即扫、不补跑。
- 每 tick `pending.hasAnyPending()`；true → scheduler.request()。
- 普通调度/查询失败 WARN + 固定 1s 可取消退避；无下一 tick 结束；close 停循环并 join，共享关闭结果。

### 8.2 Map 通知

```kotlin
internal fun interface OrganizationMapWakeup {
    suspend fun onOrganizedCommitted()
}
```

- 仅 `Committed` 后调用，不用于 AlreadyAssociated/Source cleanup。
- `CancellationException` 原样传播；其他失败记录固定事件并吞掉，不回滚已完成提交。
- 默认 no-op；CT17 才接 Map Refresh。

### 8.3 Worker 状态

建议 `ContextStatus.workers` 在 Organization 已配置时增加 `organization`：

- `IDLE`：无运行轮次；
- `RUNNING`：Worker 正在处理轮次；
- `STOPPED`：Context 已关闭；
- `FAILED`：Worker 因不可恢复异常无法继续消费；
- 单条普通失败继续运行，不标 FAILED，可记录脱敏 lastError。

不新增公开状态字段；若认为 CT16 不包含状态面，可保留 empty workers，但需 Architect 明确。

## 9. 生命周期与生产接线

### 9.1 构造顺序建议

1. 校验 `ContextConfig`/`VfsRuntimeConfig`/LLM/Organization binding（纯配置，不触资源）。
2. start：打开 DB → VFS → LLM client。
3. 创建 OrganizationPipeline（使用同一个 LlmClient、DB、Clock、Map wakeup no-op）。
4. 创建 ExtractionPipeline；其 `OrganizationWakeup` 指向 OrganizationPipeline 的 `requestImmediate()`。
5. `start()` 两条 pipeline；发布 RUNNING；`activate()` 两条 pipeline。

如果 Organization 未配置，则跳过步骤 3；Extraction 保持现状的 no-op wakeup（或测试注入）。

### 9.2 关闭顺序建议

1. Context 生命周期锁内同步封闭 Extraction 与 Organization 的准入（`beginClosing()`），切换 STOPPING。
2. 取消通知/等待在途 Ingestion。
3. 先关闭 Extraction（停止新 Raw 生产并 join Extraction Worker），再关闭 Organization（停 Periodic Cron、取消并 join Organization Worker）。
4. 释放 LLM → VFS → DB；清理失败共享结果。

Organization Pipeline 的 `closeAsync()` 自身必须按 Q11：封闭准入 → 停 Cron → 取消/join Worker → 清计数 → 发布关闭结果。
