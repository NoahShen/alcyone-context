## 2. 必须修正

### R1：启动失败与资源释放缺少完整所有权处理

`ContextDatabaseExecutor` 先创建 writeSlot，再调用 `openReadSlots`。后者失败只关闭已打开的读 Slot，没有关闭写 Slot。独立 JDBC 捕获实测：首个读 Slot 注入失败后，已打开的写 Connection 的 `isClosed=false`。

`ContextSlot` 构造器先建立 executor，再打开 Connection/执行 PRAGMA；连接取得后 PRAGMA 失败也没有 finally 释放。`disposeSlots` 遇到首个 close 异常停止，后续资源不会关闭。Slot 先标 disposed，再等待线程/关闭连接，失败后没有可靠的最终结果。等待线程超时后的第二次 await 返回值还被忽略。

要求：工厂显式持有逐步取得的资源，失败时逆序尽力释放全部资源，保留主失败与安全的清理失败信息；连接取得后初始化失败必须关连接；所有 Slot 关闭均被尝试，不能伪报释放成功。真正物理 close 只能发生在操作退出确认之后。连接初始化/PRAGMA/事务执行/收尾的线程所有权要一致，不以诊断方法直接绕过。

现有 `PartialInitCleanupTest` 的“再次打开成功”不能证明旧 Connection 已关闭；WAL 允许多连接，单线程池也延迟创建线程，无残留线程不能证明无连接泄漏。改为直接检查捕获的真实 Connection、线程和关闭顺序，覆盖读 Slot/PRAGMA 初始化失败与释放失败。

### R2：关闭协调与请求准入不是同一个原子协议

`beginClose` 使用 Mutex，`beginCloseBlocking` 使用 synchronized，两者并未互斥，`closing` 也没有统一的可见性保证；同步 close 发现已有关闭直接 return。探针在阻塞写事务尚未释放时启动 closeAsync，再调用 close，后者已返回，而写任务与异步关闭都仍未完成。

关闭设置 closed 与 enter 检查/增加 inFlight 未共用同一锁，可在最后一次检查与计数增加之间发生“关闭看见 0 并释放，已准入请求随后增加计数”。回调内部 close 也没有拒绝，会等待自身退出。

要求：统一请求准入、停止准入与唯一关闭结果的同步边界；同步/异步关闭都等待同一真实完成结果，失败不能被后续调用吞掉；禁止回调内自关闭死锁；清理不随某个等待者取消而中断。补真实多线程 sync/async 混合关闭、在途/排队/准入交错、关闭失败共享及回调内关闭拒绝测试。不要仅在一个 runBlocking 线程启动若干很快结束的 async 就宣称覆盖竞争。

### R3：作用域保护可被原始驱动和 SQL 入口绕过

`RawReadScope.sqlDriver()` / `RawTransactionScope.sqlDriver()` 只在取得驱动时检查，随后返回无保护的 Slot 驱动。探针从 write 返回驱动后，在调用方线程执行 UPDATE 成功：同时绕过回调失效、固定线程、在途计数与事务入口。SQLDelight 生成 Query 同样可以长期持有这个驱动。

`queryRaw` mapper 未设置嵌套检测；公开 ResultSet 可取得 Statement/Connection；`updateRaw` 及原始驱动可直接执行事务控制语句，`rejectSavepoint` 仅匹配首个 token，注释前缀也可绕过。不能以这组 API 声称禁止 Savepoint、逃逸及跨线程。

要求：缩小仅用于内部接线/测试的原始 JDBC API 可见性，不能为测试新增无约束公共 SQL 通道。供 CT05 使用的生成查询执行必须在每次真实操作时校验作用域和线程，禁止返回未受保护的 Driver/Connection；事务控制权只归执行器。复用 JdbcDriver 的语句机制，不从零重写 SQL 引擎。测试须覆盖取得驱动/生成 Query 后逃逸与跨线程、原始入口嵌套，以及经允许入口尝试绕过事务控制，不能只测试 scope.update 本身。

### R4：数据库路径编码与建库/打开竞争保护失效

1. Factory 拼接 `jdbc:sqlite:file:$target?mode=ro` 未做 URI 编码。独立探针初始化 `literal%41.db` 成功，随后普通打开失败。
2. Initializer 以 `Files.exists` 后 JDBC 自动创建，失败无条件删除主库及 sidecar。受控交错：检查后由另一方创建有效库，本方建表失败，清理把另一方的有效库删除，探针结果为 true。
3. 只读验证后 Slot 使用默认可创建模式连接。受控交错：只读验证关闭时文件消失，普通 open 新建空库并返回执行器，违反正常启动不得建库。

要求：使用正确编码的 SQLite 文件 URI；普通打开的每条物理连接必须使用不创建文件的模式，不只依赖前置 exists。显式初始化原子取得新文件所有权（如 CREATE_NEW），仅清理本次确实拥有的失败产物，不能删他方已存在/竞争创建的库。检查实际连接上的必要版本/结构与模式，不把前一次检查视为永久保证。补特殊路径（空格、%、?、#）、并发初始化和验证后删除交错；不要求建立通用文件锁框架。

### R5：事务收尾失败会提交失败事务或掩盖错误

write 在 rollback 失败后仍无条件 `restoreAutoCommit(true)`。Xerial 会在切换自动提交时提交未结束事务。独立探针：真实写入 checkpoint=42，业务回调抛错，注入 rollback 失败，write 对外失败但库内 checkpoint 已是 42。

read 使用 `runCatching { commitTransaction() }` 丢弃失败。独立注入 read commit 失败，read 仍成功返回 10。finally 恢复自动提交失败还可能替换原业务异常/取消；取消分支先 rollback 再进入 catch 再次 rollback，收尾也重复。

要求：显式跟踪事务开始/提交/回滚结果，失败路径不能通过恢复 autoCommit 隐式提交；rollback 或必要状态恢复失败时使连接/执行器不可继续复用并可靠释放，停止后续操作，保留原失败（取消身份与传播语义保持）。读事务收尾失败必须可观察，不能报成功；提交结果不确定不能伪装为保证回滚。补 COMMIT、ROLLBACK、autoCommit 恢复失败的受控注入，直接断言库内状态及后续请求拒绝/安全行为。

### R6：持久化异常直接带出底层敏感文本

`ContextSqliteErrors.map` 拼接 SQLException.message，并把原 SQLException 留在 cause。独立查询故障探针中，完整异常链出现 `SECRET_SESSION_BODY_MARKER`。Factory 同样直接保留底层异常，未来 SQL 业务/参数错误不能据此声称脱敏。

要求：在持久化基础设施边界保留安全的操作名、类型/错误码和诊断信息，避免直接传播可能含正文/凭据的 SQLException 消息、cause/suppressed 链；保留取消语义。若需记录路径，要遵守 CT01 路径诊断与敏感配置边界。新增独特标记的真实/注入故障断言，检查 message、toString、完整 stackTrace/cause/suppressed，而非只检查顶层通用前缀。不引入全局复杂脱敏框架。
