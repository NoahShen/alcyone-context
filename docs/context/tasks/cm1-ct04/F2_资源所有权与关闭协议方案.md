### F2-R1 关闭发起者被中断后仍必须完成唯一清理（方案 §3 修订）

- 现状缺陷：同步 `close()` 发起者在 `awaitDrainedBlocking()` 被 `Thread.interrupt` 抛出 `InterruptedException`，立即发布共享失败且 `releaseAll()` 从未执行；在途写退出后重复 `close()` 只重抛历史异常，两条真实连接仍打开。`ContextSlot.close()` 中 `awaitTermination` 被中断同样在物理 `close()` 之前退出，且 `disposed=true` 阻断重试。
- 修订：**清理责任不可被中断取消**。同步发起者的等待改为「捕获 `InterruptedException` → 记录中断状态 → 继续等待在途归零 → 执行 `releaseAll()` → 完成后恢复中断标志并返回/抛出与资源终态一致的唯一结果」，绝不在仍有在途 JDBC 时抢关连接。`ContextSlot.close()` 必须保证：即使线程等待被中断，也仍执行物理 `connection.close()` 与线程终止（必要时 `shutdownNow`），完成后恢复中断标志；不得先置 `disposed` 而跳过物理 close。被中断调用者语义写入文档并测试（记录中断、清理照常、结果与真实终态一致）。
- 同步/异步等待者观察统一实际完成结果；`awaitBlocking`/`await` 的失败语义对齐。

### F2-R2 所有用户回调统一嵌套/关闭守卫（方案 §3 修订）

- 现状缺陷：`queryRaw` 的 `mapper` 是公开用户回调，但未置 `insideScopeBody`/`insideCallback`；mapper 内调用 `close` 时 `beginClose` 不拒绝，随后等待包含自身请求的 inFlight，真实 `SELECT 1` 复现死锁。
- 修订：`queryRaw` mapper 与 `write`/`read` 回调一致地设置嵌套/关闭守卫，`finally` 恢复；同步/异步关闭在任一用户回调内均具名拒绝且不死锁。属 F2 已承诺的回调关闭协议，不扩张到 F3 driver 逃逸/事务重构。

### F2-R3 正式测试排除提前清理与调度伪通过（方案 §4 修订）

- A03：`interceptDriver` 仅包住 Executor 构造，退出时辅助 `finally` 已把 recorded 连接全部关闭，后续 `executor.close` 与连接断言发生在兜底之外，不能证明生产清理。改为**构造、故障关闭、所有真实连接断言均在兜底清理之前**；明确每个资源的尝试次数与最终状态；验证多个关闭等待者看到同一失败结果。
- A04：`syncStarted.countDown` 发生在 `close` 调用之前，立即断言 `syncReturned` 不足以保证同步 close 真正进入等待分支；改为受控确认该调用**已处于等待或已返回**后再检查。
- A02：现仅验证 version 校验 `createStatement` 失败；另补**配置 PRAGMA（applyPragmas）执行阶段**故障与真实连接关闭断言，文案区分两阶段，不混用。

## 1. 目标语义（Architect §4.2 / §7 要求）

| 项 | 目标 |
| --- | --- |
| 资源获取顺序 | 写 Slot 先建立；读 Slot 依次打开；每个实际连接在应用持久化 PRAGMA 前完成版本/结构校验 |
| 失败释放顺序 | 任一步骤失败 → 逆序尽力释放**所有已取得**资源（线程 + 连接），保留主失败，清理失败以 suppressed 附加且不掩盖主失败 |
| 连接初始化失败 | 连接取得后（含 PRAGMA/校验阶段）失败，必须关闭该连接本身，不泄漏物理连接 |
| 单一准入/关闭协议 | 请求准入（enter）、停止准入、关闭结果使用**同一同步边界**；不出现「最后检查后放行、关闭见 0 即释放」的竞态 |
| 单一完成结果 | 同步 `close()` 与异步 `closeAsync()` 等待**同一次**真实关闭完成；失败对所有等待者可见，不被后续调用吞掉；重复调用幂等 |
| 在途确认 | 关闭必须等在途阻塞 JDBC 真正退出后才释放连接/线程；取消某个等待者不中断整体清理（NonCancellable） |
| 回调内关闭 | 回调内部调用 close 不得自死锁；要么拒绝并给出具名错误，要么有明确的免死锁路径 |
| 取消语义 | `CancellationException` 原样传播，不被包装成持久化异常 |
| 清理失败呈现 | 所有 Slot 关闭都被尝试；单个 close 失败不阻断其余资源释放；最终结果如实反映（不伪报释放成功） |

## 2. 资源所有权与释放顺序

**当前缺陷（R1）**：
- `ContextDatabaseExecutor` 先建 `writeSlot` 再 `openReadSlots`；后者失败只关已打开的读 Slot，未关写 Slot。
- `ContextSlot` 构造器先建 executor 再开连接/PRAGMA；连接取得后 PRAGMA/校验失败无 finally 释放。
- `disposeSlots` 遇首个 close 异常即停止，后续资源不关。
- Slot 先标 disposed 再等线程/关连接；等待线程超时后第二次 await 返回值被忽略。

**方案**：
1. 执行器用一个显式的资源登记列表（`resources: MutableList<AutoCloseable>` 或等价结构），每成功取得一个 Slot 立即登记；构造失败时按**登记逆序**逐个尽力 close，把清理异常 `addSuppressed` 到主失败。
2. `ContextSlot` 构造改为「先开连接，再在 try 内做 PRAGMA/校验；任何异常在 finally 关连接并停线程」，确保连接取得后失败不泄漏；构造异常时不得留下已启动的线程。
3. `disposeSlots` 改为遍历全部 Slot 逐个 `runCatching { close() }`，收集失败；全部尝试完后若有失败则以聚合异常或首个失败 + suppressed 呈现，绝不在中途 `return`/`throw` 跳过其余资源。
4. Slot `close()`：真正物理 close 只发生在「执行器已确认在途归零」之后；等待线程用同一超时语义，第二次 await 结果必须纳入结果判定（未终止则 shutdownNow + 再次等待，仍失败则记录清理失败）。

## 3. 单一准入 / 关闭协调协议

**当前缺陷（R2）**：
- `beginClose`（Mutex）与 `beginCloseBlocking`（synchronized）不互斥；`closing` 无统一可见性。
- 同步 close 发现已有关闭直接 `return`，不等真实完成；异步 close 的结果不会传给同步调用者。
- `closed` 置位与 `enter` 的 inFlight 增加未共用同一锁，存在「关闭见 0 释放，随后已准入请求增加计数」的窗口。
- 回调内 close 未被拒绝，会等待自身退出而死锁。

**方案**：
1. 设一个统一同步边界（单一锁，如 `ReentrantLock` 或 `synchronized(closeLock)`，**同步与协程两侧共用**）：在该边界内完成「检查 closed → 增加 inFlight」的准入，与「置 closed → 捕获/发布唯一关闭结果」的停止准入，二者原子互斥。
2. 维护唯一 `closing` 结果对象（如 `AtomicReference<CloseState>`：`inProgress/complete/failed` + 共享 `CompletableDeferred<Unit>`）；首个发起者负责执行清理并发布终态；其余调用者（无论 sync/async）一律等待同一结果。
3. `close()`（阻塞）在关闭未启动时自己执行清理并在返回前完成；关闭已在进行中时**等待**同一 `CompletableDeferred` 完成（阻塞式等待），绝不提前 `return`。失败在该次调用中重新抛出或经共享异常呈现，不被吞掉。
4. 请求准入在回调内（insideCallback）时拒绝并抛具名异常（避免自死锁）；关闭流程中进入的请求抛 `CLOSED`。
5. 取消隔离：清理执行体包在 `NonCancellable`；某个等待者被取消不影响真实清理与其它等待者。
