## 修复范围

1. **真实 v2→v3 migration**：用现有 v2 结构创建真实文件库（不得改写 `1.sqm`），保留 Node/Metadata/Event，执行正式 `VfsStateDatabase.file` 升级，核对 `user_version=3`、journal 表/索引与旧行。覆盖失败迁移不提交版本号或 journal 结构。
2. **journal 事务 CAS/闭态边界**：同事务关闭的 generation 冲突必须连同 Node/Event 回滚；CLOSED 后 diagnose/advance 必须拒绝，未知 operation 也明确失败；现有 begin/同 operationId 冲突保持。
3. **默认禁用与请求前拒绝**：无 journal 时 safeReplace/publishNew/native/copy move 成功路径与既有事件完全不变；明确组装的 journal begin 失败禁止对应外部写；只读、不支持、source/target 预检失败不得留下 pending journal。
4. **四类操作完整进度事实**：safeReplace/publishNew/native move 的 requested→observed→CLOSED，copy move 的 target write→source delete→CLOSED；每次失败诊断、CLOSED 后无 pending；覆盖 Storage 成功而状态提交失败后 pending 不丢。
5. **真实 SQLite+Local FS 与独立 JVM**：通过显式 Core/Persistence 组装在子进程真实执行四类文件操作，在 journal 已提交的检查点结束/强制终止进程，父进程重新打开真实 SQLite/Local FS，验证持久阶段与源/目标物理事实；至少覆盖四类操作各自外部写前、外部写后/状态关闭前，以及 copy move 的源删除前/后窗口。另证明 commit/close 回滚不会伪造成功事件。不得用同进程对象重建或 Storage Fake 冒充进程崩溃。
6. **显式只读 reconcile**：核对 pending、UNKNOWN/缺失源/目标、缺失 Node 和 CLOSED 排除；所有 reconcile 均不写 Storage、Node、Event 或 journal，不自动修复。测试可新增 `testFixtures`/测试 helper，但不得进入生产 main source set。
