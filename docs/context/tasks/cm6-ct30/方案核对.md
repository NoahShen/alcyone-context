## 1. 现状核对

| 主题 | 真实实现与接缝 | 当前缺口 |

## 2. D1～D6：故障恢复最小接缝（E04）

### 数据与阶段

新增 VFS 内部 operation journal（独立表，不改 Node/Event 语义）：

- `operation_id` UUID、kind（SAFE_REPLACE/PUBLISH_NEW/NATIVE_MOVE/COPY_MOVE 等实际接线子集）、source/target 逻辑 URI、storage/mount 身份、nodeId（已知时）、state、created/updatedAt、attempt、有限错误类别与诊断字段。
- 状态只表达事实边界：`PREPARED` → `STORAGE_MUTATING`（外部写前持久化）→ `STORAGE_COMMITTED`（已观察物理完成）→ `STATE_COMMITTED`/`CLOSED`；普通 `FAILED` 不可自动等同无 effect。未知/取消至少保留 `RECONCILE_REQUIRED`。
- Core 在现有 `StateBoundary` 内、外部写前用同一 SQLite 短事务持久意图，成功后标记物理完成，再在现有 pipeline 中提交 Node+Event+journal close。这里三表同事务；Storage 与 SQLite 仍不能原子，不虚构全局事务。
- 进度更新本身失败时停止后续外部写（若尚未开始）或返回 PARTIAL/UNKNOWN；不能忽略 journal 写失败继续裸操作。

### 重启与人工核对

- **不自动重放、不自动补偿、不自动删目标/源/临时文件**。重开只读取 journal，报告 `RECONCILE_REQUIRED`；外部 Storage stat/list 由显式 reconciliation 执行，核对源/目标存在性、类型、长度及 Node 当前映射。
- 自动可关闭仅限证据充分且状态无歧义的情况；否则保持待处理并给出操作ID、源/目标与已观察事实。目录整树 move 的部分完成不能仅凭根文件存在自动判成功。
- 普通启动不执行修复，不把历史 PARTIAL 当成功 Event，不向实时订阅者补造事件。若显式 reconcile 真修改 Node/Event，必须另走正常提交，并返回恢复结果。

### 所有权与并发

- 同一 VFS Runtime 单写者，所有 journal 状态迁移与 VFS 写操作共用 `StateBoundary`；同一 `operation_id` 才能推进，CAS/旧代数防过期恢复者覆盖。
- **不承诺多进程写者/恢复者**；状态库单连接与既有“无跨进程独占检测”不变。显式恢复入口需进程级所有权/占用锁，若接 Standalone，必须先单独裁定锁协议；首版组件不接生产。
- 正常 close 先禁止新操作并 drain；已接受操作的 journal 在退出前如实收尾，不删除待核对记录。硬杀进程只通过独立进程测试验证记录仍在，不模拟人工异常后声称所有物理状态已知。

### 写集合（建议 B1）

- `vfs/core`：internal/public-core `RecoveryOperation` DTO、阶段机、`RecoveryJournal` Port、在选定的 safeReplace/publishNew/moveByCopy 外部写点接线；先不接公共 `Vfs` 恢复 API。
- `vfs/persistence`：`Recovery.sq`、schema migration、SQLite journal repository、事务扩展。
- `integration-tests/vfs`：真实 SQLite+Local FS 的每个阶段故障点与独立进程重开；跨 Mount 目标写后/删源后 Registry 失败、重复启动不自动重放。

**最小范围风险**：若把目录 move、普通 write/delete 全接入，会显著扩大状态机。建议 CT30 先覆盖 safeReplace、publishNew、文件 native/copy move；目录 move 明确保留原 PARTIAL，不宣称全操作恢复。是否可接受需 D2 裁定。

## 3. D7～D13：可靠 Event Consumer（E05）

### 序号与游标

- 现表 UUIDv7/time 不足以表达提交顺序（同批、时钟回退、UUID 实现均不可当序列）。建议新增 `event.sequence INTEGER PRIMARY KEY AUTOINCREMENT` 的迁移（保留 event_id 唯一），消费者游标为单调 sequence；旧数据迁移按现有 rowid 一次性编号，编号后不可改。新增索引支持 `sequence > ? ORDER BY sequence LIMIT ?`。
- `consumer_cursor(consumer_id PRIMARY KEY, last_sequence, updated_at)`；消费者首次启动默认从 sequence 1（含历史）开始，还是只从创建时之后开始必须显式配置，不隐式丢历史。建议默认 `EARLIEST`，提供显式 `LATEST`。
- 读批与处理不应长期持 SQLite 写事务：单写者边界内读固定有界批 → 释放 DB 锁 → 调 Consumer → 成功后同一 SQLite 短事务推进游标。崩溃于处理完成后、游标提交前会重投，这是 **at-least-once**。
- 一批游标只有批内全部处理成功才推进；失败停在当前 sequence，有限退避后重试，不跳过 poison event。无自动死信/跳过失事件；重试次数/退避有界可配置，停止状态可查询。Consumer 必须按 event ID 幂等，本组件不承诺 exactly-once。
- 外部副作用与游标不能跨系统原子；若要副作用+进度同库原子，另提供 consumer-managed transaction hook，不把普通 callback 伪称原子。

### 调度、背压与关闭

- 每 consumer 单协程串行拉取/处理，批大小有界（建议默认100、可配置1..1000）；SQLite 读只持短锁，慢 Consumer 不阻塞 VFS 写，也不依赖有界实时 Channel。
- 空闲采用可取消轮询（建议默认100ms），可叠加提交后 wakeup hint，但 hint 只是提示，丢了仍靠轮询；多个 consumer 各自独立进度。
- 启动时先读持久游标并追赶 backlog，再持续轮询；不是重放实时 Flow。关闭停止领取新批，等待已领取 Consumer 返回并提交其进度；超时/取消不提交未完成批，下批重启重复。普通 Consumer 异常隔离重试，CE 不吞，Error 不捕获。
- 同一 consumerId 进程内单实例；多进程同名消费者不在支持范围，需额外 lease/fencing 才能开放。事件保留/清理策略本版不做，不能清理未消费事件。

### 写集合（建议 B2）

- Core：EventRecord sequence、只读 `EventLogReader`、`ConsumerCursorStore`/runner DTO；persistence：migration、批量查询、游标读写；独立组件 `ReliableEventConsumer`。
- 组件构造/start/runOnce/close 供宿主显式接线，**默认不接 `AlcyoneVfs.create`、不改现有 subscribe**。Runtime 公共 API/生产默认装配另列 D13。
- 测试：真实 SQLite 重启追赶、实时通知丢失仍可靠消费、处理成功后游标前崩溃重复、失败不推进/重试、同毫秒/乱时钟按 sequence、批原子进度、背压、关闭与独立进程。

## 4. D14～D20：Local FS 原子发布

### 最小增强

- 保持同目录 temp（保证 same-filesystem）；`safeReplace` 完整写入+file fsync+长度/类型确认+ATOMIC_MOVE，**rename 成功后 fsync 目标父目录**再返回；`publishNew` 同样 file fsync+fileKey+hard link+父目录 fsync。父目录目录项是 rename/link/unlink 的共同持久性边界。
- 临时文件清理 unlink 后也需目录 fsync，失败如实 effect PARTIAL/UNKNOWN；不得因清理失败把已成功目标删回。旧目标在 rename 前失败保持；rename 后失败保留新目标，绝不恢复旧文件。
- `publishNew` 硬链接成功后 temp unlink 是清理而非提交；目标已存在由 link 原子拒绝。tempName 是调用者提供唯一名，首版只删除 fileKey 与本次创建一致的自有 temp；重启 orphan 不自动乱删，由明确前缀/所有权记录/人工清理处理。
- `FileChannel.open(parent, READ).force(true)` 在 Linux通常有效、macOS可能返回 EINVAL/不支持；**同目录 ATOMIC_MOVE 与 dir fsync 是不同能力**。建议新增 `durableDirectorySync` capability 与启动实测探测；不能 dir fsync 时：safeReplace/publishNew 对“崩溃持久”模式显式拒绝，还是保留现有原子可见性但标 `ATOMIC_NOT_DURABLE`，由 Architect 决定。建议能力拆分，默认不破坏 macOS现有功能，但不宣称 durable。
- 目录 fsync 不证明所有父目录创建、挂载/磁盘硬件 flush 或完整系统崩溃持久；测试记录实际平台能力，不跨平台保证。

### 写集合（建议 B3）

- 仅 `LocalFsStorage`、core `StorageCapabilities`（若批准）、对应 storage/integration 测试；Backup/MemoryMap 不改算法，复用已有端到端。
- 故障点：temp write/fsync、confirm、rename/link 前后、dir fsync、stat、temp cleanup；旧目标/新目标/源输入/临时文件逐项断言。
- 独立进程写后正常重开只证明重启可见；强制 kill 后重开可验证已设计故障点，**真实断电/内核崩溃 not-run**，不能伪称 fsync 已被断电验证。
