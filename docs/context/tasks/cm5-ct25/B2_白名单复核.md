## 1. 独立事实与 expected 链终裁

### 1.1 原裁定与 B1 原子提交确实冲突

B1 `DreamingCommitter.commit` 已批准且保持以下权威行为：

1. 写事务内 `readCheckpoint()` 必须等于 `context.expectedCheckpoint`。
2. Raw/Pending 成功后，`casUpdateCheckpoint(expected,lastTurnId)` 必须恰更新一行。
3. 事务提交即推进数据库 Checkpoint；成功批之间没有延迟到 run 末统一提交的机制。

因此首批 `(C0,T1)` 成功后，数据库水位已经是 `T1`。若同 run 第二批仍传 `C0`，事务内核对与 CAS 都会失败。原 §2“每批 expected 均保持 C0”与 D12/D13 的实际提交语义及 D18 的提交后 CE 恢复语义不能同时成立，属于**必要勘误，不是可选实现建议**。

### 1.2 强制澄清：固定 U，内存逐批承诺 expected

**APPROVED WITH CLARIFICATION**：D2/D12/D18 统一按以下规则执行，并取代原 §2 中“每批 expected 均保持 C0”：

```text
每个 run 开始时，在同一个固定范围 ReadContext 读取 C0/U：
  C0 = 权威 dreaming checkpoint
  U  = 权威 maxTurnId（本轮固定上界）

expected = C0
对每个串行批次：
  process(DreamingBatchContext(expected, U, turns))
  仅当 Processor 成功返回且 outcome.lastTurnId == turns.last().id：
      expected = outcome.lastTurnId

成功批之间不由 Coordinator 另起普通 ReadContext 重读 checkpoint；
每批 Committer 仍必须在写事务内 readCheckpoint==expected 并 CAS 推进。
```

- 首批 `expected=C0`；第 `i+1` 批 `expected=第 i 批已提交并校验的 outcome.lastTurnId`，即前批实际 Turn 尾 ID，不按 ID 连续性推算。
- `U` 在同一 run 的全部批次保持不变；`lastTurnId` 始终是本批实际尾 ID，满足 `expected < firstId <= lastTurnId <= U`。
- `expected` 只作为 Coordinator 的 run 局部内存承诺链推进，不跨 run 缓存，也不以 `partialResult` 代替数据库权威状态。
- 普通 Evidence/Reflection/Commit 失败时当前批不提交，Coordinator 中止并保留此前成功批的 partial；不调用后续批。
- `rawCount>0` 时通知发生在 COMMIT 后。普通通知异常脱敏记录后仍返回本批成功，承诺链继续前进；通知 CE 原样传播，run 立即中止，不把该批加入内存 partial，也不继续后续批。
- 通知 CE 前该批 Raw/Pending/Checkpoint 已提交。下一 run 必须重新从数据库读取权威 C0/U，只处理新 C0 之后的 Turn，**不得用上一 run 的 partial 或旧 C0 重做已提交批**。

该澄清只修正 B2 Coordinator 传参及测试预期，不要求修改 B1 `DreamingCommitter`、Reflection、Evidence 或 Schema。

## 4. B2 必须补齐的有效测试

以下为最低验收矩阵，不以“编译通过”或 fake 返回成功替代真实 SQLite 断言。

### 4.1 Context 与 Coordinator 承诺链

1. **唯一入口与范围防御**：源码/调用均只有 `process(DreamingBatchContext)`；拒绝空 turns、重复/降序 ID、`firstId<=expected`、负 expected/U、`lastId>U`；接受含 ID 空洞但严格升序且范围合法的 turns。
2. **至少三批真实 SQLite 成功链**：真实 Coordinator + `LlmDreamingBatchProcessor` + 真实 `DreamingCommitter`/SQLite，使用含空洞 ID，断言上下文 expected 依次为 `C0,T1,T2`、所有 upper 均为固定 U、每批 last 为实际尾 ID；最终权威 checkpoint 为最后批尾，Raw/Pending 数量及计数正确。
3. **无批间普通重读**：上述多批链断言固定范围只读取一次 C0/U，成功批之间 Coordinator 不另读 checkpoint；同时允许并验证每个 Committer 写事务内的权威 read/CAS，不能用“总 checkpoint read==1”错误否定必要事务核对。
4. **固定 U 与下一 run**：run 中新增高于 U 的 Turn 不进入当前链；下一 run 从数据库新 C0 开始处理，不能从旧内存 expected/U 继续。

### 4.2 顺序、通知与失败

5. **严格处理顺序与真实计数**：按 Evidence→Reflection→Commit→通知记录顺序；通知回调内读取真实 SQLite，证明调用时 Raw/Pending/Checkpoint 已提交；`discoveredTopics` 来自最终 Evidence Topic 数，`generatedMemories` 来自 Commit rawCount，last 来自实际批尾。
6. **通知恰好一次/零结果**：每个 `rawCount>0` 的已提交批调用 `onRawCommitted()` 恰一次；0 Topic/0 Insight 仍 CAS 推进且 0 Raw/Pending、0 通知。多批中不得按 run 聚合后重复通知。
7. **普通通知异常**：注入含敏感正文的普通异常，断言固定脱敏 warning（建议固定事件 `dreaming.organization.wakeup.failed`）、日志无异常正文/堆栈敏感内容，本批 outcome 成功、数据库保留且不重试/不重复保存；后续批按已提交 expected 继续。
8. **通知 CE 与权威恢复**：注入指定 CE，断言同一实例原样抛出、run 立即中止且无后续 Processor 调用；本批提交保留但本次 partial 不含本批。下一 run（至少覆盖复用同一 Coordinator）重读权威 checkpoint，不重复首批 Raw/Pending，不再次处理已提交 Turn。
9. **三类提交前失败分别覆盖**：Evidence、Reflection、Commit 各至少一例；当前批 0 通知、0 新 Raw/Pending、checkpoint 保持前批尾。经真实多批 Coordinator 验证普通异常映射 `BATCH_PROCESSING`、此前成功批 Raw/Pending/Checkpoint 与 partial 均保留、后续批不执行。Commit 故障须由真实 SQLite 事务回滚证明，不得只 fake committer 抛出。
10. **Topic adapter 与既有回归**：适配后仍断言 final Topic 计数、0 memories、实际批尾、Stage 失败传播；保留 CT22 分页/预算/取消/关闭/partial 与 CT23 历史组件测试，不能用新全链测试替换旧覆盖。

Evidence/Reflection 可由窄 internal seam fake，LLM 也可使用 Fake `LlmClient`；但完整链中的 Coordinator、`LlmDreamingBatchProcessor`、`DreamingCommitter` 与 SQLite 必须为真实实现。普通失败、CE 与“已提交但 partial 未更新”必须区分断言。
