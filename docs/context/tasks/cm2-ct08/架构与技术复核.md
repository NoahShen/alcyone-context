## 3. 阻断缺陷 N3（必须修复）

**`LlmBudget.estimate` 未校验 `TokenEstimator` 返回值非负，负数可绕过预算或破坏饱和算术。**

Architect 反例探针：`.local/validation/cm2/architect/ct08-b1/runtime/NegativeEstimatorProbeTest.kt`

两例均实际失败（均为“期望异常但成功返回”）：

1. `promptTokens = -1` 时，`estimatedInputTokens = -1`：
   - `-1 > task.maxInputTokens` 为 false，输入预算检查通过；
   - `requiredTotalTokens = -1 + 3000 + 0 = 2999`，也小于 64,000，容量检查通过；
   - 结果：自定义 TokenEstimator 返回负数时，本地预算完全失效。
2. `promptTokens = 1, schemaTokens = Int.MIN_VALUE` 时：
   - `saturatedAdd(1, Int.MIN_VALUE.toLong())` 的溢出保护条件对负右值失效，但结果被后续饱和路径推到 `Long.MAX_VALUE`；
   - 当前会抛 `LOCAL_BUDGET_EXCEEDED`，属于错误分类：这是非法估算器输出，应在任何预算算术前抛 `INVALID_REQUEST`。

**口径补充**：探针针对 `estimate()` 断言“应抛异常”是修复后的期望；现状失败证明它未拒绝非法负值。真实业务绕过路径是 `requireWithinBudget(promptTokens=-1)`，其 `estimatedInput=-1`、`requiredTotal=2999`，两条预算检查均通过。修复验收必须同时覆盖 `estimate()` 与 `requireWithinBudget()` 双入口。

### 修复要求

1. 在 `LlmBudget.estimate` 中，对 `estimator.estimatePrompt(...)` 与 `estimator.estimateSchema(...)` 的返回值做**前置非负校验**。
2. 违反时抛 `LlmException(INVALID_REQUEST)`，消息包含字段名（例如 `estimator.estimatePrompt` / `estimator.estimateSchema`）与“non-negative”，不回显请求/Schema 原文。
3. **不得把负数 clamp 为 0**：那是掩盖实现错误，必须 fail closed。
4. 正常估算值 0 仍合法，不能拒绝。
5. 新增正式回归：
   - prompt 为负 → 拒绝；
   - schema 为负（含 `Int.MIN_VALUE`）→ 拒绝；
   - 0 值合法；
   - 大正数仍饱和并触发 `LOCAL_BUDGET_EXCEEDED`。
6. 该修复仅限 B1，不得顺带实现 B2/B3/B4。

### 9.2 期限、重试与取消语义

1. 总 deadline 覆盖全部请求尝试、响应读取和退避等待；每次尝试前与退避前重新计算 remaining。
2. `remaining <= 0` 时不再发起请求，返回 `TIMEOUT`，attempts 为实际已执行请求数。
3. 自建 HttpClient 安装 `HttpTimeout`，逐请求设置 request/connect/socket 超时；单次 request timeout 为 `min(profile.requestTimeout, remaining)`。
4. 注入 HttpClient 未安装 `HttpTimeout` 时跳过逐请求超时，兼容 B2 注入用例；总 deadline 仍约束循环。
5. 传输异常区分三类 Ktor/JDK 超时并归 `TIMEOUT`；其他传输失败归 `NETWORK`；两者在 B3 中均可重试。
6. 429 额度耗尽优先于 Retry-After，归 `QUOTA_EXCEEDED` 且不重试；429 只有有效 Retry-After 或明确限流标记才可重试；无安全信号单次失败。
7. `Retry-After` 支持非负整数秒与 RFC1123 HTTP-date，负差按 0；无效值按退避；大于 remaining 立即失败，不截短提前重试。
8. 退避为 `min(1s * 2^(n-1), 10s)`，±20% jitter，且加 jitter 后仍不超过 10s；实际等待不超过 remaining。
9. `CancellationException` 在请求中或退避中原样传播，不包装、不重试；未使用 `withTimeout` 混淆总期限与调用方取消。
10. 未实现 B4 状态机/在途跟踪/生命周期接线，未实现 B5 日志统计。

### 10.2 取消、关闭与 Runtime 生命周期语义

1. `KtorLlmClient` 的 `state`、`inFlight`、`closeOutcome` 由同一把普通锁保护；持锁路径无挂起调用。
2. `complete()` 先 `ensureActive()`，再用 `coroutineScope { async(LAZY) }` 创建结构化子任务；准入、登记与关闭封闭同锁，移除只发生在 `invokeOnCompletion`。
3. `RUNNING` 之外的新调用先被拒绝为 `ContextLifecycleException(CLOSED)`，发生在任务配置、格式、schema、预算和 HTTP 之前；未启动的 LAZY 子任务被取消，不产生请求。
4. 调用方取消和在途关闭取消均传播 `CancellationException`，不包装为 `LlmException`，也不转换为 `CLOSED`。
5. `closeAsync()` 是唯一清理入口。owner 在 `NonCancellable` 中取消在途、循环等待 `inFlight` 为空、再关闭自建 HttpClient；失败也发布 `CLOSED`，共享结果成功/失败均覆盖，重复关闭重抛同一异常实例；等待者自身取消只放弃等待，不影响 owner。
6. 注入的 HttpClient 不由 `KtorLlmClient` 关闭；关闭后底层注入 client 仍可直接使用的测试保留。
7. `AlcyoneContextImpl.performStart` 按 `executor → vfs → llm` 构造，三者成功后才发布 `RUNNING`；启动失败逆序释放。
8. `releaseResources` 按 `llm → vfs → executor` 释放；LLM 清理失败不阻断 VFS/executor，主失败保留，其余失败 `addSuppressed`；未新增 `ReleaseTarget.LLM`。
9. Context 同步/挂起关闭仍复用 CM1 的 `NonCancellable` 与共享等待协议，client 只暴露挂起 `closeAsync()`。
10. 未实现 B5 日志、统计、重定向、全量 A08 或全量 `./scripts/check`。
