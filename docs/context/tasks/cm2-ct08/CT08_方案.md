## i. Architect 裁定（2026-10-29，原文保留，最高依据）

本节取代草案中的冲突表述。依据技术实现设计 §3.2～§3.5；Lead 须同时重写本方案与 CT08 任务书的对应正文和验收映射，不保留相互矛盾的执行要求。此为设计修订授权，尚未批准生产编码。

1. **配置和预算**：沿用冻结的 Profile/Task 两层结构。Profile 包含 baseUrl、apiKey（支持既有 ENV 展开）、model、contextWindowTokens、jsonMode，以及可省略的 HTTP 超时/重试覆盖；Task 包含 profile、maxInputTokens、maxOutputTokens、totalTimeout。不得以 Task→字符串路由替代预算配置，也不擅自把 apiKeyEnv 定为唯一入口。配置不热更新；Key 解析后只在必要的私有配置/请求头中持有，所有打印/异常脱敏。直接 Kotlin 配置与 YAML 同样校验，先取得自有集合快照再校验并使用同份快照。不要虚称凭据从未进入任何对象。
2. **超时与重试**：采用冻结默认 connectTimeout 10s、requestTimeout 180s、socketTimeout 120s、Task totalTimeout 360s、maxAttempts 2（含首次），退避初始 1s、上限 10s、轻量 jitter。允许有限配置覆盖，maxAttempts 1..5 可用；删除任务书“固定常量不可配”及 Profile 60s 总期限要求。实现单调总期限覆盖 HTTP、响应读取与所有退避；只重试可判定的暂时错误，包含 408/临时429/500/502/503/504，不笼统重试所有5xx或额度耗尽429。有效 Retry-After 优先，不能因截短等待而提前重试；秒数和HTTP日期形式的处理/无效值回退须写清。不得增加业务层重试或自动换Profile。
3. **responseFormat**：Profile jsonMode 为协议能力/选定模式，LlmRequest.responseFormat 必须一致；不一致在发送前具名 INVALID_REQUEST，不静默覆盖或降级。业务提供 schema；允许既有 LlmRequest 末尾增加 schema:String?=null，并注明仅保持既有 Kotlin 源码调用兼容，不宣称 JVM ABI 不变。缺失/非法schema属请求错误而非INVALID_RESPONSE。业务Schema语义与证据校验仍在Core业务层；Adapter须拒绝空输出、截断、拒答和非法响应，不能自动修复。
4. **异常归属**：LlmException/LlmErrorCode 放既有 core.llm 旁，作为 Port 的可分类错误，继承 api.ContextException；Runtime使用它们，Core不得依赖Runtime，也不得按message字符串分类。分类按冻结 §3.5，并区分本地预算超限与Provider context-limit错误。关闭后新调用可用既有ContextLifecycleException(CLOSED)。不新增重复LlmClient或API模块枚举。
5. **取消**：否决将关闭触发的在途取消改写为普通 CLOSED 失败。调用方取消和 Runtime 关闭导致的在途取消均传播 CancellationException（冻结设计与ContextException契约一致），不重试、不包装；自身总期限超时才映射TIMEOUT，外部取消同时发生时优先保留取消。closed&&isActive不足以替代该契约，不采用草案A06④。在途准入/登记与关闭封闭必须同锁；登记后再启动任务，完成后才移除；共享关闭等待真实退出且不被单个等待者取消。
6. **关闭验收**：不可要求HTTP服务器放行响应后客户端才可关闭——客户端取消网络请求可先于远端处理完成。用受控客户端finally/实际Job完成屏障证明close等待本地真实收尾；stub用于证明到达请求、取消后不重试及无新请求。计数只作辅助，不能代替完成证据；不得重新引入通知快照/准入竞态。
7. **预算验收**：估算完整messages、角色/协议开销、schema；校验Task输入预算以及输入+输出保留+安全余量不超过Profile容量，余量只计一次。Estimator是可校准的保守估算，不是已证明的token上界。CT08只做发送前校验，不做CT10折半/数据选择；输出token请求覆盖的优先级与合法范围写清。
8. **其余决定**：允许Runtime应用catalog已有serialization插件；Core不引Ktor/JSON传输实现。允许Runtime单个HttpClient与JDK本地stub测试，但每请求独立凭据/路径，不通过全局默认Authorization串Key；禁止凭据跨重定向泄露。A01断言ContextConfig.llm而非AlcyoneContext不存在字段。保留两Profile路径/Key/model交叉断言、真实请求次数/Retry-After到达间隔、实际日志捕获和编译类路径证据。Provider返回的finishReason/requestId/code等也是不可信内容，日志仅保留明确安全字段，不能无界回显任意原值。

## a. 配置契约（Profile / Task 两层）

```yaml
context:
  llm:
    safetyMarginPercent: 20            # 可省略，默认 20，0..100
    profiles:
      extraction:
        baseUrl: ${LLM_BASE_URL}       # 支持既有 ${ENV} 展开；也允许字面量
        apiKey: ${LLM_API_KEY}         # 支持既有 ${ENV} 展开；不要求必须是 ENV
        model: some-model
        contextWindowTokens: 64000
        jsonMode: json_schema
        connectTimeoutSeconds: 10      # 可省略
        requestTimeoutSeconds: 180     # 可省略
        socketTimeoutSeconds: 120      # 可省略
        maxAttempts: 2                 # 可省略，1..5（含首次）
    tasks:
      EXTRACTION:
        profile: extraction
        maxInputTokens: 12000
        maxOutputTokens: 3000
        totalTimeoutSeconds: 360       # 可省略
```

**语义**：`LlmTask → Profile → (baseUrl, apiKey, model, contextWindowTokens, jsonMode)`；Task 持有预算与总期限，Profile 持有协议能力与 HTTP 参数。`LlmTask` 键按枚举名**大小写不敏感**匹配（`extraction`/`EXTRACTION` 等价），归一化后重复 → `INVALID_CONFIG`。

**Profile 字段**

| 字段 | 类型 | 默认 | 约束 | 错误码 |
| --- | --- | --- | --- | --- |
| `baseUrl` | String | 必填 | 绝对 http(s)；**禁止 userinfo / query / fragment**；可含 path | `INVALID_CONFIG`（不打印 URL） |
| `apiKey` | String | 必填 | 支持 `${ENV}` 展开；展开/字面量后非空白 | ENV 未定义或空白 → `MISSING_ENV`（只报 ENV 名）；字面量空白 → `INVALID_CONFIG` |
| `model` | String | 必填 | 非空白 | `INVALID_CONFIG` |
| `contextWindowTokens` | Int | 必填（不猜测 Provider 容量） | 1..10_000_000 | `INVALID_CONFIG` |
| `jsonMode` | enum | 必填 | `json_schema` / `json_object` / `prompt_only`（大小写不敏感） | `INVALID_CONFIG`（列出三个合法值，不回显原值） |
| `connectTimeoutSeconds` | Int | 10 | 1..300 | `INVALID_CONFIG` |
| `requestTimeoutSeconds` | Int | 180 | 1..3600 | `INVALID_CONFIG` |
| `socketTimeoutSeconds` | Int | 120 | 1..3600 | `INVALID_CONFIG` |
| `maxAttempts` | Int | 2 | 1..5（含首次，1 = 不重试） | `INVALID_CONFIG` |

**Task 字段**

| 字段 | 类型 | 默认 | 约束 | 错误码 |
| --- | --- | --- | --- | --- |
| `profile` | String | 必填 | 必须存在于 `profiles` | `INVALID_CONFIG` |
| `maxInputTokens` | Int | 必填 | 1..10_000_000 | `INVALID_CONFIG` |
| `maxOutputTokens` | Int | 必填 | 1..10_000_000 | `INVALID_CONFIG` |
| `totalTimeoutSeconds` | Int | 360 | 1..3600 | `INVALID_CONFIG` |

**跨字段静态校验**（不涉及估算）：`task.maxInputTokens + task.maxOutputTokens ≤ profile.contextWindowTokens`，否则 `INVALID_CONFIG`（路径指向该 Task）。

**校验规则表**

| 规则 | 错误码 | 消息形态（不含值） |
| --- | --- | --- |
| `context.llm` / Profile / Task 内未知键 | `UNKNOWN_FIELD` | `context.llm.profiles.<name>.<key> is not a supported field` |
| `context.llm` 存在但无 `profiles` 或为空 | `INVALID_CONFIG` | `context.llm.profiles is required` |
| Profile 名为空白 | `INVALID_CONFIG` | `context.llm.profiles has a blank name` |
| 必填缺失 / 空白 | `INVALID_CONFIG` | `context.llm.profiles.<name>.<field> is required` |
| `baseUrl` 非 http(s) 或含 userinfo/query/fragment | `INVALID_CONFIG` | `...baseUrl must be an http(s) URL without userinfo, query or fragment` |
| `apiKey` 的 ENV 未定义 / 展开空白 | `MISSING_ENV` | `context.llm.profiles.<name>.apiKey refers to an unset environment variable: <ENV>` |
| `jsonMode` 非枚举 | `INVALID_CONFIG` | `...jsonMode must be one of json_schema, json_object, prompt_only` |
| 数值越界 | `INVALID_CONFIG` | `...<field> must be in <min>..<max>` |
| `tasks` 键非 `LlmTask` | `INVALID_CONFIG` | `context.llm.tasks.<name> is not a known LLM task` |
| `tasks` 指向不存在 Profile | `INVALID_CONFIG` | `context.llm.tasks.<TASK>.profile refers to an unknown profile: <name>` |
| 预算静态不自洽 | `INVALID_CONFIG` | `context.llm.tasks.<TASK> exceeds the profile context window: <profile>` |
| YAML 重复键 | 既有机制 | SnakeYAML `setAllowDuplicateKeys(false)`（不改） |

**未配置 `context.llm`**：`ContextConfig.llm == null`，CM1 ingestion-only 行为不变；不构造 HttpClient、不发起任何请求、启动不失败。

**快照与密钥**：
- 加载期一次性展开 ENV 并把 Key 存入 `LlmProfileConfig` 的**内部字段**；调用期只用该快照，不重复读 `System.getenv`，**配置不热更新**（改动需重启）。
- 明确声明：Key 会存在于内存配置对象与请求头中（不虚称“从未进入任何对象”）；它**不出现在** `toString`/日志/异常/诊断中，也不进共享 HttpClient 的默认 Header。
- 加载完成后取**自有不可变副本**（`profiles`/`tasks` 各自 `toMap()`）再对副本校验，YAML 解析结果之后的修改不影响实例。
- **直接 Kotlin 配置与 YAML 同等校验**：校验逻辑放在 `LlmConfig` 的自校验（`init` 调同一 `validateLlm(...)`）；`AlcyoneContextFactory.build` 先 `contextConfig.llm?.ownedCopy()` 再校验，与既有 `ownedVfsConfig` 同模式；Kotlin 路径下 `apiKey` 视为已解析值（非空白即可），不做 ENV 展开。

## b. Token 预算与 Estimator

- `TokenEstimator` 既有 Port（`estimateText` / `estimatePrompt` / `estimateSchema`）不改签名；CT08 新增实现 `ConservativeTokenEstimator`（Core，纯 Kotlin）。
- 估算口径（保守、可校准，**不是已证明上界**）：
  - ASCII 码点：`ceil(ascii / 3)`（≈3 字符/token，偏保守）；
  - 非 ASCII 码点（CJK/emoji）：每码点 **3** tokens；
  - `estimatePrompt` = `Σ (estimateText(role) + estimateText(content)) + perMessageOverhead(8) * messages.size + protocolOverhead(16)`：**role 按实际字符串长度估算**，不用固定角色开销替代任意 role；
  - `estimateSchema(null)` = 0，否则与 `estimateText` 同规则；`estimateText("")` = 0。
- 发送前双条件（Runtime Adapter，**CT08 只做发送前校验，不做数据选择**）：
  1. 输入预算：`estimateInput = estimatePrompt(messages) + estimateSchema(schema)`，要求 `estimateInput ≤ task.maxInputTokens`；
  2. 容量：`estimateInput + outputReserve + margin ≤ profile.contextWindowTokens`，其中 `outputReserve = effectiveMaxOutputTokens`（§d），`margin = ceil(estimateInput * safetyMarginPercent / 100)`。
- **安全余量只计一次**：Estimator 返回值不含余量；余量只在容量条件里按输入估算加一次，输出保留不再叠加余量。
- **溢出安全（§m 2）**：估算、`margin`、`estimateInput + outputReserve + margin` 全部用 `Long` 或受检运算，**不得**让 `Int` 溢出绕过限额；`estimateText` 内部对超长输入饱和到 `Int.MAX_VALUE`，预算比较用 `Long` 兜底。
- 任一条件不满足 → `LlmException(LOCAL_BUDGET_EXCEEDED)`，**不发起 HTTP**（见 §l 待确认命名）。
- Provider 返回 context-length 类错误 → `CONTEXT_LIMIT_EXCEEDED`（与本地超限分开；不据此把 Turn 标 failed —— 那是 CT11 的业务规则）。

## d. Task→Profile 路由、请求构造与 jsonMode 一致性

- 路由：`request.task` → `tasks[task]`（缺失 → `LlmException(CONFIGURATION)`，消息含 task 名）→ `profiles[profile]`（加载期已校验存在，运行期再查兜底，缺失 → `CONFIGURATION`）。**不自动换 Profile、不自动降级。**
- **`responseFormat` 一致性（发送前）**：`request.responseFormat` 必须等于 `profile.jsonMode` 映射的枚举（`json_schema→JSON_SCHEMA`、`json_object→JSON_OBJECT`、`prompt_only→PROMPT_ONLY`），否则 `LlmException(INVALID_REQUEST)`，不静默覆盖。
- **schema 归属**：`LlmRequest.schema` 字段由 **B2** 添加（B1 不做请求协议，§m「B1 实施边界」）；下述 schema 校验与使用均在 B2 落地。
- **schema（发送前）**：`jsonMode == json_schema` 时 `request.schema` 必须非空白且能被 `Json.parseToJsonElement` 解析；缺失/空白/非法 JSON → `INVALID_REQUEST`（**不是 `INVALID_RESPONSE`**），不发起 HTTP。`json_object` / `prompt_only` 忽略 `schema`（不发送）。
- 请求：`POST <baseUrl 去尾部 '/' > + "/chat/completions"`（若 baseUrl 已以 `/chat/completions` 结尾则不重复追加）。
- Header（**逐请求**）：`Authorization: Bearer <该 Profile 的 Key>`、`Content-Type: application/json`、`Accept: application/json`；**不设置 HttpClient 默认 Authorization**，`followRedirects = false`（禁止凭据跨重定向），`expectSuccess = false`。
- Body（OpenAI 兼容）：

| 字段 | 取值 |
| --- | --- |
| `model` | `profile.model` |
| `messages` | `[{role, content}]`，原顺序不动 |
| `max_tokens` | `effectiveMaxOutputTokens` |
| `response_format` | `json_schema` → `{"type":"json_schema","json_schema":{"name":<task 名小写>,"strict":true,"schema":<解析后的 schema>}}`；`json_object` → `{"type":"json_object"}`；`prompt_only` → **省略该键** |

- `effectiveMaxOutputTokens` 优先级与合法范围：`min(request.maxOutputTokens ?: task.maxOutputTokens, task.maxOutputTokens)`；`request.maxOutputTokens != null` 时必须 `≥ 1`，否则 `INVALID_REQUEST`（业务只能下调、不能超过 Task 预算）。
- 响应解析：2xx → 取 `choices[0].message.content`（string）与 `usage`、`finish_reason`；**不修复、不猜测**、不从 Markdown 围栏提取 JSON、不读取部分结果。
  - 空 body / 非 JSON / 缺 `choices[0].message.content` 或为空白 → `INVALID_RESPONSE`；
  - `finish_reason == "length"` → `OUTPUT_TRUNCATED`；明确拒答（`finish_reason == "content_filter"` 或非空 `refusal`）→ `MODEL_REFUSAL`；
  - body 内 `error.code`/`error.type` 指示 context length → `CONTEXT_LIMIT_EXCEEDED`；
  - `usage` 缺失 → `LlmResponse.usage = null`（未知，**不填 0**）；部分缺失时对应字段保持 `null`。

## e. 超时、有限重试与错误分类

**默认值（冻结 §3.5，允许覆盖）**

| 参数 | 默认 | 覆盖位置 | 范围 |
| --- | --- | --- | --- |
| connectTimeout | 10s | Profile | 1..300s |
| requestTimeout（单次请求） | 180s | Profile | 1..3600s |
| socketTimeout（无数据） | 120s | Profile | 1..3600s |
| totalTimeout（整个 `complete()`） | 360s | Task | 1..3600s |
| maxAttempts（含首次） | 2 | Profile | 1..5 |
| 退避初始 / 上限 | 1s / 10s | 常量（不配置） | — |
| Jitter | 开启（±20%，可注入随机源）；**加 jitter 后不得突破退避上限 10s** | 常量 | — |

**总期限**：`deadline = monotonicNow() + totalTimeout`，覆盖连接、请求、响应读取与**全部退避**；一律用单调时钟（默认 `System.nanoTime()`，可注入），不使用墙钟差。每次尝试的 `requestTimeout` 取 `min(profile.requestTimeout, remaining)`。

**可重试判定（只重试可判定的暂时错误）**

| 场景 | 分类 | 可重试 |
| --- | --- | --- |
| 连接失败 / DNS / 连接被拒 / 传输中 IO 断开 | `NETWORK` | 是 |
| 单次请求超时、socket 无数据超时 | `TIMEOUT` | 是 |
| HTTP 408 | `TIMEOUT` | 是 |
| HTTP 429 且可判定暂时（有有效 `Retry-After`，或 error code/type 为限流类） | `RATE_LIMITED` | 是 |
| HTTP 429 判定额度耗尽（error code 属 insufficient_quota / quota / billing 类） | `QUOTA_EXCEEDED` | 否 |
| HTTP 429 无法安全判定 | `RATE_LIMITED` | 否（单次失败，不猜测） |
| HTTP 500 / 502 / 503 / 504 | `PROVIDER_UNAVAILABLE` | 是 |
| 其他 5xx（501、505…） | `PROVIDER_UNAVAILABLE` | 否 |
| HTTP 401 / 403 | `AUTHENTICATION` | 否 |
| HTTP 400 / 404 / 409 / 422、其他 4xx | `INVALID_REQUEST` | 否 |
| 2xx 但 body 非法 / 缺 content | `INVALID_RESPONSE` | 否 |
| `finish_reason=length` | `OUTPUT_TRUNCATED` | 否 |
| 明确拒答 / `content_filter` | `MODEL_REFUSAL` | 否 |
| Provider context-length 错误 | `CONTEXT_LIMIT_EXCEEDED` | 否 |
| 本地预算超限（§b） | `LOCAL_BUDGET_EXCEEDED` | 否（且未发请求） |
| 路由缺失 / 配置错误 | `CONFIGURATION` | 否 |
| 关闭**后**新调用 | 既有 `ContextLifecycleException(CLOSED)` | — |
| 取消（调用方或关闭） | `CancellationException` 原样传播 | 否 |

**`Retry-After` 解析（写清回退）**

1. 纯整数秒（非负）→ 该秒数；
2. HTTP-date（RFC 1123，如 `Wed, 21 Oct 2026 07:28:00 GMT`）→ 与响应 `Date` 头（缺失则本地当前时刻）之差，负值按 0；
3. 其他/多值/负数/无法解析 → **视为无效**，按退避计算（不失败、不重试同一时刻）；
4. 有效且 `retryAfter ≤ remaining` → **精确等待**该时长（不加 jitter、不截短），等待在更早发生取消时立即中止；
5. 有效且 `retryAfter > remaining` → **直接以该次错误码失败**（不截短等待、不提前重试）。

**状态机**

```text
complete(request):
  ensureActive()
  route → task/profile（缺失 → CONFIGURATION）
  一致性/ schema / 预算校验（失败 → INVALID_REQUEST / LOCAL_BUDGET_EXCEEDED，不发请求）
  body = buildBody();  deadline = monotonicNow() + task.totalTimeout;  attempt = 1
  loop:
    ensureActive()                                  # 取消原样传播
    remaining = deadline - monotonicNow()           # 每次尝试前重算，不复用上一次的值
    if (remaining <= 0) → TIMEOUT
    outcome = callOnce(body, requestTimeout = min(profile.requestTimeout, remaining))
    outcome.success → 解析响应 → 返回 / 非重试错误
    outcome.failure:
      if (!failure.retryable) → 该分类失败
      if (attempt >= profile.maxAttempts) → 该分类失败
      wait = failure.retryAfter?.let { if (it > remaining) → 该分类失败; it }
             ?: min(1s * 2^(attempt-1), 10s) * jitter
      delay(min(wait, remaining)); attempt++
```

- 每次响应返回后、进入退避前都**重新计算 `remaining`**，用实际总超时边界决定是否还允许发送下一次请求，避免用过期 `remaining` 越期发送。
- 429 的额度耗尽判定**优先于 `Retry-After`**：一旦判定额度耗尽（`QUOTA_EXCEEDED`），即使带 `Retry-After` 也不重试。
- 不叠加业务层重试、不自动换 Profile/Provider；HTTP 超时后不保证 Provider 未生成结果（重复计费风险已在默认 `maxAttempts=2` 内接受）。

## f. 取消与关闭状态机（v3：按 §m 修正，旧伪代码作废）

**状态**：`RUNNING / CLOSING / CLOSED` + `inFlight: MutableSet<Job>` + `closeOutcome: CompletableDeferred<Throwable?>`；状态、在途集合与关闭结果**受同一把普通锁**保护，持锁期间不做任何挂起调用。

**调用准入（`complete()`）**

```text
ensureActive()
coroutineScope {
  call = async(start = LAZY) { execute(...) }          # 结构化子任务：父协程会等它，取消自然传播
  admitted = synchronized(lock) {
      state != RUNNING -> false
      else { inFlight += call; call.invokeOnCompletion { synchronized(lock) { inFlight -= call } }; true }
  }                                                     # 准入/登记与关闭封闭同锁
  if (!admitted) { call.cancel(); throw ContextLifecycleException(CLOSED, "llm client is closed") }
  call.start()                                          # 取消先于 start 时，LAZY 任务直接以取消终结，无需等 start
  call.await()                                          # CancellationException 原样传播，不包装
}
```

- **不使用 `Job(parent = ...)` 另行创建的游离 Job**（§m：该 Job 未 `complete` 会让父协程永远等待）；用 `coroutineScope` 的结构化子任务，父任务在子任务真正结束后才返回。
- 在途跟踪的移除**只在 `invokeOnCompletion`**（§m）：`await()` 的 `finally` 不代表实际完成，取消时子任务可能仍在收尾，提前移除会让 `close()` 漏等。
- 以调用方 Job 为祖先，调用方取消会取消 `call`；`close()` 取消 `call` 时调用方收到 `CancellationException`——符合冻结契约，**不转 `CLOSED`**，不用 `closed && isActive` 作替代判据；不使用 client 自持 scope 包裹调用。

**关闭（`closeAsync()`，唯一清理入口；不提供同步 `close()`）**

```text
1. synchronized(lock):
     CLOSED  -> 记下 closeOutcome（等待并重抛同一结果，不直接 return）
     CLOSING -> 记下 closeOutcome（等待者）
     RUNNING -> state = CLOSING; owner = true; closeOutcome = CompletableDeferred()
                snapshot = ArrayList(inFlight)             # 显式遍历复制，禁止 toList() 的 size==1 快路径
2. 等待者：closeOutcome.await()（可被自身取消，只放弃本次等待）；结果非 null 则重抛同一异常
3. owner（全程 NonCancellable，owner 不可被取消）：
     outcome = null
     try {
        snapshot.forEach { it.cancel(CancellationException("llm client is closing")) }
        循环 { pending = synchronized(lock){ ArrayList(inFlight) }; if (pending.isEmpty()) break; pending.forEach { it.join() } }
        httpClient.close()                                  # 本地在途真实收尾后才关引擎
     } catch (t: Throwable) { outcome = t }                  # 任何失败都要发布终态，不得滞留 CLOSING
     finally {
        synchronized(lock) { state = CLOSED }
        closeOutcome.complete(outcome)                       # 成功（null）或失败都发布同一结果
     }
     if (outcome != null) throw outcome
```

- 收敛性：`CLOSING` 已封闭准入，`inFlight` 只减不增（移除只由 `invokeOnCompletion` 触发），`join` 循环必终止。
- **共享关闭结果包含成功与失败**：`CLOSED` 后重复 close 仍 `await` 同一 `closeOutcome` 并重抛同一失败，**不直接 return 掩盖失败**（§m）。
- **清理 owner 不可取消、等待者可选取消**：owner 的全部步骤在 `NonCancellable` 中（含 `httpClient.close()`），保证终态一定发布；等待者的取消只影响自己这次等待。
- 只有 `CLOSED`/`CLOSING` 期间的新调用返回 `ContextLifecycleException(CLOSED)`，且**不发起 HTTP**；在途取消不转 CLOSED。

**Runtime 接线**（`AlcyoneContextImpl`）

- `AlcyoneContextFactory.create`：**零副作用**不变；`HttpClient`（含引擎）在 `start()` 内创建为受管资源。以**实现事实**描述：不宣称 `HttpClient` 构造必然不启动内部线程/协程；只要 create 阶段不创建即可。
- `performStart`：`executor → vfs → llm`（`config.llm?.let { KtorLlmClient(it) }`），随后 `startProbe` → 发布 `RUNNING`；任一失败走既有逆序清理。
- `releaseResources`：顺序 **llm → vfs → executor**，已有 `withContext(NonCancellable)` 覆盖；每项独立 try/catch，主失败保留、其余 `addSuppressed`（复用既有 `chain`）。不新增 `ReleaseTarget` 常量。
- 内部 client 只暴露挂起关闭，**同步入口由既有 `AlcyoneContextImpl.close()` 桥接**（复用其已验收的 `NonCancellable` + latch + 中断标志协议），不在 client 内自造 `runBlocking`。
- 未配置 `context.llm` → 不建 client（`llm = null`），释放跳过（A01）。

### B2～B4 方案修正（先改文档，后续批次前复核）

- B2 必须解析/验证模型content本身的JSON（只验证HTTP响应信封不是业务JSON有效证据），拒绝代码围栏和非法content；Core业务层仍负责完整Schema/证据约束。提供至少最小资源释放路径让B2测试可靠关闭HttpClient，完整竞态协议在B4验收。
- §f 额外 `Job(parent=...)` 未complete会让父协程等待不结束；应使用正常结构化子任务或明确管理该Job完整终态，不能照抄该伪代码。
- `finally { inFlight -= deferred }` 不代表任务完成：调用方await取消时子任务finally可能仍运行。只在真实invokeOnCompletion移除，关闭在完成前保留跟踪。准入登记与封闭同锁，取消LAZY任务本身会结束其未启动状态，不依赖调用线程必须抢先start。
- 共享close结果须包含成功或失败；CLOSED后重复close仍await/重抛同一结果，不直接return掩盖失败。清理所有路径发布终态结果，不能httpClient.close抛错后滞留CLOSING。清理owner不可取消，普通等待者取消只取消自身等待。
- 同步close不能简单runBlocking后声称恢复中断或与AlcyoneContextImpl等价；若确需此入口须复用已验证的真实清理/中断协议，否则内部LLM client仅挂起关闭，由既有Context同步入口桥接。
- `HttpClient` 构造是否启动内部Job/引擎资源必须以实现事实描述；要求Factory create零副作用，start阶段允许创建受管资源，不宣称HttpClient构造必然零协程。
- B3整个complete总期限从入口开始计算；每次响应/退避前重算remaining，用实际总超时边界确保不能拿过期remaining越期发送；额度耗尽判定优先于Retry-After，外部取消不包装。
