## 3. 锁定的行为契约

### 3.1 总期限与 remaining

- `deadline = monotonicNow() + task.totalTimeoutSeconds * 1000`，从 `complete()` 入口（发送前校验之后、首次请求之前）起算，**覆盖全部尝试与退避**；使用单调时钟（默认 `System.nanoTime()`，可注入）。
- 每次尝试前、每次退避等待前都**重新计算** `remaining = deadline - monotonicNow()`；**不得复用**上一次的值。
- `remaining <= 0` → `TIMEOUT`（未再发请求）；`attempts` = 已执行尝试数。
- 单次请求超时 = `min(profile.requestTimeoutSeconds * 1000, remaining)`。

### 3.2 超时来源与分类

- owned HttpClient 必须安装 `HttpTimeout`；每次请求设置 `requestTimeoutMillis = min(profile.requestTimeout, remaining)`、`connectTimeoutMillis = profile.connectTimeout`、`socketTimeoutMillis = profile.socketTimeout`（逐 Profile，不用全局默认）。
- 注入的 HttpClient 若未安装 `HttpTimeout`：跳过逐请求超时配置（用 `pluginOrNull` 判断），仍由 remaining 检查约束总期限；在 KDoc 说明「注入 client 的超时由调用方负责，B4 统一接线」。
- 以下异常 → `TIMEOUT`（可重试）：`io.ktor.client.plugins.HttpRequestTimeoutException`、`io.ktor.client.network.sockets.ConnectTimeoutException`、`java.net.SocketTimeoutException`。
- 其他传输异常 → `NETWORK`（可重试）。`CancellationException` **原样传播**，不包装、不重试。

### 3.3 可重试判定（§e 表）

| 场景 | 码 | 可重试 |
| --- | --- | --- |
| 连接/DNS/传输中断 | `NETWORK` | 是 |
| 单次请求/连接/socket 超时、HTTP 408 | `TIMEOUT` | 是 |
| 429 + 有效 `Retry-After`，或 error code/type 属限流类（rate_limit / too_many_requests / rate_limit_exceeded 等） | `RATE_LIMITED` | 是 |
| 429 无法安全判定 | `RATE_LIMITED` | **否**（单次失败，不猜） |
| 429 + 额度耗尽（insufficient_quota / quota / billing 类） | `QUOTA_EXCEEDED` | 否（**优先于 Retry-After**） |
| 500 / 502 / 503 / 504 | `PROVIDER_UNAVAILABLE` | 是 |
| 其他 5xx | `PROVIDER_UNAVAILABLE` | 否 |
| 401 / 403 | `AUTHENTICATION` | 否 |
| 其他 4xx | `INVALID_REQUEST` | 否 |
| 2xx 非法 body/content、`length`、拒答、Provider context-length | 各自码 | 否 |
| 发送前 `INVALID_REQUEST` / `LOCAL_BUDGET_EXCEEDED` / `CONFIGURATION` | 各自码 | 否（未发请求） |

- `attempts` = 实际已执行的尝试次数（含首次）；达到 `profile.maxAttempts` 后不再重试，抛该次分类。

### 3.4 Retry-After 解析与优先级

1. 纯非负整数秒 → 毫秒；
2. HTTP-date（RFC 1123）→ 与响应 `Date` 头（缺失用本地当前时刻）之差；负值按 0；
3. 其他（多值、负数、非法、溢出）→ **无效**，按退避处理；
4. 有效且 `retryAfter <= remaining` → **精确等待**该时长（**不加 jitter、不截短**），等待可被取消立即中止；
5. 有效且 `retryAfter > remaining` → **立即以该次错误码失败**（不截短、不提前重试，不再发请求）；
6. 额度耗尽判定优先于 `Retry-After`。

### 3.5 退避与 jitter

- 基础退避 `min(1000 * 2^(attempt-1), 10_000)`（attempt = 刚失败的尝试序号，1 起）。
- jitter ±20%，**加 jitter 后仍不得超过 10_000ms**；可注入 `Random` 便于测试。
- 实际等待 `min(wait, remaining)`；等待使用可取消的 `delay`。

### 3.6 取消传播

- 调用方取消（请求中或退避等待中）→ `CancellationException` 原样抛出（**不是** `LlmException`），取消后不再发起新请求。
- 内部总期限到期是 `LlmException(TIMEOUT)`，**不是**取消；不得用 `withTimeout` 把外部取消混同为超时。

### 3.7 不得回退 B2 行为

路由、`responseFormat`/schema 前置校验、预算前置、三模式请求体、content JSON 校验/围栏拒绝、拒答优先、usage 映射、非 2xx 分类、异常链不泄漏原文、`close()` 最小释放——全部保持；B2 测试除 §5 的最小定点修改外必须原样通过。

## 4. 测试要求（A05）

### 4.1 `LlmRetryPolicyTest`（纯逻辑）

- 可重试判定表（含 429 三种分支、5xx 细分、408、超时异常、非重试码）。
- 退避：attempt 1→~1s、2→~2s、3→~4s、4→~8s、5+→≤10s；固定 `Random` 断言落在 ±20% 内且 **任何情况下 ≤ 10_000ms**。
- `Retry-After`：`"1"`→1000、`"0"`→0、`"-1"`/`"1, 2"`/`"abc"`/溢出→无效、RFC 1123 日期（含 `Date` 头与缺失时用注入 now）、负差→0。

### 4.2 `KtorLlmClientRetryTest`（脚本化真实 HTTP）

脚本 stub 支持「按序返回状态/body/headers + 记录到达时间 + 可配置响应延迟」，`finally` 关闭。至少覆盖：

1. `500,500,200` + `maxAttempts=3` → 3 次请求、成功。
2. 持续 500 + `maxAttempts=2` → 2 次请求、`PROVIDER_UNAVAILABLE`、`attempts=2`。
3. 400 → 1 次、`INVALID_REQUEST`、`attempts=1`。
4. `408,200` → 2 次、成功。
5. `429 + Retry-After: 1` 后 200 → 2 次、成功、相邻请求间隔 ≥ 1000ms（允许时钟抖动下限 950ms）。
6. `429 + Retry-After: 100` + `totalTimeout=2s` → 1 次请求、`RATE_LIMITED`、总耗时 < 2s。
7. `429 + insufficient_quota + Retry-After: 1` → 1 次、`QUOTA_EXCEEDED`（额度优先）。
8. `429` 无 `Retry-After` 且无限流类标记 → 1 次、`RATE_LIMITED`（不可安全判定）。
9. 持续 500 + `totalTimeout=1s` → 在 1s + slack（< 3s）内返回，码为 `TIMEOUT` 或 `PROVIDER_UNAVAILABLE`，请求数 ≤ `maxAttempts`。
10. `Retry-After: 1` 但首个响应延迟 1.5s（`totalTimeout=2s`）→ 不发送第 2 次（`retryAfter > remaining`）、1 次请求、`RATE_LIMITED`。
11. 退避等待中取消 → `CancellationException`（非 `LlmException`），取消后请求数不再增长。
12. 请求在途时取消 → `CancellationException`，无重试。
13. 单次请求超时（stub 延迟 > `requestTimeoutSeconds`）→ `TIMEOUT`，`maxAttempts=1` 时 1 次请求。

时间断言用单调耗时上/下限（不 sleep 猜），允许合理 slack；测试总时长控制在 ~15s 内。
