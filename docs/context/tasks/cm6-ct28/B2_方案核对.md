## 1. 已核实的现状与最小缺口

1. `AlcyoneContext` 尚无 `checkReady` / `getAdminStatus`；现有 `getStatus()` 只有内存状态，`databaseInitialized` 是缓存，且 `StorageStatus.databasePath` 不可直接暴露 HTTP。
2. 权威 Ready 可直接使用现有 `database.read { read -> read.dreaming.readCheckpoint() }`：它经过受管 executor/ReadContext，并实际读取 `dreaming_checkpoint`。不需要新 JDBC 连接、SQL 或全库 quick_check。
3. Pending 只有 exists/list，没有计数。为避免为状态接口复制整表，仅需在 `OrganizationPendingReadOps` 增加 `count(): Int`，由 TxOps 继承，不增加普通 Repository 方法。
4. Dreaming checkpoint 已能由同一 ReadContext 的 `read.dreaming.readCheckpoint()` 获得；pending count 与 checkpoint 可共享 Admin 快照的一次短读。
5. Organization、Memory Map 已有真实 worker 状态。Extraction 缺公开给 Runtime 的“正在执行 Runner”位；Dreaming 缺 Runtime/coordinator 的 `activeRun` 只读状态。二者各补最小只读快照，不改调度算法。
6. LLM 已有按 `(task, profile)` 的 `LlmCallStatistics`，只需增加全部条目的防御性快照及 Ktor client/Runtime 只读转发；无记录保持 null，不新增统计表。
7. B1 Resource 已有首块预取、提交后终止、Flow 收集取消/finally 与可选计数限额，B2 复用该实现，只纳入 managed 在途关闭边界，不重写流式算法。

## 2. 最小 API 与安全 DTO 接缝

### 2.1 `AlcyoneContext`

新增默认方法，保持第三方二进制源码调用入口不被强制实现：

```kotlin
suspend fun checkReady(): Boolean = false

suspend fun getAdminStatus(): ContextAdminStatus =
    ContextAdminStatus(lifecycle = getStatus().lifecycle)
```

第三方默认管理快照只给已知 lifecycle，其余字段均为 null/空“不可用”表示，绝不把未知填成 0/CURRENT。Runtime 覆写两个方法；既有 `getStatus()` 保持无 I/O 与字段兼容。

### 2.2 新文件 `ContextAdminStatus.kt`

建议公共纯 DTO（名称可按项目风格微调，但语义不变）：

- `ContextAdminStatus(lifecycle, workers, pending: PendingStatus?, dreaming: DreamingStatus?, mapStatus: MapStatus?, llm: LlmUsageStatus?, backup: BackupAdminStatus?)`。
- `WorkerAdminStatus(state: WorkerState, lastFailure: Boolean?)`：只从已有状态/`lastError != null` 推导；没有事实来源时为 null，不输出异常文本。
- `PendingStatus(count: Int)`：来自新增真实 SQL；查询失败整次 Admin 503，不返回伪 0。
- `DreamingStatus(lastProcessedTurnId: Long)`：权威单行 checkpoint；无 Dreaming 配置时整个 dreaming 为 null。
- `LlmUsageStatus(entries: List<LlmTaskUsage>)`，未配置 LLM 时 llm=null；每条含 task/profile、calls/successes/failures/attempts、usagePresent/usageMissing、nullable input/output/totalTokens。无 usage 样本的 token 保持 null。
- `BackupAdminStatus` 只复用现有 `WorkerState`、已发布 URI、完成时间、失败 stage 与受控错误 code；不含临时目录、目标配置、后端 URL 或异常 message。
- Map 直接使用 `mapStatus(): MapStatus` 的真实 tracker 状态；不能由 ready 推断 CURRENT。

`ContextAdminStatus` 本身也不得保存 databasePath、原始 Throwable、Key、Prompt 或 body。Server 另做显式 JSON DTO，不通过通用 serializer 直接导出 `ContextStatus`。

### 2.3 Runtime 组装只读状态来源

`AlcyoneContextImpl` 可构造一个 internal 管理快照 lambda，组合：

| 指标 | 唯一事实来源 / 不可用规则 |
| --- | --- |
| lifecycle | Runtime 状态锁中的既有 lifecycle |
| extraction worker | Scheduler 锁内 `runningExecution` + state；新增只读 `workerStatus()`，Pipeline 转发。普通 Runner 异常被隔离时不伪造 FAILED；非关闭 CE 终止 worker 才记录 FAILED |
| organization worker | 既有 `OrganizationScheduler.statusForTesting()`；建议另起语义明确的 `workerStatus()` 别名，不改变原测试入口 |
| memoryMap worker | 既有 `MemoryMapRefreshCoordinator.statusForTesting()` |
| dreaming worker | `DreamingRunCoordinator` 锁内 `activeRun` 与 state；`DreamingRuntime` 非 RUNNING 时 STOPPED |
| worker lastFailure | Organization/Map FAILED、Extraction 非预期终止、Backup 已有受控错误可给 true；Dreaming 未保留事实则 null |
| pending | 同一 `database.read` 的 `read.pending.count()` |
| Dreaming checkpoint | 同一 `database.read` 的 `read.dreaming.readCheckpoint()`；未配置 Dreaming 可不读并返回 null |
| Map 四态 | 既有 `mapStatus()`，不从 worker/ready 推导 |
| LLM usage | 受管 `KtorLlmClient` 对既有 `LlmCallStatistics` 的不可变快照；client 未配置/未创建为 null |
| Backup | 既有 `backupStatusReader` 的进程内快照；未配置为 null，不能当作远端健康 |

Runtime 方法先取稳定引用，再读 DB，不持有 Context 状态锁执行 I/O。数据库读取失败抛受控 persistence/unavailable 供 Server 映 503；外部 CancellationException 原样传播。

## 3. Ready 与唯一只读 SQL

### 3.1 `checkReady()` 精确顺序

1. 非 RUNNING 立即 false。
2. 在受管 executor 上执行一次：

   ```kotlin
   database.read { read -> read.dreaming.readCheckpoint() }
   ```

   使用现有 `ContextDatabaseImpl` / `DreamingCheckpointReadOpsImpl`，不另开连接，不用 SELECT 常量或文件存在。
3. 查询返回后再次确认 RUNNING；仍 RUNNING 才 true。
4. 普通读失败、未知状态、关闭竞争均 false；外部 CE 传播。探针不调用 LLM、VFS、Map 或业务 pipeline。

HTTP `/health/ready` 使用 `server.limits.readyTimeoutMillis` 的 Server 自有期限包装：false、期限到达、受控读失败均为 503 固定短体，true 为 200。期限只取消本次等待，不声称 JDBC 已被强杀；managed close 仍必须等待 executor 的真实收尾。Live 不访问 Runtime。

### 3.2 唯一新增 Port/查询

Core：

```kotlin
interface OrganizationPendingReadOps {
    // 既有方法保持
    fun count(): Int
}
```

Persistence：

```kotlin
const val COUNT_PENDING = "SELECT COUNT(*) FROM organization_pending"
```

`OrganizationPendingReader.count()` 使用既有 `queryPrepared`，要求恰好一行，转 Int 时拒绝负值/溢出；ReadOps 与 TxOps 均转发同一 reader。无 Schema、DML、索引或迁移变化。

## 4. Admin/Health HTTP 适配

新增 `AdminHttpApi.kt`，复用 B1 `ServerAuthRegistry`、`respondError`、严格 UTF-8、重复 JSON key 扫描和有界 body：

- Admin 三路由先认证再读 body/调用 SDK；缺/未知 401，已识别错类 403。未配置 adminKey 时三路由不可访问。
- 两个管理 POST 只接受空 body 或严格 `{}`，按 maxSearchBodyBytes 计数；其他 JSON 字段/类型/重复键/非法 UTF-8 均 400。调用 SDK 使用 `requestTimeoutMillis`。
- `GET /v1/admin/status` 调 `getAdminStatus()` 并显式映射安全 DTO。
- `POST /v1/admin/dreaming` 调并等待 `runDreaming()`，返回真实结果；`POST /v1/admin/backup` 调并等待 `backupNow()`，返回已发布 URI/大小/时间/quick_check，不接目标路径。
- Health 两路由始终存在且无需 Key；live 固定 200 `{"status":"live"}`，ready 只输出 `{"status":"ready"}` 或固定 503 `{"error":"NOT_READY"}`。

错误映射集中白名单：

| 异常 | HTTP/code |
| --- | --- |
| Dreaming UNAVAILABLE | 503 `DREAMING_UNAVAILABLE` |
| Dreaming ALREADY_RUNNING | 409 `ALREADY_RUNNING` |
| DreamingRunException | 500 `DREAMING_<stage>`；可另含受控 stage，不含 partial 内容或异常文本 |
| Backup UNAVAILABLE | 503 `BACKUP_UNAVAILABLE` |
| Backup ALREADY_RUNNING | 409 `ALREADY_RUNNING` |
| Backup CLOSED/NOT_STARTED、Context 非 RUNNING | 503 `SERVICE_UNAVAILABLE` |
| Backup QUICK_CHECK_FAILED / PUBLISH_FAILED | 500 `BACKUP_QUICK_CHECK_FAILED` / `BACKUP_PUBLISH_FAILED`，可含受控 stage；WebDAV 拒绝绝不降级 |
| persistence unavailable / Admin DB 失败 | 503 `SERVICE_UNAVAILABLE` |
| 自有 request deadline | 504 `REQUEST_TIMEOUT`，仅未提交时响应 |
| 其他 Exception | 500 `INTERNAL_ERROR`；外部 CE 原样传播 |

响应和日志只含上述受控 code；不输出 Throwable.message/cause、databasePath、原始 body 或连接信息。

## 5. managed 所有权、准入与关闭时序

### 5.1 两种入口

保留 `AlcyoneHttpServer.start(config, context)`：只启动 CIO，不启动/关闭外部 Runtime，原生命周期测试不变。

新增清晰 managed 入口（可单独 `ManagedAlcyoneHttpServer.kt`）：

- `createManaged(contextConfig, vfsConfig, serverConfig)`：先由既有 Loader/直接构造配置完成校验，返回尚未取资源的 handle。
- `start()`：同一 handle 并发/重复调用共享一次真实启动；唯一创建 `AlcyoneContextFactory.create` → `context.start()` → CIO listen，全成功才发布可用。
- YAML 便捷入口先分别调用 `ContextConfigLoader.load` / `ServerConfigLoader.load`，不绕过任何校验；默认 host/port 沿用 127.0.0.1:8080。
- 任一阶段失败逆序清理：已监听先停 HTTP，已启动 Runtime 再 `closeAsync()`；保留主失败并附加清理失败，不能留下数据库/executor。

### 5.2 在途与关闭

使用共享锁 + 单调准入状态 + 在途请求计数/完成信号（或等价结构化机制），所有 protected/read/admin/health 请求经过同一 managed registration；**业务路由内不另建 Job**。

1. close 原子封闭新请求准入；已注册请求允许按现有取消/清理语义结束。
2. 调用 CIO stop，停止 listener，并等待 Ktor handler/response writer 的真实完成；不能只等固定 5 秒便继续。
3. 在途计数归零且 CIO 已完成后，调用 `context.closeAsync()`，确认 pipelines/LLM/VFS/executor 已释放。
4. 重复/并发 close 等待同一个完成结果，后续 close 重放同一成功/失败。关闭失败仍发布终态并保留异常，不重复释放。
5. stop 观察超时可以返回具名失败，但**不得把它当成 drain 成功继续释放 Runtime**。实现应让真实停止/在途完成由不可被取消的清理 owner 等待；测试不得以 sleep 替代完成信号。
6. 请求自有 deadline/客户端断开先取消 SDK/Flow；已进入 run 的外部 caller-owned 工作是否可取消由现有 Runtime 契约决定。managed close 必须等 Runtime 契约要求的 caller-owned run join，不能抢跑释放 DB。
7. managed close 对仍在执行的流先封闭并停止接收，再走真实 writer/producer finally；不允许伪正常 EOF。

首块流预取/已提交响应失败沿用 `ReadHttpApi.streamResource`：producer/channel 在 coroutineScope 内，首块到达前映射错误，提交后抛受控 abort 终止 HTTP，finally 取消并 join producer；managed 外层只负责等待这整条链路完成。
