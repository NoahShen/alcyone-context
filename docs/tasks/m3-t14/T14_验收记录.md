## 1. 证据分层口径

| 层 | 是什么 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 真实 SQLite | `EventPipelineRealStackTest`，真 `VfsStateDatabase` + 真 `SqliteUnitOfWork` | 同批提交真原子、回滚真回滚、日志真落库能重开读回、关闭后提交仍入库 | 调度穷举；任何调度下的确定性 |
| 替身故障 | Core 单测的 `FakeStateUnitOfWork`（写时复制 + 故障开关） | 分支走向、通知时点、Consumer 隔离与取消语义 | **不是真实事务**：不能证明 SQLite 的原子性，也不能替代真库证据 |
| 代码审查 | Kdoc 与源码扫描（`EventModuleBoundaryTest`） | Core 不引用后端 / 数据库类型；锁与取消的书面约定 | 不能替代实跑；静态扫描也不是依赖方向的完整证明 |

时序一律用闩锁（`CompletableDeferred`）控制，**没有 `Thread.sleep`**；超时只作测试终止保护（到点没发生就直接失败），不做互斥或顺序的证明。
「没收到」这类负向断言的依据是**末尾标记事件**：先让分发链路动起来（标记被收到），断言结论的那条事件不在收到的列表里；等不到标记就直接失败——不靠「等了一会儿也没动静」，也不靠延时。第一轮复核指出的「等待可能被错误事件提前满足」已按此改掉。

## 7. A06 取消与生命周期

| 要求 | 结论 | 证据 |
| --- | --- | --- |
| 调用方取消不被包装 | 达成 | 真库 `A06 a cancelled caller is not wrapped and nothing is committed or notified`：在事务内闩锁处取消（**控制的是提交前**），`launch` 协程 `isCancelled`，`event` 0 行、Node 0 行、Consumer 只收到探针 |
| 分发器关闭幂等 | 达成 | 真库 `A06 close is idempotent, stops the worker and leaves the host job alone`：连续两次 `close()`；`isClosed`、`job.isCompleted`；关闭后提交仍入库（2 行）但不再有进程内通知，`droppedEvents` 不变 |
| 所属任务结束且不取消宿主任务 | 达成 | 同一条：宿主自己的 `SupervisorJob` 仍是 active，宿主协程照常跑完；`AsyncEventNotifier` 用自己的 `SupervisorJob + Dispatchers.Default`，不接管宿主 Scope |
| 不补偿已提交事件 | 达成 | 关闭后提交只入库、不通知（真库 A06），无删除 / 无补偿代码（代码审查） |
| 阻塞 Consumer 协作取消 | 达成 | `AsyncEventNotifierTest :: close cancels a consumer parked on a cancellable suspension`；**不可中断的阻塞代码不在保证内**，已在使用说明第 6 节写明 |

取消窗口口径：**提交附近取消（COMMIT 前后、入队前后）可能通知、也可能没通知，两种都算正常；已提交的事实不撤回**，不补偿、不报告「必定没提交」。这个窗口没有构造用例去假装证明它，也不宣称「必定不通知」。

## 10. 变异自测对照

做法：故意改坏一处，跑 `:vfs:core:test` 与 `:integration-tests:vfs:test`（`--continue`），记录**实际报警的用例**，再改回并确认全绿。三次都是本机实跑结果，不是推断。

| 变异 | 改法 | 实际失败的用例 |
| --- | --- | --- |
| **M1 事务内直接通知**（去掉提交边界） | 把 `notifier.publish(...)` 挪进 `inTransaction` 回调内、`block()` 返回之后 | Core `EventPipelineTest :: A03 a failed commit publishes nothing`<br>集成 `A03 a real commit failure publishes nothing` |
| **M2 通道无界** | `Channel<VfsEvent>(capacity)` → `Channel<VfsEvent>(Channel.UNLIMITED)` | Core `AsyncEventNotifierTest :: a full buffer drops the event instead of blocking the publisher`<br>集成 `A05 a full buffer drops the in-process event and leaves the committed log untouched` |
| **M3 Consumer 异常冒泡** | 去掉 `EventDispatcher` 里 `catch (failure: Exception)` 的记录日志，改为原样抛出 | Core `TransactionAndDispatchTest` 三条（T07 既有）+ `AsyncEventNotifierTest :: a failing consumer does not stop the others nor the later events`<br>集成 `A04 a failing consumer and a parked one do not change the committed result` |
| **M4 标记改回普通 ThreadLocal** | 去掉 `ThreadContextElement`，改回在 `delegate.dispatch` 前后 `ThreadLocal.set(...)` | Core `AsyncEventNotifierTest :: R1 closing from inside a consumer that switched dispatchers also ends`（换线程那条自锁，撞类级 `@Timeout(60)` 失败）。**同一线程里关的那条仍然通过**——普通 ThreadLocal 只在同线程时正确，这正是本轮要修的缺口 |
| **M5 删掉容量校验** | `checkedCapacity` 直接 `return value` | Core `AsyncEventNotifierTest :: R2 the capacity must be a bounded positive buffer size` |

- M1 报警的是**提交失败**那两条，不是「提交前无通知」那两条——因为回调内的通知点在 `block()` 返回之后，测试停在回调里时两者都还没发。这一点如实记录，不把真库 A03 说成能抓 M1。
- M3 一共 5 条报警（Core 4 + 集成 1），其中 3 条是 T07 既有回归，属于预期的连带报警。
- M4 第一次跑时**没有报警**：那时用例用的是 `Dispatchers.IO`，它可能把任务发回当前线程，等于没换线程。改用专用单线程调度器后 M4 才稳定报警（这是第一次变异实跑暴露出来的用例缺陷，不是实现问题）。
- 五次变异都已改回，`./scripts/check` 全绿（459 个测试）。

## 11. 边界与未验证

**实测到的**：真库同批提交 / 回滚 / 重开可读 / 提交失败不通知 / 容量满丢弃 / 关闭幂等 / 提交前取消全回滚 / 懒注册无事件；替身层的分支与 Consumer 隔离、取消语义；构建与格式。

**用例已覆盖、但结论强度有限制的**：

- Consumer 自己抛 `CancellationException` 时「排在它后面的 Consumer 收不到这一轮」：`a consumer that cancels itself does not silently stop the notifier` 断言的正是这一条（沿用 T07 `EventDispatcher` 既有语义），不是未覆盖项。
- 「无订阅者」：`publishing with no subscriber does not fail and is not counted as dropped` 只断言不报错、不计入 `droppedEvents`；它**不断言队列被排空**（`close` 是取消，不是排空）。
- 「订阅顺序」用例记的是跨 Consumer 的调用序列（单分发协程、单队列下成立）；**没有覆盖**多分发协程或外部并发 `publish` 下的全局排序，本轮也不承诺那种排序。

**按代码审查认定、未单独造用例的**：

- 提交附近取消的窗口（COMMIT 完成后、入队前后）：**可能通知、也可能没通知**，已提交的事实不撤回；不构造极窄窗口的测试，也不宣称必定不通知。
- 不宣称能强杀不可中断代码；`close()` 对卡在阻塞代码里的 Consumer 会跟着卡住。
- 「回调内关闭只取消不等待」依赖 `ThreadContextElement` 随协程上下文传播；无关线程上看不到该标记（ThreadLocal 按线程隔离，回调退出即恢复），这一点由代码结构保证，用例只能证明「外部关闭仍然等待」。

**明确不在本轮范围**：read / list / 写文件编排（T15）、Metadata 操作（T17）、移动 / 删除（T16 / T18）、Runtime 组装与全局停机（T18 / T27）、可靠消费游标 / ACK / 重启补发（E05）、每 Consumer 独立线程池或独立队列、Git / MQ。
