# T14 使用说明

## 本次修改（2026-10-03，T14 实现交付初稿）

- 按「怎么造事件 → 怎么把状态和事件一起提交 → 提交后怎么通知 → 容量与丢弃 → 取消与关闭 → 留给谁」组织。涉及全文。
- 写清容量数值与丢弃策略、顺序承诺、三种取消的区别、关闭语义，以及「选哪种事件」留给 T15～T23。

模块路径 `vfs/core`，事件相关都在包 `core.event`：`EventFactory`（造事件）、`EventPipeline`（同事务提交 + 提交后通知）、`AsyncEventNotifier`（有界队列 + 分发协程）；`EventDispatcher`（T07 已有）本轮只补了 `unsubscribe`。

## 1. 这三个东西各管什么

| 组件 | 做什么 | 不做什么 |
| --- | --- | --- |
| `EventFactory` | 给一次成功的变更补事件 ID（UUIDv7）和时间，检查移动事件的字段自洽 | 不选事件类型；不写库；不通知 |
| `EventPipeline` | 一次事务里改状态 + 追加事件，**提交成功之后**才交给分发 | 不写 Storage；不选事件类型；不做补偿 |
| `AsyncEventNotifier` | 有界队列 + 自己的分发协程，把事件送给 Consumer | 不保证送达；不重放；不碰事件日志 |

一句话串起来：**文件写好 → 一次事务更新 Node + 追加 FILE_WRITTEN → 提交成功才通知 Consumer**。

## 2. 造一条事件

```kotlin
val events = EventFactory()                       // 想固定时间就 EventFactory { fixedInstant }

val record = events.newRecord(                     // 写好了 /resources/notes/a.txt
    type = VfsEventType.FILE_WRITTEN,              // 选哪种类型由 T15～T23 决定
    nodeId = info.id,                              // 可以为 null：没有有效 Node 的删除事件
    uri = VfsUri.parse("alcyone://resources/notes/a.txt"),
    operationId = "op-7",                          // 只用于诊断
)

// 移动事件：源和目标给全，uri 自动是移动后的目标位置
events.newMove(VfsEventType.FILE_MOVED, info.id, sourceUri = oldUri, targetUri = newUri)
```

规则只有两条：

- `FILE_MOVED` / `DIRECTORY_MOVED` 的 `uri` 必须是目标位置，`sourceUri` 和 `targetUri` 都要填；其余事件不许填这两个字段。写错了在构造时就抛 `IllegalArgumentException`。
- 时间按**毫秒**取整。事件日志表存的是 epoch 毫秒（`vfs/persistence`），生成时就取整，通知里的时间和库里那一行永远是同一个值。

`record.toVfsEvent()` 是唯一的转换入口：同一个 ID、同一个类型、同一组 URI，**通知侧不重新生成任何东西**。所以 Consumer 拿到的 ID 可以直接拿来查事件日志。

## 3. 状态和事件一起提交

```kotlin
val pipeline = EventPipeline(boundary, unitOfWork, notifier)   // 整个 Runtime 造一套

suspend fun updateMetadata(id: NodeId, metadata: NodeMetadata): NodeInfo =
    pipeline.commit { scope ->
        val info = registry.getNodeInsideBoundary(id)                          // 同一把锁内的逻辑查询
        scope.metadata.put(info.id, metadata)                                   // 状态变更
        scope.events.append(events.newRecord(VfsEventType.METADATA_UPDATED, info.id, info.uri))  // 同一批提交
        info
    }
```

- `commit` **自己拿那把共享 `StateBoundary` 锁**，里面调不加锁的入口。调用方不要再在外面套一层 `boundary.withLock`（锁不可重入，会自己等自己）。
- 事务正常返回 = 已 COMMIT，这时才把本次追加的那批事件交给分发；回调抛错或提交失败 = 一个都不通知。
- Core 只认 `UnitOfWork` 这个 Port，真实数据库由 Runtime 注入（T18）。
- **写文件的顺序属 T15**：`Storage 写入成功 → commit 提交 Node 状态与事件`。SQLite 回滚不了外部文件，本轮不代管。

## 4. 进程内通知

```kotlin
val notifier = AsyncEventNotifier()          // 默认容量 256，可调小调大，但**不能改成无界**
notifier.subscribe { event -> pushToIndex(event) }
...
pipeline.commit { scope -> /* 改状态 + scope.events.append(record) */ }
notifier.close()                            // Runtime 全局停机时调（T18 / T27）
```

- **异步**：`publish` 只是 `trySend` 入队就返回，不等 Consumer 跑完，也不在持状态锁的调用栈里执行 Consumer。
- **有界**：容量就是构造参数（默认 256，够正常负载跑完一轮，又不至于让一个卡住的 Consumer 吃光内存）。只能传**有界的普通正整数**（1..`Int.MAX_VALUE - 1`）：`0`（无缓冲）、`-1`（新事件覆盖未分发的）、`Int.MAX_VALUE`（无界）会在构造时就被 `IllegalArgumentException` 拒绝，免得「有界」只写在注释里。**队列满时的策略：记一条 warn（只记首次，不逐条刷屏）、计入 `droppedEvents`、丢弃、不抛给发布方**。慢 Consumer 会拖慢通知，但绝不会把已经提交的文件操作堵住；也不会靠无限缓存绕过慢 Consumer。丢弃不改已提交的事件——事件日志里那条还在（首版不重放，补发属 E05）。
- **顺序承诺**：一个分发协程 + 一个 FIFO 队列 = 事件按 `publish` 先后送达；同一个事件内 Consumer 按订阅顺序一个个跑。**不做全局排序，也不给每个 Consumer 单独排队**：一个慢 Consumer 会让后面的 Consumer 一起等（首版接受；换线程池或每人一套队列是更大的取舍，留后续任务）。
- **无订阅者**：事件**照样入队**，被分发协程取走时没有可投的就丢掉——不报错，也不计入 `droppedEvents`（那个计数表示没进队列：队列满，或与关闭抢先后）。分发变慢时它照样受容量约束；晚订阅的 Consumer 可能收到订阅之前入队、还没轮到分发的那一批。事件日志才是可靠的那一份。
- **退订**：`unsubscribe(consumer)` 之后的事件不再投给它；正在执行的那一次不打断。

诊断用两个只读入口：`notifier.droppedEvents`（**没进队列**的条数：队列满，或与 `close()` 抢先后时通道已关）、`notifier.isClosed`；宿主等停机时用 `notifier.job.isCompleted`。

## 5. 三种取消，不要混着看

| 场景 | 表现 | 首版怎么处理的 |
| --- | --- | --- |
| **调用方取消** | `CancellationException` 原样传播，不包装 | 提交前取消 = 整体回滚，**一个事件都不通知**；提交附近取消（COMMIT 前后、入队前后）= 可能已提交且可能有通知，也可能没有 |
| **通知器关闭**（`close()`） | 取消自己的分发协程，关闭通道，等它结束 | 已入队的没送完的就不再送了；**不补偿已提交事件**，事件日志里还在 |
| **Consumer 自己抛 `CancellationException`** | 消费者放弃了手上这一条 | 那一轮分发到此为止（排在它后面的 Consumer 收不到这一条，沿用 T07 的约定），**分发协程继续跑后面的事件**，不会被静默带走 |

第三种是特意区分出来的：消费者放弃自己的活，不等于整个通知系统停摆。真要停分发器，用 `close()`。

**提交附近取消的诚实说法**：取消可能落在「已经 COMMIT」到「事件入队」之间。**这一批可能通知了、也可能没通知**——两种都算正常；已提交的事实不撤回，VFS 不报告「必定没提交」，也不补偿删除。重启后不会自动补发（E05）。首版不对这个窗口做测试构造。

## 6. 关闭语义

```kotlin
notifier.close()      // 幂等：重复调用直接返回
```

- 取消自己的 `SupervisorJob`、关闭通道、等分发协程真正结束（`job.isCompleted` 可查）。
- **协作取消**：Consumer 挂在可取消的挂起点（`awaitCancellation`、挂起的网络读）会立刻收到取消；卡在不可中断的阻塞代码里时 `close()` 也会跟着卡住——**不宣称能强杀不可中断代码**。
- **不接管宿主的 Scope / Dispatcher**：通知器用自己建的 `SupervisorJob + Dispatchers.Default`，宿主关掉自己的 scope 不会顺手关掉它，反过来也一样。
- **在 Consumer 回调里调 `close()` 不会自己等自己**：「正在回调里」这个标记随协程换线程（回调 `withContext` 到别的线程再关也一样），这种调用只做取消 + 关闭通道，不等待；外部调用才等收尾。
- Runtime 的全局停接和在途等待属 T18 / T27，本轮只管事件组件自己。

## 7. 事件类型留给谁

| 操作 | 事件类型 | 谁决定 |
| --- | --- | --- |
| 新建文件 / 目录 | `FILE_CREATED` | T15 |
| 覆盖写已有文件 | `FILE_WRITTEN` | T15 |
| 改 Metadata | `METADATA_UPDATED` | T17 |
| 移动文件 / 目录 | `FILE_MOVED` / `DIRECTORY_MOVED` | T18 |
| 删除 | `FILE_DELETED` / `DIRECTORY_DELETED` | T16 / T18 |
| 懒注册（`stat` 首次登记） | **没有事件** | 已定：首版不发布 `NODE_REGISTERED` |

本轮只提供造事件的入口和接线，**不实现任何一种文件操作编排**。T15～T23 各自决定选哪种，然后调 `commit { … scope.events.append(…) }`。
