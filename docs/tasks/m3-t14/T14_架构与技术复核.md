## 2. 必须修改

### R1 / P1：普通 ThreadLocal 无法识别协程中的自关闭，换线程后会自锁

位置：`AsyncEventNotifier.kt:52`、`:60–69`、`:119–124`。标记在线程 A 置 true，Consumer 使用 `withContext` 切到线程 B 后调用 `close()`，B 读到 false，进入 `runBlocking { job.join() }`；job 又必须等当前 Consumer 返回，形成自等待。挂起后换线程还可能把 true 留在旧线程，使无关调用误判为 Consumer。

独立探针已复现：Consumer 切到独立单线程 dispatcher 后关闭，线程栈停在 `AsyncEventNotifier.close → BlockingCoroutine.joinBlocking`，通知 job 未完成；最后通过中断探针线程解除，未遗留挂起工作。这不是“Consumer 不可中断代码”的既定限制，而是通知器自己制造的等待。

修复要求：使用能随协程上下文正确传播、恢复的执行标记，或收敛关闭协议，避免同步等待自身；不需要引入生命周期框架。补正式用例：直接回调关闭、切换 dispatcher 后关闭均能结束；外部关闭仍等待协作取消完成，且无关协程不继承残留标记。

### R2 / P2：容量参数接受 Channel 特殊值，违反有界和显式丢弃契约

位置：`AsyncEventNotifier.kt:37–41`。构造参数直接传给 Channel，`Int.MAX_VALUE` 即 `Channel.UNLIMITED`；`-1` 即 `CONFLATED`，会覆盖待分发事件但 `trySend` 返回成功，既不告警也不增加丢弃计数。

独立探针分别传入上述值，在 Consumer 已挂起后连续发布 100 条，两者均被接受且 `droppedEvents=0`。M2 改源码为无界后能报警，不代表生产参数入口已防住相同问题。

修复要求：在创建 Channel / 启动 job 前校验明确的容量范围，拒绝无界与 conflated 等策略特殊值；是否允许零容量由开发说明，最简单可只接受普通正整数且排除 `Int.MAX_VALUE`。保留容量 1 的溢出回归，并补参数边界用例；无需新增配置框架。

### R3 / P2：验收证据和使用说明有过强或不匹配表述

以下内容影响验收判断及后续接线，应一起收口：

- **无通知证据**：Core 的失败提交用例用 `EventRecorder(1)` 等“任意一条”，错误提前通知本身就能解除等待；真库失败用例先等探针、后失败、立即查列表，也未等待失败之后的分发进度。改为失败后发送可识别的末尾标记，等待同一 FIFO 分发链处理到该标记，再核对收到的 ID；不要靠延时。真库探针的 `complete` 还在记录列表的 Consumer 之前，不能据此认定后者已执行。
- **证据分层**：真库“关库重开”用例未订阅 Consumer，仅证明持久化；通知与库行的 ID / 毫秒一致由另一条真库 A03 支撑。第 11 节把 Consumer 自抛取消列为“未单独造用例”，实际上已有该用例；所谓订阅顺序测试仅分别检查两个列表内的事件顺序，未检查跨 Consumer 的调用顺序。订正引用和强度即可，不强制为每项补新测试。
- **无订阅者**：实现仍入队，快发布时可以满并计数；先入队后订阅也可能收到尚未分发的事件。Kdoc“无缓存”、使用说明“不计数”和 no-subscriber 测试中“close 后队列已消费完”不成立：close 是取消，不是排空。明确按分发时订阅快照处理、仍受队列容量约束等实际语义，或选择更简单的显式丢弃策略并验证，不要求增建订阅框架。
- **取消窗口**：`inTransaction` 已正常返回后，map / publish 没有挂起取消点，调用方随后被取消不保证跳过通知；真实 SQLite 的 COMMIT 调用返回协程时发生取消，才可能“已提交但 inTransaction 未正常返回”，从而不入队。统一为“提交附近取消可能有通知，也可能无通知，已提交事实不撤回”，不能从非挂起 publish 推出必定不通知；无需构造本轮已明确延后的极窄窗口测试。
- **可用样例与提交号**：使用说明第 2 节 `newMove(..., source=..., target=...)` 与实际参数 `sourceUri / targetUri` 不符；交付文档仍写“未提交 Commit”。回填 `d854198`，修正命名参数，并将依赖方向写为 `core → api → common`。

验收：修正上述现有断言和表述；R1 / R2 增补用例完成后重新统计正式基线。M1 可重新实跑确认失败后末尾标记能稳定检出提前通知；保留历史实跑记录，不把它改写成确定性证明。

## 3. 重点设计判断

| 关注点 | 判断 |
| --- | --- |
| RecordingScope | delegate.append 成功返回才记录；整个事务成功返回才转换并发布，失败分支无发布。通过该接线的正常串行事务路径成立；不承诺防止调用方直接调用公开 publish、另持 Repository 或吞掉业务失败。无须为内部组件增加通用防误用框架。 |
| boundary 锁内 publish | 可接受：只 trySend，不同步执行或等待 Consumer；Consumer 即使马上调用 Registry，也只是等待发布方释放锁，发布方不反向等待它。同一 boundary 的提交可保持入队顺序，无需为缩短这段锁另建排序器。 |
| ensureActive | 判断分发协程是否真的被取消的做法正确：关闭时继续传播，Consumer 单纯抛 CE 时可继续下一事件。不能据此解决 R1 的线程标记；调用方取消由事务入口原样传播。 |
| 自抛 CE 的隔离范围 | 接受已明确选择的“结束当前事件、继续后续事件”；排在该 Consumer 后的订阅者可能持续收不到事件，这是已有分发策略的边界，不等于普通异常隔离失效。 |
| 默认 256、满则丢弃 | 策略符合首版不可靠投递边界，慢 Consumer 不令入队等待，丢弃不改数据库。R2 修复后才能声称所有受支持容量都有界。 |
| 事务与事件一致性 | 真 SQLite 重复 ID 引发回滚、成功重开可读、关库引发提交失败均有证据；无数据库 listener 接线，未发现绕过提交确认的生产路径。 |

## 4. 建议优化（不阻塞本轮）

- **S1 测试清理**：`EventPipelineTest` 创建的 notifier 多数未关闭，断言失败时其他测试也可能跳过 close。使用 `try/finally` 或小型 fixture 统一清理，避免分发协程留到测试进程退出；无需扩展生产生命周期接口。
- **S2 日志与诊断**：逐条 warn 发生在 boundary 锁内，宿主同步日志或持续溢出会放大提交耗时；可节流日志而保留累计数。publish 与 close 竞争时 `trySend` 关闭失败也会被记作“队列满”，建议区分关闭与容量原因；这两者不改变数据库结果。
- **S3 T15 接线传承**：当前 commit 自取锁，足够本轮状态变更；未来需要覆盖 Storage 与状态的完整串行编排时，应在 T15 明确唯一持锁者及内部已持锁入口。不要在本轮承诺已验证完整文件流程，也不要简单外套相同 boundary 再调 commit。

## 5. 可接受的设计取舍

首版允许通知丢失、不重放；一个 FIFO worker 按订阅顺序处理，慢 Consumer 拖慢其他 Consumer；直接抛 CE 结束当前事件，普通异常继续其他 Consumer。组件自有 SupervisorJob，不取消宿主；不可中断的业务代码导致外部 close 等待属于已说明限制，但 R1 自锁不能归入该限制。

事件工厂与转换留在 Core，时间对齐既有毫秒精度；不扩展 EventRepository 查询、Schema、MQ 或每 Consumer 队列。所有这些取舍均无需本轮扩大架构。
