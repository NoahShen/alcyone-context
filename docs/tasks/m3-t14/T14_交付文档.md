## 2. 怎么用的（最小形状）

```kotlin
val boundary = StateBoundary()                                   // Runtime 全局共享（T11 单连接不支持并发事务）
val events = EventFactory()
val notifier = AsyncEventNotifier()                               // 容量 256，满则记日志丢弃
val pipeline = EventPipeline(boundary, unitOfWork, notifier)      // Core 只认 UnitOfWork 这个 Port

// 文件写好之后（Storage 已成功）：
pipeline.commit { scope ->
    val info = registry.getNodeInsideBoundary(id)                 // 同一把锁里的逻辑查询，不再取锁
    scope.nodes.touch(info.id, now)                               // 状态变更
    scope.events.append(events.newRecord(FILE_WRITTEN, info.id, info.uri))   // 同一批提交
}                                                                 // ← 事务已提交，事件才交给分发
```

## 3. 设计决策（只回写影响调用语义的）

| 问题 | 选择 | 理由 |
| --- | --- | --- |
| 组件怎么知道本次事务追加了哪些事件 | 包一层记录用的 `EventRepository`，调用方照常写 `scope.events.append(…)` | 在**正常成功路径**上：凡是记下来的，都会尝试交给分发（不会出现「通知了没记录的事件」）；反过来「记了却没通知」仍可能发生，但只来自已接受的边界——提交附近取消、通知器已关闭、队列满丢弃。调用方不需要维护第二个列表 |
| 通知在锁内还是锁外 | 在锁内、`inTransaction` 正常返回之后立刻 `publish` | 整条链只取一次锁；同一把边界串行 → **入队顺序就是提交顺序**。`publish` 是非挂起调用，不在持锁栈里执行 Consumer |
| 队列满了怎么办 | `trySend` 失败 → 首次记 warn 日志 + `droppedEvents` 计数 + 丢弃，**不抛给发布方** | 慢 Consumer 可以拖慢通知，但不能把已提交的操作堵死；也不靠无限缓存。丢弃不碰事件日志（首版不补发，E05） |
| 容量数值 | 默认 `256`（`AsyncEventNotifier.DEFAULT_CAPACITY`，可调） | 够正常负载跑完一轮 Consumer，又不至于让一个卡住的 Consumer 吃光内存；构造参数化，测试用 1 逼出丢弃行为 |
| 顺序承诺 | 单协程 + FIFO：按 `publish` 先后送达；同一事件内按订阅顺序 | 不做全局排序，也不给每个 Consumer 独立线程池 / 队列——那是更大的取舍，留后续任务 |
| Consumer 自己抛 `CancellationException` | 分发协程捕获后先 `ensureActive()`：自己在停就照常退出；只是 Consumer 自己放弃则记日志并继续送下一条 | 一个消费者放弃自己的活，不该把整个通知系统静默带走；但也不能把「真的在关停」当成故障继续跑。排在它后面的 Consumer 收不到那一轮（沿用 T07 既有语义） |
| 三种取消 | 分开处理，不用一个 catch 吞掉全部 | 调用方取消原样传播；`close()` 只取消自己的 `SupervisorJob`；Consumer 的取消不上浮到发布方 |
| `close()` 等待 | 取消自己的协程 + 关闭通道 + 等结束（`runBlocking { job.join() }`） | 协作取消；Consumer 挂在不可中断阻塞代码里时也会跟着卡住，**不宣称能强杀**。在 Consumer 回调里调 `close()` 属于自己等自己，只取消不等待 |
| 时间精度 | 生成时就按 `Instant.ofEpochMilli` 取整；转换时再对齐一次 | 通知里的 `occurredAt` 永远等于事件日志那一行的值，哪怕记录是调用方自己拼的 |
| 移动事件的字段 | `uri` 强制等于 `targetUri`，两者必填；非移动事件禁止填这两个字段 | 在构造期把 T18 最容易写错的字段钉死，不留到通知出去才发现 |
| 退订 | 给 T07 的 `EventDispatcher` 补 `unsubscribe`（3 行） | 任务要求「订阅解除行为明确」；不新增第二套订阅机制 |
| 回调内 `close()` 怎么识别 | 「正在 Consumer 里」用 `ThreadContextElement` 传播，随协程换线程；回调内只取消不等待，外部仍等收尾（R1） | 普通 `ThreadLocal` 在回调 `withContext` 换线程后会误判，随后等的就是自己所在的分发协程 → 自锁。改成「`close` 一律不等」会丢掉「外部关闭等收尾」这个有用的语义 |
| 容量参数 | 构造时校验，只接受 1..`Int.MAX_VALUE - 1`（R2） | `Channel` 的 `-1`（conflated，新事件覆盖未分发的）和 `Int.MAX_VALUE`（无界）是特殊值，透传会让「有界」名存实亡；校验在建 Channel、起协程之前 |
| 满队列日志 | 只记首次 warn，之后靠 `droppedEvents` 累计；「队列满」与「正在关闭」分开记（S2） | `publish` 在持边界锁的调用栈里，逐条 warn 会刷爆日志；关闭竞态下的入队失败不该被说成「缓冲区满」 |

## 6. 已知限制

1. **提交附近取消**：取消落在「提交完成、入队前后」时，这一批**可能通知了、也可能没通知**，两种都算正常；已提交的事实不撤回，不补偿删除、不报告「必定没提交」，重启不自动补发（属 E05）。不对这个窗口造测试，也不宣称必定不通知。
2. **队列满会丢进程内通知**（只影响通知，不影响事件日志与已提交状态）；丢弃计数只留在内存 `droppedEvents`，不持久化。构造参数只接受有界正整数（1..`Int.MAX_VALUE - 1`），`0` / `-1` / `Int.MAX_VALUE` 直接拒绝。
2b. **无订阅者时事件照样入队**，只是分发时没有可投的人；分发变慢时同样受容量约束，晚订阅的 Consumer 可能收到之前入队的那一批。
3. **Consumer 之间没有隔离**：一个慢 Consumer 会拖慢同一分发协程上的其他 Consumer；首版接受。
4. **`close()` 是协作取消**：Consumer 卡在不可中断的阻塞代码里时 `close()` 会跟着卡住；不宣称能强杀。Runtime 全局停机与在途等待属 T18 / T27。
5. **事件查询仍只有写**：验收靠直连 JDBC 读表核对日志，`EventRepository` 没有分页 / 订阅 / 重放 API。
6. **只覆盖本轮范围**：read / list / 写文件 / 移动 / 删除编排都不在本轮，事件类型的选择留给 T15～T23；懒注册仍不发事件（`NODE_REGISTERED` 仍不存在）。
7. 平台：本轮只在 macOS arm64 实跑；Linux 未验证（沿用 T08 的 CI 结论，本轮无平台相关改动）。

## 7. 给下一棒的提示（T15 起）

- 写文件顺序：`Storage 成功 → pipeline.commit { 改 Node 状态 + 追加事件 }`。别把 Storage I/O 放进事务回调。
- 不要在 `pipeline.commit` 外面再套 `boundary.withLock`；事务内调 Registry 用 `getNodeInsideBoundary` / `resolveInsideBoundary`。
- 选事件类型见使用说明第 7 节的表；移动用 `newMove`，它会把 `uri` 钉在目标位置。
- Runtime 组装（T18）负责造 `StateBoundary`、`EventFactory`、`AsyncEventNotifier`、`EventPipeline`，并在全局停机时 `close()` 通知器。
