## 1. 目标与已有基础

在 `vfs/core` 完成可供 T15 及后续变更操作复用的事件接线：生成事件、与逻辑状态一起提交、提交后交给进程内分发。已有 `VfsEvent` / `EventRecord`、`EventRepository.append`、`UnitOfWork`、`StateBoundary` 和 `EventDispatcher` 应优先复用；T07 的分发器已有同步逐个调用与普通异常隔离，本轮不是从零重建事件系统。

依据：[T01 第 8 节](../../vfs/VFS_公共契约草案_v0.1.md)、[T03 第 3～6 / 9 节](../../vfs/VFS_状态与恢复设计_v0.1.md)、[T07 Core 边界](../m1-t07/T07_Core边界定义与验收.md)、[T13 收口复核](../m2-t13/T13_架构与技术复核.md)。实现留在 Core，实际数据库由 Port 接入，Runtime 组装仍属 T18。

例：文件内容已经写好，随后一次事务更新 Node 并追加 FILE_WRITTEN；只有事务成功后才通知 Consumer，Consumer 抛错不把这次写入变回失败。

## 2. 开发内容

### 2.1 事件生成与数据一致性

Core 使用已有 UUIDv7 工具和时间生成事件，复用七种 VfsEventType，不新增 NODE_REGISTERED、文件内容、凭据或 Agent 信息。提供必要的 EventRecord / VfsEvent 转换或等价小入口，同一事件从持久化到通知保持同一个 ID、类型和逻辑 URI；时间按既有 SQLite 毫秒精度核对。

例：FILE_MOVED 的 uri 是目标位置，sourceUri / targetUri 分别是源和目标，Node ID 保持调用方提供的原 ID。具体操作选哪种事件由 T15～T23 决定，本轮验证事件字段，不提前实现移动。

### 2.2 状态与事件同事务

提供最小可复用的 Core 接线方式，使调用方通过同一个 TransactionScope 完成 Node / Metadata 变更和 Event 追加，成功返回后才安排通知；可以是小型组件或内部函数，不只留下无法执行的示意图。沿用 T13 的共享 StateBoundary，明确哪层持锁，已持锁组合不再次取锁；Core 只接收 UnitOfWork Port，不实例化具体数据库。

例：Metadata 更新后追加事件失败，两者一起回滚，Consumer 收不到成功通知。未来文件操作必须先 Storage 成功，再提交逻辑状态与事件；SQLite 不能回滚 Storage，本轮不扩建文件操作编排。

### 2.3 提交后通知与取消

通知只能来自已确认提交成功的事件，不能在事务回调里直接执行 Consumer，也不能以 SQLDelight listener 代替提交确认。调用方取消按原契约传播；提交附近取消可能已留下状态与事件，但没有进程内通知，这在首版允许，不能因此补偿删除或报告“必定没提交”。

例：事务提交后、入队前进程退出，事件仍在库中，重启不自动补发。正常通知应能查到已提交状态，回滚或提交失败不得通知；故障测试必须说明控制的是提交前还是提交后。

### 2.4 进程内分发与 Consumer 隔离

基于现有分发器补一个简洁的异步交接方式（Channel / Flow 等），文件操作不等待 Consumer 的业务执行，也不在持状态锁的调用栈中同步执行 Consumer。Consumer 的普通异常应记录且不妨碍其他 Consumer 与后续事件；取消调用方、取消分发组件、Consumer 自己抛 CancellationException 要分别说明，不能用一个 catch 将宿主取消全部吞掉。

例：Consumer 查询 Registry 不应与发布方互相等待；一个 Consumer 抛 IOException，另一个仍能接收。慢 Consumer 可以影响通知延迟，但不能无限阻塞已经提交的文件操作；是否隔离每个 Consumer 的慢处理由最小实现决定，不要求线程池或每人一套队列。

### 2.5 容量、订阅与关闭

分发缓存应有界，明确无订阅者、缓冲满、订阅解除、关闭后发布及正常事件顺序；容量数值和丢弃策略由开发选择并写入使用说明，不承诺可靠投递或让内存无限增长。队列拒收 / 丢弃不修改已提交事件，不把普通通知失败变成文件操作失败；保留必要的诊断，不引入持久化消费状态。

明确分发协程由谁创建、如何取消和等待结束，关闭幂等，不取消宿主拥有的共享 Scope / Dispatcher；本轮仅负责事件组件自身生命周期，Runtime 的全局停接与在途等待留 T18 / T27。例：Consumer 一直挂起时，关闭分发器不要求等待它的外部 Git push 完成，资源终止的验证用协作取消场景，不宣称可以强杀不可中断代码。

## 5. 验收标准

| 编号 | 必须满足 | 核心证据 |
| --- | --- | --- |
| A01 事件数据 | UUIDv7、类型、Node ID 可空、时间与 URI 等符合既有模型；持久化与通知是同一事件 | 七种事件的必要字段及转换，移动源 / 目标，null 可选字段，不含内容 / 身份 / 凭据 |
| A02 原子提交 | Node / Metadata 与 Event 同一事务成功或回滚 | 真实 SQLite：状态成功但追加事件故障时两者均回滚；可用重复 Event ID 或局部故障触发；成功后重开数据库仍有记录 |
| A03 提交后分发 | 提交前无通知，失败 / 回滚无成功通知；不依赖 DB listener | 控制事务阶段，Consumer 确认已提交状态；发布与持锁组合无自锁；同一事件不因转换生成新 ID |
| A04 Consumer 隔离 | 普通 Consumer 异常不改变成功结果、不阻止其余 Consumer 及后续事件；慢处理不阻塞已提交操作 | 一个抛错、一个正常；一个受控挂起时提交入口仍可返回，之后释放或取消清理 |
| A05 容量与订阅 | 缓存有界，满队列 / 无订阅者 / 解除订阅行为明确，不能靠无限缓存绕过慢 Consumer | 小容量受控填满，检查选定策略和 Event 记录不被改变；按声明验证单批 / 多批顺序，不要求额外全局排序器 |
| A06 取消与生命周期 | 调用方取消不被包装，分发器关闭幂等，所属任务结束且不取消宿主任务；不补偿已提交事件 | 等待 / 执行 / 提交后阶段按实际可控点验证；阻塞 Consumer 协作取消，关闭后发布遵守说明 |
| A07 模块与范围 | Core 依赖 Port，不引用 SQLDelight / OpenDAL；不改变 Registry 的无事件语义 | 依赖审查、T13 回归；没有可靠消费 / 日志查询框架；样例使用真实已有 API，事件与状态确实同批提交 |
| A08 构建与交付 | 原 419 个测试无回归，新用例实际执行，交付可供 T15 使用 | 项目工具链 spotlessApply、scripts/check；分模块 JUnit 统计、提交号、使用说明与未验证范围 |

同目录补使用说明、验收记录和交付文档，每份修改前置“本次修改”；说明缓存 / 顺序 / 取消 / 关闭取舍，并区分真实 SQLite、替身故障和代码审查证据。成功提交后通知丢失是首版已接受的边界，不作为可靠消费缺陷追补；完整 Consumer 和 Runtime 验收留对应任务，不自动开始 T15。
