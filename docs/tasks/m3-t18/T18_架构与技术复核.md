## 2. 必须修改

### R1 / P1：同一 storageKey 的不同根被静默丢弃

位置：`VfsRuntimeConfig.kt:98–111`。putIfAbsent 先按 key 去重再规范化根，后续 Mount 的 root 不再参与校验，所有同 key Mount 都被改写为第一条根。

独立真盘探针：`/resources/a → key=same, root=A`、`/resources/b → key=same, root=B`，两盘 x 分别为 A / B；配置成功，读取 `/resources/b/x` 返回 **A**。这会把读写引向错误目录，也绕过对被丢弃根的有效性检查。

修复：先规范化每条声明，再确认同 key 的物理身份一致；不一致报 INVALID_ARGUMENT，不得静默采用第一条。补同 key 不同根拒绝、同 key 同根别名接受的最小用例；保留只创建一个 Adapter 的方案即可。

### R2 / P1：悬空数据库符号链接绕过独占

位置：`VfsRuntimeConfig.kt:141–148`。Files.exists 跟随符号链接，目标尚不存在时返回 false，代码把数据库别名当成普通新文件，使用 alias.db.lock；SQLite 随后在真实目标建库，而第二次用 real.db 会取得另一把 real.db.lock。

独立探针已同时打开两个 Runtime：先建立 `alias.db → real.db`（目标尚不存在），通过 alias create，再在第一个未关闭时通过 real create，第二次成功。修复可直接拒绝悬空最终符号链接，或完整解析未创建目标并生成一致锁路径；不要求接纳所有异常链接形态。补首次经悬空链接启动的反例，以及既有数据库文件链接 / 目录链接、相对路径正向验证；保留「残留文件不等于占用」语义。

### R3 / P1：状态库与锁落在可写 Mount 中，VFS 自己能破坏独占

位置：`VfsRuntimeConfig.resolve` 未校验数据库 / lock 与物理根的关系。配置 stateDatabase=`root/state.db`，再把 root 挂到 `/resources`，公开 list 暴露 state.db 与 state.db.lock；独立探针调用 `delete(alcyone://resources/state.db.lock)` 后，第二个 Runtime **成功打开同库**，第一实例仍存在。

这不是外部工具绕过锁，而是公开 VFS 操作破坏自身资源；状态库文件也可被覆盖或删除。最小修复是在取得资源前拒绝规范化状态库位于任一物理根内（含同根 / 别名），使其同目录锁及 SQLite sidecar 一并留在 VFS 数据目录之外；不必增加隐藏目录、ACL 或逐文件保护框架。补配置拒绝与根外状态库正常使用的用例。

### R4 / P2：命名空间删除只检查 Mount，遗漏已登记虚拟 Node

位置：`MountReconciler.kt` 只遍历 persisted Mount 检查 namespaceGone，added 为空就提前返回；后面的 Node 检查也只枚举旧 Mount 的子树。配置目录本身可以已登记但没有 Mount，因此没有被上述路径覆盖。

独立探针：初始 namespaces={resources,memory}、只挂 resources，stat(memory) 登记虚拟 Node；重开移除 memory 被接受，getNode 仍返回 `alcyone://memory/`，配置却已不再认可该命名空间。违反任务 §2.2「不能让已有 Node 无法寻址」。

修复应检查全部有效 Node 所在命名空间，包括虚拟目录，并在 added 为空的提前返回前完成；删除有记录的命名空间拒绝，删除真正空的命名空间按选定规则处理即可。不要将检查扩大成扫描物理文件树；补这个无 Mount 虚拟 Node 的真实重开用例。

### R5 / P2：A04 的取消原异常证据仍来自已取消 Deferred.await

位置：`InitializationFailureTest.kt` 的 cancellation 用例在 job.cancel 后仅通过 job.await 检查 CancellationException。被取消的 Deferred 本来就会报取消，这不能证明 create 内部没有吞掉 / 包装原异常；资源释放和再次 create 的断言有效，原样传播结论尚缺直接证据。

在调用 create 的协程内部捕获实际抛出值到独立 CompletableDeferred，检查原 CancellationException / cause；给 cancel 传入明确实例，保留资源与重新 create 断言。无需增加取消窗口矩阵或反复运行次数；清理异常 suppressed 当前属于源码审查，若仍无注入测试，交付不要写成真实故障全覆盖。

## 4. 建议优化与收口说明

- **S1 配置验证顺序。** eventBufferCapacity 直到创建 notifier 才校验，此前可能已保存 Mount；closeGracePeriod 也尚未验证。把可确认的数值非法值提前拒绝；resolve 会创建状态库父目录且读取文件系统，不应称「全部纯校验、零资源 / 零副作用」。不要求撤销建目录。
- **S2 保守遮蔽策略。** 新增祖先 Mount 包含旧子 Mount 时，最长匹配可能完全保留旧映射，目前仍拒绝。首片可接受保守拒绝，说明限制即可；若以后放宽，应证明旧路由不变，而非简单删除检查。
- **S3 清理与生命周期文档。** 统一真实释放顺序（adapters → notifier → DB → lock），Probe 位于 Core 创建前；补明 close 目前仅顺序调用幂等、没有并发幂等承诺，同步 AutoCloseable 是临时形状。T01 仍要求最终 suspend close，不把 use 示例冻结为最终公共契约。
- **S4 测试 / 异常细节。** 双 JVM 用例先 readText 再 waitFor(timeout)，子进程不退出时前者可能先无限阻塞；建议为读取 / 子进程生命周期加有界清理。StateInstanceLock.acquire 的 tryLock IOException 分支直接 channel.close 可能覆盖原异常，建议保留 acquire 失败、关闭失败进 suppressed，范围小不必建立通用清理框架。
- **S5 初始化写入的边界。** reconcile 在 Adapter 全部创建成功前提交 Mount，后续创建失败仍会保留该配置；相同配置可重试已验证，改根重试可能变成 CONFLICT。明确该事实与处置，不声称失败必定恢复到首次启动前状态；不通过删库实现补偿。
