## 1. 三十秒上手

宿主只提交配置，然后直接用 `Vfs` 的方法，最后关掉：

```kotlin
import com.github.noahshen.alcyone.context.vfs.*
import com.github.noahshen.alcyone.context.vfs.runtime.*

val vfs = AlcyoneVfs.create(
    VfsRuntimeConfig(
        stateDatabase = Path.of("data/state.db"),
        namespaces = setOf("resources", "memory"),
        mounts = listOf(
            MountConfig(VfsPath.parse("/resources/docs"), "docs", Path.of("/Users/me/docs")),
            MountConfig(VfsPath.parse("/memory"), "memory", Path.of("/Users/me/memory")),
        ),
    ),
)
try {
    val info = vfs.write(VfsUri.parse("alcyone://resources/docs/a.txt"), "hi".toByteArray())
    vfs.setMetadata(info.id, NodeMetadata(setOf("ct"), "胸部 CT"))
    println(vfs.read(VfsUri.parse("alcyone://resources/docs/a.txt")).size)
} finally {
    vfs.close()
}
```

订阅事件（T14 的有界进程内通知，提交之后才送达）：

```kotlin
vfs.subscribe { event -> println("${event.type} ${event.uri}") }
```

读大于 16 MiB 的文件用流式（`read` 会按 ByteArray 限额拒掉）：

```kotlin
vfs.openStream(VfsUri.parse("alcyone://resources/docs/big.bin")).use { result ->
    result.stream.copyTo(System.out)
}
```

宿主**不需要**创建 Operator、JDBC 连接、Repository 或各 Manager，也**不需要**关它们：`create` 建的都在实例里。

## 2. 配置长什么样

| 字段 | 说明 |
| --- | --- |
| `stateDatabase` | 状态库文件。相对路径按当前工作目录解析；父目录不存在会建出来；符号链接别名会被规范化成同一个真实路径 |
| `namespaces` | 顶级命名空间，例如 `setOf("resources", "memory")`。由配置提供，不是 API 白名单 |
| `mounts` | 挂载列表：`vfsPath`（逻辑位置）、`storageKey`（实例标识）、`root`（本机目录，必须已存在） |
| `limits` | 读写默认限额（`VfsLimits`，默认 16 MiB） |
| `eventBufferCapacity` | 事件队列容量，默认 `AsyncEventNotifier.DEFAULT_CAPACITY`（256） |
| `closeGracePeriod` | 关闭时给在途操作的自助时间（默认 5 秒）；到点还没完的会被请求取消 |
| `streamTotalLimit` | 流式读取的总量上限（字节），`null`（默认）表示不设总量上限；与 ByteArray 的 16 MiB 分开 |

`VfsLimits` 来自 `vfs/core`，因此 `vfs/runtime` 把 core 声明为 `api` 依赖：宿主配限额要能看见这个类型。
公开签名里没有 OpenDAL / SQLDelight / SQLite / Repository 类型。

**校验在创建任何资源之前完成**，非法配置直接报错，不会开库、不会开 Adapter、不会改系统环境：

| 非法配置 | 错误码 |
| --- | --- |
| 根目录不存在 / 不是目录 | `INVALID_ARGUMENT` |
| 两个不同的根互相包含 | `INVALID_ARGUMENT` |
| 挂载逻辑根 `/`、重复挂载位置 | `INVALID_ARGUMENT`（T09 沿用） |
| 挂载不在已配置命名空间下 | `INVALID_ARGUMENT` |
| `storageKey` 为空白或含空白 / 控制字符 | `INVALID_ARGUMENT` |
| 同一个状态库已经有实例在跑 | `CONFLICT` |
| 状态库目录没法用 | `STATE_ERROR` |

一个目录挂两个逻辑位置（同一个 `storageKey`、同一个 `root`）算**一块盘挂两次**，不是重叠，照样接受；
重叠检查发生在**不同的**根之间。

## 3. Mount 身份与冲突

**身份 = `storageKey` + `backendType` + 规范化物理根**三件套。Local FS 的 `backendType` 固定 `local-fs`，
物理根是 `LocalFsRoots.normalize` 的结果（符号链接已消解）。**凭据不入库**。

只比 `storageKey` 认不出「同一个 key 换了个根」，那种情况下旧 Node 会静默指向另一块盘，所以三件套缺一不可。

**首次启动**把接受的映射整批存进 `mount` 表（一个事务先清后写）；**重开时先核对再开放服务**：

| 变化 | 结果 |
| --- | --- |
| 相同配置重开 | 接受，映射一个字节都不改写 |
| 旧挂载被移除 | `CONFLICT`（旧位置下面的 Node 会变成寻址不到） |
| 逻辑位置换到另一块盘 / 换了 `storageKey` | `CONFLICT` |
| 同一个 `storageKey` 换物理根 | `CONFLICT` |
| `backendType` 变化 | `CONFLICT` |
| 旧挂载所属的命名空间被删 | `CONFLICT` |
| 新增挂载与旧挂载的路径互相包含（遮蔽） | `CONFLICT` |
| 新增挂载改变了已登记 Node 的解析结果 | `CONFLICT` |
| 新增到独立命名空间 / 不遮蔽任何旧挂载 | 接受 |

遮蔽这条的判据有两条，缺一不可：

1. **旧挂载的覆盖范围**：新增 `/resources/photos` 到已有的 `/resources` 之下，就把 A 的那片子树抢走了 ——
   即使那片子树一个 Node 都没懒注册，也不能接受；
2. **已登记 Node 在新配置下的解析结果**：逐个对照新旧路由，防止「新增一个祖先挂载」这类只影响已有 Node 的变化漏过去。

新增挂载与新增命名空间**不产生文件事件**，只影响路由。

冲突之后**原配置仍然能启动**：被拒时不改写任何映射、不重新注册旧 Node，也不会为了「回滚」删掉用户文件或状态库。

### 旧库升级（Schema 版本 1 → 2）

`mount` 表新增 `backend_type` 与 `physical_root` 两列，迁移文件 `1.sqm`（编号 N 表示「从版本 N 升到 N+1」）。
旧库已有的行拿不到真实物理根，这两列会是空串：

- **旧库有挂载行** → 启动报 `CONFLICT`，消息说明「这条记录没有物理身份，本版本无法验证配置指向的是不是同一块盘」，
  并给出处理办法：**确认配置无误后清掉 `mount` 表（或那几行）再启动**，代码不替调用方做这个判断；
- **旧库没有挂载行** → 迁移后正常初始化，按当前配置存下第一批映射。

Node / Metadata / Event 数据在迁移中原样保留。

## 4. 实例独占

- 状态库旁边的 `<state库>.lock` 上用 `FileChannel.tryLock` 占独占，**在打开状态库和写入配置之前**拿到；
- 覆盖同一个 JVM 里的第二个实例，也覆盖遵守同一协议的多进程启动（JVM 内重叠锁抛 `OverlappingFileLockException`，同样当「已占用」处理）；
- 锁随 `close()` 或初始化失败 / 取消释放；**锁文件留在盘上是正常的** —— 正常关闭、失败回滚、甚至进程被杀，文件都还在，
  「文件存在」不等于「还被占用」，能不能启动看的是锁；
- 状态库路径先规范化：相对路径、`./a/../a`、`符号链接目录`、指向别处的符号链接数据库文件，最后都收敛到同一个真实路径，
  所以别名拿不到第二把锁；
- **不承诺**阻止外部工具绕过 VFS 直接写这个 SQLite 文件（本锁只管遵守协议的启动）。

跨进程自己启动 VFS 也一样：第二个进程会拿到 `CONFLICT`，第一个进程退出后锁自动释放。

## 5. 初始化失败与取消

`create` 走到一半失败或被取消时：**已取得的资源按创建顺序的逆序释放**，原始异常原样抛出，
清理自己的失败挂在 `suppressed` 上，清理在 `NonCancellable` 里执行（不会因为调用方正在取消而被跳过）。
不删除已有用户文件或状态库来「回滚初始化」——已提交的 Node 与事件就是事实。

修好配置之后**同一个配置能再次 `create`**：没有残留的锁、没有没关的连接、没有没关的 Adapter。

## 6. 流式读取

`openStream(uri, options)` 返回一个 `VfsStreamResult`：

| 成员 | 说明 |
| --- | --- |
| `stream` | 内容流，分块读；不要 `readAllBytes()` 一次性拉全 |
| `sizeBytes` | 后端报告的文件长度，不知道时为 `null`；不是已读字节数 |
| `uri` | 这次读的逻辑文件 |
| `close()` | 放掉底层句柄；重复 close 是空操作 |

三条规则：

1. **拿到之后要 close**。忘了关的话，Runtime 在 `close()` 时会替你收回来。
2. **重复 close 是空操作**，不报错也不重复关底层句柄。
3. **关闭之后不能再读**：底层流已放掉，读取会失败。

**限额**：实际上限取 `min(streamTotalLimit, options.maxTotalBytes)`；两者都是 `null` 时**不设总量上限**（仍分块读，
不会把整个文件塞进内存）。读到超限的那一次报 `LIMIT_EXCEEDED`。调用级上限只能**收紧**配置上限，不能放宽。

**错误**：目录（含配置推导出的目录）报 `TYPE_MISMATCH`，路径不存在报 `NOT_FOUND`。
**只读语义**：开流不登记 Node、不发事件，和 `read` 一致。

**怎么关：关 `result`，不是关 `result.stream`**。两种都能释放底层文件句柄，但 Runtime 的「在途资源」是跟着
`result.close()` 摘掉的：只关 `result.stream` 的话，这条流会一直留在跟踪集合里，直到下次 `close()` 才被清掉。
所以统一写成 `result.use { }`（或 `try/finally { result.close() }`）。

若在 `openStream` 返回**之前**这次调用就被取消（例如还在交接流的那一刻），Runtime 会当场把已建好的流关掉，
不会拖到 `close()` 才回收，也不会算进跟踪集合。

**所有权**：流交给调用方后由调用方关闭；取消恰好落在「流已建好、还没交给调用方」时，Runtime 当场释放它，
不会留下没人管的句柄；调用方关流后 Runtime 立即停止跟踪。

## 7. 关闭与在途操作

`close()` 是**挂起函数**（等待期要挂起，不能承诺 `AutoCloseable` 那种阻塞语义），用 `try/finally` 而不是 `use`：

```
try { /* 用 vfs */ } finally { vfs.close() }
```

关闭做四件事：

1. **转 closing**：之后新的公共操作（read / write / stat / list / getNode / delete / metadata / openStream）直接报 `CLOSED`；
2. **等在途操作**：已经在跑的调用有 `closeGracePeriod` 的时间自己跑完；
3. **请求取消并等待收尾**：到点还没完的发协作取消（**不**碰宿主的父 Job，也**不**强杀卡在 native 里的线程），**并等待所有在途操作的必要收尾（含事务回滚、资源清理）彻底完成**；
4. **逐个释放**：流 → 通知器 → 各块盘 → 状态库 → 独占锁。锁最后放，放完才算没人占着状态库；绝不会在旧操作还在回滚时就提前把库关掉或把锁放给新实例。

- `close()` **幂等**：重复调用是空操作；**并发**调用共享同一次完成结果。**第一次关闭失败时，后续并发 / 重复调用会收到同一个失败**，
  不会有人拿到「成功」的假信号；已经在关的那一次负责把资源收干净。若从事件 Consumer 回调内部调用 `close()`，
  该调用只提交关闭请求就安全退出，不与外部关闭互等死锁（资源由外部那次释放完）。
- 清理在 `NonCancellable` 内跑：调用方正好在取消时，清理不会被跟着取消掉。
- 一个资源关失败**不阻止**其余资源拿到关闭尝试；第一个失败抛给调用方，其余挂在 `suppressed` 上。
- 已提交的 Node、Metadata 与事件不会因为 `close()` 消失，重开还在。

**边界**：等待期是「自助时间」不是「强杀期限」。等待期只限制**正常自助等待**的时间：到点发协作取消后，
关闭会等每个在途操作的**结束信号**（`done`，含 `NonCancellable` 里的事务回滚 / 资源清理）完成后，才关数据库、放独占锁。
这个结束信号只有调用自己清理完才会完成，关闭的取消**改不动它**——所以不会出现「取消一发、等待就直接放行」的情况，
也不会在旧操作还在用连接时把库关掉。

真正卡在 native 调用里、不响应取消的操作不会被强行弄死；这类操作让 close 停在「等待收尾」这一步，
它最终可能拿到 `STATE_ERROR`。这是本轮明确的边界（已验证交接取消与协作取消路径；未模拟不可中断的 native 卡死），
不是「超时后就一定能关干净」。
