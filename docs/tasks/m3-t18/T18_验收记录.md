### A03 实例独占 —— 通过

| 判据 | 证据 | 层次 |
| --- | --- | --- |
| 同进程第二实例拒绝 | `InstanceExclusivityTest`：第二个 `create` → `CONFLICT` | 真实栈 |
| 释放后可重开 | 同用例：关闭后再次 `create` 并 `stat` 成功 | 真实栈 |
| 别名不绕过 | `a path alias does not bypass the exclusive lock`：经符号链接目录指向同一状态库 → `CONFLICT` | 真实栈 |
| 文件存在 ≠ 占用 | `a leftover lock file does not count as taken`：`close` 后 `.lock` 仍在盘上，下一次 `create` 照样成功 | 真实栈 |
| 最小双 JVM 探针 | `a second process on the same database is refused and the lock dies with the process`：用项目内 JDK（`System.getProperty("java.home")`）经 `ProcessBuilder` 拉起 `LockProbeProcess`。父进程持锁 → 子进程打印 `REJECTED CONFLICT …already in use`；父进程关闭 → 子进程打印 `LOCKED`；子进程**只 create 不 close** 直接退出 → 父进程能再拿到锁 | 真实栈 |

子进程必须用和父进程**同一个磁盘目录**：早先版本给它单独一个目录，结果先被「同 key 换物理根」这条挂载冲突拒掉，
测的就不是独占锁了。子进程把 `CONFLICT` 的消息一并打印，测试断言消息含 `already in use`，避免这种「拒对了但拒错了原因」。

## 3. 变异对照（执行者：开发 Agent）

三个变异都在 `vfs/runtime` 主源码上临时改，跑指定测试，**随后立即还原**，还原后 `./scripts/check` 全绿。
每条都带 `--rerun-tasks`：不带的话 Gradle 会判 `UP-TO-DATE` 跳过却仍输出「成功」（T16 被复核指出过）。

| # | 变异 | 命令 | 结果 |
| --- | --- | --- | --- |
| 1 | 去掉「同 key 换物理根」的身份检查（`identityChanged` 的 `if` 改成 `if (false)`） | `./scripts/dev gradle :integration-tests:vfs:test --tests "*MountConfigurationTest*" --rerun-tasks --console=plain` | **失败**：`the same storage key pointing at a different root is a conflict` FAILED（6 个用例挂 1 个） |
| 2 | 去掉「新增挂载遮蔽旧挂载」检查（内层循环改成 `if (false)`） | 同上 | **失败**：`a new mount that shadows an existing one is refused` FAILED（6 个用例挂 1 个） |
| 3 | 关闭时不释放文件锁（`lock.release()` 与 `channel.close()` 都换成空 `runCatching`） | `./scripts/dev gradle :vfs:runtime:test --rerun-tasks --console=plain` | **失败**：13 个用例挂 5 个，含 `a second instance on the same database is refused and accepted again after close`、两个 A04 用例、双 JVM 探针 |

补充一条观察：只去掉 `lock.release()` 而保留 `channel.close()` 时 **A03 不会失败** ——
JVM 在关闭通道时已经把该进程在该文件上的 POSIX 锁放掉了。本实现两处都做，
`lock.release()` 的作用是把「先放锁」这个意图写明，不依赖 JVM 的这个细节。

还原后的完整检查：`./scripts/check` → `BUILD SUCCESSFUL in 31s`。

## 5. 说明与未验证项

**旧版本库怎么造的**：版本 1 与版本 2 的差别只有 `mount` 表新增的两列，
`node` / `metadata` / `event` 三张表逐字未变。因此「真实旧版本库」的做法是：
先用当前代码建库、写入真实 Node 与事件 / 挂载行，再用 `ALTER TABLE mount DROP COLUMN …` 把 mount 退回两列形状，
最后 `PRAGMA user_version = 1`。得到的是一个真的 SQLite 文件，结构与版本 1 代码写出来的等价。
这比复制一份历史 DDL 更省事，但**前提是「两版只差这两列」成立**——该前提可由 `1.sqm` 与 `Mount.sq` 直接核对。

**平台**：本轮所有证据都在 **macOS arm64**、项目内 JDK（Temurin 21.0.12.1+1）上实跑。
**Linux x64 / arm64 本轮未验证**（文件锁语义在 Linux 上同样是 POSIX `fcntl` 锁，但没实跑过，不作结论）。

**未验证 / 本轮不承诺**：

- 公共流式读取、遗漏流回收（任务 §2.4）——未做，`vfs/api` 本轮**一行未改**；
- 关闭等待期、`closing` 状态、关闭后新操作返回 `CLOSED`（任务 §2.5）——未做；
- `close()` 期间正在进行的操作会怎样：当前实现**不等**，这些调用可能报 `STATE_ERROR` / `CLOSED`；
- 不可中断的 native 阻塞（`LocalFsStorage` 的 OpenDAL 调用）超时后的行为——本轮没有超时逻辑，也不宣称能强杀；
- 事件可靠投递 / 回放——沿用 T14 的有界队列，满了丢通知；
- 多进程**并发写**同一个状态库：只验证了「第二个启动被拒」，没有验证两个已启动实例的数据竞争（独占锁就是为此存在的）；
- `VfsStateDatabase` 的跨进程独占检测（T03 §7 原写「首版不做」）现在由 Runtime 的锁文件承担，但**库层本身**仍不检测；
- Windows 平台行为：未跑，也未评估（`tryLock` 语义与 POSIX 锁不同）。
