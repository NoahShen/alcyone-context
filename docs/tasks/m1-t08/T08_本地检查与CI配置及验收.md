## 1. 目标与现状

让开发 Agent 和 CI 使用一致、可重复的入口完成编译、单元测试和格式检查，并能定位失败原因。本任务复用现有工程能力，不修改 VFS 业务代码或增加新的业务测试。

| 已有能力 | T08 的处理 |
| --- | --- |
| `scripts/dev bootstrap` | 复用项目内 JDK / Gradle 下载与校验，不重复实现安装器 |
| `scripts/dev gradle …` | 复用项目 JDK、Gradle 缓存及临时目录隔离 |
| `gradle/toolchain.versions`、版本目录 | 保持版本单一来源，不升级依赖或在 workflow 复制版本号 |
| `build` 已包含 `spotlessCheck` | 检查只报告错误，自动格式化仍由开发者显式运行 |
| macOS arm64 支持范围 | CI 与此范围匹配；本轮扩展到 Linux x64 / arm64 以适配未来部署环境 |
| T07 已通过 120 个测试 | 作为当前参考数量，不能在脚本里写死；新增测试应自动纳入 |

例：本地和 CI 都调用同一检查入口，格式不合格时返回失败，由开发 Agent 修正后重跑。

## 2. 开发内容

### 2.1 本地检查入口

提供一个简短入口（建议 `scripts/check`），执行现有 `./scripts/dev gradle clean build --console=plain`；工具链未准备时清楚提示先运行 bootstrap。检查必须保留失败退出码、不自动修改源码，除确有需要外不拆成重复执行的多组 Gradle 命令。

例：首次运行按“bootstrap → check”两步完成；已有缓存时可支持透传 `--offline`，参数形式由开发 Agent 在实现时明确。

### 2.2 GitHub Actions 配置

在 `.github/workflows/` 增加一个构建工作流，覆盖 PR、默认分支 push 和手动触发，执行“检出 → bootstrap → 本地检查入口”。运行器必须落在 `scripts/dev` 支持的平台列表内（macOS arm64、Linux x64、Linux arm64），本轮选用 `ubuntu-latest`；不得用不同架构运行器绕过现有脚本的检查。

例：CI 使用仓库内工具链，而不是调用运行器预装的默认 Java。若当前账号或仓库没有适用运行器，记录环境限制和所需条件，不为完成 T08 引入付费机器、自托管服务或多平台工具链改造。

### 2.3 结果与失败信息

工作流应在检查失败后仍尽可能保存已有 JUnit XML 与测试 / 格式检查报告，并设置合理的任务超时和最小所需权限。缓存不是本轮必需项；若启用，只缓存项目目录内的相关文件，并保持原有下载校验有效。

例：测试断言失败后能在运行记录查看对应报告；如果 bootstrap 已失败、尚无报告，则直接以安装日志定位问题，不伪造测试结果。

### 2.4 运行说明

补充首次安装、日常检查、主动格式化、报告位置和常见失败处理说明，写清当前平台范围及项目工具链隔离原则。说明以实际实现为准，已有文档可链接复用，不复制大段工具链设计。

例：格式错误先运行 `./scripts/dev gradle spotlessApply`，检查入口自身不执行这个命令；网络不可用与测试失败分别说明。

## 5. 验收标准

| 编号 | 必须满足的结果 | 验收证据 |
| --- | --- | --- |
| A01 统一入口 | 本地与 CI 调用同一检查入口，包含编译、测试、格式检查；失败返回非零，不自动格式化 | 脚本 / workflow 审查及实际命令 |
| A02 环境隔离 | 使用项目内 JDK、Gradle 与缓存；不修改系统 Java、全局 Gradle 或 shell 配置，版本复用已有来源 | 执行日志与环境配置审查；只有改动工具链时才扩大隔离回归 |
| A03 正常检查 | common、API、Core 真实编译并执行测试，完整 build 成功；仍为空的后续模块可为 NO-SOURCE | 构建输出、JUnit 数量与失败 / 错误 / 跳过统计，不把空模块算作业务验收 |
| A04 失败可见 | 在临时副本分别制造一处格式错误和一个现有测试断言失败，检查入口均返回非零且不改写源码；CI 不掩盖失败 | 两次简短验证结果、退出码，临时改动不进入交付；无需新增永久业务测试 |
| A05 CI 配置 | 触发条件、匹配的平台、统一命令和报告保存正确；不依赖作者机器绝对路径或预装 JDK | 配置语法检查、运行器依据与 workflow 审查；实际运行时补对应提交和运行链接 |
| A06 证据真实 | 分别记录本地已验证、CI 配置已检查、远端已运行 / 未运行 | 若未运行远端，明确原因，不将本地结果写成 CI 通过 |
| A07 交付说明 | 使用说明能指导首次准备和日常检查；变更文档有前部修改说明，任务状态准确 | 使用说明、验收记录及变更清单 |

T08 的交付目标是检查入口与 CI 配置；远端环境不可用时，允许以本地实跑和配置检查验收交付，但必须保留“远端 CI 未验证”的限制，不能宣称 CI 已绿。若远端实际执行失败，应先区分环境不可用与配置 / 代码缺陷；后者必须修复，不能用“未验证”掩盖失败。
