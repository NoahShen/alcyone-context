## 5. 自查中发现并修复的问题

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| CI 的 `check` 步骤会掩盖失败 | `./scripts/check 2>&1 \| tee log` 中，若 shell 未启用 `pipefail`，整条管道的退出码取自 `tee`（恒为 0）。GitHub Actions 的默认 `bash -e {0}` **不**启用 `pipefail` | 该步骤显式声明 `shell: bash`（对应 `bash --noprofile --norc -eo pipefail {0}`）。已用 `bash -eo pipefail -c 'false \| tee /dev/null'` 复现退出码 1，而默认 `bash` 退出码为 0，确认该修复是必要的 |
| 格式检查没有可上传的报告（历史记录） | Spotless 不生成报告文件，违规只打到控制台；首版写入 `.local/tmp/ci-check.log`，但该路径在隐藏目录内会被 `upload-artifact@v4` 默认跳过（详见复核 R3） | 首版写入该路径，后续按复核 R3 修复改写到 `ci-logs/check.log`（见第 5.2 节）。历史记录保留在此说明原委 |
| `find -exec` 无法调用 shell 函数 | 首版重构把 `shasum -a 256` 包成 `sha256_of()` 函数再交给 `find -exec`，但 `-exec` 只能执行真实可执行文件。实际报错 `find: sha256_of: No such file or directory`，且 `find` 对 `-exec` 失败仍返回 0，**清单被静默写成空文件** | 改为 argv 数组 `SHA=(sha256sum)` 或 `SHA=(shasum -a 256)`，用 `find . -type f -exec "${SHA[@]}" {} +` |
| GNU `sha256sum -c` 对空清单返回 0 | 上一条留下的空清单触发连锁问题：BSD `shasum -c` 对空文件返回 1（正确拦截），但 GNU `sha256sum -c` 返回 **0**，于是 `check_install` 把一个**从未被校验**的安装判为完好，`bootstrap` 会输出 `Ready` 并让构建跑在一个未校验的 JDK 上。且 `[[ ! -d $JDK_DIR ]]` 判断在目录已存在时会跳过清单重建，故障永久存在 | `check_install` 改用 `[[ -d $dir && -s $manifest ]]`（`-s` 同时覆盖缺失与空文件），并在 `bootstrap` 的两个安装分支加上“目录存在但清单为空则重建”的条件。已实测：`: > empty; sha256sum -c empty` → 0，`shasum -a 256 -c empty` → 1 |
