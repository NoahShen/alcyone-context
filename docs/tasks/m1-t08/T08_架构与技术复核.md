## 2. 必须修改

### R1 / P1：Ubuntu 工作流与 OpenDAL 模块的平台限制冲突

`.github/workflows/check.yml:24` 选择 ubuntu-latest，但 `vfs/storage-opendal/build.gradle.kts:12` 无条件要求 Mac / aarch64，且第 9 行固定 `osx-aarch_64` native classifier。该模块由 settings 无条件包含，统一入口执行全量 build，因此 Linux 会在项目配置阶段被拒绝，尚未进入测试。

处理：按已接受的 Linux 范围贯通模块构建的平台选择，或明确拆分支持范围与检查目标；不能仅删 guard、继续装载 macOS native 依赖，也不能跳过模块后仍声称完整构建通过。修复后用真实 Linux x64 完成一次统一检查；若环境不可用，明确保留验证缺口，不把已知配置错误归为“未验证”。Linux arm64 单独标明实际验证程度。

### R2 / P2：缺失清单时把现有 JDK 重新当作可信安装

`scripts/dev:83` 在 JDK 目录存在、清单缺失 / 为空时调用 unpack_jdk，但该函数第 69 行仅在目标目录不存在时移动新归档；随后第 85 行直接给旧目录生成新清单。结果是归档校验通过却实际继续使用未经该归档恢复的旧安装，损坏或不完整安装可能被重新判为完好。

已用临时副本和本地小型归档复现：归档 java 输出 VERIFIED_ARCHIVE_JAVA，既有目录 java 输出 STALE_INSTALL_JAVA，清单缺失；bootstrap 返回 0 并执行 STALE_INSTALL_JAVA，清单记录的是旧目录。日志在 `.local/tmp/t08-review-bootstrap.log`，临时副本已删除。

处理：该状态直接失败并提示移除不完整安装，或用已校验归档重新建立安装后再生成清单；两种都可，不要求自动恢复框架。补一次小范围失败 / 修复验证即可。

### R3 / P2：CI 的检查日志不会进入 artifact

workflow 第 49 行上传 `.local/tmp/ci-check.log`，但 upload-artifact@v4 默认排除隐藏文件和隐藏目录内文件，当前没有启用对应选项。因此作为格式报告的日志会被忽略；JUnit XML 仍可能正常上传，不能由“artifact 创建成功”推断日志已保存。依据：[upload-artifact v4 官方说明](https://github.com/actions/upload-artifact/blob/v4/README.md#uploading-hidden-files)。

处理：将待上传日志复制到普通报告目录，或仅对明确列出的报告路径启用 include-hidden-files；不要上传整个 `.local`。验证 artifact 的文件列表包含检查日志，失败时也保留。

### R4 / P2：交付文档与当前范围、证据不一致

`T08_交付文档.md` 一方面称三平台“已验证”，另一方面称 Linux 未支持、脚本会拒绝，末尾仍写 DONE；AGENTS 与验收记录则明确 Linux 仅部分检查、任务 IN_PROGRESS。任务第 6 节的开发指令还要求 macOS-only，与 Linux 需求变更矛盾，交付文档也缺少要求的前部“本次修改”。

处理：统一为 macOS 完整构建已验证、Linux x64 归档流程部分验证、Linux arm64 静态检查、远端未运行，并记录 R1～R3 尚待处理。完成修复后再按实际结果更新；Linux 工具链允许执行不等于完整项目或 OpenDAL native 已验证。

## 4. 可以接受的设计取舍

- `scripts/check` 作为薄入口，复用 scripts/dev 与 clean build，失败退出且不自动格式化，符合本地 / CI 一致性目标。
- Linux 扩展集中于构建与工具链，版本和校验值仍集中维护；业务源码及模块依赖方向没有被修改。扩展本身可接受，R1 是适配遗漏。
- 单个 Ubuntu CI job、暂不加缓存、无发布 / 部署流程，复杂度适合当前阶段。
- 检查步骤显式使用 Bash pipefail，避免 tee 吞掉失败；最小权限、超时、失败后上传现有报告均合理。
- 远端未运行可以如实保留限制；无需为了验收额外部署服务，但已知配置错误不能以该限制豁免。
