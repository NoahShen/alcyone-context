# T23 使用说明：失败之后盘上会留下什么

## 本次修改（2026-10-09，开发方自测）

- 新增本文件：按「看到错误后可能留下什么」组织，提醒按事实检查，不建议无条件重试或自行清库。涉及全文。

配套：[交付文档](T23_交付文档.md)、[验收记录](T23_验收记录.md)。

## 1. 为什么要有这份说明

VFS 的物理文件操作和状态库事务**不在同一个事务里**：文件已经写进磁盘、SQLite 才可能提交失败。所以「调用抛异常」**不等于**「什么都没发生」。这份说明按错误阶段告诉你**该检查什么**。

## 2. 通用的三条

1. **看 `VfsException.effect`**：

| effect | 含义 |
| --- | --- |
| `NONE` | 确认没有本次操作造成的物理或逻辑变更 |
| `PARTIAL` | **已知**存在部分变更，首版不自动修复 |
| `UNKNOWN` | 后端没说清，无法判断是否完成 |

2. **`code` 按后端原样保留**：`STORAGE_ACCESS_DENIED`、`UNKNOWN` 不会被改写成 `CONFLICT` / `NONE`；只有**已观测到的类型 / 长度矛盾**才是 `CONFLICT`。
3. **`cause` 是原始失败**：清理或包装失败挂在 `suppressed` 上，不覆盖原异常。

## 3. 按阶段检查

| 阶段 | 可能留下 | 怎么确认 |
| --- | --- | --- |
| 写入物理成功、状态 / 事件提交失败（`STATE_ERROR`） | **文件在盘上**；Node 路径 / Metadata / 事件一起回滚 | 读目标 `read`；`getNode` 查旧状态；重开确认状态库 |
| 删除物理成功、提交失败 | **文件已不在**；旧逻辑 Node / Metadata 可能仍在 | 看盘上路径；`getNode(旧 ID)` 可能仍返回 |
| 补父目录中途失败 | 已建出来的目录**留着**，`effect = PARTIAL` | `list` 父目录 |
| 移动到目标成功、源删除失败 | **两份都在**，逻辑路径**仍指向源** | 两个路径都查 |
| 整树复制后确认 / 源复查发现矛盾 | 目标可能留**部分或全部**内容，源**完整** | 比较两边条目集合与长度 |
| 目录复制整树确认后删源失败 | 目标完整、源可能**残缺** | 比条目数 |
| 提交前取消 | 物理可能已完成，逻辑未提交 | 取消异常原样传播，按上述阶段核对 |
| 已知拒绝（预检 / 结构保护 / 目标已存在） | **零副作用**，`effect = NONE` | 不用检查 |

## 4. 不要做的事

- **不要**假定「异常 = 无变更」，尤其在 `PARTIAL` / `UNKNOWN` 时。
- **不要**无条件自动重试：源可能已删（移动）、目标可能已存在（写入）。
- **不要**为了「恢复」自己删状态库或清空 `mount` 表——那会丢掉已提交的 Node 与事件。
- **不要**用会懒注册的 `stat` 去核对「失败后的待核对状态」，它本身会改状态。

## 5. 失败后怎么继续用

失败**不会**把实例或锁留坏：边界正常释放，后续操作照常可用（多处用例都验证了「拒绝 / 失败后另一次操作成功」）。正常 `close()` 后再 `create` 能读到已提交的状态。

## 6. 本任务没承诺什么

COMMIT 成功之后取消、崩溃 / 断电恢复、外部进程绕过 VFS 改文件、WebDAV。这些不在 T23 范围。
