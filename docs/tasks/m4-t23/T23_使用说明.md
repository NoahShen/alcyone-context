## 1. 为什么要有这份说明

VFS 的物理文件操作和状态库事务**不在同一个事务里**：文件已经写进磁盘、SQLite 才可能提交失败。所以「调用抛异常」**不等于**「什么都没发生」。这份说明按错误阶段告诉你**该检查什么**。

## 2. 通用的三条

1. **看 `VfsException.effect`**：

| effect | 含义 |
| --- | --- |
| `NONE` | 本次操作**确认没有造成物理变更**；但**不等于「没有任何逻辑变化」**。 |
| `PARTIAL` | **已知**存在部分变更，首版不自动修复。 |
| `UNKNOWN` | 后端没说清，无法判断是否完成。 |

   `NONE` 的例外：失败可能发生在**源懒注册之后**（例如复制读取失败前，源身份可能已经被登记）。所以只有**预检 / 结构保护 / 目标已存在**这类「**身份登记及物理修改之前**」的拒绝才是真正零副作用；带 `NONE` 的物理失败只说明「没建成父目录 / 没写目标 / 没删源」，不排除已发生的懒注册。

2. **`code` 怎么来**：
   - `UNKNOWN` 是 **effect**，不是错误码；`code` 与 `effect` 是两个字段。
   - **后端原始错误保留**只适用于对应 Storage 失败被合并那条路径（如确认 / 删源时的后端失败）：原始 `code` 不会一律改写成 `CONFLICT`；原始 `effect=UNKNOWN` 不会降成 `NONE` / `PARTIAL`。
   - **物理已完成之后的纯状态失败**是另一回事：会被**包装成 `STATE_ERROR` + `PARTIAL`**，`cause` 指向原始失败——不要以为这时 `code` 一定还是后端原值。

3. **`cause` / `suppressed` 是可选的**：很多异常会挂原始 `cause`，跨包装时也可能用 `suppressed`，但**不是每个异常都必有这两个字段**；核对时先判空、再按 `code` / `effect` 分支，不要假设它们一定存在。

## 3. 按阶段检查

| 阶段 | 可能留下 | 怎么确认 |
| --- | --- | --- |
| 写入物理成功、状态 / 事件提交失败（`STATE_ERROR`） | **文件在盘上**；本事务的状态修改回滚，旧 Node / Metadata 保留，成功事件未提交 | 读目标 `read`；`getNode` 查旧状态；重开确认状态库 |
| 删除物理成功、提交失败 | **文件已不在**；旧逻辑 Node / Metadata 可能仍在 | 看盘上路径；`getNode(旧 ID)` 可能仍返回 |
| 补父目录中途失败 | 已建出来的目录**留着**，`effect = PARTIAL` | `list` 父目录 |
| 移动到目标成功、源删除失败 | **目标已写**；源**可能仍在、可能被部分删除、结果也可能未知**，逻辑路径仍指向源 | 检查两个路径的实际内容；`effect` 本身不能确定源是否删干净 |
| 整树复制后确认 / 源复查发现矛盾 | 目标可能留**部分或全部**内容；只能保证**本次尚未进入删源**，不保证被外部改动过的源仍完整 | 比较两边条目集合与长度 |
| 目录复制整树确认后删源失败 | 目标完整、源可能**残缺**（也可能结果未知） | 核对实际条目及内容，不仅比较条目数；`effect` 不能代替检查 |
| 提交前取消 | 物理是否已完成取决于取消点（物理移动前 / 目标写阶段 / 事务内）；本次最终状态事务未提交，但之前的懒注册可能已保留 | 取消异常原样传播，按上述阶段核对 |
| 已知拒绝（预检 / 结构保护 / 目标已存在，**身份登记及物理修改之前**） | **零副作用**，`effect = NONE` | 不用检查；注意这不包括「已过预检、进入读写阶段」的物理失败 |

## 4. 不要做的事

- **不要**假定「异常 = 无变更」，尤其在 `PARTIAL` / `UNKNOWN` 时。
- **不要**无条件自动重试：源可能已删（移动）、目标可能已存在（写入）。
- **不要**为了「恢复」自己删状态库或清空 `mount` 表——那会丢掉已提交的 Node 与事件。
- **不要**用会懒注册的 `stat` 去核对「失败后的待核对状态」，它本身会改状态。

## 5. 失败后怎么继续用

本轮**已验证**的边界是：**受控失败以及回滚成功**的这些场景里，边界正常释放、后续操作照常可用（多处用例都验证了「拒绝 / 失败后另一次操作成功」）。

但这**不能推广成「任意失败后实例一定可用」**：
- 有一条复用的真 COMMIT 失败用例是**主动把状态库关掉**来造提交失败，那种失败之后库本身已经不可用；
- 正常 `close()` 后再 `create` 只会读到**已提交**的状态，**不等于**修复了物理与逻辑之间已经存在的不一致（物理变更不回滚）。

所以要继续用，先按 §3 核对实际残留，再决定下一步；不要假设一次失败之后一切照旧。

## 6. 本任务没承诺什么

COMMIT 成功之后取消、崩溃 / 断电恢复、外部进程绕过 VFS 改文件、WebDAV。这些不在 T23 范围。
