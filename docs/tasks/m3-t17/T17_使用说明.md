# T17 使用说明：Metadata 查询与更新

## 本次修改（2026-10-04，T17 实现完成）

- 新文档：讲清 `getMetadata` / `setMetadata` 的日常用法、**同值也发事件**这条最小规则、整体替换与清空、逻辑更新时间、失败与取消表现；对应实现与证据见 [验收记录](T17_验收记录.md)。

状态：随 T17 实现交付，任务 IN_REVIEW。

## 1. 这两个方法解决什么问题

一个 Node 在 VFS 里有一串「跟着它走」的逻辑信息：标签、说明、扩展字段。它们不在文件里，在状态库里，所以**不会跟着物理文件被搬走或删掉**，只有 VFS 自己的操作会改它们。

典型用法：先 `stat` 拿到 ID，再打标签。

```kotlin
val info = vfs.stat(VfsUri.parse("alcyone://resources/medical/ct/a.dcm"))
vfs.setMetadata(info.id, NodeMetadata(tags = setOf("ct", "影像"), description = "胸部 CT"))
val saved = vfs.getMetadata(info.id) // NodeMetadata(tags=[ct, 影像], description=胸部 CT)
```

## 2. 查询：有效 Node 返回保存值，没设置过返回空对象

`getMetadata(id)` 只查状态库，**不查挂载、不 stat 物理文件、不碰 Storage、不发事件**。

```kotlin
vfs.getMetadata(id) // Node 已经登记过但从没设置过 → NodeMetadata()（空 tags、无 description、空 extensions）
```

三种情况分得很清：

| 情况 | 结果 |
| --- | --- |
| Node 有效、设置过 | 返回保存的那个完整对象 |
| Node 有效、没设置过 | 返回 `NodeMetadata()`（空对象） |
| ID 没登记过，或者已被删除 | `VfsException(NOT_FOUND)` |

**空对象和「查不到」是两回事**：无效 ID 绝不会退化成空 Metadata，否则调用方会把「这个 Node 不存在」误当成「它没有标签」。

物理文件在不在不影响这两个方法。外部直接删掉了磁盘上的文件、Node 还挂着的时候，照样能读写它的 Metadata；经 `VFS.delete` 成功删掉之后，同一个旧 ID 的两个方法都报 `NOT_FOUND`。

文件、目录、已登记的虚拟目录都按同一条规则走：只认「这个 ID 现在是不是有效 Node」。

## 3. 更新：整体替换，不是合并

`setMetadata(id, metadata)` 把 `tags` / `description` / `extensions` **整个换掉**，你给什么就是什么。没提到的字段不会「保留旧值」。

```kotlin
vfs.setMetadata(id, NodeMetadata(tags = setOf("ct", "影像"), description = "胸部 CT 报告"))
vfs.setMetadata(id, NodeMetadata(description = "报告")) // 只有 description
vfs.getMetadata(id) // tags 变空、extensions 也变空 —— 整体替换，不与上一批合并
```

**清空**就是传空对象：

```kotlin
vfs.setMetadata(id, NodeMetadata())
vfs.getMetadata(id) // NodeMetadata()：三个字段全空，状态库里不留行
```

不想清空又少写字段，就把当前值读出来改一改再传回去（它是整体替换接口，不提供字段级 patch）：

```kotlin
val current = vfs.getMetadata(id)
vfs.setMetadata(id, current.copy(description = "报告"))
```

VFS 不解释 `extensions` 里的业务含义，也不校验标签拼写、不做大小写或分隔符规范化。

## 4. **同值也发事件**：本轮明确的最小规则

**每一次有效 `setMetadata` 都产生一条 `METADATA_UPDATED`，包括传入和当前完全相同的值、包括重复清空。**

```kotlin
vfs.setMetadata(id, NodeMetadata(description = "报告")) // 事件 1
vfs.setMetadata(id, NodeMetadata(description = "报告")) // 事件 2：值一模一样，照样发
vfs.setMetadata(id, NodeMetadata())                     // 事件 3：清空
vfs.setMetadata(id, NodeMetadata())                     // 事件 4：重复清空，照样发
```

事件里 `nodeId` 是目标 ID，`uri` 是这一次受保护读取里看到的 Node 当时所在路径。`getMetadata` 零事件。

为什么不省掉同值那次：判断「有没有真的变过」是**调用方**的事，VFS 不替它猜。想要安静一点，调用方自己比 `getMetadata` 的前后两次结果；下游 Consumer 也应当能对每条 `METADATA_UPDATED` 幂等处理。

## 5. 更新时间：逻辑时间，不是文件时间

每次有效替换在**同一个事务**里顺手更新 Node 的逻辑更新时间 `updatedAt`（就是 `getNode(id).updatedAt` 那个值）：

- ID、逻辑路径、类型、登记时间 `registeredAt` 都不变；
- **不动物理文件的修改时间**；
- 注入时钟精度内连续设置可能拿到相同时间，**不要求严格递增**；
- Metadata、Node 时间和事件同批提交，失败一起回滚。

所以「这个 Node 的逻辑记录最后一次被谁改了、什么时候改的」能看出来，而「文件什么时候被写到盘上」是另一回事。
## 6. 失败和取消时是什么样

| 情况 | 报什么 |
| --- | --- |
| ID 无效（没登记 / 已删除） | `NOT_FOUND`，effect `NONE`，一个字节都没改 |
| 状态库写入失败（真实实现已映射好） | 原 `STATE_ERROR`，**cause 保留**，effect `NONE` |
| 状态库抛了不是 VfsException 的普通异常 | 转成 `STATE_ERROR` + `NONE`，原异常挂在 cause 上 |
| 协程被取消 | `CancellationException` 原样传播 |

**为什么普通失败是 `NONE` 而不是 `PARTIAL`**：这两个方法完全没有 Storage 副作用，改的东西全在状态库那一个事务里，事务回滚就是干干净净什么都没发生。不套用删除操作那套 `PARTIAL`（文件已经删掉了、撤不回来）。已有事实照旧原样带出——状态库自己报的 `code` 与 `effect` 一律不改写，也不会因为「捕获到异常」就宣称一定没提交。

**取消**：`CancellationException` 原样传播，不包装。取消落在 COMMIT 之前 → 整个事务回滚；落在 COMMIT 之后 → 不证明提交被撤销。通知队列满被丢弃、或 Consumer 自己抛错，都**不撤回**已经提交的更新。

## 7. 并发时会发生什么

查询和更新排在**同一条队**上（和 T15 / T16 的文件操作共用一把边界）：

- 一个更新正在提交时，后到的查询会等，等完读到的是**已提交**的值，不会读到一半的中间状态；
- 更新和删除竞争时按排队顺序执行：删除先成功的话，后到的更新报 `NOT_FOUND`，**不会给已删除的 Node 写回 Metadata**；
- 事件一律在提交成功之后才通知。

## 8. 怎么装配

`DefaultVfs` 多了一个构造参数 `metadata`（Core 的 `MetadataRepository` Port）：

```kotlin
DefaultVfs(
    router = router,
    capabilities = capabilities,
    registry = registry,
    nodes = nodes,      // 自动提交的 Node 仓库
    metadata = metadata, // 自动提交的 Metadata 仓库：查询读它，写永远走事务里那一份
    storages = { key -> storages[key] },
    boundary = boundary,
    pipeline = EventPipeline(boundary, unitOfWork, notifier),
)
```

Runtime 组装（T18）会补上这个参数；Core 之外不需要改任何公共 API。
