## 3. 关键决定

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| 同值也发事件 | 每次有效 `setMetadata` 发一条 `METADATA_UPDATED`，包括传相同值、包括重复清空；不做相等比较或去重 | 「变没变」是调用方的判断；下游 Consumer 本就要幂等。省掉这次比较只会让「事件条数 == 实际修改次数」这个直觉失效 |
| 逻辑时间用现有时钟 | 同一事务内 `nodes.touch(id, clock())` 推进 `updatedAt`，保留 ID / 路径 / 类型 / `registeredAt`，不动物理文件时间 | T01「逻辑记录更新时间」的落实；不引入第二个时钟来源 |
| 确认回滚的失败报 `NONE` | 状态库普通失败 → `STATE_ERROR` + `NONE` | 整批改动都在状态库一个事务里，没有 Storage 副作用，不套 T16 删除的 `PARTIAL` |
| 不改写已有事实 | `VfsException`（含状态库自报的 `STATE_ERROR`、`NOT_FOUND`）原样抛，`code` 与 `effect` 不动 | 「不因为捕获到异常就宣称一定没提交」，也不把 `UNKNOWN` 之类降成 `NONE` |
| 查询复用 Registry 的有效性判断 | `registry.getNodeInsideBoundary(id)` | 一条有效性规则、一句错误消息，不另写一套；已删除记录按 T11 的 `deleted_at IS NULL` 天然查不到 |
| 一次取锁 | 查询 `boundary.withLock`，更新 `pipeline.commit`（它自己取锁） | 锁不可重入，二选一；事务内一律用 `TransactionScope` |

## 7. 异议与理由

1. **同值事件不省**（相对「只在值变化时发事件」的直觉做法）。理由：调用方比一次 `getMetadata` 就能判断变化，VFS 不替它猜；而统一规则更少意外——想安静的 Consumer 自己做幂等。
2. **`updatedAt` 允许相同值**（相对「保证严格递增」）。理由：时间来自注入时钟，精度内连续设置必然可能相同；强行递增等于编造事实。
3. **查询不包事务**（相对「读也开一次事务」）。理由：查询走共享边界即可保证不脏读，开事务只会多一次 BEGIN/COMMIT。
