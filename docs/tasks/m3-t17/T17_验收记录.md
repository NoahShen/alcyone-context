### A06 串行与取消 — 通过（R1 后判据已加强）

- **查询排队**：受控更新占着边界（事件追加后挂住）时，用 `CoroutineStart.UNDISPATCHED` 启动后续 `getMetadata`，断言它**未完成**，且 **`RecordingNodeRepository` 的 `findById` 进入记录没有增长**——查询还没进状态库；放行后**排队的那一次查询自己**返回更新后的 `NodeMetadata`（不拿另一次查询替代）。
- **事务内取消**：取消点选在「Metadata 替换 + Node 时间 + 事件都已真写进库、COMMIT 还没发生」；**从调用协程内部捕获原异常**（`try/catch` 填 `CompletableDeferred`，不用 `runCatching` 丢掉结果、不拿 `Deferred.await()` 的取消当证据），断言 `CancellationException` 原样传播且原因一致；回滚后 Metadata 与 `updatedAt` 都是旧值、事件数不变、**没有通知**；随后一次成功更新证明**锁已放行**，且挂起点只触发过一次。
- 两个并发用例都带 `@Timeout(60)`，闩锁用 `Channel` / `CompletableDeferred`，没有 `sleep`。

**判据的确定性来源（R1 修订）**：查询链是「取锁 → `findById` → 切 IO → `metadata.get`」。`findById` 的进入记录写在**委托真仓库之前**（同步执行，不经过任何挂起点），所以「这一行还没执行」就等价于「查询还没进状态库」——这是确定性的，不依赖调度时序。修订前的旧判据（只看 `metadata.get` 的调用记录）存在合法时序漏洞，见下节。

## 5. 实现要点（源码审查，非可执行证据）

- `getMetadata`：`boundary.withLock { registry.getNodeInsideBoundary(id); metadata.get(id) ?: NodeMetadata() }`——**一次**边界，Node 校验与 Metadata 读取都在里面；有效性规则复用 T13 Registry 的同一句 `NOT_FOUND`，不另写一套。
- `setMetadata`：`pipeline.commit { scope -> commitMetadata(...) }`——`commit` 自己取边界，所以**没有二次取锁**（锁不可重入）。事务内用 `TransactionScope` 的 `nodes` / `metadata` / `events`，没有用自动提交仓库替代事务；构造注入的 `metadata` 只供查询读。
- `commitMetadata` 顺序：`scope.nodes.findById` 校验有效 → `metadata.put` → `nodes.touch(clock())` → `events.append`。事件 `uri` 取自这次 `findById` 读到的 `record.path`（同一批受保护读取），Node 已删则第一步就抛，不会写回。
- 错误映射三层：`CancellationException` 原样抛；`VfsException`（`NOT_FOUND` 等领域错误、状态库自报的 `STATE_ERROR`）原样抛，不改写它的 `code` 与 `effect`；其余 `Exception` 转 `STATE_ERROR` + `NONE` 并 `initCause`。JVM 的 `Error` 不在 catch 范围内。
- 依赖接线：`DefaultVfs` 构造新增 `metadata: MetadataRepository`。这是**内部**构造签名（类不是公共 API 的一部分），按任务说明直接改调用点，未做重载兼容；调用点只有 `VfsHarness` 与 `DefaultVfsRealStackTest` 两处。`vfs/runtime` 本轮没有构造 `DefaultVfs`，故无需改动。
