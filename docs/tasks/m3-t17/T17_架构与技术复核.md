## 2. 必须修改

### R1 / P2：A06 不能直接证明排队查询被锁挡住，也未检查该查询的结果

位置：`DefaultVfsRealStackTest.kt:1102–1134`。查询执行顺序为 getMetadata → registry.getNodeInsideBoundary → SqliteNodeRepository.findById → stateCall 的 `withContext(Dispatchers.IO)` → MetadataRepository.get；当前 RecordingMetadataRepository 只记录最后一步。

因此，移除查询锁后仍存在合法时序：「UNDISPATCHED 启动查询 → findById 切 IO 时挂起 → isCompleted=false 且 Metadata 日志不变 → 测试放行更新 → 查询继续」。现有两条断言在此时序仍可通过，注释与验收 A06 的「第一个挂起点必定是取锁、一次状态库都没读」不是由测试直接证明的事实；这不是报告生产实现已漏锁，也不声称本轮实跑了移除锁变异。

此外，第二个协程用 `runCatching { getMetadata(id) }.exceptionOrNull()` 丢弃了 Metadata，放行后只检查没有异常；最终值由第三次查询验证，无法证明排队的那一次返回了提交后的值。

最小修复：测试在 NodeRepository.findById **委托给真仓库之前、任何挂起之前**同步记录进入（或另用 Core 的无挂起读替身做确定性锁判据）；检查受控更新占锁时，该查询尚未进入第一个仓库。保留第二个协程的返回值，直接对 `second.await()` 断言更新后的 NodeMetadata；不拿另一次查询替代，不加 sleep 或生产测试开关。同步订正验收的强度说明即可，无须扩展 T27 并发矩阵；移除查询锁的变异可作补充，但不能代替确定时序。

## 4. 建议优化（不单独阻塞）

- **S1：明确 UNKNOWN 证据。** 可顺手在现有失败用例注入 VfsException(STATE_ERROR, effect=UNKNOWN)，断言异常对象或 effect 原样保留；不补也可，将该条明确标为源码审查即可。不要为它构造真实 COMMIT 不确定故障或改造事务框架。
