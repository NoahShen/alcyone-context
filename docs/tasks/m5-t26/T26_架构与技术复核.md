### 7.2 必须修改：R1 回调查询没有在回调返回前完成

位置：`RuntimeEventNotificationTest.kt:88–114`。第三个 Consumer 调用 `queryScope.launch` 后立即返回，查询随后运行在测试线程的独立协程中；主测试等待 `committedQuery` 并解开 Result，因此查询确实执行、结果和异常也确实进入测试断言，但这不是“Consumer 在回调内等待公开查询完成”的证据。

例如错误实现若在持锁调用链中同步调用 Consumer，当前 Consumer 仍可先启动协程并返回，随后调用链释放锁，查询才取得锁并成功；该用例不能排除原要求针对的自锁风险。此处是静态时序分析，本轮没有执行这项变异，也不表示当前生产实现存在该缺陷。

此外 `CoroutineScope(currentCoroutineContext() + Job())` 替换了父 Job，创建的是独立作用域，注释“属于测试作用域”不准确。外层 finally 仅 `cancel()` 且发生在 `withVfs` 已关闭 Runtime 之后，没有等待查询任务结束；正常通过时结果已收到，但失败退出路径缺少明确的先结束查询、再关闭 Runtime 顺序。

**最小修复要求：**

- 保持公开 subscribe 入口，让 Consumer 返回之前完成一次公开 `getNode`（或 `getMetadata`）查询，并将 Result / 异常交给测试协程直接断言；查完前不做后续状态变更。公开回调非 suspend，可用回调内部有界的 `runBlocking { withTimeout(...) { ... } }` 桥接，不能改成脱离回调的后台任务来证明“不自锁”。不需要修改公开 API。
- 等待上限放在实际查询内部，不只放在主测试 await 上，避免反例把 notifier.close 永久卡住。如仍保留额外任务，必须管理父子关系、在 finally 中取消并等待结束后再关 Runtime；移除不必要独立作用域更简单。
- 同步订正测试注释和交付 / 验收的 A03 结论；A01 保留达成，不撤回已成立的身份比较。无需新增矩阵或重复 getNode / getMetadata 两种查询。
