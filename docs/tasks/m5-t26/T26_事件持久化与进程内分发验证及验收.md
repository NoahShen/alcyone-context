## 1. 目标与边界

核实当前文件 / Metadata 操作生成的事件与状态同事务提交，只有成功提交后才进入进程内通知，通知失败不改变已经提交的事实。优先复用 T14～T25 的实现和测试；只有发现实际缺陷才做最小实现修复，不另建事件系统。

例：写文件成功后，数据库有对应 FILE_CREATED，Consumer 收到同一个事件；Consumer 抛 IOException，写入仍成功，事件也仍在库中。

本轮不新增 ACK、消费游标、可靠投递、自动重试、去重、重启补发、外部消息队列或事件查询公共 API，这些属于 E05 或后续扩展。正常关闭重开与崩溃恢复分开；广泛并发 / 关闭竞争留 T27，方案④的 native 网络等待限制不变，T25 非阻塞 S2 不自动并入本任务。

## 2. 验证内容

### 2.1 先建证据索引

按“业务操作 → 持久事件 → 通知 → 失败边界”整理现有用例，写明文件、用例名、关键断言和证据层级；直接满足的条目引用即可，不复制测试。至少区分真实 SQLite、公开 Runtime、故障包装、组件替身和源码审查，历史实跑结果不能当成本轮实跑。

例：T23 的事件追加失败回滚已是真库证据，T25 的目录移动根事件已是真实跨后端证据，T26 不必把每个 Storage 后端再跑一遍全矩阵。

### 2.2 状态与事件同事务、提交后才通知

核对事件 ID、类型、Node ID、逻辑 URI、移动源 / 目标及时间，持久记录和通知必须是同一事件；沿用既定七种事件与目录根级粒度。复用真实事务追加失败 / COMMIT 失败代表，确认状态与事件一起回滚且没有成功通知，不能用“物理内容已写入”代替逻辑提交成功。

例：目录移动只增加一条根级 DIRECTORY_MOVED；Metadata 同值更新按已确认契约仍发事件。Consumer 查询公开接口应看到已提交的相应状态，但不承诺它读到的永远是该事件时刻的快照——后续操作可能已更新状态。

### 2.3 Consumer 隔离与公开接线

补或复用公开 Runtime 的一条代表：一个 Consumer 抛普通异常，另一 Consumer 仍收到同一事件，后续操作与事件仍正常；慢 Consumer 受控挂起时，已提交操作可以返回。Consumer 自抛 CancellationException、调用方取消、分发器关闭分别描述，不能把普通异常隔离结论套到所有取消情形。

例：普通 IOException 不影响其他 Consumer；当前通知器捕获 Consumer 自抛取消后继续处理后续事件，但同一事件尚未调用的 Consumer 可能被跳过，应如实说明而不强行扩大首版保证。已有 T14 / T18 取消与回调 close 用例可复用，不重复建设完整停机矩阵。

### 2.4 有界队列与通知丢失

沿用当前默认 256、有界队列满则丢弃通知的策略，核对发布不等待 Consumer 业务、丢弃不删持久事件，也不把成功操作改成失败。小容量故障代表可在真实 EventPipeline + SQLite 组合验证，Runtime 只补必要配置接线；不为测试增加公共诊断接口。

例：Consumer 正处理 A 时停住，容量 1 的队列装入 B，发布 C 后 C 的通知可丢，但 A / B / C 的日志都保留。无订阅者、解除订阅、关闭后 publish 的行为照现有实现说明；droppedEvents 是入队失败诊断，不代表所有未消费事件的总数。

### 2.5 正常重开与不自动重放

保存一批已提交事件的字段快照，正常关闭并重开同一库，核对日志原样保留；新 Runtime 的新订阅不应自动收到旧日志。使用重开后新生成的标记事件确认通知通路确实工作，避免把“监听器根本没接上”误当作不重放证明。

例：重开前事件 E1 仍在表中，重开后订阅并生成 E2，收到 E2 后核对观测记录中没有 E1。这个证据针对当前串行进程内分发与正常重开，不证明未来任意异步重放器不会延迟补发，也不验证崩溃恢复。

### 2.6 时序、清理与证据强度

先订阅再触发，按事件 ID 等待；否定通知用已完成分发的后续标记或可控阶段证明，不能仅 sleep 后看列表为空。提交附近取消必须标清 COMMIT 前还是后，不把 CancellationException 当作“必定无提交”；现有机制证据足够时不强行增加危险注入点。

例：挂起 Consumer 的测试在 finally 放行或取消并等待其结束，再关 notifier / Runtime / 数据库，清理失败保留原异常。持久事件通过真库查询核对，通知通过订阅核对，二者不能互相替代。

## 4. 验收标准

| 编号 | 必须满足 | 证据要求 |
| --- | --- | --- |
| A01 字段与粒度 | 既定事件类型、身份、URI、移动字段与目录根级粒度一致；读 / list / 懒注册不产生变更事件 | 索引覆盖业务类型；一个公开代表按 ID 比较持久记录与通知，其余可复用，时间按 SQLite 毫秒精度 |
| A02 原子提交 | Node / Metadata 与 Event 同事务，追加或提交失败不留下成功逻辑事件 | 真实 SQLite 代表，分别核对状态和事件；物理副作用按既定 effect 保留，不要求补偿 |
| A03 提交后通知 | 提交前 / 回滚无成功通知，正常通知能查询已提交状态 | 受控提交阶段 + 真库证据；公开 Runtime 接线代表，避免消费者查询自锁 |
| A04 Consumer 隔离 | 普通异常不影响成功结果、其他 Consumer 与后续事件；慢 Consumer 不无限阻塞已提交操作 | 公开入口代表与机制证据可组合；自抛取消与宿主 / 分发器取消单独标明，不扩大保证 |
| A05 有界与丢弃 | 队列满时不阻塞提交、不修改持久日志；订阅 / 关闭边界符合说明 | 受控小容量 + 真库；无订阅者 / 退订 / droppedEvents 可引用组件用例，不要求全部在 Runtime 重做 |
| A06 正常重开 | 原持久事件字段保留，新订阅不自动重放旧日志，新事件能正常通知 | 真库快照 + 新 Runtime 订阅 + 新事件标记，不仅等待一段时间断言为空 |
| A07 取消与清理 | 原取消语义不变，提交附近结果不被错误解释；挂起测试无遗漏任务 / 资源 | 明确控制阶段及 T14 / T18 / T23 复用范围；finally 清理到位，不要求强杀 native 或完整并发压力 |
| A08 回归与交付 | 证据索引、实际执行与计数一致，模块边界不变 | `./scripts/check` 与 `./scripts/webdav-check` 分别记录结果、平台、提交号和未验证项；源码 / XML 有差异须解释，缺服务不算通过 |

不要求特定新增测试数或变异次数；如复用已足够，可主要交付证据索引与使用边界说明。变异仅在能帮助验证关键判据时使用，并注明执行人、变更与实际报警用例。
