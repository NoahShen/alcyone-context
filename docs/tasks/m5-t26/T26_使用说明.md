## 1. 订阅与事件本身

事件在**状态变更提交成功之后**投递，是**已发生事实的通知**，不是回调式的“即将写入”。宿主只通过公开入口订阅：

```kotlin
val vfs = AlcyoneVfs.create(config)
try {
    vfs.subscribe { event ->
        // event.id / event.type / event.nodeId / event.uri / event.occurredAt / event.sourceUri / event.targetUri
        auditLog.write(event)
    }
    val info = vfs.write(VfsUri.parse("alcyone://resources/docs/a.txt"), "hi".toByteArray())
    // 到这里写入已经提交；Consumer 由 Runtime 自己的分发协程异步跑，不阻塞 write
} finally {
    // close() 是挂起函数：等通知器分发协程收尾后再关库、放锁
    vfs.close()
}
```

- 事件类型是既定七种：`FILE_CREATED` / `FILE_WRITTEN` / `FILE_MOVED` / `DIRECTORY_MOVED` / `FILE_DELETED` / `DIRECTORY_DELETED` / `METADATA_UPDATED`。**`read` / `list` 不登记、不发事件**；只有 `stat` 会对首次见到的物理文件**懒注册**（建立身份），但仍**不发变更事件**。
- 目录移动只发**一条根级 `DIRECTORY_MOVED`**，`nodeId` 是源根身份、`uri` / `targetUri` 是目标根、`sourceUri` 是源根；不为搬过去的子项补发事件。
- 同一业务操作里，**持久事件与通知是同一个事件**：同一个 ID、同一类型、同一毫秒时间、同一组 URI。通知里的 ID 可以直接拿去查库。

## 2. 持久化 ≠ 通知：两条独立事实

| | 持久事件 | 进程内通知 |
| --- | --- | --- |
| 存在形式 | SQLite `event` 表的行 | 有界队列 + Consumer 回调（内存） |
| 何时写入 | 与 Node / Metadata **同一事务** | 事务 **COMMIT 成功之后**单独入队 |
| 失败会怎样 | 事务失败 → 状态与事件一起回滚，**不留下成功逻辑事件** | 通知失败 / 丢队 **不改**已提交的状态与事件 |
| 重开 | 正常关闭重开后**原样保留** | 不自动重放旧日志（⚠️ 不等于严格订阅时间截断：队列里**尚未分发**的事件可被晚订阅者收到） |
| 可查询 | 通过状态库（不在本任务开放事件查询公共 API） | 无可靠投递 / 游标 / ACK（属 E05） |

**不要用一边证明另一边**：想确认事件真的持久了，核对真库；想确认通知到了，用订阅。物理内容写进磁盘 ≠ 逻辑提交成功——比如“物理已写入但 COMMIT 失败”时，业务报 `STATE_ERROR`，库里没有成功事件，进程内也不会有成功通知。

## 3. Consumer 的普通异常

- 一个 Consumer 抛**普通异常**（`IOException` / `RuntimeException` 等），只被记录日志：**不会**撤销已提交的文件操作，**不会**阻止同一事件里排在它后面的 Consumer，也**不会**阻止后续事件。
- 注意：这里说的是**普通异常**。Consumer 自己抛 `CancellationException` 走的不是这条隔离路径（同一事件后面未跑的 Consumer 会被跳过），见 §4。
- 宿主可以注册多个 Consumer；抛错的那个不影响其他订阅者：

```kotlin
vfs.subscribe { event -> pushIndex(event) }          // 可能抛普通异常
vfs.subscribe { event -> auditLog.write(event) }     // 仍然收到同一事件
```

- 消费失败不回滚、不重试、不补偿；上报与否是 Consumer 自己的事（首版如此）。

## 4. 三种取消要分开看

**不要把「普通异常被隔离」套到所有取消情形上。**

1. **Consumer 自己抛 `CancellationException`**：分发器把它当作“这一轮到此为止”——**同一个事件里排在它后面、还没跑的 Consumer 会被跳过**，但分发协程本身继续处理后续事件。这是既定 `EventDispatcher` 语义（T07），首版如实保留，不强行扩大保证。
2. **调用方取消**（`CoroutineScope` / `Job` 被取消）：`CancellationException` 原样传播，不被包装成 `VfsException`。
   - 取消落在**提交之前**：逻辑状态与事件**整体回滚**（限定为逻辑状态；已发生的物理副作用不回滚），不通知成功事件。
   - 取消落在**提交完成、入队前后**：COMMIT 已成功就不能笼统说通知可有可无——**已提交而调用方看到取消不等于回滚**，事件照旧落库；只是“提交返回与入队之间”这一窗口极窄，**这一批可能通知了、也可能没通知，两种都算正常**。运行时不补偿删除，也不报告“必定没提交”。
3. **分发器 / Runtime 关闭**：`close()` 停掉分发协程并等它收尾（幂等）；消费挂在**可取消的挂起点**上会被协作取消；卡在**不可中断的阻塞代码**里时不宣称能强杀，`close()` 会跟着卡住。

**回调里调 `close()` 不自锁**：Runtime 能识别“这次 close 来自 Consumer 回调（即使换了线程）”，只做取消、不等包含自己的那次收尾。

## 5. 有界队列与通知丢失

- 进程内队列**有界**，Runtime 默认 `VfsRuntimeConfig.eventBufferCapacity = 256`；队列满时**丢弃通知**并记日志（只记首次告警），**不阻塞发布方、不抛给调用方、不把成功操作改成失败、也不删持久事件**。想更保守就调小容量，代价是更容易丢通知。
- `droppedEvents` 只是**入队失败**的诊断数（队列满或正在关闭），**不代表所有未消费事件的总数**。
- 无订阅者时事件照样入队、被分发协程取走丢掉，不报错、**这种“取走丢掉”不计入 `droppedEvents`**；但若队列已满、事件**入队就失败**，仍然计数（与「无订阅者」是两回事）。
- **`publish` 不等 Consumer 业务**：慢 Consumer 会拖慢通知（一个慢 Consumer 会让后面的 Consumer 一起等），但**绝不会把已提交的文件操作堵住**。
- 首版不做补发；丢的只是进程内通知，事件日志里那条还在。

## 6. 正常关闭重开：保留日志，不自动重放

- 正常 `close()` 之后重开**同一个状态库**：已提交的 Node / Metadata / 事件原样保留；旧事件的 `event_id / event_type / node_id / uri` 等字段逐字不变，新事件按顺序追加。
- **新实例的新订阅不会自动收到旧日志**。要话说准：这**不等于严格的订阅时间截断**——晚订阅的 Consumer 可能收到**订阅之前已经入队、还没被分发**的那一批事件。“不自动重放”指的是没有旧库重放器把**已持久、已分发完**的旧日志再补一遍。
- 判断“不重放”的正确做法是：重开后先订阅，再**生成一条新事件**并等到它送达——收到了新事件，说明监听器确实接上了，此时再核对收件箱里**没有**旧日志的事件，才是有意义的“不重放”证明；只等一段时间看列表为空不算。
- 这条边界针对**当前串行进程内分发与正常重开**：不证明未来任意异步重放器不会延迟补发，也**不验证崩溃恢复**。
- **崩溃恢复仍延后，并不属于 T27**（T27 是**并发、取消与生命周期**验证）；本任务不新增 ACK、消费游标、可靠投递、自动重试、去重、重启补发、外部消息队列或事件查询公共 API。

## 7. 快捷对照

| 问题 | 怎么办 |
| --- | --- |
| 想知道某次变更有没有事件 | 查状态库 `event` 表；不要只看磁盘有没有写 |
| 想确认通知送达 | 用 `vfs.subscribe` 订阅后再触发操作 |
| Consumer 抛普通异常会不会丢数据 | 不会；普通异常不阻止同一事件里后面的其他 Consumer，也不阻止后续事件；但 **Consumer 自抛 `CancellationException` 另说**（同一事件后面未跑的 Consumer 会被跳过） |
| 队列满了会怎样 | 丢通知、留日志、不阻塞提交、不改已提交结果 |
| 重开后为什么没收到旧事件 | 设计如此，不自动重放；用新事件确认通路 |
| close 时还有挂起的 Consumer | 协作取消可取消者；不可中断阻塞不保证强杀 |
