## 2. 必须修改

以下源码位置均在 `vfs/storage/src/main/kotlin/com/github/noahshen/alcyone/context/vfs/storage/opendal/`。

### R1 / P1：关闭标志不等于 native 生命周期保护，流所有权断开

位置：`LocalFsStorage.kt:105–109、119–123、413–435、445–469`，`BoundedInputStream.kt:29–67`。`open()` 与 native 调用之间没有互斥：一个调用通过检查后，另一个线程可以 close Operator；多数方法也仅在入口检查一次，后续 stat / write / list / delete 没有生命周期保护。流自身的问题更直接：有界流的 read / skip / available 不检查自身 closed，无界流根本没有自己的关闭状态，可能在底层 reader 已释放后继续调用 native。

另一个已复现的问题是 `openStream()` 把 `native` 置空，`StorageStream.close()` 随后无流可关：有界和无界两种情况下，关闭 StorageStream 后已打开的 InputStream 仍读出字节 97。Adapter 先关后，有界流与未打开流跳过底层 close，而无界流的 close 又直接进入 delegate，所有权与关闭顺序并不一致，不能据此宣称安全释放。

修复要求：用一个清晰的资源所有权方案协调 Adapter、StorageStream、InputStream，使“检查可用 → native 使用”与释放互斥，并保证 close 任一拥有者都能幂等释放其资源。无需实现 Runtime 完整停机框架，但本地 native 使用后释放 / 释放后再使用不能靠文档顺序约定兜底；补 own-close 后 read / skip / available、只关闭 StorageStream、Adapter 与流关闭顺序及可控关闭竞争测试。`createDirectory(root)` 在已关闭实例上直接成功也已复现，应一起统一入口关闭约定（capabilities 若是纯快照可明确例外）。

证据边界：未故意运行会崩 JVM 的 native 竞争；竞态依据代码审查，关闭后仍调用 delegate 用无害计数流验证。项目实际 0.50.6 JAR 的 javap 显示 OperatorInputStream.read 直接把 Reader.nativeHandle 传入 native，不能假定依赖替 Adapter 做关闭检查。

### R2 / P1：取消发生在资源返回交接处会泄漏

位置：`LocalFsStorage.kt:64–83、151–169` 与 `StorageErrors.kt:20–24`。create / readStream 在 withContext(IO) 内取得资源，但 try/catch 只包内部构造；IO 块成功后切回已取消协程时抛出的 CancellationException 在这个 catch 外，调用方拿不到资源，内部也没有清理它。

已用独立调度器复现真实 create：IO 已完成并待返回时取消，调用方的 use 从未执行，取得的 Adapter 仍 `closed=false, disposed=false`；探针最后主动释放该对象。readStream 的资源返回结构相同，需一起修复，而不是只给构造器内部再加 catch。

修复要求：建立取消安全的资源交接与未交付资源释放，清理失败不覆盖原始异常，取消继续原样传播。增加 create / readStream“资源已经取得、调用方尚未收到”时取消的确定性用例；不要求 native 调用能即时中断，也不需要增加通用资源框架。

### R3 / P2：流读取的异常与超限后状态不符合契约

位置：`LocalFsStorage.kt:440–469`、`BoundedInputStream.kt:29–98`。readStream 返回后，read / skip / available / close 直接调用 delegate，不再经过 storageCall 的错误转换；探针确认 IOException 原样逸出。限额包装流超限后继续保留负的 remaining，实测 `available=-1`、正长度下一次 bulk read 返回 0，调用方捕获取消以外的读取错误后继续操作时可能失去进展。

修复要求：有界与无界流统一执行错误映射，保留取消语义和公开消息边界；超限后进入明确失败或关闭状态，不能返回负 available 或对正长度请求反复返回 0。补不依赖 native 崩溃的错误注入、超限后重复调用、零长度 / 负 skip 等基本 InputStream 边界测试；不要把所有普通参数异常一概包装成存储故障。

### R4 / P1：悬空链接被后端 list 隐藏，先规划后删除的保证失效

位置：`LocalFsStorage.kt:282–290、358–400`；现有 `LocalFsPathBoundaryTest` 将跳过悬空链接写成通过预期。Adapter 只检查 OpenDAL 返回的条目，因此看不到被后端略掉的链接；这与任务中“链接拒绝”和交付宣称的“规划阶段遇链接即无副作用失败”不符，不属于外部进程竞争。

真实临时目录探针：目录同时含普通文件和悬空链接，recursive delete 先删除普通文件，最终报 `STORAGE_ERROR / PARTIAL`，普通文件已消失。非递归删除只含悬空链接的目录也不能靠被过滤的列表判断为空，应保持 DIRECTORY_NOT_EMPTY 语义。

修复要求：对本地目录增加不跟随链接的条目检查，覆盖悬空链接，确保 list 拒绝与递归删除规划发生在破坏性操作前；可以使用 JDK 做边界检查，内容访问继续 OpenDAL，不必重写后端。增加“普通文件 + 悬空链接”拒绝后全部保持的回归测试，并把现有跳过用例改成契约要求，不能以记录后端事实替代适配。

### R5 / P2：effect 按整个方法设默认值，不能准确表示失败阶段

位置：`LocalFsStorage.kt:190–214、219–226、239–252、286–290`，`StorageErrors.kt:35–43`。write / move 把预检和真实变更都包在 UNKNOWN 范围内，因此仅 stat 阶段的底层失败也被记为 UNKNOWN；相反，变更成功后的 statOrFail / typeOf 自行抛 VfsException 默认 NONE，会被映射器原样透传，丢失已发生变更的事实。

递归删除已有成功删除后用 PARTIAL 有依据，现有权限测试也验证了物理文件确实消失；但“第一项失败所以必然 NONE”不能仅凭 index 推断。createDirectory 可创建多级父目录，使用默认 NONE 包裹整个创建也没有体现中途失败可能留下目录的情况。

修复要求：在适配方法中区分尚未执行变更、已进入变更但结果不确定、已知发生变更三个阶段，按证据给 NONE / UNKNOWN / PARTIAL；不要直接修改通用映射器来覆盖所有 VfsException 的 effect。补预检 I/O 失败、变更成功后元数据失败，以及有已知部分结果的用例；单次 Local FS 删除若能依据实现证明失败无变更，可保留 NONE，但须说明证据，不能用“第一个”代替依据。不要求补偿或持久化操作日志。

### R6 / P2：move 父目录规则需回写边界，交付证据需纠正

当前 move 目标父目录缺失返回 NOT_FOUND 的选择可以接受：Storage 是低层操作，补父目录由 Core 编排负责，T02 对最终 VFS 的自动补齐要求仍有效。但 T07 Storage.move Kdoc 未定义这一前置条件，应回写 Port 与 T02 第 6.2 / 7.1 节的职责说明，T20～T22 的 move 编排也需承接，不能只写“留 T15”。

请删去“避免出现 VFS 状态不知道的目录”这个理由：现有设计允许未注册物理目录，真正理由是补父目录的职责分层。同步 `a8a08a6` 提交号（交付文档仍写不提交）、进度的 TODO、能力已验证与尚未验证范围；“76 个全部真实目录、没有任何替身”应改为真实后端用例 + 流白盒 + 错误映射单测 + 静态边界检查的实际组合。

## 3. 九项后端差异逐项判断

| 后端差异 | 当前适配 | 复核判断 |
| --- | --- | --- |
| write 自动补父目录 | 预检父目录存在 | 合理，落实 Port 的不隐式补齐；外部替换竞争不承诺 |
| rename 覆盖目标 | 预检目标不存在 | 单 Runtime 串行变更前提下可接受，不得声称原子防覆盖；外部竞争仍可能覆盖 |
| delete 缺失返回成功 | 删除前 stat | 合理，映射明确 NOT_FOUND；依赖后端失败仍需真实报告 |
| 非空目录删除错误不具体 | 先列举判断非空 | 合理，但列举会漏悬空链接，需 R4 处理 |
| 目录 rename 不支持 | 类型预检 + capability=false | 合理，明确拒绝；不在 T12 偷做复制删除 |
| list 包含自身 | 过滤自身 | 合理，落实单层条目契约 |
| list 需要尾斜杠 | 统一后端路径形式 | 合理，属于适配，不应漏到 Core |
| 不使用 range read | 包装实际读取计数 | 方向合理；R1 / R3 修生命周期及失败状态，不能宣称包装器限制了 native 内部所有缓冲内存 |
| 关闭后调用 native 风险 | 原子布尔 + 每次读取检查 | 不充分，检查不等于与释放互斥，R1 必须处理 |

CREATE_NEW 在预检外使用 if_not_exists 是正确方向；REPLACE_EXISTING 和 move 目前仍只靠预检，符合已接受的“上层串行、不抵御外部竞争”边界。条件创建能力若不可用，应如实写明保证下降或明确拒绝，不把 stat 预检描述成后端原子条件写。

## 4. 建议优化

- `collectForDeletion` 刚经过 listChildren 的完整 LocalPath 检查，又对同一 child 重复解析；注释所说“补中间组件检查”实际上前一次已经做过，可合并。重复检查无法消除 TOCTOU，不应把它当成并发安全。
- 先规划整棵树的 O(n) 内存与递归调用栈在首版可保留，明确面向个人规模；没有实际深树需求前不必创建遍历框架。以后需要支持极深目录时再改迭代遍历。
- `LocalFsModuleBoundaryTest` 扫描源码文本会连注释中的 NodeId / Repository 也算违规，反射检查又不能覆盖 suspend 返回值的泛型；它只能作为粗略辅助，不是模块边界的完整证明。可简化为依赖 / import 检查或保留人工审查，不必引入新架构测试库。
- 新增失败测试应优先确定性控制时机，避免反复循环赌 native 崩溃；权限用例在非 root 平台有价值，但并发 close 与取消交接不能用“取消异常映射器单测”替代。

## 5. 可以接受的设计取舍

- 六个实现文件的职责划分、按实际能力禁目录原生 move、公开签名隐藏 OpenDAL、物理根校验独立于 Router，均符合架构。根创建要求已存在、根自身链接规范化而根内链接拒绝，也已作为本轮决定记录。
- 符号链接统一拒绝用 STORAGE_ACCESS_DENIED 合理；非递归删除有链接的非空目录用 DIRECTORY_NOT_EMPTY 合理，前提是确实能看见所有物理目录项。
- write / move 进入无法确定结果的后端操作后使用 UNKNOWN 是保守且合理的；确认删过条目后失败使用 PARTIAL 同样成立。问题是 R5 的阶段判断不完整，而不是要求所有失败都精确探测结果。
- 不做外部进程路径替换防护、硬链接全面识别、即时取消 JNI、Linux 未实跑不宣称通过可以保留。Adapter 自身 close 竞争与取消泄漏不属于这些可延后边界。
- 76 个测试数量本身不构成过度设计；多数真实文件、路径和限额用例有价值。目录移动拒绝等少量交叉覆盖可合并，但不需要为了减少数量删测试；应优先填补下表中的真实风险。

**R1 / P1：锁保护了 Operator，却没有完整保护和释放 Reader。** `LocalFsStorage.kt:591–606` 仍在 openStream 后将 native 置空，StorageStream.close 不关闭已打开的 InputStream；有界 / 无界探针均得到 `closeCalls=0, read=97`。Adapter 先关时，流 close 被 lifetime 的 CLOSED 拒绝且自身已标为关闭，重试也不清理；真实 Reader 诊断得到 `operatorDisposed=true, readerDisposed=false`，因此第 579–580 行“Operator 连带释放 reader”的注释不成立。

**R3 / P2：零长度读取仍把 OpenDAL 的差异漏给调用方。** `StorageInputStream.kt:69–74` 把 length=0 直接交给 delegate；真实空文件实测 `read(buffer, 0, 0)=-1`，应为 0。现有白盒源主动实现了零长度返回 0，因此只证明替身正常；包装层应在有效状态与参数校验后处理零长度，补真实空文件 / EOF、有界 / 无界证据。

**R5 / P2：变更后自行构造的 VfsException 仍报 NONE。** `LocalFsStorage.kt:299–300、357–358、432–451` 中，NotFound 先变 null，再由 statOrFail 构造默认 NONE 的 VfsException；StorageErrors 的透传分支不会应用外层 PARTIAL。用现有 statFactory 仅在 write 第 3 次 / move 第 4 次 stat 抛 NotFound，实测两者均 `NOT_FOUND / NONE`，但目标文件已经写入或移入；UNKNOWN 元数据类型及阶段间 close 引发的 CLOSED 也应检查同一问题。

同时纠正 `NativeLifetime.kt:22–26` 的 Direct 理由：项目 JDK 的 ReentrantReadWriteLock 支持**同一线程重入读锁**，即使写者排队也有专门放行分支；真正不可行的是持读锁升级写锁。不要用不存在的重入死锁论据维护绕过守卫的路径，也不要把 native 阻塞称为有时限的“短暂阻塞”。

### 8.3 四个重点设计问题

| 问题 | 结论与边界 |
| --- | --- |
| 四个内部测试接缝 | **可以接受。** readerFactory 观测实际释放次数，operatorFactory 保存实际 Operator 以核对 isDisposed，statFactory 注入阶段故障，onNativeCall 控制 IO / 取消时机；均为实例级 internal 入口，公共 create 不暴露 OpenDAL 类型。没有必要为了减少四个参数再建通用后端接口或测试框架；生产 null 回调及小型委托的代价合理。 |
| NativeLifetime 读写锁阻塞 close | **取舍可以接受，但不能承诺限定等待时间。** 等正在使用 native 的操作退出后才释放符合本地安全要求；慢盘 / 卡住的调用可能使 close 长时间甚至无限等待。T18 / T27 承接停接新请求、等待在途操作及宿主停机策略，调用方不应在关键事件线程同步等待；不能在超时后强行释放仍在使用的句柄。本项接受不代表 R1 的 reader 所有权已通过。 |
| OpenDAL list + JDK 枚举 | **可以接受。** 多一遍 O(n) 目录名遍历和 reported 集合，换取发现后端隐藏的悬空链接；仍仅由 OpenDAL 做内容访问，未跨模块职责。两遍不是原子快照：外部新增可能触发 STORAGE_ERROR，外部删除可能留下旧列表；符合既有“不抵御外部竞争”的边界，不需加重试、缓存或目录事务。 |
| handoffOrRelease 与 T11 | **思想一致，契约并不相同。** 两者都在取得资源的 IO 块内登记，外层失败清理；T11 捕获 Throwable 并通过 NonCancellable 调度回滚，这里仅捕获取消且 release 是同步函数，因此当前无需为了形式一致套 NonCancellable。它只服务取得资源到返回的取消窗口，不是通用 use / 事务工具；未来若在登记后新增会失败的挂起步骤，或把 release 改为挂起 IO，必须重新覆盖非取消失败和不可取消清理。 |

### 8.4 建议优化

- 保留测试接缝，但削减与实现不符的长注释：open Kdoc 还称“两工厂”“readerFactory 在最后”；测试暂停的是 IO 块入口，不能一律称为暂停已取得资源后的 continuation。用准确的两三句话说明即可。
- Direct 当前 read 用法位于外层 lifetime 中，尚无独立逃逸证据；建议不再默认绕过守卫，显式传 scope 或直接使用可重入的 lifetime，降低未来复用遗漏保护的风险。无需创建新的生命周期框架。
- `handoffOrRelease` 标明仅取消交接用途和登记 / 清理责任，限定调用范围；不要将其提取到 common 作为通用资源工具。当前释放在取消处理线程同步执行，后续若清理可能明显阻塞，再用 NonCancellable + IO 调度，不能直接 withContext(IO) 跑在已取消 Job 下。
- `LocalFsStorage.open` 仍在 IO 块外调用 LocalFsRoots.normalize（isDirectory / toRealPath）；建议也移入打开操作的 IO 边界。独立同步工具 normalize 本身可保持同步，避免“全部阻塞文件调用已在 IO”这类过强声明。
- `skip(-1)` 的特意抛错无助于限额正确性，按 InputStream 返回 0 即不移动、不计费，建议恢复标准行为。close 竞争测试用 Thread.sleep 判断时序也宜改成双向闩锁；重点覆盖 R1 的真实资源路径，不靠增加大量同义状态测试。

### 9.2 必须修改：R7 / P2，排空中一次 close 失败会跳过其他资源

位置：`LocalFsStorage.kt:59–64、231–236`，`NativeLifetime.kt:43–50`（路径同第 8 节）。`drainReaders()` 遍历时一旦 handle.release 抛错，立即退出，剩余 reader 和后面的 operator.close 都不再执行；此时 closed 已为 true，再次调用 Adapter.close 也不会重新执行释放逻辑。

用现有 readerFactory 注入两个合法的 InputStream（close 抛 IOException），实际 Operator 仍为真实 OpenDAL，确定性结果如下。集合遍历顺序不影响结论：两个都可抛错，必然只有第一个收到关闭调用。

```text
DRAIN_FAILURE code=STORAGE_ERROR closed=true disposed=false closeCounts=[0, 1]
```

这是新排空流程的异常安全问题，不是要求恢复中断操作，也不是要求后端 close 必须成功。探针证明“遇到关闭异常，其他资源必被遗漏”，**不声称本机真实 OpenDAL Reader 已自然发生 IOException**；现有流接口和错误转换已经支持关闭异常，此路径应保持可用。

修复要求：一个 reader 关闭失败时继续尝试关闭其余 reader，并保证最后尝试关闭 Operator；保留首个失败，后续失败可作为 suppressed，向调用方明确报错。不要求自动重试失败的 reader，也不要求保证抛错资源一定已释放；不能因一个失败放弃其他独立资源，更不能吞掉错误伪装成功。

验收只需一个集中场景：多个 reader 中至少一个关闭失败，所有 reader 都获得一次关闭尝试，真实 Operator 的 isDisposed 为 true；异常及 cause 保留，重复 Adapter.close 不重复释放已处理资源。另核对多次清理失败不会覆盖最初异常，无需搭建通用资源管理框架。
