## 5. 时序、清理与证据强度口径

- **启动门 ≠ 同时进入临界区**：A02 的启停门只保证「一起发起」；无论谁先，结果都必须是合法集合（一成一败）。串行机制由 T13 的真库排队用例与 T15 的受控包装用例单独证明，不靠启动门。
- **到达阶段、等待、放行、返回写清**：A03 受控代表用 `awaitFirstMove()` 确认第一操作已停在 rename 前（持边界），用 UNDISPATCHED 确认第二操作已跑到第一个挂起点（取边界）而未完成，「放行后」断言第二调用**自身**的返回 / 异常。
- **否定事实的直接判据（R1）**：A03 受控代表包装一层 `UnitOfWork`，在委托真事务、**任何挂起点之前**同步记进入次数。移动停住后记基线，UNDISPATCHED 启动更新后直接断言入口计数**未涨**（这才是「被外层 StateBoundary 挡住、根本没到事务委托入口」）；放行后再断言计数增加。`setMetadata → EventPipeline.commitInsideBoundary → SqliteUnitOfWork.inTransaction` 内部还有 `withContext(Dispatchers.IO)` 调度点，光看库没变化排除不了它已走到那里，所以库状态不变仅作补充证据。
- **取消原异常身份**：Storage / 事务内两类与目录移动在**调用协程内**捕获后 `assertSame`；入口等待改用组件替身 `NodeRegistryBoundaryTest :: A04`（只断言 `isCancelled`）；`EventPipelineRealStackTest :: A06` 只用 `isCancelled`，三类分列（§2.3 口径）。
- **物理事实 ≠ 逻辑回滚**：目录 / 删除 / 移动在 COMMIT 前取消时，物理变化不自动恢复，只断言逻辑回滚；「取消后实例仍可用」仅限于用例实际验证的场景。
- **底层释放需计数 / handle 证据**：A06 的「集合已清空」不单独作为释放证据，引用 Adapter 的计数 / handle 用例。
- **反复生命周期限定轮次**：A07 记录 3 轮，只断言所测轮次的可观测资源（旧流不可读 + 重开成功），不作堆内存 / 全局线程无泄漏推断。
- **清理写法（R2）**：
  - `DefaultVfsRealStackTest :: A03` 受控代表从第一个子任务（`move`）启动后就进入 `try/finally`；失败 / 超时路径先在 `NonCancellable` 里**放行 pausing 门**（幂等，避免死等），再取消并 `join` `move` 与 `update` 两个子协程（含事务回滚）真正结束，之后才退出 `withStack` 关资源。
  - `RuntimeConcurrencyLifecycleTest` 的 stat / CREATE_NEW 两例在 `withVfs` **内部**用 `coroutineScope { ... }` 托管这批并发 `async`；只要 `awaitAll` 抛错，作用域先取消并等待这批子任务收尾，然后才回到 `withVfs` 的 `finally` 调 `vfs.close()`，不把未收尾的子任务挂到外层 `runBlocking` 上。
  - 叠加清理失败保留主异常、清理失败挂 `suppressed`（见 §2.6）。

## 6. 未验证边界与失败观察

- 无失败观察：本轮两次命令均 BUILD SUCCESSFUL，0 失败 / 错误 / 跳过。
- 未验证 / 明确不在本轮范围：崩溃恢复、断点续做、可靠消费（E05）；外部程序同时改文件的隔离；堆内存 / 全局线程 / 平台 FD 级别的无泄漏推断；跨平台实跑（T28）；广泛压力与变异。
- **R1 判据做过一次性探针（未入库）**：临时把 `setMetadata` 从 `pipeline.commit` 改为绕过边界的 `commitInsideBoundary`，A03 用例在「入口计数未涨」上失败（expected 1 / was 2），随即恢复生产代码（`vfs/*` 零 diff）。这证明该直接判据能识别边界接线失效，不是「正常实跑通过就当规则成立」；探针改动未提交，不计入交付。
- **方案④保持**：协作取消不等于能中断 native 阻塞；`closeGracePeriod` 不是 `close` 的最长耗时；不新增网络超时或强杀机制。测试超时只用于防挂死，不当作 native 请求有超时保障。
