## 1. 并发调用同一 Runtime：串行边界与合法结果

一个 Runtime 里的公共操作（`write` / `move` / `delete` / `setMetadata` 等）共用**一把串行边界**：同一时刻只有一个变更操作在保护区内工作。但这不等于「谁先发起谁先提交」——启动顺序与提交顺序无关。

- **同一路径同时 `CREATE_NEW`**：两个调用都会有结果，但只有一条合法集合：

```kotlin
// 甲、乙同时对 /a.txt 用 WriteMode.CREATE_NEW
// 合法结果：一个成功（FILE_CREATED），另一个 VfsException(ALREADY_EXISTS)。
// 最终磁盘内容、有效 Node、成功事件都只对应**获胜**的那一个调用，不会留下两个身份。
```

不要预设谁赢。正确做法是**收集所有调用的返回 / 异常后再判断**，按合法结果集合核对，而不是「最后只剩一个文件」就当规则成立。

- **`read` / `list` 不是登记操作**：它们不会给物理文件建立身份，也不发变更事件。只有 `stat` 会对首次见到的文件**懒注册**（建立身份），但也不发变更事件。
- **同一路径并发 stat**：所有调用最终拿到**同一个** Node ID，状态库里只有一条有效记录；不需要宿主自己做去重。

## 2. 取消：按阶段看事实，不要笼统当「回滚」

取消（`CancellationException`）会**原样传播**，不会被包装成 `VfsException`。但「收到取消」在不同阶段对应不同事实：

| 取消发生的阶段 | 物理内容 | 逻辑记录 / 事件 |
| --- | --- | --- |
| 入口等待（还没进保护区） | 未动 | 未提交，无事件 |
| Storage I/O 中 | 视后端而定，可能已落一部分 | 未提交，无事件 |
| 事务内、COMMIT 前 | **已完成的不自动恢复** | 随事务回滚，无成功事件 |
| 流交接（已建流、未交给调用方） | 流当场关闭 | 无 Node / 无事件 |
| COMMIT 之后 | 已发生 | 已提交，取消**不代表**回滚 |

- **目录已搬完、事务提交前取消**：路径更新回滚，但磁盘上的移动**不会自动恢复**。单凭 `CancellationException` 不能断言「什么都没发生」。
- **「取消后实例仍可用」只指已验证场景**（例如目录移动提交前取消后，同一个状态库还能再开），不要推广到任意失败。
- 方案④：取消是**协作**的。卡在 native 里不响应取消的操作不会被强杀，可能拿到 `STATE_ERROR`；`closeGracePeriod` 也不是 `close` 的最长耗时。测试超时只用于防挂死，不是「native 请求有超时保障」的证据。

## 3. 关闭：顺序与在途工作

`close()` 是**挂起函数**（不是 `AutoCloseable` 的阻塞语义），用 `try/finally`：

```kotlin
val vfs = AlcyoneVfs.create(config)
try {
    vfs.write(VfsUri.parse("alcyone://resources/docs/a.txt"), "hi".toByteArray())
} finally {
    vfs.close()   // 幂等；并发调用共享同一次结果
}
```

顺序固定：

1. 转 `closing`：**新操作立即被拒**（`VfsErrorCode.CLOSED`）；
2. 给在途操作 `closeGracePeriod` 自助时间，期内能跑完就跑完；
3. 到点还没完的，发**协作取消**（只取消这次调用自己的子协程，**不牵连宿主的父 Job**）；
4. **等这些调用真正收尾完**（含 NonCancellable 里的回滚 / 关流），再按「流 → 通知器 → 各块盘 → 状态库 → 独占锁」逐个释放，锁放最后。

- 收尾没做完时，`close()` 不会提前返回，独占锁也不会提前放——此时同库重开仍 `CONFLICT`；等 `close()` 走完才能重开。
- 关掉再开：**已提交的 Node / Metadata / 事件都还在**；关闭不是「回滚初始化」。
- 从事件 Consumer 回调里发起 `close()` 不会自锁。

## 4. 流的所有权与回收

`openStream` 返回 `VfsStreamResult`。**谁拿到谁负责关**：

```kotlin
vfs.openStream(uri).use { result ->          // 推荐：显式关
    result.stream.copyTo(output)
}
// 调用方自己关的流，Runtime 立刻不再跟踪。
```

- **忘了关**：`vfs.close()` 会替调用方把还没关的流收回来，不留悬着的句柄。
- **重复关**是空操作，不报错、不重复释放底层句柄。
- **关闭后读**一定失败（`CLOSED` 或 `IOException`），不给读到旧数据的口子。
- **流交接时被取消**：流当场关闭，不会变成没人管的句柄。
- 底层 handle 是否真的释放，由 Adapter 层计数 / handle 证据保证；只看「集合清空」不足以证明。

## 5. 反复创建 / 关闭

正常模式下可以「创建 → 用 → 关闭 → 再创建」循环，同一个状态库能被反复打开：

```kotlin
repeat(3) {
    val vfs = AlcyoneVfs.create(config)
    try { vfs.write(...); vfs.openStream(...).use { ... } } finally { vfs.close() }
    // 下一轮 AlcyoneVfs.create(config) 能成功：锁已放、连接已关、流已收
}
```

- 已提交的身份跨轮保留；旧流在 `close()` 后不可读。
- **边界**：已验证的是「所测轮次内、可观测资源（旧流不可读 + 同库可重开）没有残留迹象」。这不等于堆内存 / 全局线程 / 平台 FD 级别「绝对无泄漏」——那些不作未测推断。

## 6. 本轮补证口径（怎么读这些用例）

- **启动门只保证「一起发起」**：并发用例用 `CompletableDeferred` 让多个调用一起出发，但**不冒充「同时进入临界区」**。无法控制先后时，只核对合法结果集合（例如 CREATE_NEW 一成一败），谁赢都对。
- **第二调用的返回值直接断言**：交错用例保存并发调用**自身**的返回 / 异常后判断，不另查一次再把那个结果当成并发调用的返回。
- **取消异常身份区分两种证据**：入口 / Storage / 事务内 / 目录移动的用例在**调用协程内**捕获后直接比较原异常；另有用例只断言 `isCancelled` 与回滚事实。两类分开读，不互相替代。
- **物理事实与逻辑事实分开**：物理内容查磁盘，逻辑记录 / 事件查真库，进程内通知查订阅——三者不互相替代。
- **测试清理**：失败路径先放行（幂等）→ 取消 / 等待自己启动的任务 → 再关 Runtime / 数据库；叠加清理失败时保留主异常、清理失败挂 `suppressed`。

## 7. 明确不在本任务范围

崩溃恢复、断点续做、可靠消费（ACK / 游标 / 重试 / 去重）、外部程序同时改文件的隔离、网络超时或强杀机制、跨平台实跑（T28）。方案④保持：协作取消不中断 native 阻塞，`closeGracePeriod` 不是 `close` 最长耗时。
