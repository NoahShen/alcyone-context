## 2. 必须修改

### R1：A03 的“没进受保护工作”尚无直接判据

位置：`DefaultVfsRealStackTest.kt:1242–1253`。UNDISPATCHED 保证第二调用执行到第一个挂起点，但没有证明该挂起点就是边界锁；`update.isCompleted == false` 和查询数据库尚未变化也不能排除它已经进入事务入口、尚未执行写入。

具体原因：`setMetadata → EventPipeline.commit → SqliteUnitOfWork.inTransaction → stateCall` 内部还会通过 `withContext(Dispatchers.IO)` 挂起。若共享锁接线失效，第二调用仍可能先在这个调度点交回控制；此时事件 / Metadata 都未变化，当前否定断言可通过，放行后最终顺序又取决于调度。正常实跑通过不等于这个判据能确定识别锁失效；本轮没有执行变异，这一结论来自调用链审查。

**最小验收要求：**利用既有 `withStack(unitOfWork = ...)` 包装入口，在委托真实事务、任何挂起点之前同步记录进入次数。第一移动停住后记基线，UNDISPATCHED 启动 Metadata 更新后直接断言该入口记录未增加；放行后再确认入口实际执行、保存的第二调用 Result 成功、新路径与事件 URI 正确。可选等效判据，但不能只检查事后库值；不改生产 API，不另建测试框架。

现有 `Result<Unit>` 保存并断言成功是有效的第二调用结果证据，`setMetadata` 本来就不返回 Metadata；保留即可。公开配套用例是顺序操作，能证明旧 ID 移动后仍可更新，但不能替代这个受控交错判据。

### R2：新增子任务没有按说明在失败时先结束再关资源

A03 用例从启动 `move` 到 `update.join()` 没有 try/finally。`awaitFirstMove` 或放行前断言抛错时，会先退出 `withStack` 并关闭 notifier / 数据库 / Storage，随后外层 runBlocking 才取消子任务；包装器只在收到取消时自行放门，不能保证资源关闭前任务已退出。

`RuntimeConcurrencyLifecycleTest` 的 stat / CREATE_NEW 用例同样将 async 子任务挂在外层 runBlocking，`withVfs` 内 awaitAll 失败时先执行 vfs.close，没有任务级 finally 等待。Runtime 自身会管理已接纳操作，但尚未接纳的任务不在其中，不能据此声称“本轮失败路径统一先取消并等待自启任务，再关 Runtime”。

**验收要求：**A03 从第一个子任务启动后就进入 try/finally，失败时放行或取消任务，并在 NonCancellable 中等待所有已启动任务结束，再让 withStack 关闭资源；不可只写正常路径 join。公开两个并发用例可在 withVfs 内用 coroutineScope 管理这批任务，或等效显式取消并等待；不必重写历史全套测试。给出放行前失败 / 取消时清理顺序的针对性验证或明确代码依据，不能仅凭正常路径全绿。
