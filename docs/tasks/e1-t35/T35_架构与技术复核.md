## 2. R1：订阅回调仍保留整个插件及Worker

`GitBackupPlugin.eventConsumer = { consumerRef?.onEvent(it) }` 捕获插件this。javap明确显示 Function1 的 invokedynamic 接收 GitBackupPlugin，lambda方法也带插件参数。VFS永久保留callback后，引用链为 callback → plugin → final worker/runtime，清空consumerRef并不能释放Worker，违反A05。

修复：稳定回调只捕获独立的可清空引用容器或轻量Consumer；容器目标关闭后置空，不能由外层lambda重新捕获plugin。已取到旧目标的并发回调仍须被Worker closing屏障拒绝。验证对象引用结构或可靠弱引用/回收判据，以及并发旧引用行为；现有“close后调用不再同步”只能证明不运行，不能证明不保留资源。

## 3. R2：close被调用方取消后可能永久跳过清理

close先将state置CLOSED，再挂起执行worker.shutdown。调用方在join/宽限等待期间被取消，会跳过scope.cancel/join；后续close看到CLOSED直接返回，无法补完成清理。并发第二个close也可能在第一个仍清理时提前返回。

修复：把“停止接纳”与“清理完成”分开，使用共享完成信号，让并发close等待同一次清理；必要自身清理不随调用方取消中途丢弃，并有finally确保自身Scope回收。不要取消宿主Scope，不增加公开状态。补调用方取消close、并发close、真实RepositorySyncExecutor/runInterruptible与本地可控进程的接线退出证据；仅fake挂起Executor不足以证明生产取消链。

## 4. R3：已到期排队的事件请求不会被新事件重置

源码交错：启动同步仍运行；t=0事件在t=60计时到期，把pendingImmediate=true且reason=EVENT；t=61新事件只重建debounceJob，没有使已排队的EVENT请求失效；t=62启动同步结束，scheduler立即执行旧EVENT请求，而新事件静默期应到t=121。现有旧计时器测试只覆盖“到点尚未运行的timer”，不覆盖“timer已排队、scheduler尚忙”。

修复：事件待执行状态携带代数/截止时间，领取执行前重新验证最新静默期；新事件应失效旧EVENT请求，但不能推迟真正MANUAL/CRON等立即请求。补上述受控交错，以及立即请求与新事件的独立合并语义。保持单串行和运行中变更保留，不引入逐事件队列。

## 5. R4：生产接线重复日志及取消结果语义未验

Worker.runSync记录start/result，实际RepositorySyncExecutor调用的GitRepository也记录start/result；同runId生产执行会有两套日志。现有日志测试只使用fake Executor，因此不能支持A07“不重复”。Worker对`SyncResult.Failed(cancelled=true)`只打印后继续循环，与T34交接要求取消停止循环不符。取消异常日志又缺阶段/耗时；普通执行器异常没有受控终结记录且会让scheduler退出，可能留下仍接纳请求但不执行的实例。

修复：明确唯一运行日志责任层，生产链每轮一条开始和一条终结，普通失败后等待正常触发；取消异常和取消结果一致停止/清理，不把失败结果日志当作状态管理。异常摘要遵守T34受控日志规则。补真实RepositorySyncExecutor/Repository接线日志捕获与取消结果行为，不只测fake。

### R3 残留：合并信号不能遗留无唤醒的pending状态

独立Java探针调用实际编译Worker（使用闸门执行器，无真实Git）：STARTUP阻塞期间先MANUAL，再事件；静默100ms到期并确认pendingEvent=true；释放STARTUP及MANUAL后，500ms未启动第三次，calls=2而pendingEvent仍true。见 `PendingProbe.java` 与 `pending-probe.log`。

`Channel.CONFLATED`只保留一个唤醒，nextDueReason只领取优先的pendingImmediate，随后scheduler再次receive，剩余pendingEvent没有信号。此例MANUAL同步可能覆盖之前的事件，因此不将结果夸大为已证实文件遗漏，但状态与唤醒协议不闭合。

修复选择保持简单：把signal仅作为唤醒，醒来/每次执行完毕后重新核对全部待执行状态；或在领取立即请求时按明确快照/代数合并并清除其确实覆盖的事件。不能留下pending=true却无唤醒。新执行期间收到的事件不能被旧完成逻辑吞掉。补受控时间+闸门代表，明确允许的合并结果及最终pending清空；保留原防抖与立即请求契约。

### R4 残留：取消终止调度必须同时停止接纳和计时

schedulerLoop因cancelled结果break或取消异常退出，但closing仍false，cronJob/debounce可继续运行，Plugin仍STARTED且requestSync返回成功，后续请求只堆在无消费者的signal。新增测试只证明停止执行，未证明停止资源与接纳。

修复：统一调度终止路径，取消时停自身计时、关闭接纳并清除待处理信号，公开请求按既定不可用语义拒绝或明确受控失败，不静默接受不会执行的任务；后续close仍可靠完成且幂等。不得取消宿主、不新增公开状态模型或自动重试。覆盖取消结果与取消异常两条路径，以及终止后的手动/事件/Cron无泄漏；普通失败仍保持可再次触发。
