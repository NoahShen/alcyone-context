## 1. 一次 delete 做什么

例：挂载 `/resources` 指向本地盘，`delete(alcyone://resources/notes/a.txt)` 会让磁盘上的 `notes/a.txt` 消失、旧 Node ID 查不到、Metadata 被清掉，并追加一条 `FILE_DELETED`。`notes/` 目录留在原地——删除不顺带清理目标之外的空父目录。

顺序（任何可确认的拒绝都发生在碰盘之前）：

1. 结构保护：逻辑根、命名空间根、挂载根、承载后代挂载的祖先 → `UNSUPPORTED_OPERATION`，`recursive = true` 也不例外；
2. 路由（`MOUNT_NOT_FOUND`）、只读（`READ_ONLY`）、能力快照缺失（`INVALID_ARGUMENT`）：走 T10 的 `OperationGuard`；
3. `Storage.stat` 确认目标**真的存在**并拿到**实际类型**；不存在 → `NOT_FOUND`（不当作幂等成功）；
4. 按实际类型构造 `OperationIntent.delete` 再跑一遍 Guard——声明类型是调用方给的，不是验证过的事实；
5. 逻辑记录类型冲突 → `CONFLICT`；把要清理的记录先读出来（文件看自身，目录看已登记子树）；
6. `Storage.delete`（递归遍历、防符号链接、`PARTIAL` / `UNKNOWN` 都由 T12 负责，Core 不重写物理算法）；
7. 一个事务里：`markDeleted` → 清各自 Metadata → 追加**一条**目标级事件。

| 操作 | 碰后端 | 写状态 | 发事件 |
| --- | --- | --- | --- |
| `delete` 文件 | `stat` → `delete(rel, recursive)` | 一个事务：`markDeleted` + `metadata.delete` | 同事务追加一条 `FILE_DELETED` |
| `delete` 目录 | 同上 | 一个事务：目标 + 已登记子树 | 同事务追加一条 `DIRECTORY_DELETED` |

**唯一持锁者**：整条链（预检 → Storage 删除 → 逻辑提交）只取一次 `StateBoundary` 锁，SQLite 事务只覆盖第 7 步。内部用 `pipeline.commitInsideBoundary`，不会自锁。

## 2. 文件与目录语义（T02 §8.1）

| 调用 | 结果 |
| --- | --- |
| 删文件（`recursive` 任意） | 删掉；`recursive` 对文件没有额外含义 |
| 删空目录，`recursive = false` | 删掉 |
| 删非空目录，`recursive = false` | `DIRECTORY_NOT_EMPTY`，一个字节都没删 |
| 删目录，`recursive = true` | 删掉整棵物理子树 |
| 删不存在的路径 | `NOT_FOUND`（**不是**幂等成功） |
| 删逻辑根 / 命名空间根 / 挂载根 / 后代挂载的祖先 | `UNSUPPORTED_OPERATION`，`recursive = true` 也不行 |

例：挂了 `/resources/work/medical` 之后，`delete("/resources/work", recursive = true)` 被拒；但 `/resources/work/note.md` 是普通文件，照常能删。

已登记 Node 的类型与实际类型冲突时按 `CONFLICT` 拒绝，不借删除把逻辑记录「改对」。

## 3. 逻辑清理范围

- **文件**：只清理目标自己的记录和 Metadata。
- **目录**：清理目标 + **完整段边界**内已登记的全部子树，不要求目录根自己登记过。
  例：`a` 从没登记，但 `a/b.txt` 登记了——删 `a` 仍会清掉 `b.txt` 的记录和 Metadata。
- 兄弟不动：`a-old`、`A` 不属于 `a` 的子树（`NodeRepository.findSubtree` 按完整段匹配，Core 不自己写前缀比较）。
- 物理上已经缺失的已登记子记录，会随目录删除一起失效（包括「非递归删了一个物理上确实是空的目录」）。
- 历史事件不删：里面留着的旧 Node ID 仍然是那次写入的事实。

删除**不会**为物理子项批量登记 Node：没登记的就是没登记。

## 4. 事件粒度：本轮的决定

一次成功的 `delete` 产生**一条**目标级事件：

| 目标 | 事件类型 | `uri` | `nodeId` |
| --- | --- | --- | --- |
| 文件 | `FILE_DELETED` | 请求目标 | 目标已有 ID；未登记则 `null` |
| 目录 | `DIRECTORY_DELETED` | 请求目标 | 同上（目录根未登记时为 `null`，即使子项有 ID） |

**为什么不为后代逐个造事件**：目录删除是一次动作，事件表里的每个后代要靠猜路径前缀才能还原，而那条前缀匹配规则正是 `findSubtree` 的实现细节，不该成为 Consumer 的契约。

**Consumer 该怎么用**：把 `DIRECTORY_DELETED` 理解为「该 URI 之下整棵逻辑子树失效」——按前缀清理自己的索引，不要期待每个文件各有一条事件。需要逐文件信号时，请在删除前自行 `list` 展开。

## 5. 失败与取消

| 发生了什么 | 错误码 | effect |
| --- | --- | --- |
| 结构 / 路由 / 只读 / 类型冲突被拒 | 原码 | `NONE`（一个字节都没动） |
| 非空目录非递归 | `DIRECTORY_NOT_EMPTY` | `NONE` |
| Storage 删除失败 | **原码** | **原样带出后端的 `NONE` / `PARTIAL` / `UNKNOWN`，不降级** |
| 删除已在盘上生效但状态或事件提交失败 | `STATE_ERROR`（保留 cause） | `PARTIAL` |
| 通知队列满、Consumer 抛错 | 不报错 | 已提交结果不变（复用 T14） |
| 协程取消 | `CancellationException` 原样传播 | 不声称「取消 = 全部回滚」 |

**删除后物理与逻辑可能不一致的边界**（首版不自动补偿）：

- Storage 报失败但 effect 是 `PARTIAL` / `UNKNOWN` 时，可能已经删掉一部分甚至全部内容，而 Node 与 Metadata **原样保留**——这一批记录等效于「指向已消失的物理资源」，后续 `stat(uri)` 会报 `NOT_FOUND`，外部变更修复仍属 E04。
- Storage 成功但提交失败时，物理删除**回不来**：文件没了，Node 与 Metadata 因为事务回滚而留着。`getNode(旧 ID)` 仍能查到，`stat` 会说文件不存在。
- 不自动重试、不自动补偿、不按猜测「部分清理」；调用方按 effect 自行决定后续处理。
