## 5. 实测 vs 推断

**实测**（本机跑过，有输出）：全部 528 例；上述五处变异；分模块计数。

**推断（未实测）**：

- Storage 报告 `PARTIAL` / `UNKNOWN` 的**真实后端**行为：本轮只用包装器注入。真实 Local FS 不会自发产生「删一半才失败」，`LocalFsStorage` 自己的 `PARTIAL` / `UNKNOWN` 路径由 T12 用例覆盖，本轮没重跑其断言。
- 跨进程 / 绕过 VFS 的外部并发删除：首版不承诺，删除链的 `stat` → `delete` 不是原子条件删除。
- Linux x64 / arm64 与 GitHub Actions 运行：**本轮未验证**。

## 6. 已知边界（交付给复核方）

1. **目录事件粒度**是本轮的契约决定（一条 `DIRECTORY_DELETED` 表示子树失效），已写进 [使用说明](T16_使用说明.md) 第 4 节与本任务文档 §2.4；若复核方倾向逐文件事件，需要同时改契约与本轮用例。
2. A04 用例的预置**不走 `DefaultVfs`**：主键冲突包装器会把每个事务的第一条事件换成固定 ID，所以文件、Node、Metadata、历史事件都直接用真仓库预置，只让待测的删除撞主键；这不是绕过验证，删除链本身完全真实。
3. 取消现在有**两个**用例，分别覆盖两段路径：物理删除前（`Storage.delete` 挂起点）与提交附近（第一次 `markDeleted` 写入后，`commitInsideBoundary` 内）。提交附近那个是 R1 补的，回滚由 `SqliteUnitOfWork` 在 `NonCancellable` 里真实执行。
4. `PausingCommitUnitOfWork` 只让**第一次** `markDeleted` 挂起；后续操作的 `markDeleted` 不再被拦，用例用 `pausedMarks() == 1` 固定这个前提。
