## 1. 需求目标

实现 `Vfs.delete(uri, DeleteOptions)`：文件与目录删除、结构保护、逻辑状态与 Metadata 清理、目标级事件、失败事实与取消。复用 T12 `Storage.delete`、T07 四个 Repository、T14 `EventPipeline`。不增加公共 API，不提前实现移动、Metadata 公共操作或 Runtime。

## 2. 主要实现

单文件改动：`vfs/core/.../DefaultVfs.kt`（+165 行）。

| 成员 | 作用 |
| --- | --- |
| `delete` | 取一次 `StateBoundary` 锁，整条链在锁内 |
| `deleteInsideBoundary` | 结构保护 → 路由 → `stat` 确认实际类型 → `OperationGuard.check(delete intent)` → `planLogicalCleanup` → `Storage.delete` → `pipeline.commitInsideBoundary`；取消原样传播，提交失败映射 `STATE_ERROR` + `PARTIAL` 并保留 cause |
| `requireDeletableStructure` | 逻辑根 / 命名空间根 / 挂载根 / 承载后代挂载的祖先一律拒；`recursive = true` 不绕过 |
| `planLogicalCleanup` | 物理删除**前**读逻辑记录：文件看自身，目录 `findSubtree`；已登记类型与实际类型冲突 → `CONFLICT` |
| `commitDelete` | 一个事务内 `markDeleted` → 逐个 `metadata.delete` → 追加**一条**目标级事件（`FILE_DELETED` / `DIRECTORY_DELETED`） |
| `DeleteCleanup`（private 顶层） | 目标 Node ID + 待清理 ID 列表 + 实际类型 |

实现上值得留意的几点：

- **物理递归不在 Core**：非空目录非递归由 T12 的 `Storage.delete` 报 `DIRECTORY_NOT_EMPTY`，Core 不重写遍历，也不自造删除顺序。
- **前缀匹配不在 Core**：子树范围完全交给 `NodeRepository.findSubtree`（完整段边界），`a-old` / `A` 天然不会被误伤。
- **不懒注册**：删除链只用 `nodes.findByPath` / `findSubtree` 查记录，不走会注册的 `registry.resolveOrRegister`。
- **空集合安全**：`markDeleted` 在空 ID 列表时由持久化层直接返回（`NodeQueries.markDeleted`），Core 无需分支。

## 3. 本轮明确的契约决定

**一次成功 delete = 一条目标级事件**：文件 `FILE_DELETED`、目录 `DIRECTORY_DELETED`，`uri` 为请求目标，`nodeId` 为目标已有 ID（未登记则 `null`）。目录事件表示整棵逻辑子树失效，不为后代逐个造事件。Consumer 应把目录事件理解为子树失效。已写进 [使用说明](T16_使用说明.md) 第 4 节。

同时明确：删除后物理与逻辑**可能不一致**且首版不补偿——后端报 `PARTIAL` / `UNKNOWN` 时 Node 与 Metadata 原样保留；物理成功但提交失败时文件删不掉、记录留着。
