## 1. 这个模块是干什么的

VFS 有两类东西：文件本身在存储里，而「这个文件是谁、在哪儿、被人打过什么标签、发生过什么事」是**状态**。文件在硬盘上可以被任何人直接改动，状态不行 —— 状态必须由 VFS 自己记，而且要**跟文件操作对得上**。

这个模块就是记状态的地方，四个概念各一张表：

| 概念 | 是什么 | 关键问题 |
| --- | --- | --- |
| Node | 一个逻辑位置上的资源身份（文件或目录） | 改名、移动之后还是不是同一个 Node |
| Metadata | 挂在某个 Node 上的标签、描述、扩展 JSON | 换路径之后标签还在不在 |
| Event | 已经完成的变更记录 | 改到一半失败时，会不会留下一条「成功」事件 |
| Mount | 逻辑路径到存储实例的映射 | 本轮只读，配置由上层给 |

为什么值得单独一个 SQLite 文件，而不是每次现算：

- **Node ID 必须稳定**。把 `/notes/a.txt` 改名成 `/notes/b.txt`，用户看到的是「同一个东西换了个名字」，Metadata、事件历史都得跟着走。靠路径找，就断了。
- **状态和事件要同生共死**。写完文件、更新状态、记事件三件事必须一次成功或一次都不成功，否则会出现「文件写了但状态没记」「状态改了但事件丢了」这种事后没法收拾的现场。
- **跨重启要能接着用**。Agent 上次退出了，下次打开还得知道上次有哪些文件、什么标签。

它不碰文件本身，也不决定 Agent 能不能看某个目录；它只是「记住发生了什么」，并且保证这件事要么全记上，要么一点没记。

## 3. 打开与关闭

**做什么**：打开（或创建）状态库，把它变成一个能用的入口对象；用完关掉，释放底层连接。

**什么时候用**：Runtime 启动时打开一次，进程结束时关闭。**不要**每次操作都开一次 —— 开一次就是一次建表检查加一次连接。

```kotlin
// 正式使用：文件库
val state = VfsStateDatabase.file(databasePath)
try {
    val nodes = SqliteNodeRepository(state)
    // ... 用起来 ...
} finally {
    state.close()
}

// 测试或临时状态：私有临时库，关掉即丢
val memory = VfsStateDatabase.inMemory()
```

**边界情况**：

- `inMemory()` 打开的是**私有临时库**（`jdbc:sqlite:` 空路径，落临时文件、连接关闭即删除），别的连接看不到。它不是纯内存库（纯内存写法是 `jdbc:sqlite::memory:`，本轮不采用）。适合测试，不是缓存。
- `close()` 之后这个对象就废了：再拿它做任何数据库操作（Repository 方法、事务）都会以 `STATE_ERROR` 失败。这是刻意的 —— 不想让人在关库之后还能悄悄写进去。
- `close()` 可以重复调用，不报错。
- 关闭本身失败（JDBC 报错）时同样是 `STATE_ERROR`，原始异常保留在 `cause` 上。
- 一个库只给一个 Runtime 用。**别**开两个 `VfsStateDatabase` 指向同一个文件同时写（见第 6 节）。

## 4. 四个 Repository

四个实现类都只接一个 `VfsStateDatabase`，语义与 T07 定义的接口一致。这里只说容易用错的地方。

### 4.1 `SqliteNodeRepository`：Node 身份

```kotlin
val nodes = SqliteNodeRepository(state)
```

#### `register`：登记一个 Node

**做什么**：把一个 Node 写进状态库，返回**最终生效的那条记录**。

**什么时候用**：资源确认存在之后登记它（`stat` 触发的懒注册、T13 的 Registry 都会用）。

```kotlin
val node = nodes.register(
    NodeRecord(
        id = NodeId.parse(newUuidV7().toString()),   // ID 由调用方生成，库不会自动生成
        path = VfsPath.parse("/notes/a.txt"),
        type = NodeType.FILE,
        physical = true,
        registeredAt = now,
        updatedAt = now,
    ),
)
```

**Node ID 从哪来**：`id` 是**程序生成的 UUIDv7**。`node.id` 虽然是 SQLite 的 TEXT 主键，但**主键不会自动生成 ID** —— 调用方必须先造一个再传进来。T13 的 Node Registry 负责调 `common` 的 UUIDv7 生成工具造 ID；本模块只存和查，**不生成、也不会在冲突时自动换一个**。

**边界情况**：

- **同一个路径注册两次，第二次不会报错，而是返回第一条**。两个协程同时给 `/notes/a.txt` 登记，只会有一个 Node ID 生效，另一个调用方拿到的就是那个已生效的 ID —— 不需要调用方先查后插，也不会产生两个身份。裁决它的是数据库里的一条唯一索引，不是应用层逻辑。
  **所以竞争注册后以 `register` 返回的记录为准**：`node.id` 才是最终生效的 ID，不要拿自己传进去的那个继续用。
- 反过来，**传入的 Node ID 已经在库里、而目标路径又没有有效记录可读回**时，`register` 失败并报 `STATE_ERROR`（Node ID 复用是调用方的 bug，不属于「路径被占用」）。注意前提是「读不回有效记录」：目标路径若已有有效记录，返回的是那条记录而不是报错。
- `registeredAt` 和 `updatedAt` 会被**截断到毫秒**再存（库里的时间戳统一是毫秒精度）。要用毫秒精度的时间戳比较回读结果。

#### `updatePath`：改名 / 移动，身份不变

**做什么**：改逻辑路径，**Node ID 不变**（这与「删除后重建」不同：重建是新身份，移动是同一个身份）。

```kotlin
nodes.updatePath(node.id, VfsPath.parse("/notes/b.txt"), now)
// 之后 nodes.findByPath(VfsPath.parse("/notes/b.txt")) 查得到，findById(node.id) 还是同一个
```

**边界情况**：

- 新路径**已被别的有效记录占用**时报 `STATE_ERROR`，状态不变。这里**不做**「复用既有记录」—— 那是 `register` 的语义；移动撞上已存在的路径是另一回事，由调用方（T15 / T20）决定怎么处理。
- 已经标记删除的 Node 更新不了（也不该更新）。

#### `touch`：内容变了，改个时间

**做什么**：只更新 `updatedAt`，别的都不动。内容被覆盖但路径没变时用。

#### `markDeleted`：软删除，顺带把路径还回去

**做什么**：批量标记删除。标记之后所有正常查询都查不到它，**而且它的路径立刻可以被新 Node 占用**。

```kotlin
// record(path, id) 是上面那段 NodeRecord(...) 构造的简写，只列关键字段。
// 下面三个场景各自独立，互不影响；每个场景都从「库里只有 A」开始。

// 场景 1：库里有一条【已删除】的 A（deleted_at 非空）——同路径可以登记新身份 B
// 初始：库里只有 A，且 A 已标记删除
val a1 = nodes.register(record("/notes/a.txt", id = newUuidV7()))   // 先有 A
nodes.markDeleted(listOf(a1.id), now)
val b1 = nodes.register(record("/notes/a.txt", id = newUuidV7()))   // → B（新的 UUIDv7，b1.id != a1.id）
nodes.findByPath(VfsPath.parse("/notes/a.txt"))                     // → B

// 场景 2：库里有一条【有效】的 A —— 再登记被部分唯一索引忽略，register 返回 A 自己
// 初始：库里只有 A，且 A 有效
val a2 = nodes.register(record("/notes/a.txt", id = newUuidV7()))
val again = nodes.register(record("/notes/a.txt", id = newUuidV7())) // → A（不是新传进去的 ID）

// 场景 3：库里有一条【已删除】的 A，却拿 A 的旧 ID 去登记
// 初始：库里只有 A，且 A 已标记删除（目标路径没有有效记录）
val a3 = nodes.register(record("/notes/a.txt", id = newUuidV7()))
nodes.markDeleted(listOf(a3.id), now)
nodes.register(record("/notes/a.txt", id = a3.id))                   // → STATE_ERROR
```

场景 3 报错的完整条件是：**旧 ID 冲突被忽略 + 按路径读不回有效记录**。如果那时路径上已经有一条有效记录（例如先建了 B），`register` 返回的是 B，根本不会报错。边界说明：Node 行还在库里（历史事件还引用着它），只是不再「有效」。`deleted_at` 非空只释放了**路径占用**，那行的**主键仍然在**，所以重建必须换一个新的 UUIDv7，**不能复用 A 的 ID**。本模块不会自动换号，换不换由调用方（T13 的 Registry）决定。
删掉的目录要连子树一起清理时，先用 `findSubtree` 拿到全部 ID，再一次 `markDeleted`。

#### `findSubtree`：按段边界查后代

**做什么**：返回这个路径**自己 + 全部后代**（不含已删除的）。

```kotlin
// 库里有 /notes/a、/notes/a/b、/notes/a/b/c.txt、/notes/abc、/notes/a-b
nodes.findSubtree(VfsPath.parse("/notes/a")).map { it.path }
// → [/notes/a, /notes/a/b, /notes/a/b/c.txt]   ← /notes/abc 和 /notes/a-b 都不在里面
```

**边界情况**：

- **按完整段边界匹配**：`/notes/a` 只认以 `/notes/a/` 开头的后代，不会把 `/notes/abc` 当成子目录。
- **大小写敏感**：`findSubtree("/notes/a")` 不会命中 `/Notes/A/b`。
- 查逻辑根 `/` 返回全部有效 Node。
- 结果按路径排序（SQLite 的 BINARY 顺序，`-` 排在 `/` 前面）。

#### `findByPaths`：批量补全

**做什么**：给一批路径，返回其中当前有效的 Node 记录。`list` 之后给每个条目补 Node ID 用它。

**边界情况**：不存在的、已删除的路径不出现在结果里；**传空列表返回空列表**（不是全部）；结果顺序不保证和传入顺序一致。

#### 路径比较：大小写敏感

VFS 保留路径里的大小写，库里的比较也一致：`/notes/A.txt` 和 `/notes/a.txt` 是两个不同的 Node，可以同时存在。

### 4.2 `SqliteMetadataRepository`：标签与描述

```kotlin
val metadata = SqliteMetadataRepository(state)
metadata.put(node.id, NodeMetadata(tags = setOf("ct", "影像"), description = "胸部 CT"))
metadata.get(node.id) // → NodeMetadata(tags=[ct, 影像], description=胸部 CT)
metadata.delete(node.id)
```

**边界情况**：

- `put` 是**整体替换**，不是合并：旧的 tags 不会残留。
- **`put` 一个空 `NodeMetadata()` 等于清空**：这一行会被删掉，之后 `get` 返回 `null`（和 Core 的内存实现一致，避免「清空后还留着一条空记录」这种两套语义）。
- 内容以 JSON 文本存，键固定是 `tags` / `description` / `extensions`；空 tags、`null` 描述、空 extensions 都能原样往返。
- Metadata 只按 Node ID 存取，不含路径。**Node 改名或移动之后不用动它**。

### 4.3 `SqliteEventRepository`：事件日志

```kotlin
val events = SqliteEventRepository(state)
events.append(
    EventRecord(
        id = VfsEventId.parse(newUuidV7().toString()),
        type = VfsEventType.FILE_CREATED,
        nodeId = node.id,          // 可空
        occurredAt = now,
        uri = VfsUri.parse("alcyone://notes/a.txt"),
    ),
)
```

**边界情况**：

- **事件 ID 重复会失败**并报 `STATE_ERROR`（事件 ID 是 UUIDv7，不会自然重复；重复说明重放出了 bug）。不要用「重复就忽略」的方式绕过 —— 那会让失败的操作留下假事件。
- 可空字段（`nodeId` / `operationId` / `sourceUri` / `targetUri`）就存 NULL。
- 这个接口**只负责把事件存下来**，不通知任何人。分发属 T14：**在事务提交之后**分发成功事件，不要拿驱动的查询 listener 当成事件订阅机制（见第 9 节）。

### 4.4 `SqliteMountRepository`：挂载映射（只读）

```kotlin
val mounts = SqliteMountRepository(state)
mounts.list() // → 所有挂载：路径 + storageKey（不存凭据和具体 URL）
```

**边界情况**：本轮**只有读**。挂载记录由启动时写入（T18），包括「配置改了但库里的映射不一样就拒绝启动」这条校验。

## 5. `SqliteUnitOfWork`：把几件事绑成一个成败

**做什么**：在一个数据库事务里做多件事。**全部成功才生效，中间任何一步抛异常，这几件事一件都不生效。**

**什么时候用**：任何「更新状态 + 记事件」的组合。典型是：文件已经写好了，现在要把它变成「一次创建」—— 更新 Node、写 Metadata、记事件，这三件事必须一起成功。

```kotlin
val uow = SqliteUnitOfWork(state)

val node = uow.inTransaction { scope ->
    val n = scope.nodes.register(record)          // Node 身份
    scope.metadata.put(n.id, NodeMetadata(setOf("ct")))  // 标签
    scope.events.append(eventFor(n))              // 事件
    n                                            // 回调的返回值原样返回
}
```

**事务里的 `scope.nodes` / `scope.metadata` / `scope.events` 和外面的 Repository 接口一模一样**，调用方不需要为事务换一套写法。

**边界情况**：

- **回滚是真的回滚**。回调里抛异常，Node 不会被半路留下，事件也不会有一条「成功了但其实没成功」。测试里验证过：同一文件里先提交一组、再回滚一组，重开库后只剩提交的那组。
- **事务对象出了回调就作废**。把 `scope` 存到外面再用，会得到 `IllegalStateException`（不是 `STATE_ERROR`），而且**不会退化成自动提交写入** —— 想在事务外偷偷写是写不进去的。
- **协程取消按异常处理**：取消一个正在跑事务的协程，事务回滚，异常继续往上传播，不会被改写成 `STATE_ERROR`。
  注意边界：这是「**提交前**取消会回滚」。`COMMIT` 在 IO 线程上成功之后、切回调用协程之前若被取消，数据**已经落库**，再回滚也撤不回来 —— 所以调用方不能看到 `CancellationException` 就断定「什么都没发生」。
  （回归用例用钩子把 BEGIN 停在「语句已准备好、尚未 `execute()`」，放行后才真正发出 BEGIN；取消发生在 BEGIN 执行完成之后、业务回调之前。）
- **事务只管状态库**。它不碰文件：文件已经写好了才开事务。文件那边失败了，这里回滚不了物理文件（T03 §3 就是这么定的）。
- **不支持嵌套事务**。

## 6. 并发边界：状态变更要串行

**整库只有一条数据库连接。** 这是本模块最需要知道的一条约束（原因见验收记录：SQLite JDBC 默认按线程持有连接，事务一旦跨线程就会失去原子性）。

- **并发读允许，但看得到未提交数据**。普通 Repository 与事务视图共用这条连接，所以另一个协程刚写进去、还没提交的记录，普通查询**能查得到**；那次事务随后回滚，记录就消失了。这不是快照一致性差异，是单连接的固有结果。
  **所以由编排层决定哪些查询需要与变更共用同一把串行锁**（T13 / T15），不要指望本模块提供隔离；自动提交 Repository 的写入也必须纳入同一串行约束，不能只锁 `inTransaction`。
- **`inTransaction` 不支持并发调用**。两个协程同时开事务，第二个的 `BEGIN` 会被 SQLite 直接拒绝，报 `STATE_ERROR`。这是故意的：宁可当场报错，也不要两个事务在半路交织、最后提交出一份谁也没打算提交的状态。
- **所以状态变更要由调用方串行化**：同一时刻只跑一个 `inTransaction`。串行化放在编排层（T13 / T15），本模块不代劳，也**不做**跨进程独占检测。

```kotlin
// 对的：变更串行
val node = uow.inTransaction { scope -> scope.nodes.register(record) }

// 错的：并发开事务，第二个会 STATE_ERROR
coroutineScope {
    launch { uow.inTransaction { … } }
    launch { uow.inTransaction { … } }   // ← 竞争
}
```

## 7. 迁移与版本管理

**库版本号存在哪**：SQLite 自己的 `PRAGMA user_version`，和 SQLDelight 生成的 `Schema.version` 是同一个数字。**当前基线版本 = 1**（四张表，无历史迁移文件）。

**打开时会做什么**：

| 库里的版本 | 行为 |
| --- | --- |
| `0`（空库 / 新文件） | 建表，写入当前版本号 |
| 低于当前版本 | 按版本逐步迁移，写入当前版本号 |
| 等于当前版本 | 什么都不做，直接用 |
| **高于当前版本** | **拒绝打开**，`STATE_ERROR`；原库的版本号和数据都不动（拿旧代码开新版库会破坏它） |

**任何一种可以打开的情况都不删除重建**。已经写进去的 Node、Metadata、Event 原样保留。

**将来要改表结构怎么办**：在 `vfs/persistence/src/main/sqldelight/com/github/noahshen/alcyone/context/vfs/persistence/sqldelight/` 下新增迁移文件。文件**从 `1.sqm` 起连续编号**，编号 N 表示「从版本 N 升到 N+1」：1 → 2 写 `1.sqm`，2 → 3 写 `2.sqm`，依此类推；`.sq` 始终表示最新结构。规矩三条：

1. **只加不改**：已经发出去的 `.sqm` 不要再动，老库必须能照原样升上来。
2. **DDL 和版本号同一个事务提交**：升级成功之后才写 `user_version`，中途失败会整体回滚，不会留下「改了一半的库」。
3. **改代码不会自动升版本**：只有**持久化结构或数据格式变化**才需要新的 `.sqm`。改 Kotlin 逻辑（查询、映射、错误处理）不写迁移，Schema 版本不动。

## 8. 错误码与边界

| 情况 | 表现 |
| --- | --- |
| 数据库操作失败（连接关了、SQL 冲突、库坏了） | `VfsException(STATE_ERROR)`，原始异常保留在 `cause` 上 |
| 打开库失败（路径不存在、非 SQLite 文件、建表失败） | 同样是 `STATE_ERROR` |
| 库版本高于当前代码 | `STATE_ERROR`，原库不被修改（先升级或换回新代码） |
| 事务视图逃逸到回调外 | `IllegalStateException`（不是 `STATE_ERROR`） |
| `register` 撞上已占用的路径 | **不是错误**，返回已生效的那条记录 |
| `register` 复用了已在库的 Node ID，且该路径没有有效记录 | `STATE_ERROR`（主键冲突，读不回有效记录） |
| `updatePath` 撞上已占用的路径 | `STATE_ERROR`，状态不变 |
| 事件 ID 重复 | `STATE_ERROR`，已写入的不受影响 |
| 并发开两个事务 | `STATE_ERROR`（第二个 `BEGIN` 被拒） |

`STATE_ERROR` 的消息只说「状态库操作失败」和底层异常类型，**原始异常在 `cause` 里**，不猜原因、不吞异常。调用方按错误码分支，不要解析消息文本。

## 9. 它不管的事

- **不编排文件操作**：不读、不写、不删文件，不做移动编排。事务开始时文件通常已经落到存储上了（T15 / T20 负责）。
- **不分发事件**：只负责把事件存下来。谁订阅、怎么通知、失败怎么重试，是 T14 的事；业务事件**在事务提交后**分发，可靠消费与重启重放是 E05。
  驱动里那个 listener 只是实现 **SQLDelight 的查询变化通知接口**（生成的查询在数据变化后经驱动通知 listener）；**当前没有任何 Repository 注册监听者**，因此既没有查询结果缓存，也没有「提交后通知」保证。裸 SQL 事务下这个通知**不代表事务已提交**，更不是 VFS 事件，不能拿它替代 T14 的成功事件。
- **不写 Mount 映射**：本轮只有 `list()`。写入和「配置与库内映射不一致就拒绝启动」属 T18。
- **不回滚外部 Storage**：事务只覆盖状态库内部。文件已经写了、状态回滚了，这种半完成按 T03 的规则如实报告 effect，不自动补偿。
- **不做跨进程独占检测**：一个库只由一个 Runtime 用；两个进程开同一个文件是上层要避免的事。
- **不做恢复与修复**：中断的操作不续做，重启只加载已提交的状态（T03 §9）。
- **不缓存、不做性能优化**：每次调用直接查库。
