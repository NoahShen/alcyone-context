## 3. 关键实现说明

### 3.1 Schema 与唯一约束

- 四张表全部由 `.sq` 定义，列名与 T07 的领域类型一一对应。
- **当前有效路径唯一由数据库保证**：`CREATE UNIQUE INDEX node_active_path ON node (vfs_path) WHERE deleted_at IS NULL`。`markDeleted` 写入 `deleted_at` 的瞬间路径占用即释放；被删行保留在库中（历史事件仍引用它的 Node ID），但所有正常查询按 `deleted_at IS NULL` 过滤。
- **`register` 不先查后插**：直接 `INSERT OR IGNORE` 再按路径读回，冲突由索引裁决，读回的就是竞争获胜的既有记录（R3）。只有「同一 Node ID 复用」才失败（`STATE_ERROR`）。
- **Node ID 的职责在调用方**：ID 是程序生成的 UUIDv7（未来由 Node Registry 调 `common` 的生成工具产出），SQLite 的 TEXT 主键**不会自动生成** ID。三种情形的实际行为（已删除后换新 ID、A 仍有效时返回 A、复用已删除记录的 ID 报 `STATE_ERROR`）见 [使用说明](T11_使用说明.md) 第 4.1 节；前两种由 A01 的 `marking a node deleted releases its path for a new id` 与 `second registration of the same path returns the existing record` 覆盖，第三种由 `NodeQueries.register` 读回为空即抛错的分支保证（本轮未新增用例）。第三种的完整前提是「旧 ID 冲突被忽略 **且** 该路径没有有效记录可读回」—— 若路径上已有有效记录，`register` 返回那条记录而不报错。
- 时间戳统一 **epoch 毫秒 `INTEGER`**（`.sq` 注释与 Kdoc 均写明，毫秒精度）；`physical` 存 0/1 并加 `CHECK (physical IN (0,1))`。

### 3.2 SQLite 的两个陷阱

- **大小写敏感**：`LIKE` 对 ASCII 不区分大小写，VFS 保留路径大小写。全部等值与前缀比较走 SQLite 默认的 **BINARY** 排序规则，未加 `COLLATE NOCASE`，未设 `PRAGMA case_sensitive_like`。
- **`_` 是 LIKE 通配符**：`%` 已被 T09 在路径段层禁掉，`_` 没有。子树查询因此**不用 LIKE**，改用
  `vfs_path = ? OR instr(vfs_path, ?) = 1`，第二个参数由调用方给出 `path + '/'`，段边界由这个前缀保证。查逻辑根时前缀为空串，`instr` 恒命中，即「根的子树 = 全部有效 Node」。
  （实现中曾用 `substr(vfs_path, 1, length(?))`：SQLDelight 会把 `length()` 的参数推断成整型绑定，与 UTF-16 长度口径也不一致，故改为 `instr`。）

### 3.3 整库单连接：为什么不用 `JdbcSqliteDriver`

`JdbcSqliteDriver` 对文件库**按线程**持有连接（`ThreadedConnectionManager`），且非事务语句执行完会**关闭该线程的连接**（`closeConnection`）。两个后果是 B 阶段实测踩到的：

1. 「BEGIN → 若干次挂起后的语句 → COMMIT」只要有一次线程切换就换了一条连接，事务静默失效；
2. 语句级 `BEGIN` 根本不成立——BEGIN 执行完连接就被关掉，后续语句自动提交，`ROLLBACK` 报 "no transaction is active"。

因此继承 `JdbcDriver` 实现 `SingleConnectionJdbcDriver`：**整库一条 `java.sql.Connection`，`closeConnection` 不作为**（这正是 SQLDelight 自己的内存库 `StaticConnectionManager` 的做法）。**SQLite 事务属于连接、不属于线程**，于是事务内的语句无论在哪个线程执行，用的都是同一条连接、同一个事务；也不再需要为事务钉一个专用线程。

驱动里的 listener 只是实现 **SQLDelight 的查询变化通知接口**（生成的查询在数据变化后经驱动通知 listener）；当前没有任何 Repository 注册监听者，**既没有查询结果缓存，也没有「提交后通知」保证**。裸 SQL 事务下这个通知不代表事务已提交，不能拿来分发 VFS 业务事件 —— 业务事件仍由 T14 在事务提交后分发。

### 3.4 事务：显式 SQL，不用 `runBlocking`

第一版实现是「`Transacter.transactionWithResult`（阻塞）+ `runBlocking` 驱动挂起回调 + 固定线程」，协程取消用例**实际挂死**（外层等内层结束、内层等同一个协程，测试跑了 48 分钟）。根因是用阻塞事件循环驱动了外部挂起函数。

改为：普通挂起协程 + 显式 `BEGIN IMMEDIATE TRANSACTION` / `COMMIT` / `ROLLBACK`（`RawTransaction.kt`）。之所以不用 SQLDelight 的事务 API：驱动级 `Transacter.Transaction` 在 2.1 没有公开的 commit / rollback，只有阻塞入口，而 `SuspendingTransacter` 仅在 `generateAsync`（Android 异步驱动）下生成，JDBC 驱动用不了。

- 选 `IMMEDIATE` 而不是延迟事务：延迟升级锁会在事务中途失败，不如一开始就失败得明确。
- **BEGIN 也在事务生命周期内**（本轮修复 R1）：`BEGIN` 是在 IO 线程上真正执行的，切回已取消的调用协程时 `withContext` 会抛 `CancellationException`；它在 `try` 之外时，这个异常发生在回滚与 `finally` 之前，连接上就留下一个开着的事务，下一个 `inTransaction` 直接报 “cannot start a transaction within a transaction”。现在标志在**同一个 IO 执行块里**置位（`AtomicBoolean`），只有本次调用确实取得事务才回滚；`BEGIN` 本身失败时事务属于别人，不回滚。
- 回滚包在 `NonCancellable` 里：协程已取消时也必须执行，否则事务与写锁留在库里；回滚自身失败只 `addSuppressed`，不掩盖原始异常。
- 测试侧的时序控制点：`Connection` 代理挂在 `prepareStatement` 上，拿到的是**已准备好的语句、尚未 `execute()`**。取消用例的顺序因此是「BEGIN 语句准备好 → `job.cancel()` → 放行 → `execute()` 真正发出 BEGIN 并置位 `transactionStarted` → 切回已取消协程时抛取消」，即**取消生效于 BEGIN 执行完成之后、业务回调之前**；钩子那一刻不能说 BEGIN 已执行。
- `BEGIN` / `COMMIT` / `ROLLBACK` 三条语句都经 `stateCall`，与 Repository 同一条错误映射路径。
- 事务内三个视图与自动提交 Repository 共用同一套查询映射，只多一个 `ScopeGuard`：提交、回滚、抛异常三条路径后作用域都失效，逃逸使用得到 `IllegalStateException` 且不退化为自动提交。
- `UnitOfWorkSqliteTest` 加了 `@Timeout(60)` 看门狗：再出现挂死会变成一次失败而不是长时间空等。

### 3.5 Metadata 序列化与空元数据

`NodeMetadata` 以 JSON 文本存 `metadata.payload`，固定三个键 `tags` / `description` / `extensions`，**不给 API 类型加序列化注解**（T11 §2.5）。`JsonNull` 本身是 `JsonPrimitive`，解析时必须先排除再取 `content`。**空元数据（无 tags、无 description、无 extensions）按清空处理：删行而不是留空行**，`get` 随后返回 `null` —— 与 Core 的 `InMemoryMetadataRepository` 保持同一语义，避免同一套行为有两套实现。

### 3.6 打开、迁移与资源释放

- 打开即读 `PRAGMA user_version`，**四种情况分得很清楚**（本轮修复 R2）：`0` → `Schema.create`；`0 < v < 当前` → `Schema.migrate`；`v == 当前` → 不做任何事；`v > 当前` → **拒绝打开**，抛 `STATE_ERROR`（消息说明库版本高于当前代码支持版本），不改原库的版本号与数据，连接随之释放。前三种都**不删除重建**。
- DDL 与版本号写入在**同一个事务**里提交，中途失败整体回滚，不会留下改了一半的库；打开失败时释放连接并映射为 `STATE_ERROR`。
- `close()` 释放整库唯一连接，**关闭自身的异常也经 `mapStateErrors` 映射为 `STATE_ERROR`**（S3）；关闭后再调用任何数据库操作同样以 `STATE_ERROR` 失败（有测试）。
- 迁移文件**从 `1.sqm` 起连续编号**，编号 N 表示「从版本 N 升到 N+1」（1 → 2 写 `1.sqm`，2 → 3 写 `2.sqm`），`.sq` 始终表示最新结构；**程序逻辑变更不会自动提高 Schema 版本**，只有持久化结构或数据格式变化才需要新增 `.sqm`。当前基线版本 = **1**，有测试断言 `VfsDatabase.Schema.version == 1`。
- `inMemory()` 用的是 `jdbc:sqlite:`（空路径），SQLite 侧是**私有临时库**（落临时文件、连接关闭即删除），不是纯内存库；纯内存写法是 `jdbc:sqlite::memory:`，本轮不采用。所以 A01～A03 / A06 的用例走的是真实文件 IO（只是路径由 SQLite 自己分配），这也是它们能覆盖真实 SQL 行为的原因。

## 8. 证据边界与未验证事项

- **并发 `inTransaction` 不支持**：整库单连接，两个事务同时开会被 SQLite 拒绝（`STATE_ERROR`），不会静默写坏，但也不提供排队。状态变更的串行化由编排层（T13 / T15）负责，本模块不代劳。**未实现**跨进程独占检测（T18）。
- **单连接没有读隔离（S1，已定为文档结论）**：普通 Repository 与事务视图共用同一条连接，能读到另一个协程尚未提交、随后又回滚的记录（第一轮复核已复现）。哪些查询需与变更共用同一把串行锁由 T13 / T15 决定；**自动提交 Repository 的写入也要纳入同一串行约束**。本轮不加连接池或隔离框架，也没有对应的测试用例（这是已记录的行为，不是待验证项）。
- **取消与提交的边界（S2，已定为文档结论）**：提交前取消会回滚；`COMMIT` 已在 IO 线程成功、切回调用协程时再被取消，数据已落库且撤不回来。**未实现**可靠投递与操作恢复，上层不得把 `CancellationException` 一概当成无副作用。
- **句柄泄漏只能部分验证**：`close()` 的释放路径经代码审查（`SingleConnectionJdbcDriver.close()` → `Connection.close()`），测试验证了「close 后可再打开、文件可删」；macOS 允许删除已打开文件，所以没有进程级句柄计数证据。Linux / Windows 上的强制删除行为未验证。
- **迁移路径未实跑**：当前是基线 schema（版本 1），没有历史迁移文件，`Schema.migrate` 的实际执行路径**未被测试覆盖**；只验证了「版本相等时不重建」「空库 create」「版本更高时拒绝打开」。首次引入 `.sqm` 迁移时应补一个「旧版本库 → 升级 → 数据完好」的用例。
- **时间戳精度到毫秒**：亚毫秒部分被截断，`NodeRecord` 的两个时间戳按毫秒比较。首版无需求要更高精度。
- **事务只覆盖状态库**：不承诺回滚外部 Storage 操作（T03 §3）；中断操作不恢复，重启只加载已提交状态（T03 §9）。
- **未实现的部分**：事件分发与可靠消费（T14 / E05）、Mount 映射写入与配置一致性校验（T18）、Node Registry 懒注册编排（T13）、文件操作编排（T15 / T20）、busy_timeout / WAL 调优与多进程访问、降级迁移。
- **远端 CI 未运行**：本轮全部为本地 `./scripts/check` 结果（macOS arm64）；本轮修复已在本地 main 提交、未推送，未运行 GitHub Actions。
