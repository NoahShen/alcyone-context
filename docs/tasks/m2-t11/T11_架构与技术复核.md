## 2. 必须修改

### R1 / P1：BEGIN 成功后的取消会遗留事务

位置：`vfs/persistence/src/main/kotlin/com/github/noahshen/alcyone/context/vfs/persistence/sqldelight/SqliteUnitOfWork.kt:49`，及 `StateCall.kt:16`。`BEGIN` 的 `stateCall` 在 `try` 外；IO 线程执行成功后，切回已取消的调用协程会抛 `CancellationException`，此时尚未进入回滚与 finally，连接仍持有事务。

例：临时测试控制调度顺序为「BEGIN 完成 → 取消调用协程 → 恢复调用协程」，业务回调从未执行，下一次 `inTransaction` 却报 `cannot start a transaction within a transaction`；这不涉及并发事务，也不属于延后的中断恢复。

修复要求：让事务取得、取消交接与清理形成完整生命周期，准确记录本次调用是否真正取得事务；不要简单把 BEGIN 移进 catch 后无条件回滚，否则失败的第二个 BEGIN 可能回滚另一个事务。补上述确定性回归测试，并验证 BEGIN 失败不影响已存在事务；取消异常仍原样传播。该取消行为符合 [withContext 官方说明](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/with-context.html)。

### R2 / P1：打开较新版本库会静默改低版本号

位置：`VfsStateDatabase.kt:51–59`（与 R1 同包）。当前使用 `currentVersion != schema.version`，把较新版本也送入 migrate；基线生成的 migrate 是空操作，随后无条件把 `user_version` 写成当前版本。

例：真实文件库设置 `user_version = 2` 后由当前版本 1 打开，调用成功且版本变成 1。这会丢失版本保护，未来升级可能重复执行迁移或由旧代码操作不兼容结构。

修复要求：明确区分空库、旧版、同版与新版；新版拒绝打开并返回 `STATE_ERROR`，不修改原版本与数据，失败时释放连接。补「较新版本被拒绝且原文件保持不变」测试；不要求本轮实现降级迁移。

### R3 / P2：迁移文件的命名说明错误

位置：`T11_使用说明.md` 第 7 节（第 273 行）、`T11_交付文档.md`“生命周期与迁移”节，以及 `VfsStateDatabase.kt` 第 18～21 行 Kdoc。文档要求与表文件同名，例如 `Node.sqm`，但 SQLDelight 按升级前版本编号迁移文件，不能按表名命名。

修复要求：统一为「版本 1 → 2 使用 `1.sqm`，同时更新 `.sq` 表示最新 Schema」，不要描述为文件数加一即可；本轮无需编造历史迁移。依据：[SQLDelight 2.1 迁移文档](https://sqldelight.github.io/sqldelight/2.1.0/jvm_sqlite/migrations/)。

### R4 / P2：模块重命名与交付状态尚未完成文档同步

构建配置和当前受 Git 管理的模块路径已完成重命名，但当前有效的《项目搭建说明》的目录树、模块说明及依赖图仍使用旧路径，《VFS 技术设计》第 201～202 行的模块表也未同步；历史任务记录可以保留旧名，当前架构入口需要更新。交付相关文档另有「未提交」、`187 → 223`、Core `120` 等过期或错误口径，正确测试数为 `180 → 223`、Core `106`。

修复要求：同步当前架构目录、依赖图与测试路径，保留“原名”说明即可，不必批量改写历史记录；统一三份交付提交、实际测试数量与复核状态，并为交付文档补前置“本次修改”。本轮复核已更新进度与验收入口，其余交给开发 Agent 随修复收口。

## 3. 建议优化

### S1：把单连接的读可见性说清楚

`SqliteRepositories.kt` 与事务视图共用同一连接，普通 Repository 读取可以看到另一协程尚未提交、随后又回滚的记录；临时测试已复现「事务中可查到，回滚后查不到」。这不同于两次读取没有快照一致性；当前测试注释“事务外看不到中间状态”也未被测试实际验证。

建议在使用说明和 T13 / T15 承接点明确此限制，由编排决定哪些查询需与变更共用锁；本轮不要求为此增加连接池或完整隔离框架。自动提交 Repository 的写入也必须纳入同一变更串行约束，不能仅锁 `inTransaction`。

### S2：取消与 COMMIT 的边界避免过度承诺

COMMIT 已在 IO 线程成功后，切回调用协程仍可能收到取消，此时再 ROLLBACK 无法撤销已提交数据。文档宜限定“提交前取消回滚”，补充提交与取消竞争时结果可能已持久化；后续编排不能将 CancellationException 一概解释为无副作用，不要求本轮实现可靠事件投递或操作恢复。

### S3：收紧生命周期说明与错误映射

`VfsStateDatabase.close()` 直接调用驱动，没有经过 `mapStateErrors`，若 JDBC 关闭抛异常就会泄漏底层异常；建议与其他状态库失败采用一致映射，并保留 cause。`inMemory()` 使用 `jdbc:sqlite:`，准确说是关闭即删除的临时库；如需严格纯内存语义可使用 `jdbc:sqlite::memory:`，当前真实 SQLite 测试的有效性不受影响。

## 4. 可以接受的设计取舍与确认项

- **部分唯一索引与注册复用合理。** `WHERE deleted_at IS NULL` 只约束有效路径，软删除释放路径；`INSERT OR IGNORE` 后按有效路径读回符合 T07 R3，字段由强类型输入约束，不需要为首版重建竞争框架。同一路径的注册竞争已实测，涉及移动 / 删除的变更仍由编排串行。
- **大小写与子树处理正确。** 等值、IN、唯一索引与 Mount 主键使用默认 BINARY；`instr(path, prefix)` 没有 LIKE 通配符语义，前缀末尾的 `/` 保证段边界，根使用空前缀。`markDeleted` 不自行清理 Metadata 符合 T07：由调用方在同一事务调用 Metadata 删除。
- **单连接驱动有实际动机。** 核对 [SQLDelight 2.1.0 源码](https://raw.githubusercontent.com/sqldelight/sqldelight/2.1.0/drivers/sqlite-driver/src/main/kotlin/app/cash/sqldelight/driver/jdbc/sqlite/JdbcSqliteDriver.kt)，文件库确实使用线程局部连接，未进入其受管事务的语句结束后会关闭连接；它与“裸 SQL 事务跨挂起”的用法不兼容，不能泛称 SQLDelight 本身事务有缺陷。保留当前小型 Adapter 合理，无须回退到 runBlocking。
- **常规挂起事务流程成立。** 当前实现已移除原先的阻塞事件循环，原有取消测试正常完成；NonCancellable 回滚、原异常及 suppressed 保留、回调结束后视图拒绝使用均合理。但不能据此声称取消修复彻底，R1 必须关闭。
- **首版不支持并发 / 嵌套事务可接受。** 结合 T03 的单 Runtime、串行变更约束，不必在 persistence 增加事务排队框架；前提是 R1 修复不误回滚别人的事务，并把 S1 的普通 Repository 边界交给后续编排。
- **基线无历史迁移、跨进程独占延后可接受。** 真实升级用例留到首次引入编号 `.sqm`；但“无历史迁移”不能豁免 R2 的拒绝新版库。独占检测、Mount 写入由 T18 承接，事件分发由 T14 承接。
- **资源释放证据范围如实披露即可。** 连接正常关闭、打开失败关闭与重开测试有证据；macOS 删除文件不是无句柄泄漏的证明，本轮不要求跨平台进程级句柄统计。Runtime 停止接收与等待在途操作仍属 Runtime 生命周期任务。
- **模块边界保持正确。** persistence 依赖 core 并实现 Port，无 Storage / Router / Guard 依赖，SQLDelight 与 JDBC 未进入 API / Core 契约。保留 `...persistence.sqldelight` 实现包名与按职责命名模块并不冲突；时间戳毫秒精度、Metadata JSON 和不增加外键级联也符合当前职责分配。
