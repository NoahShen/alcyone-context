## 2. 开发与审查内容

### 2.1 完整用例证据索引

### 2.2 模块依赖与公共边界

核对 Gradle 依赖、生产 imports 和公共签名：Core 定义 Port，Storage / Persistence 实现，Runtime 负责组装；API 不泄漏 OpenDAL / JDBC / SQLDelight 类型，common 不依赖 VFS。测试组合依赖和有意公开的内部模块类型要如实区分，不因类是 public 就认定 SDK 契约泄漏，也不为本轮新建架构检查框架。

例：集成测试可以同时依赖 Runtime、Storage 与 Persistence；Core 生产代码直接引用具体 SQL Driver 则应说明并修正。检查生产仍只依赖 SLF4J API，工具链仍局限项目目录。

### 2.3 路径、结构保护与后端职责

核对 URI / Path 校验、按段路由、虚拟目录、挂载根及嵌套 Mount 保护，确认 Core 编排与 Adapter 实际能力没有重复实现或相互绕过。沿用 Local FS 根 / 符号链接与 WebDAV endpoint / root 的既有证据，不扩展成对任意外部文件竞争的安全保证。

例：`a` 子树不能影响 `a-old`，普通祖先包含子 Mount 的拒绝不能用“目标本身就是挂载根”的测试替代；WebDAV 无目录 rename 不代表公共目录 move 不可用，Core 可复制删除。

### 2.4 身份、事务、事件与失败

检查覆盖和同 / 跨 Mount 移动保留 ID、Metadata、registeredAt，删除后同路径新建获得新身份；正常关闭重开保留已提交记录。确认 Storage I/O 不在 SQLite 事务内、逻辑状态与事件同事务、提交后通知，失败保留 code / cause / 已知副作用和 UNKNOWN，取消语义与实际阶段一致。

例：物理移动完成但逻辑提交失败，不能用回滚断言推导磁盘恢复；目录根级事件不等于每个子文件都产生事件。复用 T23 / T26 / T27 的直接证据，不重做取消与失败全排列。

### 2.5 生命周期、技术债与文档一致性

复用 T18 / T25 / T27 / T28 核对初始化清理、在途工作与完成信号、流所有权、关闭顺序和凭据诊断边界。列出本轮发现的必须修复 / 建议优化 / 已接受限制，修复真正阻碍既定契约的问题；不把已接受的平台与网络等待限制重新升级为缺陷。

例：T28 的反射测试 Provider 与子进程退出补证是建议，不要求为 T29 扩建框架。旧用例文档中“消费状态支持重试”等历史表述若与当前首版不重试 / 不重放冲突，应最小回写为后续能力，不能照旧文实现新功能。
