## 1. OperationGuard 是干什么的

你要写一个文件、移动一个目录、删掉一个东西，VFS 在**真正动手之前**先问 `OperationGuard` 一句「这事能不能做」。它只看你给的配置（有哪些挂载、每块盘支持什么能力），不给通过就抛异常，**一块存储都碰不到**。它的价值在于「早」：

- 拒绝一个已知做不了的操作，比在写了一半之后失败要好：没有半成品，没有「文件写进去了但状态没记上」这种要人工收拾的现场。
- 它给出的不是「行 / 不行」，而是「**该怎么做**」：直接写、直接删、还是用后端原生的改名、还是走复制回退。真正执行的那层（T15 / T16 / T20 / T21）照着办。

它不碰文件、不连存储、不查文件存不存在，所有答案只来自你给的两个输入：一个 `MountRouter`（T09 的挂载视图）和一份 `CapabilitySnapshot`（`storageKey → StorageCapabilities`）。

## 2. 贯穿全文的例子：笔记本场景

假设这台笔记本的配置是：

| 命名空间 | 含义 |
| --- | --- |
| `memory` | 智能体长期记忆 |
| `notes` | 笔记 |

| 挂载点 | 落到哪个存储 | 这块盘的特点 |
| --- | --- | --- |
| `/memory` | `local-disk`（本地硬盘） | 可写、支持原生改名 |
| `/notes/team/docs` | `docs-disk`（另一块盘，可以是 WebDAV） | 可写、**不支持原生移动** |

注意 `/notes/team` 没有自己的挂载：它只是 `/notes/team/docs` 这个深层挂载在配置里缺掉的中间层，属于「配置推导目录」。这类目录可以被浏览，但**不能被写、被移动、被删除**。

下文所有例子都用这套配置：

```kotlin
val router =
    MountRouter.of(
        namespaces = setOf("memory", "notes"),
        mounts =
            listOf(
                MountRecord(VfsPath.parse("/memory"), "local-disk"),
                MountRecord(VfsPath.parse("/notes/team/docs"), "docs-disk"),
            ),
    )

val capabilities =
    CapabilitySnapshot.of(
        mapOf(
            "local-disk" to StorageCapabilities(),
            "docs-disk" to StorageCapabilities(nativeFileMove = false, nativeDirectoryMove = false),
        ),
    )
```

## 3. 三个入口

### 3.1 `OperationIntent`：把一次操作说清楚

**做什么**：告诉预检「要做什么、动哪个路径、条目是文件还是目录」，外加这次操作特有的参数。write 带 `WriteMode`，delete 带 `recursive`，move 两者都有。

**什么时候用**：任何 write / move / delete 开始之前，先造一个 intent 交给 `check`。这是纯参数描述，不含任何「文件存不存在」的事实。

```kotlin
OperationIntent.write(VfsPath.parse("/memory/notes/a.txt")) // 写入目标文件
OperationIntent.move(VfsPath.parse("/memory/a.txt"), VfsPath.parse("/memory/b.txt"), NodeType.FILE)
OperationIntent.delete(VfsPath.parse("/memory/notes"), NodeType.DIRECTORY, recursive = true)
```

**边界情况**：

- write 不接受条目类型：写入的目标一定是文件。目录类型的判断属于执行期事实（`TYPE_MISMATCH`），预检不猜。
- move / delete 必须说清 `entryType`，因为「移动一个目录」和「移动一个文件」需要的能力不一样（见第 6 节）。
- 工厂方法只留合法形状：write 没有 source，delete 没有 target。构造器是私有的，写不出不完整的 intent。

### 3.2 `CapabilitySnapshot`：每块盘会做什么

**做什么**：一个不可变的 `storageKey → StorageCapabilities` 映射，回答「这块盘能不能写、支不支持原生移动、能不能建目录、是不是只读」。

**什么时候用**：Runtime 组装阶段按打开的存储实例填好，交给预检。创建后不再变，要改就重新建一个。

```kotlin
val capabilities = CapabilitySnapshot.of(mapOf("docs-disk" to StorageCapabilities(readOnly = true)))
```

**边界情况**：

- 构建后会复制一份入参，之后你修改自己那份 `Map` 不影响已创建的快照。
- **快照必须覆盖本次操作涉及的所有 `storageKey`**。查不到就直接抛 `INVALID_ARGUMENT`（理由见第 7 节），不会当成「能力齐全」放行。
- 快照只反映**打开后端时已知**的信息。挂载之后才出现的只读或限制，按执行期错误处理（T12 负责转换）。

### 3.3 `OperationGuard.check(intent, router, capabilities)`：跑一遍预检

**做什么**：按固定顺序检查这次操作。通过就返回「用什么策略做 + 源和目标各自落在哪个挂载的哪个相对位置」，不通过就抛 `VfsException`（此时没有任何副作用）。

**什么时候用**：写 / 移动 / 删除的执行层第一行。返回的路由结果直接就是 Storage 需要的参数，不用再查一次。

```kotlin
val result = OperationGuard.check(OperationIntent.write(VfsPath.parse("/memory/notes/a.txt")), router, capabilities)
// result.strategy == DIRECT_WRITE
// result.target!!.mount.path == /memory，result.target!!.relativePath.toRelativeString() == "notes/a.txt"
```

为什么是这个结果：`/memory` 是挂载点，`notes/a.txt` 挂在它下面不是配置推导目录，能路由到 `local-disk`，这块盘可写，所以直接写。

```kotlin
val moved =
    OperationGuard.check(
        OperationIntent.move(VfsPath.parse("/notes/team/docs/a.txt"), VfsPath.parse("/memory/a.txt"), NodeType.FILE),
        router,
        capabilities,
    )
// moved.strategy == CROSS_MOUNT_COPY_MOVE：跨了两块盘，一律按"读 → 写 → 确认 → 删源"复制
// moved.source!!.mount.path == /notes/team/docs，moved.target!!.mount.path == /memory
```

**边界情况**：

- 抛出的异常 `effect` 是默认的 `NONE`：预检确认这次操作没有产生任何物理或逻辑变更。
- 预检**通过不代表操作会成功**。它只拒绝「已知做不了」的变更；文件不存在、类型对不上、目标已存在，都是执行期的事实（`NOT_FOUND` / `TYPE_MISMATCH` / `ALREADY_EXISTS`）。
- 每次调用都是纯读取，同样的输入得到同样的结果，没有缓存。

## 4. 五个方法合起来走一遍

```kotlin
// 1) 写一个文件：配置结构没问题，local-disk 可写
OperationGuard.check(OperationIntent.write(VfsPath.parse("/memory/notes/a.txt")), router, capabilities)
// → DIRECT_WRITE，目标 local-disk 的 notes/a.txt

// 2) 删一个空目录：不在配置结构上、docs-disk 可写
OperationGuard.check(OperationIntent.delete(VfsPath.parse("/notes/team/docs/old"), NodeType.DIRECTORY), router, capabilities)
// → DIRECT_DELETE，源 docs-disk 的 old

// 3) 同一个盘里改名：docs-disk 不支持原生 move，回退到复制
OperationGuard.check(
    OperationIntent.move(VfsPath.parse("/notes/team/docs/a.txt"), VfsPath.parse("/notes/team/docs/b.txt"), NodeType.FILE),
    router,
    capabilities,
) // → COPY_FALLBACK_MOVE

// 4) 跨盘移动目录：复制语义，目录复制要保留空子目录，目标盘必须能建目录
OperationGuard.check(
    OperationIntent.move(VfsPath.parse("/memory/notes"), VfsPath.parse("/notes/team/docs/notes"), NodeType.DIRECTORY),
    router,
    capabilities,
) // → CROSS_MOUNT_COPY_MOVE

// 5) 整棵删掉 /notes/team：它下面是挂载点 docs-disk，绝不能被一次删除带走
OperationGuard.check(OperationIntent.delete(VfsPath.parse("/notes/team"), NodeType.DIRECTORY, recursive = true), router, capabilities)
// → 抛 UNSUPPORTED_OPERATION
```

## 5. 检查顺序是契约

顺序固定，一共五步，**前一步拒绝就不会走后面**：

| 顺序 | 检查 | 拒绝时的错误码 |
| --- | --- | --- |
| 1 | 纯参数与路径冲突（同路径 move、目标落进源子树） | `INVALID_ARGUMENT` |
| 2 | 结构保护（配置推导出来的目录） | `UNSUPPORTED_OPERATION` |
| 3 | 路由判定（能不能落到某个挂载） | `MOUNT_NOT_FOUND` |
| 4 | 只读 | `READ_ONLY` |
| 5 | 能力组合（能不能用回退的办法完成） | `UNSUPPORTED_OPERATION` |

**为什么是这个顺序**：便宜的检查放前面。判断两个路径是不是一样、是不是配置里的目录，读一下内存里的配置就完了；判断挂载点有没有后端文件、目录是不是空的，才需要真的访问存储。顺序保证「能靠配置判断的问题，永远不会因为后端状态不同而给出不同答案」。

顺序在实际使用中是能看出来的：

```kotlin
// /notes/team 既没有自己的挂载（route == null），又是 /notes/team/docs 的祖先目录
OperationGuard.check(OperationIntent.write(VfsPath.parse("/notes/team")), router, capabilities)
// → UNSUPPORTED_OPERATION（结构保护），不是 MOUNT_NOT_FOUND
```

同一个路径如果先查路由，答案就变成「这块盘没挂到这里」；但它明明是配置里的目录，说「不能改」比说「没挂载」更贴近真实原因。

## 6. 哪些路径受结构保护，为什么

以下路径**不能被 write / move / delete**，一律 `UNSUPPORTED_OPERATION`：

| 路径类型 | 例子 | 为什么 |
| --- | --- | --- |
| 逻辑根 `/` | `/` | 整个命名空间空间的父级，改它没有意义 |
| 命名空间根 | `/memory`、`/notes` | 命名空间是隔离单位，它本身就是「这一片内容归谁管」的声明 |
| 挂载点 | `/notes/team/docs` | 它是 `/notes/team/docs` 到物理目录的映射本身，被替换或删除等于把这块盘摘掉 |
| 配置推导目录 | `/notes/team`（挂载的祖先层）、含子挂载的目录 | 它是由挂载配置推出来的虚拟层，或者整棵搬走会连带别的盘 |

为什么挂载点不能删：删掉 `/notes/team/docs` 等于让「`/notes/team/docs` 下面的文件」失去存储归属——配置还在，数据却不在了；反过来写一个新目录覆盖它，等于让 `docs-disk` 上的内容凭空消失。两种情况都不是「改一个文件」，而是「改配置和存储的对应关系」，那不是 VFS 文件操作该做的事。

递归也不放宽：

```kotlin
OperationGuard.check(OperationIntent.delete(VfsPath.parse("/notes/team"), NodeType.DIRECTORY, recursive = true), router, capabilities)
// → UNSUPPORTED_OPERATION，recursive = true 与 false 一样
```

**但挂载点里面的普通条目不受影响**：

```kotlin
OperationGuard.check(OperationIntent.delete(VfsPath.parse("/notes/team/docs/a.txt"), NodeType.FILE), router, capabilities)
// → 通过，DIRECT_DELETE
```

「不能搬动挂载边界」不等于「不能跨盘搬文件」：普通文件、目录照样能在两个盘之间移动，只要这个目录里没有别的挂载。

move 的目标也要查同一套规则：如果目标路径本身是挂载点，或者是某个挂载点的祖先（移动过去会「吞掉」一块已配置的区域），同样拒绝。

## 7. 错误码与决策

消息里只有逻辑路径和角色（source / target），不含物理路径、连接串、凭据或 `storageKey`。

| 场景 | code | 触发它的输入 |
| --- | --- | --- |
| 源和目标是同一个路径 | `INVALID_ARGUMENT` | `move("/memory/a.txt", "/memory/a.txt")` |
| 目标落进源自己的子树 | `INVALID_ARGUMENT` | `move("/memory/notes", "/memory/notes/backup")` |
| 改配置推导出来的目录 | `UNSUPPORTED_OPERATION` | `delete("/notes/team")`、`write("/memory")`、`move` 的源或目标是 `/`、`/notes/team/docs` |
| move 目标会吞掉已配置挂载 | `UNSUPPORTED_OPERATION` | `move("/memory/a.txt", "/notes/team")` |
| 目标路径没有挂载 | `MOUNT_NOT_FOUND` | `write("/other/x")`、`write("/notes/team/x.txt")`（`/notes` 下没挂存储） |
| 涉及的存储只读 | `READ_ONLY` | `docs-disk` 只读时的 `write`、`delete`、`move`（源或目标任一只读即拒绝） |
| 能力组合做不到 | `UNSUPPORTED_OPERATION` | 目录 move 回退复制，但目标盘 `createDirectory = false` |
| 能力快照缺这块盘 | `INVALID_ARGUMENT` | 快照里没有 `docs-disk`，却要对 `/notes/team/docs/a.txt` 做变更 |

**为什么快照缺 `storageKey` 要报错而不是放行**：预检的职责是「在副作用之前拒绝已知无效或不受支持的变更」。快照缺一块盘意味着只读和这两块能力组合**判不出来**；如果默默当成「能力齐全」，那些真正做不了的变更会一路溜到执行期才失败——正好违背预检存在的理由。所以宁可当场报「能力快照不完整」，让组装阶段把快照补齐。

## 8. 五种执行策略

通过之后，`PreconditionResult.strategy` 说明该怎么做。它只描述方式，**不执行任何 I/O**；执行层（T15 / T16 / T20 / T21）照着它编排实际操作、状态更新和失败时的 effect 报告。

| 策略 | 什么时候用 |
| --- | --- |
| `DIRECT_WRITE` | write 直接执行；除了只读，写入没有额外的组合能力要求 |
| `DIRECT_DELETE` | delete 直接执行 |
| `NATIVE_MOVE` | 同一个挂载点内，且后端支持对应的原生移动：文件看 `nativeFileMove`，目录看 `nativeDirectoryMove` |
| `COPY_FALLBACK_MOVE` | 还是同一个挂载点，但原生能力缺失，改按「读 → 写 → 确认 → 删源」复制 |
| `CROSS_MOUNT_COPY_MOVE` | 跨挂载点，一律按复制语义执行 |

回退复制里，**文件**没有额外要求（读出来写回去就行）；**目录**必须能建目录，否则空子目录会悄悄丢失，明确拒绝：

```kotlin
// docs-disk 不支持原生目录移动，也建不了目录 → 明确不支持，而不是搬一个残缺目录过去
OperationGuard.check(
    OperationIntent.move(VfsPath.parse("/notes/team/docs/sub"), VfsPath.parse("/notes/team/docs/other"), NodeType.DIRECTORY),
    router,
    CapabilitySnapshot.of(mapOf("docs-disk" to StorageCapabilities(nativeDirectoryMove = false, createDirectory = false))),
)
// → UNSUPPORTED_OPERATION
```

**跨挂载点一律复制，哪怕两块挂载共用同一个 `storageKey`**：

```kotlin
// /notes/team/docs 和 /notes/team/wiki 都挂在 docs-disk 上
OperationGuard.check(
    OperationIntent.move(VfsPath.parse("/notes/team/docs/a.txt"), VfsPath.parse("/notes/team/wiki/a.txt"), NodeType.FILE),
    router,
    capabilities,
) // → CROSS_MOUNT_COPY_MOVE，不是 NATIVE_MOVE
```

理由：`storageKey` 只是「用哪个存储实例」的名字，同一个 key 只说明是同一个实例，**不保证两个逻辑目录在物理上是挨着的**。真实后端的 rename 能否跨目录、跨挂载点生效，要等 T12 摸清 OpenDAL 行为、T18 掌握物理映射之后再重估；在那之前保守地按复制语义执行，代价是慢一点，收益是不会因为「以为能原子改名」而丢数据。

## 9. 它不管的事

- **不执行任何 I/O**：不读、不写、不列目录、不 stat。它只看配置和入参，不打开后端。
- **不判断文件存不存在**：源在不在、目标是不是已存在、是不是个目录，都是执行期的事实（`NOT_FOUND` / `ALREADY_EXISTS` / `TYPE_MISMATCH`）。预检只拒绝「已经知道做不了」的情况。
- **不产生事件、不碰状态库**：不发布任何 VFS Event，不读写 Node。状态更新由执行层在真实操作成功后做。
- **不决定 Node 身份**：跨挂载移动之后还是不是同一个 Node、Metadata 怎么留，是执行层的责任。
- **`readOnly` 只反映打开后端时已知的信息**：挂载之后权限被改、盘满了、后端中途开始拒绝，都是执行期错误。
- **不做符号链接和物理边界检查**：逻辑路径没法通过路由逃出挂载的相对路径，但这不代表抵御了文件系统层面的符号链接或外部并发替换（T12）。
- **不缓存、不做性能优化**：线性直查，每次调用都重新判断。挂载和盘能力都不够快吗？重算一遍就行，没有性能证据前不引入缓存。
