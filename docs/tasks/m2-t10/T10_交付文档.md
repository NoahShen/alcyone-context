## 需求目标

在 `vfs/core` 实现变更操作（write / move / delete）的预检组件 `OperationGuard`：结合 T09 的 `MountRouter` 路由视图与各存储的能力快照，在任何存储副作用之前拒绝已知无效或不受支持的变更，并为允许的操作输出执行策略。纯逻辑实现，零 I/O，用假能力数据做真实单元测试。

本任务不含：操作编排（T15/T16/T20/T21）、真实后端能力探测（T12）、配置组装（T18）、存在性与覆盖等执行期判定。

## 主要实现

### 交付组件（`vfs/core` 新包 `core.operation`）

| 类型 | 职责 |
| --- | --- |
| `OperationIntent` + `OperationType` | 操作意图：write/move/delete 工厂方法固定形状（write 无 source、delete 无 target、write 恒 FILE）；携带 `entryType` / `WriteMode` / `recursive` |
| `CapabilitySnapshot` | `storageKey → StorageCapabilities` 不可变快照，入参防御性复制 |
| `ExecutionStrategy`（5 值） | `DIRECT_WRITE` / `DIRECT_DELETE` / `NATIVE_MOVE` / `COPY_FALLBACK_MOVE` / `CROSS_MOUNT_COPY_MOVE` |
| `PreconditionResult` | 策略 + 源/目标各自命中的 `RouteMatch`（挂载记录 + 相对 StoragePath） |
| `OperationGuard.check(intent, router, capabilities)` | 预检入口：拒绝抛 `VfsException`，通过返回策略与路由结果 |

### 检查顺序（契约）

参数与路径冲突（`INVALID_ARGUMENT`）→ 结构保护（`UNSUPPORTED_OPERATION`）→ 路由判定（`MOUNT_NOT_FOUND`）→ 只读（`READ_ONLY`）→ 能力组合（`UNSUPPORTED_OPERATION`），前一步拒绝即停止。

### 结构保护

逻辑根、命名空间根、Mount 根、配置推导目录的 write/move/delete 一律拒绝；含后代挂载的目录整体移动/删除拒绝（`recursive=true` 不放宽）；move 目标是挂载点或其祖先（会吞掉已配置挂载）拒绝。全部复用 T09 `MountRouter.isConfiguredDirectory` 一次查询（挂载点及其祖先都在 `configuredDirectories` 内），零重复推导。

### 只读与能力

- 任一涉及存储只读 → `READ_ONLY`（信息不含 storageKey）
- 同挂载点 move：按条目类型选 `nativeFileMove` / `nativeDirectoryMove`，原生优先；缺失按复制回退，目录回退要求目标 `createDirectory`，缺失拒绝
- 跨挂载点 move：一律复制语义（read → write → 确认 → delete），**不因 storageKey 相同改用原生**（保守取舍，T12/T18 掌握物理映射后重估）
- write / delete 除只读外无组合能力要求

### 既有类型唯一改动

`StorageCapabilities` 增补 `readOnly: Boolean = false`（T07 兼容性补充）：只读在打开后端时即可得知，预检据此在副作用前拒绝；默认值不改变既有实现与测试。

## 关键设计决策

1. **快照缺失 storageKey → `INVALID_ARGUMENT`**（本任务确定）：预检无法判定只读与能力组合，静默假设能力齐全会让不受支持的变更漏到执行期，违背预检存在的理由；宁可在组装阶段报「快照不完整」。
2. **结构保护复用一次 `isConfiguredDirectory` 查询**：T09 已把挂载点与全部祖先纳入配置目录，三类保护结构（根/命名空间根/挂载根/推导目录/含后代挂载目录）落在同一查询上，无双拒绝无漏拒绝。
3. **跨挂载点不因同 storageKey 改用原生 move**：同一 key 只说明同一实例，不保证物理目录相邻；保守按复制语义，避免「以为能原子改名」而丢数据。
4. **检查顺序是契约**：能靠配置判断的问题永远不会因后端状态不同给出不同答案（便宜的检查在前）。
5. **策略只描述不执行**：T15/T16/T20/T21 据此编排，预检零 I/O。

3. **`readOnly` 只反映打开后端时已知的信息**：运行中新出现的拒绝按执行期错误处理。
4. **跨挂载同 storageKey 一律复制**：可能牺牲可用原生 rename 的性能，保守取舍待 T12/T18 重估。
