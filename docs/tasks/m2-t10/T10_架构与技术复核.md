## 2. 逐项复核结论

### 2.1 A01～A07 与 T02 语义：符合

- **检查顺序契约（任务文档 2.1 / T02 §8.2）**：实现严格按参数冲突 → 结构保护 → 路由 → 只读 → 能力组合，前一步拒绝即停止；顺序确定性有专门用例（参数先于结构、结构先于路由、只读先于能力缺失）。
- **结构保护（T02 §8.2 全表）**：根 / 命名空间根 / Mount 根 / 配置推导目录的 write / move / delete 均拒绝；含后代挂载的目录整体移动删除拒绝且 `recursive=true` 不放宽；move 目标为挂载点或其祖先拒绝；子挂载内普通条目不受影响。
- **参数冲突（T02 §7.1）**：同路径 move（规范化后判等，尾斜线变体能抓住）、目标入源子树（段级前缀）返回 INVALID_ARGUMENT，且早于结构检查。
- **路由判定**：无挂载且非配置目录返回 MOUNT_NOT_FOUND；允许结果携带源 / 目标 `RouteMatch`（挂载记录 + 相对 StoragePath），供 T15 / T16 / T20 / T21 编排。
- **执行期事实不越界**：NOT_FOUND / ALREADY_EXISTS / TYPE_MISMATCH 不在预检产生，预检全程零 I/O（A06）。

### 2.2 结构保护单次查询推理：成立（独立推演验证）

交付方声称"复用 T09 `isConfiguredDirectory` 一次查询覆盖全部结构保护"。复核推演：**包含后代挂载的目录必然是该挂载的祖先（或挂载点本身）**，而 T09 的 `configuredDirectories` 恰好包含挂载点及其全部祖先；T02 §8.2 禁止变更的四类路径（根、命名空间根、挂载根、推导目录 / 含挂载祖先）全部落在该集合内。无过拒（集合外路径都是普通条目）、无漏拒（集合内路径都该拒）。推理成立，是本任务最有价值的设计简化。

### 2.3 两项设计决策：合理

- **快照缺失 storageKey → `INVALID_ARGUMENT`**：能力判不出时按"齐全"放行会让不受支持的变更漏到执行期，违背预检目的；报配置错误更诚实。一个固有顺序细节：该检查在路由命中之后才能执行（需先拿到 storageKey），因此可与 MOUNT_NOT_FOUND 交错出现——两者都是拒绝路径、无副作用且结果确定，不违反顺序契约的精神，可接受。
- **跨挂载点不因同 storageKey 改用原生 move**：同一 key 只保证同一实例，不保证物理目录相邻；保守按复制语义避免"以为能原子改名"而丢数据，且已在任务文档 / 交付文档记录为待 T12 / T18 重估的取舍。

### 2.4 `readOnly` 兼容性补充：准确

`StorageCapabilities` 增补 `readOnly: Boolean = false`，是唯一既有类型改动；Kdoc 写明理由（打开后端时即可得知）与默认值影响。T07 / T09 既有测试零回归（本机 180 全绿验证）。错误消息不泄露 storageKey（有专门断言），与 T02"不为凑错误码猜测后端原因"的精神一致。

### 2.5 实现细节与测试质量

- `OperationGuard` 为纯函数 object，仅依赖路径 / 路由 / 能力模型，零 Storage / Repository / 事件引用（A06）。
- `CapabilitySnapshot` 防御性复制 + 不可变值对象，同 T09 模式；快照不可变有专门用例。
- `entryType` 由调用方提供：预检是"给定意图下的判定"，类型事实由编排层 stat 后填入，Kdoc 已说明"只装参数，不装事实"的边界；可接受。
- `writeMode` / `recursive` 携带但不参与判定：符合"三模式一视同仁、recursive 不放宽结构保护"的设计，Kdoc 有说明。
- 33 个用例覆盖 A01～A06 全部场景 + 顺序契约 + 消息不泄露 storageKey + 五种策略逐一选择，质量高。
- 无越界实现：未做操作编排、未改 Vfs 公共签名 / Schema / 工具链 / CI。
