### 2.1 Storage 边界

```kotlin
enum class StorageWriteMode { CREATE_NEW, REPLACE_EXISTING, UPSERT }

data class StorageAttributes(
    val type: NodeType,
    val sizeBytes: Long? = null,
    val modifiedAt: Instant? = null,
)

data class StorageEntry(
    val name: String,
    val type: NodeType,
    val attributes: StorageAttributes? = null,
)

class StorageContent(val bytes: ByteArray, val attributes: StorageAttributes)

interface StorageStream : AutoCloseable {
    val attributes: StorageAttributes
    fun openStream(): InputStream
}

data class StorageCapabilities(
    val nativeFileMove: Boolean = true,
    val nativeDirectoryMove: Boolean = true,
    val createDirectory: Boolean = true,
    val boundedRead: Boolean = true,
)

interface Storage {
    suspend fun read(path: StoragePath, maxBytes: Long): StorageContent
    suspend fun readStream(path: StoragePath, maxBytes: Long? = null): StorageStream
    suspend fun stat(path: StoragePath): StorageAttributes
    suspend fun list(path: StoragePath): List<StorageEntry>
    suspend fun write(path: StoragePath, content: ByteArray, mode: StorageWriteMode): StorageAttributes
    suspend fun createDirectory(path: StoragePath)
    suspend fun move(source: StoragePath, target: StoragePath): StorageAttributes
    suspend fun delete(path: StoragePath, recursive: Boolean)
    fun capabilities(): StorageCapabilities
}
```

`StoragePath` 关键语义：挂载根是 `segments` 为空的独立表示（不用空字符串），规范相对文本为 `.`；输入已解码，`parse` 不做百分号解码；拒绝绝对路径、空中间段、`.` / `..`、段内 `/` 与 `\`、C0/DEL/C1 控制字符、孤立代理字符；不可变（入参防御性拷贝 + `Collections.unmodifiableList`）。

### 2.3 事务与通知边界

```kotlin
interface TransactionScope {
    val nodes: NodeRepository
    val metadata: MetadataRepository
    val events: EventRepository
}

interface UnitOfWork {
    suspend fun <T> inTransaction(block: suspend (TransactionScope) -> T): T
}

fun interface VfsEventConsumer {
    suspend fun onEvent(event: VfsEvent)
}

class EventDispatcher {
    fun subscribe(consumer: VfsEventConsumer)
    suspend fun dispatch(events: List<VfsEvent>)
}
```

`EventDispatcher` 是 **Core 内部组件**，不是 Storage 或 Repository 的方法。`CancellationException` 在分发时原样抛出（不吞），其余消费者异常只记日志、不冒泡。

## 6. 提请设计审核的具体问题

以下是本次交付中**已知存在设计张力**的地方，请设计 Agent 明确裁决，不要默认接受。

### 问题 1：G3 改判与 T02 §6.2 冲突

T02 §6.2 原文：**「某个实际父路径为文件时返回 `TYPE_MISMATCH`」**。

T07 B1 评审时用户改判为 `STORAGE_ERROR`，理由是：只有当实现层能确认是类型冲突时才用 `TYPE_MISMATCH`，识别不出父路径类型就按真实 I/O 失败处理。

**张力**：`TYPE_MISMATCH` 的语义在 T01 §7 是「文件 / 目录类型不符合操作」，父路径是文件**恰好就是这个语义**。改成 `STORAGE_ERROR` 会让 T02 §11 的 W04 场景（父路径为实际文件）期望的类型错误变成泛化 I/O 错误。

**请裁决**：是否恢复 T02 §6.2 的 `TYPE_MISMATCH`？若维持改判，T02 §6.2 与 §11 W04 需同步回写。

> **2026-09-30 复核裁定：维持 B1 改判，但改为条件式表述。** 实现**能确认**是文件 / 目录类型冲突时用 `TYPE_MISMATCH`；无法识别失败原因的真实 I/O 错误用 `STORAGE_ERROR`，不要求额外探测。原无条件写 `STORAGE_ERROR` 过强，已修订 `Storage.createDirectory` / `write` 的 KDoc 与 `StorageFakeImpl` 的对应行为；T02 §11 W04 在**可确认类型冲突**时继续成立。T02 §6.2 无需回写。

### 问题 2：`Storage.readStream` 的契约强度不足

当前 `StorageStream` 只提供 `openStream(): InputStream` 与 `attributes`，**限额参数 `maxBytes` 在接口上没有任何约束**——实现是否真的在读取过程中中止，接口层无法表达。

G4 要求「读前 stat 快速拒绝 + 读取中逐块计数中止」两层防护，但第二层目前只是 KDoc 里的文字承诺，**没有任何机制强制**。

**请裁决**：是否需要在接口层增加可验证的约束，例如让 `StorageStream` 暴露「已读取字节数」或让 `readStream` 返回一个在超限时必然抛异常的包装？

> **2026-09-30 复核裁定：不扩充接口。** 公开计数器并不能保证限额，接口只需在 KDoc 规定行为：`maxBytes = null` 表示调用方不设上限，非 null 表示读取上限且限额约束**实际读取到的内容**；返回的 `StorageStream` 持有底层资源，**由调用方关闭**。读取中如何计数并中止、异常转换、重复打开与关闭后的行为属**实现细节，留 T12** 补实现与测试，不作为 T07 阻塞项。公共流式方法方向已在 T01 记录，但公共 `Vfs` 尚无对应方法，不当作公共 API 已交付。

### 问题 3：`markDeleted` 与 T03 §2「标记删除」的实现落差

T03 §2 写的是「成功删除后**将 Node 标记删除**、释放有效路径并清理 Metadata」，即软删除；但 T07 的 `NodeRecord` 是「活着的 Node」读取模型，不含删除状态，`markDeleted` 收的 `deletedAt` 在内存替身中被忽略。

**当前设计**：`deletedAt` 是给 Repository 实现写入自己存储用的（T11 建表时会有 `deleted` 标志与 `deleted_at`），`NodeRecord` 不暴露。

**遗留**：如果 T11 实现为软删除，`findById` 必须过滤已删除记录；如果实现为硬删除，删除时间会丢失。**这个决定留到 T11**，但 T07 的接口契约没有把「软删除」这一语义写进 KDoc。

**请裁决**：`NodeRepository.markDeleted` 的 KDoc 是否应补写「实现方需保留删除标记，查询时对已删除记录返回 null」？这会约束 T11 的实现方向。

> **2026-09-30 复核裁定：只补最小语义，不约束实现。** KDoc 已写明「标记后正常查询不再返回该节点、其 `VfsPath` 立即可被新节点复用」；`NodeRecord` 继续只表示有效节点。T03 的删除标记与清理语义继续有效，但**数据库字段、存储方式、索引与清理顺序一律留 T11**，T07 不追加实现约束。`deletedAt` 参数保留作为实现自用（当前替身忽略它）。

### 问题 4：`EventDispatcher.dispatch` 的「只在提交后调用」无强制手段

`EventDispatcher` 的 KDoc 写明「只能在事务提交成功后由编排层调用」，但这是**纯约定**。`UnitOfWork` 与 `EventDispatcher` 之间没有结构性绑定，任何调用方都可以在事务提交前调用 `dispatch`。

B5 阶段我认可了「不提供成对封装」的取舍（避免提前锁死 T15 编排形态），测试也只用「提交失败时可分发集合为空」间接演示。

**请裁决**：接受纯约定，还是在 T15 编排时要求成对封装？

> **2026-09-30 复核裁定：接受分离接口，本轮不增加协调器。** 代价是「仅在提交成功后通知」在 T07 无法用替身结构化验证：现有测试只靠「提交失败时可分发集合为空」间接演示，属弱证据。**T14 / T15 必须通过编排测试证明：提交成功才通知、提交失败不通知、通知失败不改已提交结果**，不能仅验证一份手工置空的事件集合。

### 问题 5：A06 验收面过窄

按 I1/I2 决议取消了可注入时钟与 ID 生成器，**本任务没有产生任何时间字段与 ID 的填充逻辑**。A06 实际只验证了「没有注入框架」，未验证 Core 侧的 ID 生成路径。

**请裁决**：A06 是否应移出 T07 的验收范围，改为在 T13（Node Registry）与 T14（事件持久化）验收？

> **2026-09-30 复核裁定：接受取消注入的用户决定，A06 记为不适用。** 理由是 T07 没有时间 / ID 生成流程，A06 无可验证对象，标「通过」会误导。Node 生成与时间字段在 **T13** 验证，事件在 **T14** 验证；`common` 现有 UUIDv7 工具测试保留。

### 问题 6：`StorageCapabilities` 的四项是否覆盖 T02 全部能力差异

T02 §4 提到后端差异包括「后端自身只读、拒绝访问、文件名不受支持、原生 move 缺失」，T02 §8.1 要求递归删除能力检查，T02 §4 还提到符号链接边界。

当前 `StorageCapabilities` 只有四项（原生文件移动、原生目录移动、创建目录、有界读），**没有**递归删除能力、符号链接策略、文件名支持范围。
