## 2. 必须修改

### R1 / P2：整树最终枚举失败遗漏已发生副作用

`DefaultVfs.moveDirectoryByCopy` 第 5 步直接调用 `enumerateTree(targetStorage, ...)`，位于前面逐项复制的 catch 之外。此时目标根和全部复制条目已经写入，若目标 list 或枚举内部 stat 抛 `VfsException(..., effect=NONE)`，最终异常仍是 NONE，违背 A06；注释称“枚举失败按阶段合并”但这里没有接线。

**修复与补证：**对复制后确认阶段的后端失败合并已知目标变化，保留原 code / cause 与 UNKNOWN，NONE 升 PARTIAL。分别让最终目标根 list、一个后代目录 list 或属性查询失败，核对源完整、目标残留、未调用源 delete、逻辑未迁移且无成功事件；一个额外 UNKNOWN 输入可与同一装置合并。不要把所有后端失败改成 CONFLICT。

### R2 / P1：整树确认丢掉可用长度，源树也未按注释复查

`TreeEntry.attributes` 已保存枚举得到的属性，但后续从未使用；copyOneFile 再 stat 时忽略最初已知长度，最终目标枚举也只把条目变成“段列表 + 类型”。例如第一份文件先通过逐文件确认，复制第二份时第一份被截短，最终 list 已报告更短长度，当前仍因集合 / 类型相同而递归删源——已经拿到的矛盾不能当作未知外部竞争忽略。

另一个边界是初始 sourceEntries 后不再枚举源，`TreeEntry` 注释“删源前再回读一次比对”并未实现；末尾递归删除覆盖的是删除时的实际树，新增且未复制的源项也可能被带走。任务要求发现已知源集合 / 长度变化时拒绝，这需要与整树删除范围匹配的最小确认，不能仅比目标与旧快照。

**最小修复与验收：**保存每个成功复制文件的字节数，最终枚举时核对可用长度，初始已知源属性也不要静默丢弃；删除前复查源条目集合 / 类型及可用长度，检测到矛盾报 CONFLICT + 已知 effect，禁止进入删除。补“前项确认后截短、最终 list 报短长度”和“复制中源多出一项、删除前可见”两个受控反例，断源均未删除；null 仍只表示未知。不要求哈希、锁住外部进程或消除最终检查之后的所有竞争窗口，文档明确这是检测保障而非目录原子快照。

## 4. 建议优化

copyOneFile 与 T21 moveByCopy 有较多长度 / 错误处理重复，本轮已出现整树枚举遗漏合并的情况。可在修复时抽取小型私有“复制并返回确认事实”辅助方法，供最终整树核对使用；不要求通用执行器，也不把单纯重复代码作为阻塞项。

enumerateTree 在属性缺失时 stat，但只保存了原先为空的 attributes，且忽略 StorageEntry 已有 type；处理 R2 时可保留真正取得的属性，避免额外查询后又丢弃。返回目录 StorageStat 字段未知可接受，不为补返回值追加无关后端请求。

## 5. 可以接受的设计取舍与下一步

Local FS 同 Mount 目录复制回退、逐文件有界内存复制、保存条目清单、根级事件、根懒注册及全部逻辑路径同事务合理。源递归删除仍可作为底层原语，但必须在整树确认之后，并诚实报告部分删除；全链持锁、不补偿、未注册后代不批量登记均符合基线。

不要求新增 WebDAV、目录原生后端、流式写入、可靠消费或崩溃恢复。完成 R1～R4 后交回复核；本轮仅维护文档，不修改生产 / 正式测试，不提交或推送，不开始 T23。
