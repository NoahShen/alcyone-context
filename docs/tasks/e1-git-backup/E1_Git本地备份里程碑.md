## 1. 目标与架构输入

交付可选 `vfs/git-backup` JVM 模块，仅依赖 VFS API，通过宿主调用现有 subscribe 接线。技术输入见 [设计 v0.1](../../vfs/Git_本地目录备份设计_v0.1.md)；截至 2026-10-16 的用户确认是实施基线，局部实现选择由 Lead 提案并由 Architect 在任务复核确认。

本地 Mount 根就是专用 Git 工作区；远端地址、身份和认证由宿主预配置。事件重置 60 秒静默倒计时，Cron 使用本机时间，启动与手动触发同一同步流程；完整工作区暂存、按需提交、始终尝试推送已有 HEAD，每次运行写执行日志。

不增加公开状态模型、时区字段、持久化队列、事件重放、自动冲突处理、`.git` 保护或动态插件框架。既有 VFS 生产代码、Runtime 构建依赖与数据库 Schema 零改动，不引入新平台支持承诺或外部发布。

## 3. 三级协作与交付门槛

Architect 通过 Paseo 创建并复用一个 Lead；Lead 通过 Paseo 创建 Worker 承担实现，Lead 负责详细设计、实际代码审查和初验。用户明确要求 Architect → Lead → Worker，优先于 profile 中“Lead 可直接实现普通功能”的默认建议。

每任务流程：Worker 实现/自测 → Lead 审查/实跑 → IN_REVIEW 并立即交 Architect → Architect 独立检查 Diff、关键代码和必要测试 → 通过后 DONE 并通知 Lead 启动下一项。问题必须回 Lead 安排 Worker 修复，不能跳过复核或等待全部实现后一起审查；不需要每个常规步骤重新向用户确认。

同一工作区顺序施工，不同时运行互相清理输出的 Gradle 检查。Architect 维护顶层进度和复核文档；Worker 只修改当前任务白名单与该任务交付文档，不覆盖现存未提交设计文档。代码提交与证据需列出精确文件和基线，不使用 git add . 混入他人修改。
