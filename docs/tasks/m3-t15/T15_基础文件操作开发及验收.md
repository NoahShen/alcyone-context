## 1. 目标与范围

在 `vfs/core` 交付可直接注入已有组件的 `DefaultVfs`，贯通创建 → 读取 → 覆盖 → stat → list，并接上已有 getNode。Core 继续只依赖 Port；真实 SQLite 和 Local FS 组合放 `integration-tests/vfs`，无需提前实现 Runtime 配置、数据库打开或 Operator 生命周期。

若 DefaultVfs 实现完整 Vfs 接口，尚未交付的 move / delete / getMetadata / setMetadata 暂时明确抛 `UNSUPPORTED_OPERATION` 且无副作用，不能静默成功或使用 `TODO()`；说明这是阶段实现，分别由 T16 / T17 / T20～T22 接续。首版流式读取的需求仍保留，本轮按现有 ByteArray 公共签名交付，公共流式入口与 SDK 接线在 T18 明确、T19 验证，不把 Storage.readStream 已实现误报为 SDK 已交付。

例：测试手动组装 DefaultVfs、真实状态库和临时本地目录即可完成写读；用户通过配置创建 SDK 的入口留 T18。

## 2. 开发内容

### 2.1 依赖与唯一持锁者

复用 MountRouter、OperationGuard、NodeRegistry、StateBoundary、EventPipeline 和 Storage / Repository Port。DefaultVfs 不反向引用 persistence / storage 实现，限额与已创建组件由构造接入，不引入 DI 框架或新的配置系统。

写入的共享锁应覆盖配置/状态预检、实际类型与存在性确认、补父目录、Storage 写入、状态与事件提交；SQLite 事务仅覆盖最后的逻辑提交。对 T14 增加最小 internal 已持锁入口（或等价的小型组合方式），保留公开 commit 自取锁行为，内部调用 Registry 时也使用已有无锁入口，禁止重复获取同一 Mutex。

例：两个 CREATE_NEW 写同一路径，在同一共享边界内恰有一个成功；不能先在锁外各自完成物理写入，再只串行提交数据库。read / list 不要求内容快照，但它们访问单连接 Repository 时仍须遵守共享边界，最简方案可以串行整个调用。

### 2.2 read、stat 与 getNode

read 路由到 Storage 的有界读取，不懒注册、不改 Metadata、不发事件；逻辑目录（含配置推导目录）返回 TYPE_MISMATCH。ByteArray 读写默认限额 16 MiB，可注入调整；read 的实际上限为配置与 `ReadOptions.maxBytes` 中较小者，null 使用配置、0 只接受空文件，不能只根据 stat 大小判断实际读取量。

stat / getNode 复用 T13 已确认行为，包括已有 Node 的 includeStorage=false 逻辑查询、未登记资源的存在确认、虚拟目录懒注册及挂载根类型检查。无需重新实现 Registry 或在查询时修复外部删除/改型；查询与懒注册均不发布成功变更事件。

例：物理文件尚未登记时 read 仍可成功，getNode 不会凭空找到它；首次 stat 才创建身份，后续 stat 复用该 ID。

### 2.3 list 与挂载覆盖

按 T02 第 5.2 节单层合并：物理目录直接子项，加配置推导的本层目录入口；同名时配置入口优先、按完整子路径去重，不混入被子 Mount 遮蔽的父后端内容。通过 Repository 批量补已有 Node ID，不注册新 Node、不逐项调用 Storage.stat，返回集合无排序保证。

纯虚拟目录不伪造物理访问；必要祖先被物理文件遮蔽时沿用 T13 的目录优先边界，实际 Mount 根不得回退为虚拟目录。父列表不连接子后端；本次确实需要访问的后端 list 失败应整体报错，不能吞掉一般 I/O / 拒绝访问后仅返回配置入口。

例：父盘有 `medical` 文件，配置 `/resources/medical/ct` 挂载，父列表返回逻辑目录 medical，下一层能看到 ct；ct 后端离线不影响父层入口可见，进入该挂载才报告其真实错误。

### 2.4 write 预检与自动补父目录

按 T02 矩阵执行 CREATE_NEW / REPLACE_EXISTING / UPSERT；先拒绝参数、受保护结构与已知能力问题，再确认实际文件存在性、类型及逻辑记录冲突，任何可确认的拒绝都须在创建目录或写内容之前完成。OperationIntent 的类型不是实际类型验证：写入期望 FILE 仍须核对 Storage，不能直接覆盖目录，也不能只从 Registry 推断文件存在。

仅在目标所属 Mount 内补缺失父目录，缺少建目录能力且确需补目录时返回 UNSUPPORTED_OPERATION；父组件是物理文件时拒绝，不改写遮蔽物理文件。父目录不批量注册、不产生单独目录创建事件，超限写入在任何物理变更前拒绝。

例：REPLACE_EXISTING 写不存在的 `/resources/a/b.txt` 直接 NOT_FOUND，不留下 a；UPSERT 则在确认约束后建 a，再写 b.txt。现有父目录齐全时，不因后端缺少 createDirectory 能力而拒绝普通文件写入。

### 2.5 成功状态、事件与失败事实

Storage 写入成功后，在一个事务内创建/更新 Node 并追加 FILE_CREATED 或 FILE_WRITTEN；事件类型依据写入前的实际文件存在性，覆盖保留有效 Node ID、registeredAt 和 Metadata，updatedAt 随成功变更更新。NodeInfo 可复用写入返回属性或令 storage 为空，不为返回值额外 stat；不能先调用会自提交注册的 Registry 方法，再另起事务追加事件。

Storage 失败不提交成功状态/事件；物理写成功但状态/事件提交失败返回 STATE_ERROR，报告已知物理变化（PARTIAL），不自动补偿。补父目录必须逐层保留事实：第一层建成、第二层失败时报 PARTIAL（盘上确实留着第一层），第一层就失败仍是 NONE；补完父目录后写失败同样不能降回 NONE。后端 UNKNOWN 不降级也不改判；取消异常原样传播，不声称取消即全部回滚。

例：a 已创建、b 写失败，允许留下空目录 a 并报告实际 effect；文件已写好但事件追加失败，则 Node 与事件一起回滚，物理内容保留、无成功通知。事件入队满或 Consumer 失败仍不反向改变成功结果，复用 T14 而非另建分发器。

| A03 父目录与拒绝 | 自动补多层父目录且不批量登记；模式、结构、类型、只读/能力、限额拒绝先于副作用 | 真实目录创建；替身记录无效写的 createDirectory/write 调用为零；父路径文件冲突、缺建目录能力且父目录缺失/已齐全两个分支 |

| A05 事务与失败报告 | Storage 失败无成功状态；写成功后 Node/Event 失败同批回滚、effect 保留实际副作用，无成功通知 | 真实文件已改变 + 真实 SQLite 事务故障（如确定的追加冲突）至少一例；补目录后写失败、后端 UNKNOWN 用小替身验证。通知负向断言复用 T14 按 ID 末尾确认 |
