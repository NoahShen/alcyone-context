### R1 / P2：补父目录中途失败会丢失已经创建目录的事实

位置：`DefaultVfs.createMissingParents` 的 `missing.forEach { storage.createDirectory(it) }`，以及 `writeInsideBoundary` 调用该函数的位置。已有 effect 合并只包住最终 `storage.write`；父目录创建成功一部分后，后续 createDirectory 抛错会直接退出，先前副作用未合并。

独立探针：写 `/resources/a/b/file.txt`，创建 a 成功，创建 a/b 返回 `STORAGE_ACCESS_DENIED/NONE`，最终仍报告 NONE，盘中 a 却已存在。未产生 Node / Event 是正确的，但不能据此宣称整次操作无副作用。

## 3. 用户关注的设计边界

### 3.1 write 全链持锁：接受

参数限额在锁外完成，其余预检、Storage stat、补父目录、write、状态事务和非阻塞事件交接均在同一个 StateBoundary 内。对于首版单状态库、单 Runtime 的串行策略，这是必要且简单的保证，能避免 CREATE_NEW 在物理层已竞争完才排队提交状态。

代价是慢 Storage I/O 会阻塞其他写和当前同样持锁的 read/list/stat；首版可以接受，不要求细粒度路径锁或把 I/O 移到锁外。真实 Runtime 停机和超时仍留 T18 / T27，当前代码不承诺锁等待时限。

### 3.2 commitInsideBoundary：没有发现公开路径误用

生产调用只有两处：EventPipeline 公开 commit 在 boundary.withLock 内调用，DefaultVfs 在 write 的同一外层锁内调用。方法为 internal，数据库事务仍在 Storage 成功后才开启；T14 公开入口的锁与提交后通知行为保留，回归通过。

它仍依赖组装时注入同一个 boundary，属于既有内部约定，不要求新增锁所有权检查或 DI 框架。DefaultVfs 不会在写入前用 Registry 自提交注册，Node 与 Event 留在最后同一事务中。

### 7.2 剩余必须修改：A06 证据与文档

**并发：** `DefaultVfsRealStackTest.kt:327–344` 仍在第二次调用前完成 secondCalling，测试随后立即放行第一写。第二个协程可能在信号之后才获得执行机会，因此即使没有锁，也可能得到同样的事后顺序；而 `PausingStorage.kt`（同文件底部）的 write 日志记录在挂起/真实写入之前，`stat → write → stat` 本身不表示物理写完成顺序。

无需生产接缝：可用测试内受控调度或 `CoroutineStart.UNDISPATCHED`，确保第二请求实际执行到第一个挂起点，再检查没有越过锁进入 Storage，最后释放第一写并核对最终结果。保留现有真实栈验证，不用超时或事后自然顺序替代“竞争已发生”的证明。

**取消：** `DefaultVfsRealStackTest.kt:364–375` 在 async 内用 runCatching 捕获入口异常，却没有检查这个捕获结果；随后检查的是已显式 cancel 的 Deferred.await。即使入口把取消包装为 VfsException、被 runCatching 转成返回值，已取消的 Deferred 仍可向 await 抛原取消原因，因此该断言不能证明入口原样传播。

应在调用 DefaultVfs 的协程内部捕获异常时，将它保存到独立观察信号/引用，外部取消并 join 后直接检查捕获值，再保留后续写成功与无失败操作事件的检查。现有测试确实证明受控写未落盘、状态未提交、锁可再用；不要求扩建提交附近取消或 native 在途取消矩阵。

**文档：** 同步交付第 4 节 api 变更说明与 A06 强度；验收第 4 节“118 例口径下 core 218”是残留错字。若保留 helper 的当前实现，还应订正其 Kdoc：message 会追加 note，不是原样；首层创建失败是“保留后端 effect”，并非任何首层失败都必然 NONE。

### 7.3 withEffect：建议收回 Core 私有范围

新增扩展位于 `vfs/api/VfsException.kt:64`，是 public API；唯一调用点是 Core 的 withKnownChanges。它只复制异常字段、追加说明并将原异常设为 cause，不包含副作用判定；没有必要为这一处内部组合引入面向 Context System 的新公共入口，推荐移到 Core private/internal，而非增加限制或抽象框架。

尤其要区分：`withKnownChanges` 保证仅把 NONE 提升为 PARTIAL；`withEffect` 本身允许任意赋值，包含 UNKNOWN → NONE，和“不改判 UNKNOWN”的 Kdoc 容易混淆。当前生产调用传 PARTIAL 且有前置判断，没有发现实际错误降级；公共 API 收敛是建议，不另判为已发生的业务故障。若选择保留公开入口，应准确说明任意复制语义并记录公共契约增加，交付不能再写 api 无变更。
