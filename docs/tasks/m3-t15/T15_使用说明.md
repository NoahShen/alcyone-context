# T15 使用说明

## 本次修改（2026-10-03，T15 实现交付初稿）

- 按「怎么组装 → 锁由谁持有 → 每次操作碰什么 → 失败报什么 → 哪些还没做」组织。涉及全文。

模块路径 `vfs/core`，主类 `com.github.noahshen.alcyone.context.vfs.core.DefaultVfs`（另有 `VfsLimits`）。Core 只依赖 Port，不出现 SQLite / OpenDAL / LocalFs 类型。

## 1. 组装：注入什么，谁拿锁

```kotlin
// 整个 Runtime 造一套：boundary 必须与 Registry、EventPipeline 是**同一个实例**
val boundary = StateBoundary()
val storages = mapOf("local" to localFsStorage)          // storageKey -> Storage
val router = MountRouter.of(setOf("resources"), listOf(MountRecord(VfsPath.parse("/resources"), "local")))
val nodes = SqliteNodeRepository(state)
val notifier = AsyncEventNotifier()                      // close 归 Runtime 管（T18）

val vfs = DefaultVfs(
    router = router,                                     // 挂载与配置目录（T09）
    capabilities = CapabilitySnapshot.of(storages.mapValues { it.value.capabilities() }), // T10 预检
    registry = NodeRegistry(router, nodes, { key -> storages[key] }, boundary),              // T13
    nodes = nodes,                                       // 自动提交仓库：写前查逻辑记录、列表补 ID
    storages = { key -> storages[key] },
    boundary = boundary,
    pipeline = EventPipeline(boundary, SqliteUnitOfWork(state), notifier),                  // T14
    events = EventFactory(),                             // 可选：固定时钟
    limits = VfsLimits(),                                // 可选：读写上限，默认 16 MiB
    clock = Instant::now,                                // 可选：Node 逻辑时间
)
```

**唯一持锁者**：写文件从预检到状态提交全程只取一次 `StateBoundary` 锁，SQLite 事务只覆盖最后的「Node + 事件」。
内部一律用已持锁入口（`commitInsideBoundary`、`registry.*InsideBoundary`），不会自锁。`read` / `list` 整次调用在同一把锁里；`stat` / `getNode` 委托 Registry，它自己取锁。

## 2. 每个操作碰什么

| 操作 | 碰后端 | 写状态 | 发事件 |
| --- | --- | --- | --- |
| `read` | `Storage.read(rel, min(配置上限, options.maxBytes))` | 否（不登记、不改 Metadata） | 否 |
| `stat` | `Storage.stat`（`includeStorage=false` 且已登记时不碰） | 未登记的懒注册 | 否 |
| `getNode` | 否 | 否 | 否 |
| `list` | 物理目录 `stat` + `list`；纯虚拟目录不碰 | 否（`findByPaths` 批量补 ID） | 否 |
| `write` | `stat` 确认 → 缺失父目录 `createDirectory` → `write` | 一个事务：`register` 或 `touch` | 同事务追加 `FILE_CREATED` / `FILE_WRITTEN` |
| `move` / `delete` / `getMetadata` / `setMetadata` | 否 | 否 | 否（本轮抛 `UNSUPPORTED_OPERATION`） |

写之前拒绝的顺序（都在建目录和写内容之前）：限额 → T10 预检（结构 / 路由 / 能力）→ `Storage.stat` 确认实际类型与存在性 → 模式矩阵 → 逻辑记录类型冲突 → 父路径组件是物理文件 → 缺建目录能力且确需补。

## 3. 失败时报告什么

| 发生了什么 | 错误码 | effect |
| --- | --- | --- |
| 参数、限额、结构、路由、能力、模式、类型冲突被拒 | 原码 | `NONE` |
| 补了父目录后 Storage 写失败 | 原码 | 至少 `PARTIAL` |
| 后端说不清是否写成功 | 原码 | 保持 `UNKNOWN` |
| 写成功但状态 / 事件提交失败 | `STATE_ERROR`（保留 cause） | `PARTIAL` |
| 通知队列满、Consumer 抛错 | 不报错 | 已提交的结果不变（复用 T14） |
| 协程取消 | `CancellationException` 原样传播 | 不声称「取消 = 全部回滚」 |

不自动补偿：文件留在原地、Node 与事件一起回滚、无成功通知。
