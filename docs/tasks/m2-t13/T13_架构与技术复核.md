## 2. 必须修改

### R1 / P2：配置目录判断方向正确，资源确认漏了两条路径

位置：`vfs/core/.../registry/NodeRegistry.kt:116–130`。`isConfiguredDirectory && !isMountPoint` 正确限定了可虚拟回退的位置，但现在只捕获 NOT_FOUND，并仅在目标 stat 返回 FILE 时遮蔽文件；更高一层物理文件导致 LocalPath 抛 TYPE_MISMATCH 时，逻辑祖先就无法访问。

真实探针：父挂载 `/resources`，子挂载 `/resources/a/b/c`，父盘 `a` 是文件；查询 `/resources/a` 返回 DIRECTORY，接着查询配置祖先 `/resources/a/b` 却返回 TYPE_MISMATCH。T02 §3.2 要求必要祖先优先于父后端同名文件，`a/b` 应继续作为虚拟目录可导航，且不修改物理 `a`；按可识别的组件类型冲突处理，不得将权限、关闭或一般 I/O 故障一并吞掉。

第二条是挂载根：`isMountPoint` 只阻止虚拟回退，未检查后端成功返回的类型。用 Storage Port 注入根属性 FILE，Registry 实际返回并注册 `FILE / size=7`，与 T02 §3.3“确认后端根是目录”不符；应明确拒绝，不能注册为文件或降级虚拟成功。

补证据：真实 Local FS 上多层祖先被物理文件遮蔽，返回 DIRECTORY、physical=false、storage=null，物理内容不变；根 stat 返回 FILE 时拒绝且不新增 Node，已有 Node 的 includeStorage=false 仍按逻辑查询例外执行。

### R2 / P2：StateBoundary 示例不能作为 T15 的正确接线依据

位置：`core/state/StateBoundary.kt:20–32`、使用说明第 6 节、交付文档第 4 节。Kdoc 和使用说明先提交状态 / 事件再执行 storage.write，违反 T03“Storage 成功后再提交成功状态与事件”；交付文档却把 Storage I/O 放在事务内部，三处不是同一个示例。示例先 resolve 一个尚未创建的文件也会 NOT_FOUND，不能直接作为新建 write 的流程。

另有 API 与模块口径问题：`storage.write(storagePath, bytes)` 缺少必填 StorageWriteMode；Core 的组合实现不能直接依赖 Kdoc 中的 SqliteUnitOfWork，具体组装属于 Runtime，Core 接收 UnitOfWork Port。Registry 构造器中的自动提交 Repository 也不会因为对象名称而独立于当前单连接事务，不能将事务中调用它描述为独立提交。

修复只需统一一个最小、真实可用的组合示例，明确外层只取一次共享锁、Core 内调用 internal 无锁入口、Storage 成功后才提交逻辑状态 / 事件；或者用已有 Node 的逻辑查询展示锁组合，写入流程留 T15。无需本轮实现 DefaultVfs、加 owner token 或通用重入锁；但不能把错误写入顺序作为后续开发模板。

### R3 / P2：A04 证据与交付记录应按实际强度表述

位置：`NodeRegistryRealStackTest` 的共享边界用例、交付文档第 4 / 9 节、验收记录第 8 节。`querying.complete` 发生在 Registry 调用前，之后仍需调度、JDBC 查询和 Storage.stat；`withTimeoutOrNull(2_000) { pending.await() } == null` 证明的是观察窗口内没有返回，仍可能是任务尚未继续运行或 I/O 较慢。

新断言比瞬时 isCompleted 更有效，交付记录的空锁变异失败是有效的**一次实跑证据**，但不能据此写“锁失效必然失败”“确定性地证明被锁挡住”。请明确区分 Mutex 代码审查、真实串行场景实跑和有限等待窗口；本轮不要求穷举调度，亦不因采用超时断言否定正确锁实现。若保留“确定性”强承诺，则需进一步控制调度 / Registry 已进入的检查点，而不是增加等待秒数。

同时回填交付第 9 节的 `a83c375`（当前仍称“不提交、留在工作区”）；`VfsUri.of` 本身只是持有已验证路径，编码发生在 toString，不是调用 of 时编码，也不是“没有此入口就绝对无法构造合法 URI”（逐段正确编码再 parse 也能做到）。复核方已将接受的入口补记 T01，使用说明 / Kdoc 的其余收尾由开发方处理。

## 3. 五个重点设计判断

| 问题 | 复核判断 |
| --- | --- |
| VfsUri.of(VfsPath) | **接受最小增量。** 复用不可变且已校验的 VfsPath，不引入第二套校验 / 编码，不改变 parse 行为；toString 仍统一逐段编码。理由应是避免 Core 重复实现 URI 序列化，而非此前无法构造；已回写 T01 的类型入口说明 |
| StateBoundary | **接受约定式无锁组合。** 公开方法取锁、internal 方法留给同一 Core 模块的 T15，在正确使用下不会重入；它不会检测错用另一把锁、未持锁或持锁后调用公开方法。文档必须明确这些边界，不必现在引入令牌 / 调度框架；R2 修正的是示例和职责顺序 |
| includeStorage=false | **符合契约，无需改行为。** 已注册时不查 Storage；未注册时确认并真正注册，随后返回 storage=null。NodeInfo.id 必须稳定，T01 / T13 本来就是懒注册语义，不应返回临时 ID；“只控制返回属性”须带上“已有记录可跳过确认”的条件 |
| 虚拟目录判定 | **谓词接受，完整行为待 R1。** 配置目录不是纯虚拟目录的同义词，需要结合后端事实；Mount 根排除回退后还须显式确认 DIRECTORY |
| A04 及变异 | **实跑有效，确定性说法过强。** 锁实现与真实 DB 的对照用例支持共享边界的必要性；一次变异报警不证明任何调度下都报警。未独立重跑交付方四项变异，不将其列为本轮实测 |

## 4. 建议优化与可接受取舍

- 建议 A04 增加一个 Core 层可控调度的小用例：在不访问真实 I/O 的前提下确认竞争调用已推进到锁入口，解锁前不能到 Repository；保留现有真库集成证据。无需新增生产测试接缝或扩大框架。
- 时钟函数注入、两个小包、StateBoundary 的 Mutex 薄封装都属局部实现，可接受；不为收敛类数合并职责，也不为暴露 internal 入口扩大为公共 SDK API。
- 查询不更新 Node 的 physical / 时间、不自动修复外部改型和不识别同路径新世代，符合既定边界。Node ID / Metadata 的修复、动态重挂载、跨进程同步和 read / list 实现继续留后续任务。
- 静态边界测试只作辅助：源码扫描和反射不能完整证明所有依赖或 suspend 泛型返回值；本轮人工审查未发现生产依赖倒置。无需为了这个局限引入新的架构测试库。
