## 8. 变异验证

Lead 提出的变异：`StateBoundary.withLock` 改成 `block()`（锁完全失效）。逐项结果：

| 变异 | 结果 |
| --- | --- |
| `includeStorage=false` 也查后端 | 被测试咬住 |
| 挂载根降级成虚拟目录 | 被测试咬住 |
| `register` 返回本地候选 ID | 被测试咬住 |
| `withLock` 变成空操作（锁失效） | **修复前：412 个测试全过（漏网）→ 修复后：被咬住**（真库 A04 用例 + `StateBoundaryTest.critical sections never overlap`） |
| R1：`SHADOWED_CODES` 去掉 `TYPE_MISMATCH` | 被咬住：真盘 `R1 a needed ancestor behind a real file...` 失败 |
| R1：去掉挂载根非目录检查 | 被咬住：`R1 a mount root that is a file on the backend is rejected` 与 `R1 the logical query exception...` 失败 |

修复后的实际输出（变异版）：

```
NodeRegistryRealStackTest > A04 the registry queues behind an open transaction that shares the boundary() FAILED
> Task :integration-tests:vfs:test FAILED
AssertionFailedError: 事务提交前 Registry 就返回了 —— 共享边界没有生效 ==> expected: <null>
  but was: <NodeInfo(id=018f0000-0000-7000-8000-0000000000ee, ...)>   // 读到了未提交的行
```

还原后 `./scripts/check` 全绿（见第 1 节）。原来的 `assertFalse(pending.isCompleted)` 之所以漏网：它赌的是一个瞬间，协程只是「还没跑到」也会通过；现在换成「窗口内提前拿到返回值」这一正向判据。

### 证据强度分三层说

1. **实现代码审查**：`withLock` 就是 `mutex.withLock { block() }`，互斥性由 `kotlinx.coroutines` 的 `Mutex` 保证，本模块不加任何自制同步。
2. **真实数据库串行场景实跑**：`A04 the registry queues behind an open transaction that shares the boundary`（真 SQLite + 真 Local FS）：持同一把边界的未提交事务期间，Registry 在 2 秒窗口内没有返回；提交后返回事务那条记录。
3. **有限窗口内的违规检测**：空锁变异（`withLock` 改空操作）实跑时，本条用例如实失败并打印出读到的未提交记录。这**是一次有效证据**，证明该变异被咬住；它不构成对所有调度顺序、任意机器负载下的证明——第 1、2 层才是常态保证。

## 10. 未验证 / 推断事项

1. **真 SQLite 下「注册提交后被取消」的 effect 未实测**：Core 用例用内存 Repository + 闩锁把这个时机卡住并断言了「记录仍在、下次复用」。真库下同样的时序依赖 T11 的提交路径，本轮没有专门构造。属**推断**（T11 §R7 已验证 BEGIN/COMMIT 与取消的边界）。
2. **`StateBoundaryTest.a competing resolve reaches the state store only after the holder leaves` 的强度**：它证明的是「实际观测到的调用顺序」；在锁失效时它**不一定**失败（竞争方可能碰巧排在后面）。同文件的 `critical sections never overlap` 使用 Dispatchers.Default + yield，增加了观测交错的机会，也不保证空锁在所有调度下必定失败；两者作为补充回归，不能替代 Mutex 实现审查。该顺序用例未记录 holder 退出，调用日志也不能单独证明 Repository 访问发生在退出后。
3. **Windows / Linux 平台未跑**：本轮全部在 macOS arm64 上执行。OpenDAL native 与 SQLite 行为沿用 T12 / T11 的平台结论，没有新增平台相关代码。
4. **WebDAV（挂载根目录的 stat 语义）**未验证：T24 接入时，WebDAV 挂载根的 `stat(StoragePath.root)` 是否返回目录属性需要单独确认；Registry 的挂载根分支已按「必须确认后端」实现，届时直接验证。
5. **跨进程并发**不做（T13 边界内明确排除）；本地单进程内的并发已实测。
