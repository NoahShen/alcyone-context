## 1. 这个东西是干什么的

Node Registry 只做一件事：**给一个逻辑位置发一个稳定的 Node ID，并把这次发号记下来**。

例：磁盘上已经有 `a.txt`，以前没人管它。你第一次问「`/resources/a.txt` 是谁」，Registry 会去磁盘上确认它真的在，然后发一个 ID 存进状态库。下次再问，还是这个 ID；以后写它、改名、挂 Metadata，都用这一个 ID 串起来。

它**不做**：读文件内容、列举目录、写文件、发事件、改 Metadata。这些分别是 T15、T14、T17 的事。

## 2. 怎么用

```kotlin
val boundary = StateBoundary()                                   // 整个 Runtime 共用一个（见第 6 节）
val router = MountRouter.of(setOf("resources"), mounts)           // T09
val registry = NodeRegistry(
    router = router,
    nodes = SqliteNodeRepository(state),                          // 自动提交那份 Repository
    storages = { key -> storages[key] },                          // storageKey → Storage 实例
    boundary = boundary,
)

val info = registry.resolveOrRegister(VfsPath.parse("/resources/a.txt"))
info.id            // 稳定的 Node ID，之后所有操作都带着它
info.storage       // 磁盘属性：sizeBytes、modifiedAt
info.registeredAt  // VFS 自己的登记时间，不是文件的创建时间
```

`getNode(id)` 查的是**已经登记过**的节点，纯查库，不碰磁盘；ID 没登记过或已经删除就报 `NOT_FOUND`。

## 3. 什么时候问后端，什么时候写状态

这是本模块最容易搞混的地方。规则只看两个问题：**这个 Node 登记过吗**、**调用方要不要磁盘属性**。

| 情况 | 问后端吗 | 写状态吗 | 说明 |
| --- | --- | --- | --- |
| 第一次查一个真实文件 | 是 | **是**，发新 ID | 不然调用方拿不到能用的 ID |
| 已登记，再查（默认） | **是** | 否 | 文件被人在外面删了，这次就该报 `NOT_FOUND` |
| 已登记，`includeStorage = false` | 否 | 否 | 纯逻辑查询，磁盘上删了也照样返回旧记录 |
| 没登记，`includeStorage = false` | **是** | **是** | 先确认资源真的在，不让调用方伪造一个不存在的文件 |
| 配置目录（缺层祖先），磁盘上也没有 | 否 | **是**，记成虚拟目录 | 例：只挂了 `/resources/medical/ct`，那么 `/resources/medical` |
| 没有任何挂载覆盖，也不是配置目录 | 否 | 否 | 报 `MOUNT_NOT_FOUND` |

## 4. 虚拟目录

「虚拟目录」是配置推出来的目录，磁盘上不一定有，甚至永远不会有。例：只挂载 `/resources/medical/ct`，那 `/resources` 和 `/resources/medical` 就是为了导航存在的目录。

- 登记成 `DIRECTORY`、`physical = false`、`storage = null`，**不会为了它去磁盘上建目录**；
- 如果磁盘上刚好真的有这个目录，就按真目录处理，返回真实属性；
- 如果磁盘上是个**文件**（同名），按 T02 被逻辑目录遮蔽，仍然当目录处理，那个文件当它不存在；
- 如果这个目录**正好是挂载点自己**，必须真的能访问到后端。后端挂了就是挂了，绝不降级成「虚拟目录，正常」；
- 权限不足、后端关闭、一般 I/O 错误**原样抛出**，不吞。只有「后端明确说没有」这一种可识别情况会转成虚拟目录。

## 5. 出错时它绝不干什么

- 磁盘上明明是目录、记录里写的是文件（或反过来）→ 报 `CONFLICT`。**不换 ID、不删 Metadata、不顺手把记录改对**——改数据是写操作的活，不是查询的活。
- 挂载配了、但没有对应的 Storage 实例 → 报 `STATE_ERROR` 并在消息里点名缺哪个 key。这是装配写错了，不能装作「文件不存在」把问题藏起来。
- 后端确认失败 → 库里不会多出任何 Node。

## 6. 共享串行边界（T15 怎么用）

状态库整库只有一条 JDBC 连接，也不支持并发或嵌套事务。**同一时刻一个协程在事务里写、另一个协程用自动提交 Repository 读，读会看见对方还没提交的行**（这条本轮有实测用例，见交付文档 A04）。所以所有状态读写必须排在同一条队伍里。

`StateBoundary` 就是这把队伍：一个 `Mutex` 加一个名字，不做调度。

**锁不可重入。** 所以组合时由最外层取一次锁，里面调**不加锁**的版本。下例是「已有 Node 的逻辑查询 + 状态变更」的组合：

```kotlin
// 「已有 Node 的逻辑查询 + 状态变更」怎么组合：最外层取一次锁，里面调不加锁的入口。
// 完整的写文件流程属 T15，这里不展开。
suspend fun withMetadata(
    boundary: StateBoundary,        // 整个 Runtime 共用同一个实例
    registry: NodeRegistry,
    unitOfWork: UnitOfWork,         // 具体实现由 Runtime 组装；Core 这边只认这个 Port
    id: NodeId,
    metadata: NodeMetadata,
): NodeInfo =
    boundary.withLock {                                 // ← 整个操作只取一次锁
        unitOfWork.inTransaction { scope ->
            val info = registry.getNodeInsideBoundary(id)  // ← 不加锁入口：内部不会再取同一把锁
            scope.metadata.put(info.id, metadata)       // 仅示范事务内状态变更；此片段省略事件追加
            info
        }
    }
```

| 入口 | 谁拿锁 |
| --- | --- |
| `NodeRegistry.resolveOrRegister(path, includeStorage)` | 方法自己拿锁 |
| `NodeRegistry.getNode(id)` | 方法自己拿锁 |
| `NodeRegistry.resolveInsideBoundary(path, includeStorage)` | **调用方**必须已经拿着边界 |
| `NodeRegistry.getNodeInsideBoundary(id)` | **调用方**必须已经拿着边界 |

后两个是 `internal`，只在 `vfs/core` 模块内可见——T15 的 `DefaultVfs` 就在这个模块里，直接复用，不复制注册算法。

**约定边界**：`StateBoundary` 不检测误用。在 `withLock` 里又去调 Registry 的公开方法会重入同一把锁并自锁；两个组件各拿一个 `StateBoundary` 则会失去串行保护，可能读到未提交数据，并不是必然挂住。靠调用方遵守：整个 Runtime 造一个实例，组合时由最外层取一次锁。

上例仅展示 Core 内部锁与事务的组合。完整 Metadata 更新还须在同一事务追加事件（T14 / T17）；完整文件写入遵循 Storage 成功后再提交逻辑状态的顺序（T15），不能把此例直接当成完整 API 实现。

## 7. 取消

等锁时取消：照常传播，不会在别人手里留下一把没释放的锁。

已经提交之后被取消：**Node 可能已经落库**。Registry 不做补偿删除，也不假装「收到取消就等于没提交」；下一次查同一个路径会复用那条记录。这是 T11 S2 的教训。

## 8. 边界

- `registeredAt` / `updatedAt` 是 VFS 的逻辑时间，**永远不会被磁盘的修改时间覆盖**；物理属性只出现在 `storage` 字段里。
- 注册**不发事件**、不改 Metadata，只写一条 Node。
- 不做外部文件世代识别：同一个路径被删掉又建回来、类型还一样，Registry 认不出这是新的一代，继续用旧 ID。
- 本轮没有接进 `Vfs.stat`：T15 把 `resolveOrRegister` 接到 `Vfs.stat` 上即可。
