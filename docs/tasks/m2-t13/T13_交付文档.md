## 4. 串行边界的最终设计

**最终方案**：`StateBoundary`（`core/state`）对 `Mutex` 的薄封装，只暴露 `suspend fun <T> withLock(block: suspend () -> T): T`。Registry 构造时收一个 `StateBoundary`；公开方法 = `boundary.withLock { 内部实现 }`，内部实现是**不加锁**的 `internal` 函数（`resolveInsideBoundary` / `getNodeInsideBoundary`），同模块可见，供 T15 组合调用。

理由（为什么不选别的）：

- **为什么不建通用调度器 / 读写锁**：T11 的问题只有一条——单连接上「别人未提交的行能被读到」。一把互斥锁就够；读写锁会诱使调用方以为「只读时可以并发」，而这条连接根本做不到。
- **为什么不给 Registry 私锁**：任务书明确要求「只给 Registry 私有锁、后续写入另用一把锁，不能满足要求」。共用一把才拦得住 T15 的事务与 Registry 的自动提交读交错。
- **为什么不传 owner token / 断言对象**：本轮没有需要重入的场景，加了就是没被使用的机制。可重入的检查留到真出现死锁时再加。
- **锁不可重入怎么解决**：不加锁的 internal 层。没有第二把锁，也就没有「拿 A 再拿 B」的死锁组合。
- **单条注册不开事务**：数据库唯一索引 + `register` 的返回值已经是最终兜底，边界内的复查只用来少一次无效写。

**T15 的调用示例**（与 `StateBoundary` Kdoc、[使用说明](T13_使用说明.md)第 6 节**完全一致**，不要各写一份）：

```kotlin
// 「已有 Node 的逻辑查询 + 状态变更」怎么组合：最外层取一次锁，里面调不加锁的入口。
// 完整的写文件流程属 T15，这里不展开。
suspend fun withMetadata(
    boundary: StateBoundary,        // 整个 Runtime 共用同一个实例
    registry: NodeRegistry,
    unitOfWork: UnitOfWork,         // 具体实现由 Runtime 组装；Core 这边只认这个 Port
    id: NodeId,
    metadata: NodeMetadata,
): NodeInfo =
    boundary.withLock {                                 // ← 整个操作只取一次锁
        unitOfWork.inTransaction { scope ->
            val info = registry.getNodeInsideBoundary(id)  // ← 不加锁入口：内部不会再取同一把锁
            scope.metadata.put(info.id, metadata)       // 状态变更与事件同批提交
            info
        }
    }
```

**约定边界**：`StateBoundary` 不检测误用。在 `withLock` 里又去调 Registry 的公开方法（那会自己等自己），或者两个组件各拿一个 `StateBoundary` 实例，它都不会报错，只会挂住。靠调用方遵守：整个 Runtime 造一个实例，组合时由最外层取一次锁。

共享边界的证据分三层，各说各的强度（细节见[验收记录](T13_验收记录.md)第 8 节）：实现是 `mutex.withLock { block() }`（代码审查）；真实数据库上的串行场景实跑；以及有限观察窗口内的违规检测——空锁变异那一次实跑确实失败，**这是一次有效证据，不是对所有调度顺序的证明**。

两条真 SQLite 用例一起把「必须共享」钉成事实：

- `A04 the registry queues behind an open transaction that shares the boundary`：事务未提交期间，Registry 在 2 秒观察窗口内**拿不到任何返回值**，提交后才拿到事务那条记录的 ID。判据是「窗口内提前返回就是违规」，不是「此刻还没完成」——后者在协程还没跑到时会被骗过去。
- `A04 an auto-commit read really can see uncommitted state, which is why the boundary is shared`：反证，换一把边界的 Registry 确实读到了别人未提交的行。

## 5. 本轮确定的设计决定

1. **`includeStorage=false` 对未注册路径仍然登记**：先 `Storage.stat` 确认资源在，再发 ID 并落库，但返回 `storage = null`。理由：T01 §5.1 允许「仅有 URI 的 Metadata 调用先 `stat(uri, includeStorage=false)` 拿 ID」，如果返回一个没落库的临时 ID，后续 `setMetadata(id)` 就会指向不存在的节点。`includeStorage` 只控制**是否返回磁盘属性**，不控制是否确认与登记。
2. **虚拟目录的回退只认两种「可识别的遮蔽」**：`Storage.stat` 抛 `NOT_FOUND`（后端说没有）或 `TYPE_MISMATCH`（必要祖先在磁盘上就是个文件，例：父盘 `a` 是文件却在其下挂了 `/resources/a/b/c`），且路径是「配置目录且不是挂载点」时才按虚拟目录处理；`STORAGE_ACCESS_DENIED`、`CLOSED`、`STORAGE_ERROR` 等一律原样抛，一个不吞。
3. **挂载根必须真的是目录**：`router.isMountPoint(path)` 且后端 stat **成功返回**了非目录时抛 `TYPE_MISMATCH`（T02 §3.3），拒绝发生在 register 之前——既不登记成文件，也不降级成虚拟成功。已有 Node 的逻辑查询（`includeStorage=false` / `getNode`）早退在后端之前，例外依旧成立。
4. **配置目录位置上的物理文件被遮蔽**：返回逻辑目录（`DIRECTORY`、`physical=false`、`storage=null`），不返回那个文件的属性（T02 §3.2）。若库里已有该路径的 `FILE` 记录，则报 `CONFLICT`——配置与记录不一致，交人工判断，查询不自动修。
5. **逻辑根 `/` 按配置目录处理**：可以 stat 并登记成虚拟目录，不额外拒绝。
6. **`VfsUri.of(path: VfsPath)`（唯一触及公共契约的改动）**：`NodeInfo.uri` 是必填，Core 必须把 `VfsPath` 变成 `VfsUri`。入口缺失本身不是无解——自己在 Core 里逐段编码再 `parse` 也能拼出来——但那等于把 URI 序列化规则复制一份到业务层，迟早抄错：scheme 怎么写、哪些字符要编码、空格和 `unreserved` 怎么处理，规则都在 `VfsUri` 里。新增 `of(path)` 后 Core 只调这个入口：编码仍由 `VfsUri.toString` 逐段完成（不是 `of` 里编码），4 行代码 + Kdoc，`VfsUriTest` 补 1 条往返用例。**没有改变任何既有行为或签名**，复核方已把该入口补记进 T01。
7. **注册只提交 Node**：不写事件、不改 Metadata。单条注册走自动提交 Repository，不套事务；但自动提交写入**在边界内**，这是 T11 S1 的要求。

## 6. 与任务文档不一致 / 需要复核确认的地方

1. **入口命名**：`getNode(id)` 与任务书一致；按路径的入口任务书只说「返回类型建议用 `NodeInfo`」，实现取名 `resolveOrRegister(path, includeStorage = true)`（理由见使用说明第 2 节）。T15 直接复用即可。
2. **包名**：任务书允许自定。Registry 放在 `core.registry`；共享边界另放 `core.state`，因为它是 T15～T23 共用的状态库串行约束，不属于 Registry 私有。若复核方倾向单包，合并成本很低。
3. **`includeStorage=false` 会登记新节点**（第 5 节第 1 条）——任务书只写了「仍须先 Storage.stat 确认存在，返回 `storage = null`」，没明说是否落库。本轮选了落库，理由已写；这是**行为决定**，若复核方要求不落库，需要同时给出「那 `NodeInfo.id` 是什么」的答案。
