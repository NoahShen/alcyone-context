## 2. 常用执行入口

### 2.1 项目工具链准备
所有构建与检查必须通过项目私有工具链执行，不使用系统全局 JDK 或 Gradle：
```bash
# 自动下载并校验项目私有 JDK 21 与 Gradle 8.14.3
./scripts/dev bootstrap

# 验证工具链版本
./scripts/dev gradle --version
```

### 2.2 本地全量回归检查
执行编译、Spotless 代码格式检查、单元测试与集成测试：
```bash
./scripts/check
```
*注：该命令会在每次运行前自动执行 clean，确保无增量残留；全量用例为 751 例。*

### 2.3 真实 WebDAV 网络测试
拉起本地一次性 WsgiDAV 测试服务，验证网络后端读写、认证异常与生命周期：
```bash
./scripts/webdav-check
```
*注：服务依赖 Python 3 及 `tools/testing/webdav/requirements.txt`。测试结束后会自动停止服务并清理临时目录。用例为 42 例。*

## 3. 常见故障排查步骤

### 3.1 工具链未准备或清单损坏
- **现象**：执行 `./scripts/check` 时提示 `Missing installation/manifest` 或 `Damaged installation`。
- **原因**：`.local/jdk` 或 `.local/gradle-dist` 目录不完整，或者校验和文件 `install.sha256` 丢失/不匹配。
- **排查与修复**：
  1. 检查网络是否能正常访问 Adoptium / Gradle 官方源。
  2. 删除损坏的私有目录：`rm -rf .local/jdk .local/gradle-dist`。
  3. 重新执行 `./scripts/dev bootstrap`。不要试图切换到系统默认 JDK 或手动修改 SHA 清单。

### 3.2 平台不支持（报错退出）
- **现象**：`scripts/dev` 报错 `ERROR: Unsupported platform: <OS/ARCH>`，或 Gradle 构建报错 `Unsupported OS/CPU for OpenDAL native`。
- **原因**：当前系统或 CPU 架构不在项目支持列表（如 Windows 或 32 位系统）。
- **处理**：本项目首版严格限定于指定平台，不会对未列出的架构做降级处理。请在受支持的 macOS arm64 或 Linux x64/arm64 目标机上运行。

### 3.3 OpenDAL native 动态库加载失败
- **现象**：运行时报 `UnsatisfiedLinkError: no opendal in java.library.path` 或找不到底层符号。
- **排查步骤**：
  1. 执行 `uname -s` 与 `uname -m`，核对本机操作系统与 CPU 架构。
  2. 检查 `System.getProperty("java.home")` 对应的 JDK 架构是否与操作系统原生架构一致（如避免在 macOS arm64 上运行 x86_64 架构的 JDK）。
  3. 检查 Gradle 依赖中下载的 classifier 是否正确（执行 `./scripts/dev gradle :vfs:storage:dependencies --configuration runtimeClasspath`，确认引入的 `opendal-0.50.6-<classifier>.jar` 与本机一致）。

### 3.4 WebDAV 认证或连接失败
- **现象**：文件读写抛出 `VfsException(code=STORAGE_ACCESS_DENIED)` 或 `VfsException(code=STORAGE_ERROR)`。
- **排查步骤**：
  1. 查看异常消息：格式为 `"webdav storage <operation> failed (<code/status>)"`。
  2. 若为 `STORAGE_ACCESS_DENIED`，检查 WebDAV 挂载配置中的 `username` 与 `password` 是否与服务端配置一致（HTTP 401 会被精准映射为此状态）。
  3. 若为 `STORAGE_ERROR`，检查 endpoint 地址与端口是否正确，网络链路是否存在连接中断、DNS 失败或服务端异常退出。
  4. 检查异常的 `cause` 获取底层的 `OpenDALException` 详细错误码。
  5. **注意**：VFS 抛出的异常链已进行凭据脱敏，不会回显实际密码。排查时请勿尝试从异常链逆向读取密码。

### 3.5 状态数据库文件冲突（CONFLICT）
- **现象**：`AlcyoneVfs.create(...)` 抛出 `VfsException(code=CONFLICT, "the VFS state database is already in use by another instance")`。
- **原因**：SQLite 状态库同一时刻只允许一个活动 VFS 实例持有独占锁，检测到已有活动进程或未释放的实例持有该库。
- **排查步骤**：
  1. 确认前一个 `AlcyoneVfs` 实例是否已显式调用 `close()`。
  2. 检查是否有并发进程正在访问同一 `stateDatabase` 路径。
  3. 检查状态库同级目录下的 `.lock` 文件是否被残留进程占有。

### 3.6 异步事件通知丢弃（Event Dropped）
- **现象**：日志出现 `Event buffer is full (capacity ...), event ... is not delivered in process`，或 `AsyncEventNotifier.droppedEvents` 计数大于 0。
- **原因**：事件队列达到容量上限（默认 256），Consumer 消费过慢，为防止阻塞核心文件变更流程，超量事件被丢弃。
- **排查步骤**：
  1. 确认 Consumer 回调中是否存在长时间阻塞操作（如慢网络请求、死锁等）；建议在 Consumer 中将耗时工作异步化。
  2. 若业务吞吐确实较大，可在构造时调大 `capacity` 参数。
  3. **数据一致性确认**：丢弃仅影响内存中的进程内通知，事务已持久化至 SQLite `event` 表，底层数据与事件记录无丢失。

## 4. 方案④保持与网络等待约束

- 本项目遵循方案④：**不承诺 WebDAV native 请求或 close 的最长等待时间**。
- `closeGracePeriod` 仅为本地协程取消前的优雅等待期，底层阻塞的 JNI / 网络 I/O 无法通过协程协作取消强杀。
- 测试中的 `@Timeout` 仅用于防止 CI 构建陷入死锁，不代表对生产环境请求完成时间提供超时兜底。
