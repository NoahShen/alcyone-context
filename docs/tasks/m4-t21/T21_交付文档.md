## 1. 本轮交付什么

普通文件的**复制回退**（同 Mount 但后端不支持原生 move）与**跨 Mount 复制移动**（两个挂载点背后即使都是 Local FS），
在 Core 编排层接成真实的复制流程：读源 → 补目标父目录 → 写目标（`CREATE_NEW`）→ 确认目标 → 删源 → 同事务提交同一 Node 的新路径与一条 `FILE_MOVED`。

**目录移动仍阶段拒绝**（`UNSUPPORTED_OPERATION` + `NONE`），留给 T22。T20 的同 Mount 原生移动路径行为不变。

## 2. S1 盘点结论（Lead 已核对，本轮验证后确认）

| 盘点项 | 结论 |
| --- | --- |
| 策略来源 | 复用 `OperationGuard.moveStrategy`：`source.route.mount == target.route.mount` 时看 `nativeFileMove` 能力，跨 mount 一律 `CROSS_MOUNT_COPY_MOVE`。T21 不改 Guard |
| 要改的那根接线 | T20 在 `moveInsideBoundary` 第 5 步后对 `strategy != NATIVE_MOVE` 抛阶段拒绝。T21 把它换成三分支策略分派 |
| 复制限额取值 | `min(limits.defaultReadMaxBytes, limits.defaultWriteMaxBytes)`，默认各 16 MiB。**取小的那个**：写侧也要过一遍内容，写限额更小时必须先拒 |
| 两侧 Storage | `COPY_FALLBACK_MOVE` 两侧是同一个 `Storage` 实例（同 Mount）；`CROSS_MOUNT_COPY_MOVE` 两侧各按自己的路由取。**不用 `storageKey` 是否相同判断** |
| 复用入口 | `createMissingParents`、`ensureSourceIdentity`、`commitMove`、`withKnownChanges(Int)` 全部沿用 T20，不改签名 |
| 已有写入模式 | `StorageWriteMode.CREATE_NEW` 早已存在，T21 直接用，不需要新枚举值 |

## 3. S2 实现

### 3.1 改了什么

**唯一生产代码改动**：`vfs/core/.../DefaultVfs.kt`。

`moveInsideBoundary` 从「预检 + 阶段拒绝 + 后续 T20 原生逻辑」变成「预检 + 策略分派」，拆出两个私有方法：

```
moveInsideBoundary(source, target)
├── 1. rejectMoveArgumentConflicts      （纯参数，原样）
├── 2. requireMovableStructure × 2     （结构保护，原样）
├── 3. router.route × 2                （路由，原样）
├── 4. sourceStorage.stat              （确认源存在与实际类型，原样）
├── 5. OperationGuard.check            （按实际类型拿策略，原样）
├── 5'. if (actualType == DIRECTORY) 抛阶段拒绝   ← T22
└── 6. when (precondition.strategy)
    ├── NATIVE_MOVE            → moveNative(...)          （T20 原样搬过去）
    ├── COPY_FALLBACK_MOVE     → moveByCopy(source=source, target=source)
    └── CROSS_MOUNT_COPY_MOVE  → moveByCopy(source=source, target=storageFor(targetRoute))
```

- `moveNative`：T20 的原生路径**逐行搬过去**，行为零变化。
- `moveByCopy`：T21 新增的复制路径。**没有新增 Manager、公共 API 或通用执行器**；`ExecutionStrategy` 的
  `DIRECT_WRITE` / `DIRECT_DELETE` 分支用 `else ->` 兜住（`when` 编译器要求穷尽，运行时不可能出现在 move 上）。

### 3.2 复制路径的完整顺序

```
1. confirmMoveTargetAbsent(target, targetStorage, targetRoute)   目标全新（ALREADY_EXISTS）
2. ensureSourceIdentity(source.path)                              身份：已登记复用 / 未登记只注册一次
3. sourceStorage.read(sourceRoute.relativePath, copyLimit)        有界读源
   ├─ 失败（含 LIMIT_EXCEEDED）→ 原样抛出，源保留、目标不写、状态不动
   └─ copiedBytes = content.bytes.size
4. createMissingParents(target, targetStorage, targetRoute)        读完确认真实字节数后才补目录
5. targetStorage.write(..., StorageWriteMode.CREATE_NEW)          写入目标
   └─ 失败 → withKnownChanges(createdDirectories) 合并 effect
6. targetStorage.stat(targetRoute.relativePath)                    确认目标
   ├─ 抛异常 → CONFLICT + PARTIAL，cause 保留后端原始错误
   ├─ type != FILE → CONFLICT + PARTIAL
   └─ 长度核对：copiedBytes == written.sizeBytes == targetAttributes.sizeBytes
      └─ 不一致 → CONFLICT + PARTIAL
7. sourceStorage.delete(sourceRoute.relativePath, false)          确认通过后才删源
   └─ 失败 → 保留后端原始 code，effect 提到 PARTIAL，不提交新映射
8. pipeline.commitInsideBoundary { commitMove(..., written) }     同事务：updatePath + 一条 FILE_MOVED
   ├─ CancellationException → 原样传播
   └─ 其他 → STATE_ERROR + PARTIAL，initCause 保留原始失败，不回移、不通知成功
```

### 3.3 关键决策与理由

| 决策 | 理由 |
| --- | --- |
| **读取上限取 `min(read, write)`** | 复制路径的内容要过 `write` 一次。只按读限额把关，写限额更小时会撞上第二道坎、报出一个对调用方没意义的错误。取小的那个，一次讲清 |
| **先读、再补目录、再写** | 任务文档 §2.2 要求「读取成功并确认实际字节数后」才补目录。超限时目标盘一个目录都不留（真栈用例断言目标盘根为空列表） |
| **写入用 `CREATE_NEW`** | 预检与写入之间目标可能被别人创建。`CREATE_NEW` 让这种情况在后端原子失败，不覆盖别人的文件 |
| **确认只用一次 `stat`** | 任务文档 §2.3「不为拼返回值再追加一次无关查询」。确认拿到的那份 `StorageAttributes` 直接进 `NodeInfo.storage` |
| **长度不一致报 `CONFLICT`、确认调用失败也报 `CONFLICT`（cause 保留原错误）** | 任务文档 §2.3 原文。已知不一致是 `CONFLICT`；后端调用失败「保留原错误」= 保留在 `cause` 上，同时把整体定位成「确认阶段失败」 |
| **删源失败时 effect 提到 `PARTIAL`** | 目标已经真的写出来了，这是已知变更。照抄后端 `NONE` 会谎报「什么都没发生」 |
| **不用公开 `Vfs.read/write/delete` 拼移动** | 任务文档 §2.4。它们各自取一次锁并会生成中间身份 / 事件。这里全程只用 `storage` Port 与自动提交仓库 |
| **不在原生 move 报错后重试复制** | 任务文档 §2.1。原生 move 可能已经把文件挪了，报错后改走复制会写出第二份。复制只在**能力判定**出 `COPY_FALLBACK_MOVE` 时进入 |

### 3.4 复制限额差异（已回写 T01）

| 路径 | 限额 | 依据 |
| --- | --- | --- |
| 同 Mount 原生移动 | **无大小上限** | 不把内容读进内存。20 MiB 文件照常移动（`RuntimeMoveTest` 原有反证用例仍通过） |
| 同 Mount 复制回退 / 跨 Mount | `min(defaultReadMaxBytes, defaultWriteMaxBytes)`，默认各 16 MiB | 内容过一遍 ByteArray。超限 `LIMIT_EXCEEDED`，源保留、目标不写 |

回写位置：[T01 公共契约 §5 补充约束](../../vfs/VFS_公共契约草案_v0.1.md)与
[T18 使用说明 §8](../m3-t18/T18_使用说明.md)、[T19 §7/§9](../m3-t19/T19_使用说明.md)。
**没有新增公共 `MoveOptions`**：两条路径对调用方签名完全一致，差异只体现在错误上。

## 6. 没有做的事（明确留给后续任务）

- **目录移动 / 目录复制**（T22）：目录仍阶段 `UNSUPPORTED_OPERATION` + `NONE`。已登记子 Node 路径批量更新、
  空子目录保留、目录自包含与嵌套 Mount 组合都不在本轮。
- **分块 / 流式复制**：首版复用 `Storage.read` / `Storage.write`（Port 没有分块写），所以复制路径受 16 MiB 限额。
  没有用分块 `UPSERT` 冒充追加写入。
- **失败组合全矩阵**（T23）：本轮覆盖 5 个注入点（写失败、确认失败、长度不一致、删源失败、事务失败），
  「建目录中途失败」「读源失败」「后端 `UNKNOWN`」沿用 T20 / T15 既有证据与 helper，只在复制路径补了定向断言。
- **崩溃恢复 / 重试 / 补偿**：`STATE_ERROR + PARTIAL` 不回移、不补偿，按 T03 口径报出即可。
- **内容哈希校验**：长度核对 ≠ 哈希校验，不承诺防御外部进程任意并发改写（任务文档 §2.3 原文）。
- **WebDAV 跨协议移动**（T24 / T25）：本轮跨 Mount 只用 Local FS 验证；协议转换（编码、换行、权限位）不在范围。
