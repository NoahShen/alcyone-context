## 0. 证据分层约定

| 层级 | 含义 |
| --- | --- |
| **真栈** | 公开 `AlcyoneVfs` 或 `DefaultVfs` + **真 SQLite** + **真 Local FS 磁盘**。物理事实与事务回滚都是真的 |
| **真栈 + 包装** | 真栈，但失败点用包装 Storage / 包装事务注入（真文件系统不会恰好停在**一半**）。断言仍对着真盘与真库 |
| **替身** | 内存盘 `StorageFakeImpl` / 包装 Storage。证明**调用顺序、分支选择、错误码与 effect**，不证明物理与事务语义 |
| **源码审查** | 直接读生产代码，不跑测试 |

**失败测试的区分**：本轮所有「失败不发成功通知」都分成两类证据，不互相冒充——
(1) **无事件入库**：读 `event` 表行数不变（`eventCount()` 断言）；
(2) **直接观测无通知**：订阅 `AsyncEventNotifier`，发一条哨兵事件按 ID 等待，若真有过成功通知它一定先到
（`DefaultVfsCopyMoveRealStackTest` A05 的 `CopyMoveRecorder`）。
只有 (2) 算「直接观测无通知」；(1) 不能当它用。

## A06 副作用合并

**要求**：建目录后复制失败保留 `PARTIAL`；目标已成功后删源报 `NONE` 仍反映已变更；`UNKNOWN` 不降级。少量定向替身用例覆盖新增复制阶段。

| 证据 | 层级 | 观察到的结果 |
| --- | --- | --- |
| 建目录后复制失败 → `PARTIAL` | 替身 | `A04 a target write failure...`：`sub` 真的建在目标盘上 → effect `PARTIAL`（复用 `withKnownChanges(Int)`，T20 helper） |
| 删源报 `NONE` 仍反映已变更 | 替身 | `A05 a source delete failure...`：后端注入的 `delete` 失败**没有声明 effect**（即 `NONE`），生产代码把整体报成 `PARTIAL`——因为目标确实已写出来 |
| `UNKNOWN` 不降级 | 替身 | `A06 a backend UNKNOWN on the target write...`：先建出 `sub`，再让写入报 `UNKNOWN` → 最终 effect **仍是 `UNKNOWN`**，不被已知变更压成 `PARTIAL`；`sub` 是真事实但 effect 按后端说的来 |
| 新增阶段的接线 | 源码审查 | `moveByCopy` 里三处 effect 处理：写失败走 `withKnownChanges(createdDirectories)`；确认失败与删源失败走新增的 `withKnownTargetWrite()`——保留后端 `code / effect`，只把 `NONE` 提到 `PARTIAL`，`UNKNOWN` 与已有 `PARTIAL` 不动 |
| T20 helper 证据仍有效 | 源码审查 | `DefaultVfs.kt` 尾部 `withKnownChanges(Int)` 未改；T20 的三个 effect 用例原样通过。`withKnownTargetWrite()` 是本轮新增的兄弟规则 |

**满足**：是。本轮为复制阶段补了 3 条定向 effect 用例，不是全部留给 T23。

## A07 串行与取消

**要求**：复制流程全链单次取锁；**一个**已进入流程的取消点原样传播、不继续删源或提交、后续操作可用。证据是受控相遇证明第二个变更未碰后端、协程内捕获实际异常并核对取消处物理事实、finally 放行和等待清理。

| 证据 | 层级 | 观察到的结果 |
| --- | --- | --- |
| 全链单次取锁 | 源码审查 | `DefaultVfs.move` 仍是 `boundary.withLock { moveInsideBoundary(...) }` 一次；`moveByCopy` 全程在边界内，只用 `storage` Port 与自动提交仓库，**不调用公开 `Vfs.read/write/delete`**（那些会重复取锁）。`withStack` / `VfsHarness` 的注释与接线保持 |
| 受控相遇（第二个变更未碰后端） | **真栈 + 包装** | `DefaultVfsCopyMoveRealStackTest` `A07 a second cross mount move is held at the boundary...`：第一个移动挂在 `Storage.delete` 之前（此时**已确认、即将删源**）正拿着边界；第二个用 `CoroutineStart.UNDISPATCHED` 起，`assertFalse(second.isCompleted)` 且**后端调用计数没变**；放行后两个移动各一条 `FILE_MOVED`、两块盘上文件都到位 |
| **一个**取消点 | **真栈 + 包装** | `A07 a cross mount copy cancelled at the target write propagates and commits nothing`：选**写入目标之前**为受控取消点（读源与补父目录都已真发生，可同时核对已发生 / 未发生的事实）。捕获发生在**调用 `DefaultVfs` 的协程内部**（`async` 里 try/catch 记 `escaped`），不是拿 `Deferred.await()` 的取消当证据 |
| 取消原样传播 | **真栈 + 包装** | `escaped` 是 `CancellationException`、**不是** `VfsException`；`pausedWrites() == 0`（已退出闩锁）；后续移动正常完成 → 边界可放行 |
| 取消处物理事实 | **真栈 + 包装** | 第一块盘源仍在、第二块盘目标**没出现**、`findByPath` 仍指原 ID、`eventTypes() == []`（stat 懒注册不发事件，取消也不发移动事件） |
| 取消后没有继续删源 / 提交 | 源码审查 + 替身 | 替身 `A07 a copy move cancelled at the target write...` 额外用 `deleteCalls == 0` 计数证明没碰 `delete`，并断言取消后紧接着的移动正常完成、只发一条 `FILE_MOVED` |
| 清理 | **真栈 + 包装** | 两个挂起用例都在 `finally` 里**先放行幂等门**、再 `jobs.forEach { it.cancelAndJoin() }`；`withStack` 的 `finally` 随后才关真库 / 真盘（顺序不反，遵 T20 R3） |
| 串行回归 | 替身 | `A07 a refused copy move leaves the boundary usable and does not touch the node count`：被拒后记录数与 ID 不变，后续移动正常完成 |

**未验证边界（明确不声称）**：只覆盖了「写入目标之前」这一个取消点。
**没有**覆盖：读源期间取消、补父目录期间取消、确认 `stat` 期间取消、删源期间取消、提交期间取消。
任务文档 §2.5 明确「不要把这个用例写成所有取消窗口均已覆盖」，此处严格照办；其余窗口留 T23。
