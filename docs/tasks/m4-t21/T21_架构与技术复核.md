## 2. 必须修改

### R1 / P2：确认 / 删源失败改写错误并降低 UNKNOWN

位置：`DefaultVfs.kt:706–716`、`740–750`。目标 stat 的任何 VfsException 都变成 CONFLICT + PARTIAL，源 delete 的任何 VfsException 都变成 STORAGE_ERROR + PARTIAL；这违反任务 §2.3 的后端错误保留与 §2.5 / A06 的 UNKNOWN 不降级。把原异常挂 cause 并不能代替保留调用方用于分支判断的 code / effect。

**修复与验收：**复用已知变化合并规则，保留后端 code、原因与 UNKNOWN；目标已写入时将 NONE 提到 PARTIAL。仅已观测的类型 / 长度矛盾用 CONFLICT；补确认 stat 与源 delete 的 UNKNOWN 反例，至少一个非 STORAGE_ERROR 错误码反例，直接核对抛出异常、源 / 目标事实、逻辑映射和无成功事件。现有确认失败用例断言 CONFLICT 正好固化了错误行为，应随契约修正。

### R2 / P1：复制确认遗漏源长度，未知长度被误作冲突或零

位置：`DefaultVfs.kt:688–691`、`727–730`。源预检属性与 `StorageContent.attributes.sizeBytes` 都未参与确认：若源可用长度为 5、返回内容只有 3 字节，而写入 / 目标均为 3，当前会继续删源并成功，未满足“核对可获取源长度、检测已知变化”的要求。此处只要求使用已有长度事实，不要求额外哈希或并发快照。

另一端 `written.sizeBytes == null` 会使非空 / 空内容都不等，`targetAttributes.sizeBytes ?: 0L` 又把未知等同空文件；StorageAttributes 的长度本来允许缺失，缺失不能证明冲突。应比较各个**可用**长度与复制字节数，保留“未知”的含义，并明确最小确认依据；不要悄悄把 Port 改成长度必填。

**修复与验收：**在获得内容后尽早检查已知源长度矛盾，拒绝继续删源，按发生阶段报告 effect；覆盖“已知源长度 5 / 内容 3 / 目标 3”的反例。补写入回执长度缺失但目标长度正确、目标长度缺失但其他已知长度一致的代表用例（含空文件边界可合并），确保缺失不冒充 0 或不一致；保留真实目标截短反例。

### R3 / P2：A04 缺少写入留下部分目标后抛错的证据

当前 write 故障在写前直接抛出，留下的只有父目录；截短用例则是 write 正常返回后确认失败，两者不能证明 write 本身部分完成后抛错的接线。生产 `DefaultVfs.kt:701` 的“CREATE_NEW 保证不会写出一份半成品”也不成立，CREATE_NEW 表达不覆盖已有目标，不承诺写入原子性。

**最小补证：**一个受控 Storage 在写入部分内容后抛带 PARTIAL 的异常，断目标残留、源内容保留、**源 Storage.delete 未调用**、原映射 / Metadata 保留、无成功事件，不自动清目标；不要求真实磁盘损坏。修正该注释和 A04 满足度，现有确认 / 写失败用例中检查 target.deleteCalls / target.calls 的断言不能单独证明源 delete 未调用，应检查源侧（已有源仍在断言保留）。
