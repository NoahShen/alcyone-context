## 1. `move` 现在能做什么

`move(source, target)` 对**普通文件**有三条路径，由后端能力和挂载关系决定，**调用方不需要也不应该选**：

| 条件 | 策略 | 实际做法 |
| --- | --- | --- |
| 同一挂载点，后端支持原生 move | `NATIVE_MOVE`（T20） | `Storage.move`，不把内容读进内存 |
| 同一挂载点，后端**不**支持原生 move | `COPY_FALLBACK_MOVE`（T21） | 读源 → 写目标 → 确认 → 删源 |
| 跨挂载点 | `CROSS_MOUNT_COPY_MOVE`（T21） | 同上，源与目标各按自己的路由 |

**目录**（同挂载点或跨挂载点）仍阶段拒绝 `UNSUPPORTED_OPERATION`，属 T22。

三条路径的**外部契约完全一致**：
同一个 Node ID、同一个 Metadata、一条 `FILE_MOVED`、旧路径随即 `NOT_FOUND`、在旧路径另建文件得到新 ID。
调用方不需要知道自己走的是哪条。

### 1.1 两条复制路径的调用顺序

```text
1. 目标必须全新                    → 已有文件 / 目录都报 ALREADY_EXISTS
2. 身份：已登记源复用 ID，未登记源只注册一次
3. 读源（有界）                    → 超限 / 读失败：源保留，抛错
4. 补目标缺失的父目录              → 读完确认真实字节数之后才补
5. 写目标（CREATE_NEW）            → 写失败：源保留，已建目录留着
6. stat 确认目标：必须是文件、长度与实际复制字节数一致
                                   → 任何不一致都不删源
7. 删源                            → 删失败：目标留着，逻辑路径仍指向源
8. 同事务：更新 Node 路径 + 一条 FILE_MOVED，提交成功后才通知
```

关键点：

- **先复制、后删源**。确认不过（目标不是文件、长度对不上、stat 报错）时**源一定还在**。
- **写入用 `CREATE_NEW`**。预检到写入之间目标被别人创建，后端会原子失败，不会覆盖别人的文件。
- **确认不追加查询**。第 6 步那次 `stat` 拿到的长度直接进返回的 `NodeInfo.storage`，不会再查一次。
- **长度核对不是哈希校验**。它能发现「写少了 / 写歪了」这类已知不一致，**不承诺**防御外部进程在移动过程中任意改写文件。
- **同 Mount 回退不会先试原生 move 再改复制**。复制只在能力判定出 `COPY_FALLBACK_MOVE` 时进入——
  原生 move 报错时文件可能已经被改动了，那时再复制会写出第二份。

## 2. 复制限额（与原生移动的差异）

这是 T21 引入的**唯一**对外可见的行为差异，**没有新增 `MoveOptions`**，`move` 签名没变。

| 路径 | 大小上限 | 依据 |
| --- | --- | --- |
| 同 Mount 原生移动 | **无** | 不把内容读进内存。20 MiB 文件照常移动 |
| 复制回退 / 跨 Mount | `min(VfsLimits.defaultReadMaxBytes, defaultWriteMaxBytes)`，**默认各 16 MiB** | 内容要过一遍 `read` / `write` 的 ByteArray |

取**较小**的那个：写侧也要过一遍内容，写限额更小时若只按读限额把关，调用方会撞上一个对没意义的后端错误。
**后端自己更严格的上限仍然生效**（更小者胜出）。

超限时的行为：

- 报 `LIMIT_EXCEEDED`，`effect = NONE`；
- **源文件原封不动**（不是删了再报错）；
- **目标一个字节都不写**，连缺失的父目录都不补；
- 逻辑路径仍指向源，状态库不变，不发事件。

> 所以：`read` 会被 16 MiB 挡住的大文件，用 `openStream` 仍能读完整；但**跨挂载点移动**它会报 `LIMIT_EXCEEDED`。
> 首版不提供分块移动，调用方要搬超限大文件得自己「流读出 + 分块写 + 删源」。

口径同时回写进 [T01 公共契约 §5](../../vfs/VFS_公共契约草案_v0.1.md)。

## 3. 错误码速查（复制路径）

| 场景 | 错误码 | effect | 物理残留 |
| --- | --- | --- | --- |
| 源 / 目标同路径，或目标落进源子树 | `INVALID_ARGUMENT` | `NONE` | 无 |
| 源不存在 | `NOT_FOUND` | `NONE` | 无 |
| 目标已存在（文件 / 目录） | `ALREADY_EXISTS` | `NONE` | 无（不建父目录） |
| 源 / 目标是受保护配置目录 | `UNSUPPORTED_OPERATION` | `NONE` | 无 |
| 源是**目录**（T22） | `UNSUPPORTED_OPERATION` | `NONE` | 无 |
| 任一侧只读 | `READ_ONLY` | `NONE` | 无（只发生一次为拿实际类型的 stat） |
| **读源超限 / 读源失败** | `LIMIT_EXCEEDED` / 后端原码 | `NONE` | 无（目标盘连目录都没建） |
| 目标父路径是文件 | `TYPE_MISMATCH` | `NONE` | 无 |
| **写入失败**（已补过父目录） | 后端原码 | `PARTIAL` | 已补的父目录留着，源还在 |
| **确认失败 / 长度不一致** | `CONFLICT`（cause 保留后端原错误） | `PARTIAL` | **残留目标不自动删除**，源还在 |
| **删源失败** | 后端原码 | `PARTIAL` | **两块盘上文件都在**，逻辑路径仍指向源 |
| **删源成功但状态 / 事件提交失败** | `STATE_ERROR` | `PARTIAL` | 源已删不回退、目标保留、同批状态与事件一起回滚、无成功通知 |
| 协程取消 | `CancellationException`（原样传播） | — | 已发生的事实不撤回 |

**预检拒绝（纯参数、结构、只读、目标存在、阶段）都发生在注册源、补目录、物理复制之前**，
所以这些错误的 effect 是 `NONE`，调用方可以放心重试或改路径。

## 4. 失败之后世界是什么样（重要）

复制移动是「多步物理 + 一步事务」，失败时**盘上可能留下东西**，`effect` 如实反映：

| 失败点 | 源 | 目标 | 逻辑路径 | 事件 |
| --- | --- | --- | --- | --- |
| 读源失败 / 超限 | 还在 | 什么都没有（连目录都没建） | 指向源 | 无 |
| 写目标失败 | 还在 | 已补的父目录留着，目标文件没有 | 指向源 | 无 |
| 确认失败 / 长度不一致 | 还在 | **目标文件在（可能不完整），不自动清理** | 指向源 | 无 |
| 删源失败 | 还在 | 完整的目标在 | **仍指向源** | 无 |
| 提交失败 | 已删，**不回退** | 完整的目标在 | 随事务**回滚到源** | 无 |
| 取消 | 视取消点 | 视取消点 | 指向源（未提交） | 无 |

**调用方要点**：`CONFLICT` 与 `PARTIAL` 不代表「重试就行」。
确认失败留下的目标文件是**残留物**，VFS 不会自动删除它（自动清理属于补偿，T23 及以后）。
如果需要幂等，请自己按 `getNode` / `stat` 核对目标位置后再决定。

## 5. 一个可运行的例子（公开 API）

两个挂载点背后都是本地目录，即使物理上是同一台机器，逻辑上跨挂载点就走复制删除：

```kotlin
val runtime =
    AlcyoneVfs.create(
        VfsRuntimeConfig(
            stateDatabase = Path.of("data/state.db"),
            namespaces = setOf("resources"),
            mounts =
                listOf(
                    MountConfig(VfsPath.parse("/resources/local"), "local", Path.of("data/local")),
                    MountConfig(VfsPath.parse("/resources/archive"), "archive", Path.of("data/archive")),
                ),
        ),
    )
try {
    val vfs: Vfs = runtime
    val note = vfs.write(VfsUri.parse("alcyone://resources/local/note.txt"), "hello".toByteArray())
    vfs.setMetadata(note.id, NodeMetadata(setOf("ct"), "跨盘搬运"))

    val moved = vfs.move(
        VfsUri.parse("alcyone://resources/local/note.txt"),
        VfsUri.parse("alcyone://resources/archive/2026/note.txt"),
    )

    check(moved.id == note.id)                 // 同一个 Node ID
    check(vfs.getMetadata(note.id).tags == setOf("ct"))  // Metadata 跟着身份走
    check(vfs.read(VfsUri.parse("alcyone://resources/archive/2026/note.txt")).decodeToString() == "hello")
} finally {
    runtime.close()   // suspend close()
}
```

会看到的事实：第一块盘上 `note.txt` 消失、第二块盘上 `2026/` 与 `2026/note.txt` 出现且逐字节一致、
事件日志里只有一条 `FILE_MOVED`（`source_uri` 是源、`uri` / `target_uri` 是目标、`node_id` 是原 ID）。
正常重开 Runtime 后这些都还成立。

## 6. 怎么自己跑一遍回归

```bash
# 只跑 T21 新增 / 改写的四个类
./scripts/dev gradle :vfs:core:test \
  --tests "*DefaultVfsCopyMoveTest*" \
  --tests "*DefaultVfsMoveTest*" --console=plain
./scripts/dev gradle :integration-tests:vfs:test \
  --tests "*DefaultVfsCopyMoveRealStackTest*" \
  --tests "*RuntimeCopyMoveTest*" --console=plain

# 定向全跑
./scripts/dev gradle :vfs:core:test :integration-tests:vfs:test --rerun-tasks --console=plain

# 全量检查
./scripts/check
```

测试只在 `@TempDir` 临时工作目录读写，状态库在挂载物理根之外；不需要清系统环境。
跨挂载点用例用**两个不重叠的临时本地目录**（`source` 与 `archive`）。

## 7. 还没做的 / 没验证的

| 项 | 现状 |
| --- | --- |
| **目录移动** | 阶段 `UNSUPPORTED_OPERATION`（T22）。同 / 跨挂载点都一样 |
| **分块 / 流式复制** | 不做。超限大文件跨挂载点移动报 `LIMIT_EXCEEDED` |
| **除「写入目标之前」外的其他取消窗口** | 未验证。T21 只钉了这一个点，其余留 T23 |
| **失败组合全矩阵** | 本轮覆盖 5 个注入点，完整矩阵留 T23 |
| **崩溃恢复 / 重试 / 补偿** | `STATE_ERROR + PARTIAL` 不回退、不补偿；残留目标不自动清理 |
| **内容哈希校验** | 只做长度核对，不承诺防御外部并发改写 |
| **WebDAV 跨协议移动** | 只用 Local FS 验证；协议转换不在本轮（T24 / T25） |
| **覆盖目标** | 不开放。目标已存在一律 `ALREADY_EXISTS`；首版没有 `MoveOptions` |
