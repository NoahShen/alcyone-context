## 1. 状态库定位与重开独占机制

### 1.1 状态库是持久真理源（不是缓存）
Alcyone VFS 的 SQLite 状态库（`stateDatabase` 指定的文件）**保存着文件系统全部的核心元数据**，包括：
- 节点全局身份（UUIDv7 格式的 Node ID）
- 逻辑路径映射与命名空间
- 用户自定义元数据（Tags、Description、时间戳）
- 挂载点身份对齐记录（Mount 表）
- 历史操作事件流水

> **严禁操作**：
> - **切勿将状态库当做普通缓存随意删除！** 删除状态库将导致所有文件的 Node ID 丢失、元数据清空、移动链路断裂，且未登记文件的逻辑属性失效。
> - 状态库文件必须放在挂载的物理根目录之外，防止底层递归扫描时将自身纳入受管文件。

### 1.2 进程独占与重开一致性
1. **文件锁独占**：同一个状态库同一时间仅允许一个 `AlcyoneVfs` 实例打开。运行时会在数据库同级目录生成独占锁文件（`<dbName>.lock`）。若检测到冲突，启动将直接抛出 `CONFLICT`。**切勿通过强行删除锁文件绕过冲突检查**，否则会导致多进程并发写库引发 SQLite 损坏。
2. **挂载身份比对**：重新打开状态库时，VFS 会严格比对当前配置与历史记录中的挂载身份（`storageKey`、后端类型、规范化物理路径/WebDAV endpoint+root）。若发现相同 `storageKey` 被指向了不同的物理根，将视为挂载错位并拒绝启动（抛出 `VfsException: VFS configuration conflict`）。

## 2. 离线备份与隔离验证恢复规范

由于底层文件可能分布在本地物理磁盘及远端 WebDAV，且 SQLite 采用写前日志（WAL）机制，**首版不提供在线快照或跨存储后端的分布式事务快照**。必须遵循以下**离线冷备份**流程。

### 2.1 离线备份标准步骤
1. **停机阻断**：暂停上层业务写入，确保无外部并发写入。
2. **正常关闭**：调用 `vfs.close()`，等待所有在途操作完成并释放文件锁，确保 WAL 日志落盘 checkpoint。
3. **备份文件复制**：
   - 复制主状态库文件（如 `state.db`）；
   - 若同目录下仍存在伴随文件（如 `state.db-wal`、`state.db-shm`），必须一并复制到备份目录；
   - 复制对应本地挂载的全部物理目录及文件数据。
4. **归档配置**：将当前启动使用的 `VfsRuntimeConfig`（包含挂载路径和 storageKey）一同归档。

### 2.2 灾备恢复与隔离验证步骤（实机验证）
当物理介质损坏或需要灾备验证时，执行恢复流程：
1. **原挂载路径环境恢复**：将备份的状态库文件及所有本地物理存储数据回拷到配置指定的物理路径。
2. **配置重开**：使用原 `VfsRuntimeConfig` 启动 `AlcyoneVfs.create(config)`。
3. **一致性检查**：
   - 执行 `stat(uri)` 核对 Node ID 与备份前一致；
   - 执行 `getMetadata(nodeId)` 核对 Tags 与 Description 完整；
   - 执行 `read(uri)` 核查文件内容哈希。

> **端到端验证结论（T30 实测）**：
> 在临时隔离环境中通过“写入数据/Metadata -> 正常 close() -> 离线复制库与数据 -> 原路径覆盖清除 -> 备份还原重开”流程，验证 Node ID、Metadata 及文件内容完全一致，无状态丢失与挂载冲突。
> 若在测试机等隔离环境验证，需保证挂载的绝对物理路径与原配置记录完全一致（例如使用相同的容器挂载路径或统一工作路径）。

## 3. 错误模型与故障诊断

### 3.1 异常结构：`VfsException`
当调用失败时，VFS 统一抛出领域异常 `VfsException`：
- `code`（`VfsErrorCode`）：稳定错误枚举（调用方应根据枚举做业务分支，切勿正则解析异常 message）。
- `effect`（`VfsEffect`）：指示已产生的副作用范围：
  - `NONE`：确认没有任何逻辑或物理变更提交；
  - `PARTIAL`：已知产生部分变更（例如跨后端移动已在目标写入，但源文件删除失败）；首版不自动修复；
  - `UNKNOWN`：无法确认底层是否完成（例如网络超时、写响应丢失），不能武断当作成功或失败。
- `cause`：底层原始引发异常。

### 3.2 六类常见故障排障指南

| 场景 | 错误码 | 副作用 (`effect`) | 常见原因及应对 |
| :--- | :--- | :--- | :--- |
| **挂载/路径不存在** | `MOUNT_NOT_FOUND` / `NOT_FOUND` | `NONE` | 请求的 URI 命名空间未挂载，或文件确实不存在。检查 URI 拼写与配置。 |
| **实例已关闭** | `CLOSED` | `NONE` | 在 `vfs.close()` 调用之后发起新操作。检查生命周期编排。 |
| **读写超出限额** | `LIMIT_EXCEEDED` | `NONE` | 读取内容超过了配置的 `limits.readBytes` 或流上限。需改用 `openStream` 或调整限额配置。 |
| **移动目标冲突** | `ALREADY_EXISTS` | `NONE` | `move` 目标路径已存在文件或目录。VFS move 绝不隐式覆盖目标。 |
| **并发独占冲突** | `CONFLICT` | `NONE` | 另一进程或线程已持有该 SQLite 数据库的锁。检查是否存在遗留僵尸进程。 |
| **底层存储拒绝** | `STORAGE_ACCESS_DENIED` / `READ_ONLY` | `NONE` | 磁盘权限不足或远端 WebDAV 服务为只读共享。排查磁盘权限或挂载凭据。 |

### 3.3 凭据脱敏安全保护
- VFS 严格保证凭据安全：错误消息、异常调用栈、数据库持久化表、身份标识串（identity）均**绝对不包含 WebDAV 密码**。
- 生产环境建议宿主系统通过集中配置中心或环境变量注入密码，切勿将明文写在应用代码中。

## 4. WebDAV 等待限制与部分失败应对（方案④）

### 4.1 方案④机制说明
在处理远端 WebDAV 网络操作时，当前架构沿用已确认的**方案④**：
1. **无全局超时强杀保证**：底层 native 请求与网络 I/O 并不提供全局超时强行中断保证。
2. **`closeGracePeriod` 语义**：该参数仅代表运行时进入 closing 状态后，等待在途任务完成的协作等待期限；**不等于 native 请求或 close 调用的最长绝对耗时**。
3. **禁止强杀线程**：若远端服务端无响应或网络阻塞，不建议外部调用方强行终止工作线程，否则容易损坏底层的 OpenDAL native 状态及资源句柄。

### 4.2 部分失败应对（切勿盲目全量重试）
- 当跨后端移动操作（如 Local FS → WebDAV 或 WebDAV → Local FS）因网络抖动中断并返回 `PARTIAL` 或 `UNKNOWN` 时：
  - 可能目标端文件已完整写入，但源端删除失败（此时两个后端均存在该文件）；
  - 或者写入响应丢失，无法确认目标端状态。
- **运维与重试禁忌**：
  - **严禁无条件直接重试整个 `move` 操作**（因为目标端可能已存在，盲目重试将立即因 `ALREADY_EXISTS` 失败）；
  - 应当首先分别对源端和目标端路径进行 `stat` 检查，确认各端实际物理存在状态；
  - 根据两端状态决定是补做源端删除，还是重新发起写入；首版暂不支持自动崩溃补偿。
