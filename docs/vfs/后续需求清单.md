## 2. 既有计划扩展需求 (E01～E05)

### E01：Git 本地备份配置与事件策略
- **需求来源**：开发计划 E1 与 2026-10-15 用户范围确认，见 [设计草案](Git_本地目录备份设计_v0.1.md)。
- **当前边界/限制**：尚无 Git 模块；Git 不是 Storage Backend，拟新增可选 `vfs/git-backup`，宿主通过既有 subscribe 接线；插件仅依赖 VFS API，不改 Runtime。
- **对调用者的影响**：宿主准备专用 Local FS 工作区、分支和非交互认证；不提供 `.git` 保护。
- **建议启动条件**：用户已授权启动，对应 T33 IN_PROGRESS；其余按前置复核门槛推进。
- **可观察验收目标**：文件通知重置 60 秒倒计时，支持Cron 定时、启动与手动触发；每次执行记录成功/失败日志，不提供公开状态模型；Git 失败不改变 VFS 保存结果。

### E02：独立 Git 备份插件、内部调度与宿主接线
- **需求来源**：E1 与用户简化决定，原持久化消费进度要求在本版取消。
- **当前边界/限制**：VFS 通知仍为尽力而为；不保证每个中间文件版本被提交。
- **对调用者的影响**：遗漏通知及离线期间的变更依靠Cron 定时/启动时完整检查当前工作区补足，宿主不运行时不会执行定时任务。
- **建议启动条件**：E01 契约确定，不依赖 E05。
- **可观察验收目标**：插件独立配置和关闭，内部调度单仓库串行 add/按需 commit/push；无新差异仍补推已有提交；失败等待后续触发再尝试；不建数据库表、消费位点或重放队列。

### E03：Git 本地备份集成与边界验收
- **需求来源**：E1 与 [设计草案第 8 节](Git_本地目录备份设计_v0.1.md#8-验收设计与后续任务边界)。
- **当前边界/限制**：尚无 Git 自动备份测试套件；不实现拉取、自动冲突处理或强推。
- **对调用者的影响**：需明确时间、失败、关闭及同步状态的实际保证范围。
- **建议启动条件**：E02 实现完成并逐任务复核通过。
- **可观察验收目标**：临时源仓库与本地 bare remote 覆盖防抖、Cron 定时/启动/手动、移动/删除、推送失败后再触发、进程清理及独立产物消费，不接触真实远端。

### E04：变更事务崩溃恢复与补偿机制
- **需求来源**：开发计划 E2（中断与重启恢复优化）；T23 失败报告评审结论。
- **当前边界/限制**：首版在发生底层物理成功但数据库失败，或跨后端移动源端删除失败时，仅如实返回错误并标注副作用（`PARTIAL` / `UNKNOWN`），不提供自动回滚、状态回退或重启补偿。
- **对调用者的影响**：发生进程崩溃或非预期失败时，可能残留物理孤儿文件或处于未完成状态的逻辑记录，需人工介入比对核实。
- **建议启动条件**：生产环境或集成层反馈孤儿文件与未结事务率高，需要自动化清理与一致性检查。
- **可选实现方案（启动时评估）**：建立操作日志（Intent Log）、两阶段悬挂状态记录，或提供离线 Reconciliation Tool。
- **可观察验收目标**：
  - 系统提供可观察的悬挂状态检查与恢复能力；
  - Runtime 重启时具备可配置的修复/扫描入口；
  - 能够在不盲目删源的前提下实现幂等恢复或安全孤儿垃圾回收。

### E05：可靠事件消费与重放
- **与 Git 备份的关系**：本版 Git 备份不依赖本项，使用 Cron/启动完整检查兜底；本项继续独立保留为候选。
- **需求来源**：开发计划 E2（中断与重启恢复优化）；T26 事件持久化结论。
- **当前边界/限制**：首版事件通知仅限当前运行时实例内的实时分发；正常关闭后重开不回放历史未读事件；无消费端位点持久化（Ack / Commit 位点）。
- **对调用者的影响**：订阅方若在事件发射瞬间处于异常状态或进程被强退，无法通过重开 Runtime 重新获取错过的事件。
- **建议启动条件**：存在对事件“至少一次（At-least-once）”投递有强诉求的审计、索引或外部协同组件。
- **可选实现方案（启动时评估）**：在 SQLite 中维护消费者组与消费位点（Offset / Watermark），引入显式 Ack 确认接口、死信沉淀与重试退避机制。
- **可观察验收目标**：
  - 进程重启后可根据持久化位点重新消费未结事件；
  - 确认消费进度、重试后结果可查询且不遗漏待消费事件；
  - 消费者异常具备可观测的隔离与失败处置能力。

## 3. 后续工程候选清单 (E06～E09)

### E06：真实 Linux (x64 / arm64) 实机验证
- **需求来源**：T28 平台支持核查结论与用户平台方案二确认。
- **当前边界/限制**：当前仅承诺 macOS arm64 已验证支持；Linux 构建配置虽保留，但未在真实 Linux 内核与文件系统环境下实跑完整测试套件与 WebDAV 套件。
- **对调用者的影响**：在 Linux 服务器或 Docker 容器环境下运行可能因 glibc 版本、内核调用或底层依赖差异触发未经验证的问题。
- **建议启动条件**：具备 Linux 持续集成（CI）机器或容器执行流水线，且上层业务计划部署到 Linux 生产环境。
- **可观察验收目标**：
  - 在真实 Linux 环境中执行常规测试套件与真实 WebDAV 测试套件全量通过（当前基线为 752 例与 43 例，未来以演进基线为准，不冻结计数）；
  - 执行独立消费工程验证（`./scripts/t31-consumer-check`）通过且退出码为 0。

### E07：跨平台构建与发布产物矩阵
- **需求来源**：T31 SDK 打包与本地消费复核结论（见 [T31 复核第 4 节](../tasks/m6-t31/T31_架构与技术复核.md#4-可以接受的设计取舍) 与 [第 6.4 节](../tasks/m6-t31/T31_架构与技术复核.md#64-可以接受的设计取舍与边界)）。
- **当前边界/限制**：当前在 macOS 上打包的本地发布物中，`alcyone-vfs-storage` 的 OpenDAL classifier 硬编码固定为 `osx-aarch_64`，发布产物不具备多平台自适应能力。
- **对调用者的影响**：跨不同平台构建时需重新针对宿主平台构建或发布，无法一份二进制到处运行。
- **建议启动条件**：准备正式对外提供跨平台通用 JAR / SDK 依赖包。
- **可选实现方案（启动时评估）**：Gradle 变体机制（Variant-aware dependency resolution）、统一聚合 multi-platform JNI binary（fat-jar）或分平台发布物编排。
- **可观察验收目标**：
  - 消费工程在目标受支持平台（如 osx-aarch_64、linux-x86_64、linux-aarch_64）上无需手工切换 classifier 即可正常解析依赖并启动；
  - 产物构建与发布过程可重复、元数据完整。

### E08：网络等待与外部原生请求超时机制重新评估（方案④演进）
- **需求来源**：T24 / T25 / T28 WebDAV 方案④边界（native 等待不可被协程取消强制终止，关闭无最长耗时上限）。
- **当前边界/限制**：底层 JNI 阻塞调用不受 Kotlin Coroutine 协作取消控制；若网络发生严重死锁或无响应，`close()` 只能无限期等待原生层返回，禁止强杀外部线程。
- **对调用者的影响**：极端网络异常下，调用线程或清理流程可能长期挂起，宿主系统难以设定严格的 SLA 截止时间。
- **建议启动条件**：上层系统对系统优雅停机（Graceful Shutdown）时限有硬性指标要求（如 Kubernetes 30 秒下线窗口），或需要更细粒度的物理 I/O 超时控制。
- **可选实现方案（启动时评估）**：底层传输层配置（OpenDAL 底层 reqwest/hyper 超时注入）、C/Rust 边界超时熔断机制或非阻塞 I/O 探针。
- **可观察验收目标**：
  - 具有受控的 I/O 等待与超时边界，网络挂起时不产生无法退出的死锁；
  - 形成严格超时场景下的安全关闭与资源释放规范。

### E09：正式 Maven Central / 远端仓库发布流程
- **需求来源**：T31 SDK 本地发布收口与 M6 交付定义。
- **当前边界/限制**：当前产物仅发布至项目内本地仓库（`.local/sdk-repository/`），无 GPG 签名，无 javadoc / sources jar 生成，未建立 Sonatype / Maven Central 凭据与发布流水线。
- **对调用者的影响**：外部工程集成必须通过源码构建本地发布，或通过相对/绝对文件路径引用本地仓库，无法像常规开源库一样一行坐标直接拉取。
- **建议启动条件**：M0～M6 核心全部通过独立验收，且确定对外公开发布版本与发布渠道。
- **可观察验收目标**：
  - 确认并注册 Maven Central Group ID 所有权（如 `com.github.noahshen`）；
  - 配置标准 `sourcesJar` 与 `javadocJar` 任务；
  - 配置标准 GPG 签名机制与 Sonatype Central Portal 发布凭据；
  - 验证外部干净工程仅配置 `mavenCentral()` 即可成功解析并运行。
