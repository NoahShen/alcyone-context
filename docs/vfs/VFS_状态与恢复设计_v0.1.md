### 1. 保存哪些状态

SQLite 保存 Mount、Node、Metadata 和 Event，文件内容仍在 Storage 中。首版不保存未完成操作的恢复日志或消费者进度，具体表名、字段与索引在实现时补充。

例：`report.md` 的内容在 WebDAV，Node ID、当前位置和标签在 SQLite。

### 2. 资源身份与删除

有效 Node 的规范化路径保持唯一，懒注册遇到竞争时复用已有 ID；虚拟目录可以没有物理映射。覆盖和移动保留 ID，成功删除后将 Node 标记删除、释放有效路径并清理 Metadata，历史事件保留原 ID。

例：删除 A 后在同一路径新建文件 B，B 获得新 ID；A 的旧 ID 查询返回 NOT_FOUND。

### 3. 一次变更的提交边界

先执行 Storage，成功后在同一 SQLite 事务中更新逻辑状态并写入成功事件，提交后再分发。SQLite 事务不能回滚外部文件操作；首版不提供自动补偿或跨存储原子性。

例：文件写入成功但数据库提交失败，返回 STATE_ERROR 并说明已发生物理变更，不返回整体成功。

```text
Storage 操作 → 事务提交 Node / Metadata + Event → 分发事件
```

### 4. 纯逻辑操作

Metadata 更新及其事件在一个 SQLite 事务中提交，失败则一起回滚。懒注册只提交 Registry，首版不发布 NODE_REGISTERED；read / list 也不产生变更事件。

例：修改标签时事件记录失败，标签更新同样不提交；仅调用 stat 注册文件不会触发同步。

### 5. 部分失败与移动

异常仍通过 effect 区分 NONE、PARTIAL 和 UNKNOWN，不把失败解释为没有副作用；返回对应 Storage / State 错误，不要求持久化恢复进度。跨 Mount 移动仍先完整复制并确认目标，再删除源，成功后保留原 Node ID；失败可能留下目标文件或不一致的逻辑映射，首版不自动修复。

例：目标复制完成但源删除失败，报告部分完成，不发布整个移动成功的事件，也不自动重试。

### 6. 事件分发

事件随逻辑状态持久化，提交后进行进程内分发；Consumer 失败不回滚文件操作。首版不承诺可靠投递、离线补发或重启重放，持久化消费进度和去重机制留到后续优化。

例：数据库已提交，但进程在通知 Consumer 前退出，事件记录仍在，重启后不会自动补发。

### 7. 并发与实例边界

首版建议一个状态库只由一个 Runtime 管理，先用一把变更锁串行处理写入、移动、删除、Metadata 更新和懒注册。读操作不承诺快照。

**独占检测（T18 已落实）**：Runtime 在**打开状态库和写入配置之前**，用状态库旁 `<状态库>.lock` 上的
`FileChannel.tryLock` 取独占，取不到报 `CONFLICT`。它覆盖同一个 JVM 里的第二个实例，也覆盖遵守同一协议的多进程启动；
同一个 JVM 的重叠锁（`OverlappingFileLockException`）同样按「已占用」处理。锁随关闭或初始化失败释放，
**锁文件留在盘上是正常的** —— 文件存在不等于还被占用。状态库路径先规范化（相对路径、符号链接别名收敛到同一真实路径），
所以换写法拿不到第二把锁；这**不承诺**阻止外部工具绕过 VFS 直接写 SQLite 文件。

例：两个 CREATE_NEW 同时写同一路径，一个成功，另一个返回 ALREADY_EXISTS。

### 8. Mount 配置与状态库升级

首次启动保存 Mount 的路径和后端映射，之后已有映射被修改或移除时拒绝自动替换；迁移工具另行安排。新增挂载不遮蔽已有资源映射时可以接受，凭据轮换不算资源迁移；数据库升级使用版本化迁移，不删除重建。

**资源身份（T18 已落实）**：挂载身份是 `storageKey` + `backendType` + **规范化后的物理根**三件套，
凭据不入库。只比 `storageKey` 认不出「同一个 key 换了个根」，旧 Node 会静默指向另一块盘，因此三者缺一不可。
旧 Mount 被移除、逻辑位置变化、同 key 换物理根、后端类型变化、所属命名空间被删，一律 `CONFLICT`，不改写原映射、不重新注册旧 Node。

**新增挂载的放行条件（T18 已落实，两条判据）**：

1. **旧挂载的覆盖范围**：新增挂载与任一旧挂载的逻辑路径互相包含（新增在前或在后）就拒绝 ——
   已有 `/resources` → A 时在其下新增 `/resources/photos` → B，即使 A 的子树一个 Node 都没懒注册也不能接受；
2. **已有物理 Node 在新配置下的解析结果**：逐个对照新旧路由，新增挂载使任何已登记 Node 换盘或换相对路径就拒绝。

新增到独立命名空间且不改变旧映射可接受；新增挂载与命名空间**不产生文件事件**。

**Schema 版本 1 → 2（T18）**：`mount` 表新增 `backend_type` 与 `physical_root` 两列，迁移文件 `1.sqm`。
旧库已有的行拿不到真实物理根（两列为空串），此时**明确拒绝**并给出处理办法 ——
确认配置无误后清掉 `mount` 表（或那几行）再启动；**不拿当前配置自动认证为旧身份**。空的旧库正常初始化。

例：将 `/resources` 从目录 A 改为目录 B，不直接沿用 A 的 Node ID 去描述 B 中的同名文件。

### 9. 取消、关闭与再次启动

close 停止接收新操作，在限定时间内等待在途操作并释放资源，取消异常按公共契约传播。再次启动只加载已提交状态，不扫描或续做中断操作；正常持久化读取仍需验证，崩溃后的文件与状态一致性修复不在首版范围。

**当前实现范围（T18 第二片）**：`close()` 是挂起函数，先转 `closing`（新公共操作报 `CLOSED`），再等在途操作至
`closeGracePeriod`，到点发**协作取消**（不碰宿主父 Job、不强杀 native 卡死线程）；随后按
「流 → 通知器 → 各块盘 → 状态库 → 独占锁」释放，清理在 `NonCancellable` 内跑。`close()` 幂等，
并发调用共享同一次完成结果；一个资源失败不阻止其余，首错抛出、其余进 `suppressed`。调用方漏关的流由 `close()` 回收。
等待期是自助时间不是强杀期限，卡在 native 里不响应取消的操作可能拿到 `STATE_ERROR`。
初始化中途失败或被取消时，已取得的资源逆序释放、保留原始异常，清理失败进 `suppressed`，不删除用户文件或状态库。

例：正常写入并关闭后，再次启动能查询原 Node；移动中途退出则不承诺下次启动继续完成。
